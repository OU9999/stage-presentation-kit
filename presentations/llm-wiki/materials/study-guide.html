LLM Wiki · 자료가 지식으로 쌓이는 방식

LLM Wiki 혼자 공부하기

세 영상의 목적·연결·검색에서 출발해 지속 문서와 다중 갱신·재사용을 이해하는 안내

LLM Wiki는 자료를 읽으며 이해한 관계를 다음 질문에도 쓸 수 있게 남기는 패턴입니다. LLM이 원자료의 개념·개체·비교·종합을 연결된 문서로 작성하고 유지합니다. 사람은 어떤 자료와 질문이 중요한지 정하고 결과를 살펴 다음 탐색을 이끕니다.

48장 발표 읽기 · 실습과 해설 · 세 영상 복사용 팩

기: 저장한 자료를 다시 쓸 지식으로

영상과 PDF를 모아도 다음 질문에서 다시 처음부터 자료를 엮는 일이 생깁니다. 자료의 위치는 기억하지만 여러 자료를 읽으며 이해한 개념·차이·잠정 결론이 어디에 남았는지 찾기 어렵기 때문입니다. LLM Wiki는 그 결과를 문서로 작성하고 갱신하는 층을 두려는 설계입니다.

이는 특정 앱이나 공식 표준의 이름이 아닙니다. 폴더를 예쁘게 정리하거나 문서 형식만 바꾸는 일에 그치지도 않습니다. 이미 쓴 개념을 새 자료와 연결하고, 현재 비교와 계획을 바꾸며, 다음 질문에서 다시 읽는 방식입니다.

내 맥락과 목적이 정리 방향을 바꾼다

같은 자료라도 강의를 준비하는 사람, 프로젝트의 선택을 검토하는 사람, 자기 회고를 하는 사람에게 필요한 정리는 다릅니다. ‘왜 저장했나, 무엇이 중요했나, 어디에 다시 쓰고 싶나’를 함께 알려주면 무엇을 연결하고 강조할지 정할 수 있습니다.

첫 영상 11:04와 30:08 이후는 목적과 입력을 함께 다루는 개인 작업 흐름을 설명합니다. 여기서 모든 사람이 생활 전체를 기록하거나 거대한 프로필을 먼저 만들어야 한다는 조건을 가져오지는 않습니다. 이번 목적 한 문장과 자료 몇 개로 시작할 수 있습니다.

네 가지 특징을 함께 기억하기

특징 실제로 남거나 일어나는 것
연결 자료 사이의 공통 개념·조건·차이·근거가 드러남
축적 자료별 요약을 넘어 개념·비교·종합이 지속 문서로 남음
갱신 새 자료 때문에 관련된 기존 여러 쪽도 다시 검토하고 고침
재사용 필요한 페이지를 찾아 읽어 새 질문·계획·결과에 활용

연결은 링크 개수가 많다는 뜻만은 아닙니다. ‘무엇이 같고 어떤 조건이 다른지’를 문장으로 설명해야 관계를 다시 읽을 수 있습니다. 파일을 저장했어도 다음 요청에 읽히지 않으면 그 답에 쓰이지 않을 수 있습니다.

좋은 재료와 사람의 세 행동

공동 세미나 08:43~14:23는 목적에 관련된 선별 자료·경험·생각을 ‘골드 데이터’라고 부릅니다. 이는 정답 라벨이나 사실 인증이 아니라 사람이 자기 문제에 쓸 재료를 고른다는 표현입니다.

16:30~18:10의 세 원칙을 이번 작업에 옮기면 쓸 결과 정하기, 내 이유와 판단 적기, 생성된 종합을 구별해 근거와 대조하기입니다. 원문에서 확인한 사실, 사람이 직접 쓴 관찰·선택, AI가 정리한 문서를 구분합니다. 예제 팩의 선택 이유와 위키 문장은 발표팀이 구성한 예문이며 실제 사용자의 생각이나 실행한 모델 출력으로 표시하지 않습니다.

승: RAG와 같은 질문으로 비교하기

비교할 공통 질문은 **‘다음 AI 스터디에서 LLM Wiki를 어떻게 시도할까?’**입니다. 입력은 사용자 제공 세 영상의 읽기 메모입니다. 어느 쪽에 나쁜 답이나 좋은 답을 미리 써서 성능 차이처럼 보여주지 않습니다.

기본 검색-생성의 흐름

RAG는 질문에 필요한 외부 자료를 찾아 생성 모델의 입력에 넣고 답합니다. 기본 예에서는 현재 질문에 맞는 원자료의 근거를 모아 이번 답을 구성합니다. 자료를 나누는 방식·검색·선별·프롬프트·출처 표시 등은 구현에 따라 달라집니다.

지속 문서를 유지하는 흐름

LLM Wiki에서는 자료를 반영할 때 개념·비교·종합을 문서로 작성합니다. 질문할 때는 필요한 위키 페이지와 원자료를 찾아 다시 읽어 답합니다. 유용한 새 설명도 저장해 다음 탐색과 연결할 수 있습니다.

공통 축 기본 검색-생성 예 위키를 유지하는 예
초점 이번 답에 필요한 근거 찾기 이미 정리한 관계를 유지하고 재사용
입력·변경시 정제·분할·색인과 갱신 원자료 읽기·관계 종합·관련 문서 갱신·검토
질문시 근거 검색·선별·현재 답 종합 관련 쪽 검색·재읽기·현재 답 종합
남는 지식의 모양 원자료와 검색용 표현, 구현에 따라 저장한 결과 개념·비교·종합 등 사람이 읽는 연결 문서
운영 부담 검색/생성 품질·색인·접근 범위 문서 최신성·중복/모순·연결·검색·검토

이 표는 두 교육용 흐름의 대비입니다. 검색과 지식 정리는 함께 쓸 수 있습니다. RAG 시스템도 답·요약·관계를 축적할 수 있습니다. 예를 들어 GraphRAG의 공식 색인 설명은 개체·관계를 추출하고 커뮤니티 요약을 생성합니다. 위키도 목차·키워드·벡터 검색 등으로 필요한 쪽을 찾을 수 있습니다.

핵심 차이는 ‘검색이 있나 없나’가 아닙니다. 어디에 어떤 관계를 남기고 언제 고치며 어떻게 다시 읽는지입니다. 관계를 미리 정리하면 질문에서 활용할 출발점이 생기는 대신, 입력·갱신·검토에도 일이 듭니다. 이번 발표는 정확도·비용·속도의 보편 우위를 측정한 실험이 아닙니다.

Agentic RAG와 모델 학습도 같은 축에 놓기

방식 중심 작업 주로 사용하는/바꾸는 대상
RAG 외부 근거를 찾아 생성에 사용 현재 입력 문맥
Agentic RAG 검색할 곳·도구·방식·반복을 에이전트가 판단 검색 계획과 현재 문맥
파인튜닝 예제로 모델 동작을 학습해 조정 파라미터·학습 가능한 어댑터
LLM Wiki 연결된 지식 문서를 작성·갱신 지속되는 문서

네 방식은 서로 다른 설계 축이며 순서대로 갈아타는 세대가 아닙니다. 위키를 검색 대상으로 쓰고 에이전트가 읽을 곳을 고를 수 있습니다. 조정한 모델과 검색도 함께 사용할 수 있습니다. RAG 원논문에는 검색기·생성기를 학습하는 과정도 있으므로 모든 RAG를 ‘학습이 전혀 없다’로 정의하지 않습니다. 원문 읽기 안내.

전: 세 영상에서 연결된 위키로

1. 원자료·위키·규칙의 역할

위치 역할 이번 예제
raw/ 보존하는 입력 두 실제 영상의 읽기 메모, 나중에 추가하는 가상 조건
wiki/ LLM이 작성·갱신하는 지식 자료 요약·개념·비교·계획·질문·목차·로그
rules.md 목적과 정리·연결·검토 방식을 안내 원자료 보존, 근거·해석 구별, 관련 쪽 갱신

원자료를 보존한다는 것은 원자료의 모든 문장이 참이라는 뜻이 아닙니다. 어떤 입력을 읽고 지금의 설명을 썼는지 다시 확인할 수 있게 하는 원칙입니다. 살아 있는 웹페이지라면 읽은 구간·판·확인일을 남기는 것도 도움이 됩니다.

rules.md는 실습에서 정한 중립적인 파일 이름입니다. 시작 요청에 명시적으로 읽으라고 합니다. 사용하는 도구의 자동 지침 파일과 같은 것으로 가정하지 않습니다.

2. 읽은 자료 자체를 설명하는 쪽과 개념 쪽

세 입력은 raw/brian-video.md, raw/yongdam-video.md, raw/seminar-video.md입니다. 각 메모는 원문 위치·발언 요지·우리 해석·교정할 일반화를 나눕니다. 자막 전문을 복제한 파일이 아닙니다.

자료 요약 쪽은 ‘이 영상은 어떤 자료인가?’에 답합니다. 개념 쪽은 여러 자료에서 함께 설명하는 ‘LLM Wiki’, ‘필요한 근거 찾아 읽기’를 모읍니다. 필요하다면 사람·도구·프로젝트 같은 개체도 별도 쪽으로 정리할 수 있습니다. 모든 단어를 파일 하나씩으로 나눌 의무는 없습니다.

3. 비교와 종합은 자료를 함께 읽은 결과

wiki/comparisons/rag-vs-wiki.md는 같은 질문으로 RAG와 위키의 작업 시점·남는 결과·갱신·부담을 비교합니다. 두 자료를 옆에 붙여 두는 것에서 한 단계 더 나아가 공통 축이 남습니다.

wiki/syntheses/study-plan.md는 우리 목적에 맞춰 현재 첫 시도를 정리합니다. 두 공개 메모에서 개념·비교·계획을 만들고 다음 질문에 다시 써 보자는 초안입니다. 참가자 배경과 실습 길이는 아직 미정으로 남깁니다. 출처의 사실과 우리가 선택한 계획을 구분합니다.

4. 인제스트는 관련 여러 쪽을 함께 보기

Ingest는 새 자료를 읽고 위키에 반영하는 작업입니다. 읽기 가능한 형태로 바꾸고 자료 요약을 쓴 뒤, 기존 개념·비교·종합에 어떤 영향이 있는지 살펴봅니다. 관련 쪽을 연결하거나 갱신하고 목차·로그도 정비합니다.

예제의 완성 결과를 한 쪽씩 확대해 볼 때, 한 장면마다 실제로 파일이 하나씩 생성됐다고 가정하지 않습니다. 실제 실행을 했다면 무엇을 읽고 어느 파일을 바꿨는지 결과에서 확인합니다.

5. 목차·로그·그래프·규칙은 다른 질문에 답하기

  • index.md: 무엇이 어디에 있고 어느 쪽으로 들어갈까?
  • log.md: 언제 무엇을 왜 바꿨고 어디까지 진행했나?
  • 그래프 보기: 어떤 문서들이 연결되어 있고 어디가 떨어져 있나?
  • 작업 규칙: 어떤 기준으로 분류·연결·갱신할까?

첫 영상 34:50 이후는 지식 그래프와 정리의 질서를 구별해 설명합니다. 그래프가 예쁘다는 사실만으로 의미가 맞거나 정교한 온톨로지가 완성됐다고 판정하지 않습니다. 문서화한 분류·연결 기준과 실제 쪽의 내용을 함께 봅니다.

6. 새 조건은 여러 페이지를 다르게 바꾸기

나중에 raw/study-retro.md를 추가합니다. 실제 운영 성과가 아닌 설명용 가상 조건입니다. 입문자와 함께하고 별도 실습은 15분, 공개 읽기 팩의 세 메모를 쓰며 다음 질문을 목차에서 이어 가고 싶다는 설정입니다. 전체 위키의 입력은 세 메모이고, 짧은 활동에서는 그중 두 개를 골라 읽습니다.

페이지 바뀌는 곳 유지하는 곳
LLM Wiki 개념 우리 스터디의 적용 범위 연결 문서를 지속 작성·갱신한다는 정의
RAG와 위키 비교 입문자·15분에 맞는 선택 기준 검색과 문서 정리는 병행 가능하다는 구분
현재 계획 목차·연결 읽기→근거 찾기→질문 답 저장 공개 자료로 작게 시작한다는 목적
목차·로그 갱신된 쪽의 입구와 변경 이유 원자료와 이전 작업의 추적 경로

사람의 조건이 바뀌었다고 개념의 보편 정의를 임의로 고치는 것은 아닙니다. 자기 적용 범위·선택·계획을 명확하게 보완합니다.

7. 후속 질문에서 실제로 다시 읽기

이제 ‘입문자와 15분 활동은 무엇부터 할까?’라는 더 구체적인 질문을 합니다. 목차에서 관련 개념·비교·갱신한 계획을 찾아 현재 문맥에 읽습니다. 필요한 경우 원자료까지 확인합니다.

예시 답은 새 도구 설치보다 목차와 연결을 따라 근거를 찾는 작은 실습부터 하자는 것입니다. 이것은 가상 조건에 맞춘 계획이며 모든 위키에 검색이 필요 없다는 주장이 아닙니다. 실제 사용한 도구에서는 이번 답에 읽힌 파일과 부족한 근거를 함께 확인합니다.

8. 유용한 답 저장과 유지 점검

검토한 답은 wiki/questions/first-study.md에 남기고 개념·비교·계획에서 연결합니다. 답만 저장하는 대신 근거·읽은 파일·아직 확인하지 못한 점도 남깁니다. 다음 탐색이 이 쪽에서 출발할 수 있습니다.

Lint는 낡은 설명·모순 후보·고립된 쪽·끊긴 링크·빠진 개념 등을 점검하는 유지 작업입니다. 이번에는 가상 조건 이전의 계획이 현행처럼 남았는지, 질문 쪽이 목차와 계획에서 연결되는지 살펴봅니다. 문제가 보이면 근거를 다시 읽고 문장을 고친 뒤 다시 확인합니다. 링크 검사 통과가 의미 정확성의 인증은 아닙니다.

작업 입력 위키에 돌아오는 것
Ingest 새 자료·조건 자료 요약과 관련 설명의 작성·갱신
Query 새 질문과 찾아 읽은 쪽 현재 답, 검토 뒤 저장할 유용한 결과
Lint 현재 위키와 근거 수정할 설명·연결·다음 확인 질문

9. LLM과 사람의 역할

LLM은 요약·연결·작성·갱신·점검 후보 찾기를 수행합니다. 사람은 가치 있는 자료와 질문·범위를 고르고 분석 방향을 바꾸며 중요한 결과를 확인합니다. 모든 페이지를 사람이 직접 작성하는 절차로 LLM Wiki를 정의하지 않습니다.

Obsidian은 문서를 보고 연결을 탐색하는 창, Claude Code는 파일을 읽고 쓰는 에이전트의 한 예입니다. 다른 조합으로도 역할을 나눌 수 있습니다. 도구가 실제로 어느 폴더를 읽고 무엇을 고칠 수 있는지 확인하고, 자신의 방식에 맞게 규칙을 전달합니다.

지식에서 실제 사용할 한 쪽 결과로

질문의 답을 위키에 저장한 다음에는 그 결과를 어디에 쓸지도 정합니다. 공동 세미나 38:43~39:16은 종합을 저장해 콘텐츠에 다시 쓰는 흐름을 설명합니다. 뒤의 공유 작업 예는 여러 작업자가 같은 근거와 현재 판단을 읽는 공간으로 위키를 사용합니다.

구분 이번 스터디 예제에서 남기는 것
맥락 세 메모·관련 개념/비교·현재 계획, 가상 입문자·15분 조건
요청 준비된 팩을 쓰는 진행안 한 쪽, 근거와 작성 주체·미확인 조건
논의 왜 두 메모를 골랐고 15분을 어떻게 배분할지의 이유
결과 실제 진행안, 문서 확인 기록, 다음 질문

이는 네 개 파일이나 다중 에이전트가 필수라는 뜻이 아닙니다. 한 사람과 한 도구의 작업에서도 구분해 읽을 수 있습니다. 문서 규칙을 적는 것과 도구가 실제로 읽고 실행하는 일도 구별합니다.

우리 스터디의 실제 진행안

입문자와 함께 읽는 15분 LLM Wiki 활동은 열어 볼 수 있는 실제 예제 문서입니다. 전체 세 메모 중 brian-video.md와 seminar-video.md를 목적·연결과 사람 입력·산출물·검토라는 이유로 선택합니다. 목적 2분, 선택 메모 읽기 4분, 관계/근거 확인 5분, 후속 질문과 남은 확인 4분으로 배분합니다.

팩의 wiki/syntheses/study-plan.md는 현재 계획, wiki/outputs/study-session-plan.md는 사람이 쓸 결과, wiki/reviews/study-session-plan.md는 실제 대조한 범위와 미확인 사항입니다. 서로 다른 역할이지만 같은 내용을 이어 읽습니다. 등록 학습 문서와 팩의 진행안은 같은 활동안입니다.

검토한 것은 시간 합계·선택한 메모 이름과 이유·원문 위치·작성 주체·링크입니다. 실제 입문자 이해·모임 진행·모델 호출·학습효과는 확인하지 않았습니다. 다음에 ‘30분이라면 무엇을 더 읽고 확인할까?’라고 물을 때 이번 결과와 선택 이유부터 다시 읽을 수 있게 남깁니다.

참고 시연의 실행 범위

새 강의 38:17에는 방금 수집한 두 글이 아직 검색되지 않았다는 발언이 있습니다. 82:19~82:40에는 자료 혼선과 PDF/슬라이드 사전 제작, 약10분에 수행한 것은 위키 저장·토론이었다는 고지가 있습니다. 77분의 약60% 자동화도 화자의 개인 추정입니다. 이 사례를 최신 자료가 즉시 반영된 완전 자동 제작의 성과로 읽지 않습니다.

결: 어디에 쓰고 무엇을 확인할까

학습·기획·개인 회고 — 확장 읽기

학습에서는 자료별 요약 외에 개념·의문·비교를 유지해 다음 스터디 질문을 이어 갈 수 있습니다. 기획과 회의에서는 요구의 조건·선택 이유·현재 상태를 연결해 같은 판단을 매번 다시 찾는 일을 줄이려 시도할 수 있습니다. 효과는 자신의 질문에서 확인해야 합니다.

첫 영상 17:19 이후는 의도·실행·현실·해석·AI 로그를 구분하는 개인 시스템을 소개하고, 37:15 이후는 기록을 회고와 계획에 다시 쓰는 경험을 말합니다. 이는 화자의 자기보고이며 LLM Wiki의 필수 다섯 계층이나 검증된 생산성 수치가 아닙니다.

기록→기간별 종합→본인 확인→다음 계획처럼 결과를 재사용하는 흐름을 참고할 수 있습니다. 요약을 다시 요약할수록 원자료와 적용 범위를 놓칠 수 있으므로, 사실과 해석을 구분하고 필요한 근거로 돌아갈 경로를 남깁니다.

문서도 틀리고 낡고 누락될 수 있다

위키에는 잘못 연결된 개념·지원되지 않는 종합·낡은 답·검색 누락이 생길 수 있습니다. 자료가 많아지면 중복·여러 쪽 변경·동시 편집·문맥 한계도 고려해야 합니다. 팀 자료라면 원자료뿐 아니라 파생 문서를 누가 읽을지 정해야 합니다. 로컬 실행 여부만으로 그 문제가 모두 해결되지는 않습니다.

둘째 영상 07:16~09:53의 HR 예는 자료를 모으는 일 외에도 정책·운영·검토 부담을 고민해야 한다는 설명으로 읽습니다. 이 자료가 특정 기업 사고나 해결 성공을 독립 검증한 것은 아닙니다.

도입 여부를 판단하는 질문

  • 같은 개념과 비교를 반복해서 쓰는가?
  • 새 자료가 들어오면 어떤 기존 설명을 고칠지 보이는가?

  • 관계 정리·검토·검색·갱신에 드는 부담을 감당할 만한가?

단발 질문은 짧은 노트와 검색으로 충분할 수 있습니다. 원문을 정밀하게 찾아야 하는 과제라면 검색 품질을 먼저 살펴야 합니다. 문서 개수 하나로 위키와 RAG를 고르는 대신 실제 질문·자료·접근 범위·변경 빈도와 비용을 보세요.

작게 시작하는 첫 순환

자기 질문 하나와 목적을 적습니다. 자기 자료로는 접근 가능한 자료 두 개부터 정하고 개념·비교·계획을 연결합니다. 새 조건 하나를 넣어 관련 여러 쪽을 고치고, 후속 질문에서 실제로 다시 읽어 봅니다. 유용한 답을 저장한 뒤 낡은 문장과 빠진 연결도 한 곳 고쳐 보세요.

구판 부록과 더 깊게 읽기

RAG·LoRA 구판 팩은 파일·입력 문맥·모델 파라미터를 구분하는 별도 연습입니다. 고정 교정 기록은 사람이 승인한 문장을 Node로 반영한 실습이며 모델 호출이나 새 답 생성의 성공 기록이 아닙니다. 기술 원문의 설계·공개 코드·논문 상세와 연결해 읽으세요.

기존 독서·고객 요구·강의 메모는 다른 분야로 옮길 때 참고할 가상 예로 보존합니다.
