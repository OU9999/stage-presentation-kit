실제 파일 읽기와 교정 실행 기록

Q1의 근거 교정에서 Q2의 재사용·pending·D1 대체까지, ZIP 재현과 검사 한계

데모 ZIP 내려받기 · 자료 목차 · 발표 10장

이 문서는 40장 발표의 실제 파일을 천천히 읽는 길입니다. 발표자가 만든 학습용 오류와 고정 승인 교정안을 Node 스크립트로 적용했습니다. 실제 AI의 오답 수집, 자동 검색, 모델 답 생성이나 성공 실험이 아닙니다. Q2의 ‘다시 읽은 파일’은 이 구성 예제의 판단 입력입니다. 스크립트가 의미를 자동 판단한 기록으로 읽지 않습니다.

ZIP에는 초기 파일, 읽기 메모, 승인안, 수정 후 파일, diff, 실행 도구와 영수증이 들어 있습니다. 아래 경로는 ZIP을 푼 폴더 안의 경로입니다. 파일 전체는 ZIP에서 열어 보세요. 실행하지 않아도 이 문서의 실제 발췌와 비교를 읽을 수 있습니다.

1. 무엇이 실제이며 무엇을 구성했나

구분 내용 여기서 알 수 없는 것
실제 공개 원문 Karpathy LLM Wiki, RAG v4, LoRA v2, Nygard ADR 현재 도구의 품질·검색 누락·스터디 도입 효과
로컬 읽기 메모 source-notes/ 5개: 공개 원문의 한국어 읽기 메모 원문 전문이나 공식 번역을 대신하지 않음
구성 예제 C1·Q1의 학습용 오류, Q2·D1·D2·pending과 고정 승인안 실제 AI 실패·실제 스터디 운영 성과
실제 실행 승인안 적용·diff 생성·링크 확인·SHA 보존 검사 문장 진실성, 모든 영향 관계의 자동 발견

원문 지원과 우리 해석을 분리합니다. 원문을 읽고 사람이 승인한 의미 검토는 review/review.json에 남겼습니다. 스크립트는 그 승인안과 결과 파일의 일치·무결성을 검사합니다.

2. 첫 질문과 의도적으로 넣은 오류

before/wiki/questions/wiki-and-learning.md의 Q1은 ‘위키 파일을 고치면 모델도 그 내용을 학습하나요?’입니다. 답 초안은 다음과 같습니다.

위키 파일을 고치는 것은 파일을 수정하는 작업이다. 외부 파일을 쓰는 시스템은 모델을 학습하지 않는다.

첫 문장은 이 파일 수정의 범위에서 유지할 수 있습니다. 두 번째 문장은 외부 파일을 쓰는 시스템 전체로 일반화합니다. C1 before/wiki/claims/file-update.md에도 같은 문장이 있고, 범위는 ‘외부 파일을 쓰는 모든 시스템’입니다. 이 오류는 발표자가 학습용으로 넣었습니다. 링크가 있으니 검토 완료라고 표시하면 어떤 일반화가 섞일 수 있는지 읽기 위한 구성입니다.

3. 같은 논문에서 읽은 범위가 늘었다

메모 원문 실제 읽은 범위 보존 이유
source-notes/rag-initial.md 같은 RAG v4 최초 §2.3 처음 무엇을 읽고 메모했는지 남김
source-notes/rag.md 같은 RAG v4 §2.3과 §2.4까지 확장 학습 대상을 더 확인한 메모를 따로 남김
source-notes/lora.md LoRA v2 Abstract·§4.1 기본 가중치 고정과 추가 행렬 학습을 함께 확인

원논문의 판이 바뀐 사건이 아닙니다. 같은 v4에서 읽은 범위가 달라졌습니다. RAG v4 §2.4는 질의 인코더와 생성기를 미세조정하는 과정을 설명합니다. LoRA v2 §4.1은 기본 가중치를 고정하면서 추가 행렬을 학습합니다. 외부 파일 사용이나 기본 가중치 고정만으로 학습이 전혀 없다고 결론 내릴 수 없습니다.

실제 원자료가 새 판으로 교체될 때 판·날짜·주장 범위를 대조하는 28장의 절차는 앞으로 적용할 운영법입니다. 이번 실행의 원문 교체 결과라고 소개하지 않습니다.

4. 실제 diff에서 달라진 문장

review/review.json의 해당 결정은 ‘일반화 삭제 후 범위 교정’입니다. 이유는 RAG §2.4의 학습과 LoRA의 추가 행렬 학습을 원문에서 확인했기 때문입니다. 다음은 changes.diff의 실제 C1 부분입니다.

-- 문장: 외부 파일을 쓰는 시스템은 모델을 학습하지 않는다.
-- 근거 후보: [RAG 읽기 메모](../../../source-notes/rag-initial.md)
-- 범위: 외부 파일을 쓰는 모든 시스템
+- 문장: 이 데모의 파일 수정은 모델 매개변수 학습을 실행하지 않는다. 외부 파일을 쓰는 시스템에도 별도의 학습 과정이 있을 수 있다.
+- 근거: [RAG 읽기 메모의 §2.4](../../../source-notes/rag.md), [LoRA 읽기 메모](../../../source-notes/lora.md)
+- 범위: 이 파일 교정 절차와 두 논문에 기술된 학습 대상

문장, 근거 위치, 범위를 함께 바꿉니다. 반대의 일반화인 ‘외부 파일을 쓰면 항상 학습한다’로 바꾸지 않습니다. 파일 수정 데모의 범위와 두 논문의 학습 대상을 구분합니다. 전체 diff에는 아래 8개 현행 파일의 변경이 들어 있습니다.

5. 고친 Q1과 다음 확인

after/wiki/questions/wiki-and-learning.md는 다음 두 문장으로 시작합니다.

이 데모에서 바뀌는 것은 Markdown 파일이며 모델 매개변수 학습을 실행하지 않는다. 다음 질문에 반영하려면 고친 파일을 다시 찾아 읽어 답의 문맥에 넣어야 한다.

파일이 존재하는 것과 다음 답이 그것을 읽는 것은 다릅니다. 그래서 다음 질문으로 ‘고친 파일이 있어도 다음 답에서 읽지 않으면 어떻게 확인할까?’를 남겼습니다. 읽은 파일·근거 위치·지원하지 못한 부분을 남기게 하는 방법을 후속 실습에서 검토합니다. 이 데모는 검색 품질이나 모델 정확도를 측정하지 않습니다.

6. 새 질문 Q2가 이전 결과를 다시 쓴다

after/wiki/questions/what-to-save.md는 ‘우리 스터디는 어떤 답을 저장할까’라는 새 운영 질문입니다. ‘다시 읽은 파일’에 교정된 C1, Q1, 초기 D1이 적혀 있습니다.

다시 읽은 파일 가져온 내용 새 질문에 쓰는 이유
C1 · claims/file-update.md 링크가 있어도 일반화가 잘못될 수 있었음 링크 유무만으로 현행 답을 정하지 않음
Q1 · questions/wiki-and-learning.md 고친 파일을 다시 찾아 읽어야 함 파일 저장과 다음 답의 활용을 구분
D1 · decisions/save-all.md 채팅에서 다시 찾기 어려워 모든 답을 모으려 했음 기존 정책의 목적을 보존하며 현행 기준 재검토

Q2 실제 답 발췌:

모든 질문을 똑같이 현행 노트로 넣으면 검토 전 설명이 섞일 수 있다. 이 예제에서는 원문과 범위를 대조한 답은 현행 위키에 연결하고, 근거가 부족한 답은 검토 대기함에 남긴다.

이 문장은 고정 승인안 안에서 구성한 운영 선택입니다. 모든 스터디에서 최선인 정책이라는 실험 결과는 아닙니다. 자동 검색이나 LLM의 새 답 생성 성공으로 해석하지 않습니다. 다음 확인은 자료 세 개와 검토할 사람을 정하고, 다음 모임에서 근거 재탐색과 검토 부담을 살피는 것입니다.

Q2 재사용 도식 원본 · 발표 22장

7. pending은 이유와 다음 행동을 남긴다

after/wiki/pending/retrieval-coverage.md의 상태는 보류입니다. 근거가 부족한 초안은 ‘파일 위키를 만들면 필요한 파일을 언제나 찾을 수 있다’입니다.

보류 이유는 현재 원문과 파일 교정 실행이 우리 스터디 자료에서 검색 누락이 없다는 주장을 지원하지 않기 때문입니다. 존재하는 파일을 다음 답이 실제 읽었는지 따로 확인해야 합니다. 다음 행동은 실제 스터디 질문 몇 개를 정하고 답이 읽은 파일과 빠뜨린 근거를 사람이 확인하는 것입니다. 검토 전에는 이 문장을 현행 답으로 옮기지 않습니다.

이 상태를 별도로 두면 ‘아직 모름’이 현행 설명에 섞이는 것을 구분하고 다음 모임에서 이어갈 확인도 찾을 수 있습니다. 보류 자체가 내용의 거짓 판정은 아닙니다.

현행·보류 도식 원본 · 발표 25장

8. D1을 삭제하지 않고 D2로 대체한다

기록 상태·선택 보존할 맥락·결과
D1 decisions/save-all.md superseded · 모든 질문 답을 현행에 저장 채팅에서 다시 찾기 어려워 모으려 했음. 지원되지 않는 일반화도 섞일 수 있었음
D2 decisions/review-before-current.md 이 학습 예제에서 채택 · 근거와 범위를 대조한 뒤 현행 갱신 수정 이유로 돌아갈 수 있음. 매번 검토 시간이 들고 관련 페이지 누락을 점검해야 함

D1에는 D2로 가는 대체 링크가 있고, D2에는 D1을 대체했다는 링크가 있습니다. 현행은 D2이고 D1의 당시 맥락과 결과는 남습니다. 이 결정 형식은 Michael Nygard의 ADR 글을 스터디에 응용했습니다. 원래 글은 중요한 소프트웨어 아키텍처 결정을 다룹니다. 우리 저장 정책은 원문에서 자동으로 결정된 사실이 아닙니다.

10. ZIP에서 재현하기

Node.js가 있는 컴퓨터에서 ZIP을 내려받아 압축을 풀고 llm-wiki-demo/로 이동합니다. 추가 패키지·로그인·API·네트워크 없이 파일 작업을 재현합니다. 공개 원문을 새로 대조하려면 인터넷이 필요합니다.

cd llm-wiki-demo
node run-demo.cjs --check
node run-demo.cjs
node run-demo.cjs --check

첫 check는 들어 있는 결과를 승인안과 대조합니다. 가운데 명령은 after/, changes.diff, receipt.json을 씁니다. 마지막 check는 파일을 바꾸지 않고 결과·링크·해시를 다시 검사합니다. 원본에 손대고 싶지 않으면 압축을 별도 폴더에 풀어 실행하세요.

실제 확인 수치 뜻 뜻하지 않는 것
기존 5쪽 갱신 + 3쪽 생성 = 8쪽 고정 승인안에 해당하는 현행 파일 반영 지식 증가량·학습 효과
로컬 링크 25개 검사 대상 파일의 상대 경로 연결 모든 문장이 원문에 의해 지원됨
불변 파일 10개 읽기 메모 5개와 before 5쪽의 SHA 보존 원문 자체의 진실성
model_invoked: false 이 스크립트에서 모델 호출 없음 실제 LLM 사용 결과나 정확도 평가

인계 검수에서 ZIP을 별도 폴더에 풀어 check → apply → check를 실행해 모두 exit 0을 확인했습니다. 또한 별도 before 복사본에 diff를 patch로 적용해 after 8개 파일과 전체 바이트가 일치함을 확인했습니다. 원문 대조와 검토의 의미는 이 기계 검사와 따로 유지합니다.

11. 내 자료로 옮길 때

starter.txt의 요청은 원문을 보존하고 근거 위치·지원하지 못한 부분·연결 후보·변경 diff를 보여 달라는 시작 문구입니다. 실제 LLM 수행 결과가 아닙니다. 자신의 자료로 실행하면 읽은 파일과 변경 후보를 별도로 확인하세요.

처음에는 자료 세 개, 질문 하나, 검토할 사람 한 명을 정합니다. 다음 모임에서 이전 답과 근거를 다시 찾을 수 있는지, 검토 부담을 감당할 수 있는지 보세요. 잘 찾지 못하면 목차·연결·검색을 함께 점검할 수 있습니다. 모든 자료를 위키로 옮겨야 하는 것은 아닙니다.
