LLM Wiki: 읽은 자료를 다음 질문으로 잇기

원문 읽기 안내와 용어 모음

LLM Wiki, RAG, LoRA, 출처, 결정 기록, 인용 평가를 연결해 읽는 6개 1차 자료

이 문서는 링크를 모으는 데서 한 걸음 더 나아가, 어떤 질문으로 원문을 읽고 어디까지 주장할 수 있는지 안내합니다. 먼저 스터디 가이드를 읽고 궁금해진 주제의 원문을 골라도 좋습니다. 직접 파일을 써 보려면 실습과 해설, 말로 설명하려면 발표 대본을 이용하세요.

여기서 S로 시작하는 ID는 실제 외부 자료입니다. 학습 자료의 X로 시작하는 기록은 그 원문을 공부하는 상황을 만들기 위한 가상 메모·주장·결정입니다. 학습 가이드의 보조 시간 공지도 가상입니다. 실제 논문이 있다는 사실은 가상 학습 과정이나 운영 성과를 입증하지 않습니다. 원문은 2026년 10월 28일 확인했으며 아래 요약은 직접 인용이 아닌 한국어 설명입니다.

질문에 따라 읽는 순서

지금 궁금한 것 먼저 읽을 곳 읽은 뒤 남길 것
LLM Wiki에서 무엇이 지속되는가 Karpathy의 설계 글 원자료·위키·작업 규칙의 역할을 한 문장씩
파일 저장·검색·학습은 어떻게 다른가 RAG §2와 LoRA Abstract·§4.1 입력 문맥과 학습 파라미터를 구분한 비교 표
출처에 무엇을 적어야 다시 확인할 수 있는가 PROV-Overview Abstract·Introduction 자료·생성 과정·검토자 중 현재 빠진 정보
왜 그렇게 선택했는가를 어떻게 남길까 Nygard의 Decision 부분 배경·선택·상태·결과를 갖춘 결정 한 개
답의 링크가 실제 문장을 뒷받침하는가 ALCE §3.3 미지원 문장과 불필요한 인용을 나눈 검토 결과

전체 논문을 한 번에 읽을 필요는 없습니다. 아래 ‘첫 읽기’ 구간만 읽고 질문을 적은 다음, 실험 조건이나 수식이 필요한 경우 ‘더 읽기’로 넘어가세요. 각 구간을 이해하는 데 걸리는 시간은 독자의 배경에 따라 달라집니다.

1. LLM Wiki 설계 글

Andrej Karpathy, LLM Wiki 원문 · 자료 ID S1. GitHub 생성 표시는 2026-04-04이며 별도 수정일과 고정 revision SHA는 이번 자료에서 확보하지 못했습니다. 댓글과 홍보 링크는 저자 본문과 구분하세요.

읽는 이유: ‘AI에게 문서를 맡긴다’는 말을 실제 저장 대상과 반복 작업으로 바꾸기 위해 읽습니다. 첫 읽기는 The core idea → Architecture → Operations → Indexing and logging → Note 순서입니다. 저자가 제안하는 것은 원자료를 읽어 연결된 Markdown 페이지를 유지하는 설계 패턴입니다. 원자료·위키·schema의 역할, ingest/query/lint, index와 log의 차이를 확인할 수 있습니다. 저자 본문

지원하는 주장: 질문에서 얻은 설명도 파일로 남겨 다음 탐색에 이어 쓸 수 있다는 설계입니다. 지원하지 않는 확장: 모든 RAG가 지식을 축적하지 못한다거나, 위키가 항상 모순을 발견하고 저렴하게 유지된다는 보편적 결론은 이 글로 입증할 수 없습니다. 비교 성능을 검증한 논문이나 공식 표준도 아닙니다.

읽은 뒤 할 일: 스터디 가이드의 학습 예제에서 원자료, 개념 페이지, 질문 페이지를 찾아보세요. ‘규칙에 적어 둔 기대’와 ‘변경 결과에서 확인한 사실’을 다른 색으로 표시해 보면 좋습니다. 더 읽을 때는 원문이 권하는 사람의 요약·수정 검토를 찾아, 자동 유지라는 표현의 운영 조건을 따져보세요.

2. RAG 원논문

Patrick Lewis 외, Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks · 자료 ID S12. 최초 제출 2020-05-22, 여기서는 v4 본문(2021-04-12)을 읽습니다.

읽는 이유: 검색한 자료를 생성에 쓰는 과정과 모델을 학습하는 과정을 분리해 보기 위해 읽습니다. 첫 읽기는 Figure 1과 §2 첫 문단, §2.4 Training입니다. 이 논문은 검색기와 생성기를 결합하며, 검색한 문서를 생성 문맥으로 사용하고 학습도 수행합니다. 따라서 ‘RAG는 학습이 전혀 없다’는 정의로 줄이면 원논문을 잘못 읽게 됩니다. §2 Methods

지원하는 주장: 외부 자료 검색과 생성 모델을 결합하는 방법이 존재합니다. 지원하지 않는 확장: 모든 검색 결과가 관련 있고, 모든 응답이 최신·정확하다는 보장은 아닙니다. §4.3의 Table 4는 특정 생성 과제·비교 모델에 대한 사람 평가입니다. 그 수치를 현재 사용 중인 도구의 품질로 옮기면 안 됩니다.

읽은 뒤 할 일: 실습의 검색 개념 카드에 ‘어디서 가져와 무엇의 입력으로 쓰는가’를 적으세요. 더 읽기는 §4.5의 index hot-swapping과 Broader Impact입니다. 자료 교체의 가능성과 원자료 편향·오류의 위험을 함께 읽습니다. 위키도 필요한 페이지를 검색해 사용할 수 있다는 병행 설계는 이 학습 자료의 해석이며, 해당 조합의 성능 실험 결과가 아닙니다.

3. LoRA 원논문

Edward J. Hu 외, LoRA: Low-Rank Adaptation of Large Language Models · 자료 ID S20. 최초 제출 2021-06-17, v2 본문은 2021-10-16 판입니다.

읽는 이유: ‘저장했으니 AI가 배웠다’는 표현에서 실제로 무엇이 바뀌었는지 묻기 위해 읽습니다. 첫 읽기는 Abstract, Figure 1, §4.1입니다. LoRA는 사전학습 가중치를 고정하고 저랭크 행렬을 학습해 가중치의 변화를 표현합니다. 기본 가중치를 고정한다는 문구만 보고 ‘아무 파라미터도 학습하지 않는다’고 정리하지 마세요. Abstract·§4.1

지원하는 주장: 파일에 메모를 저장하는 일과 학습 가능한 행렬을 최적화하는 일은 구분해야 합니다. 지원하지 않는 확장: LoRA가 모든 작업에서 전체 미세조정보다 낫다거나, 위키를 만들면 LoRA가 필요 없어졌다는 결론은 나오지 않습니다. 초록의 자원 절감 수치는 특정 모델·옵티마이저·비교 조건을 갖습니다.

읽은 뒤 할 일: 스터디 가이드의 비교 페이지에 ‘바뀌는 대상’을 적고, RAG는 ‘검색된 문맥’, LoRA는 ‘학습한 파라미터’에 표시하세요. 이 구분은 두 방법을 배타적으로 선택하라는 뜻이 아닙니다. 더 읽기는 §5의 비교 대상과 Appendix D의 실험 설정입니다. 도입을 검토한다면 논문 이름보다 자신의 과제·데이터·평가 조건을 먼저 정해야 합니다.

4. PROV 출처 정보 개요

W3C, PROV-Overview · 자료 ID S11. 편집자 Paul Groth·Luc Moreau, 2013-04-30 판입니다.

읽는 이유: 출처를 URL 하나보다 넓게 보기 위해 읽습니다. 첫 읽기는 Abstract, Status of This Document, §1 Introduction입니다. provenance는 결과물과 그것을 만든 활동·관여자의 정보를 다룹니다. 이런 정보는 품질과 신뢰성을 평가할 재료가 됩니다. 문서 자체는 비규범 Working Group Note이며 PROV 계열 문서로 가는 안내입니다. Abstract·§1

지원하는 주장: 무엇을 바탕으로 누가 어떻게 결과를 만들었는지 기록할 이유가 있습니다. 지원하지 않는 확장: 출처 정보가 있다는 사실만으로 내용이 참이 되지 않습니다. 이 학습 자료의 자료·주장·결정 카드가 W3C 인증 양식이라는 뜻도 아닙니다.

읽은 뒤 할 일: 실습의 카드에서 원문 위치, 읽은 판, 검토자, 확인일을 찾아보세요. URL은 있지만 어느 절을 읽었는지 없다면 재확인이 어려운 이유를 설명해 보세요. 더 읽기는 이 개요의 §2 Document Roadmap입니다. 상호운용 가능한 출처 데이터를 실제 구현해야 할 때 PROV-DM, PROV-O 등 역할에 맞는 규범 문서를 골라야 하며, 작은 스터디가 그 전체를 구현할 필요는 없습니다.

5. 짧은 결정 기록의 원문

Michael Nygard, Documenting Architecture Decisions · 자료 ID S10. 작성 2011-11-15, 별도 수정일은 이번 확인에서 확정하지 않았습니다.

읽는 이유: 확인한 정보와 우리가 선택한 행동을 나눠 남기기 위해 읽습니다. 첫 읽기는 Context에서 문제를 파악한 뒤 Decision의 형식 설명, 마지막 Consequences입니다. 중요한 소프트웨어 아키텍처 결정에 배경·선택·상태·결과를 남기며, 후속 결정으로 바뀌어도 이전 기록을 대체 상태로 보존합니다. Decision·Consequences

지원하는 주장: 과거 선택의 이유와 현재 유효한 결정을 함께 읽을 수 있게 기록할 수 있습니다. 지원하지 않는 확장: 모든 사실 확인이 결정이 되는 것은 아닙니다. 스터디의 답 저장 기준에 이 방식을 적용하거나 담당자·재검토 조건·대안을 추가하는 것은 우리의 응용입니다.

읽은 뒤 할 일: 스터디 가이드의 ‘검토한 답만 저장한다’는 가상 선택을 보세요. ‘논문에 이렇게 적혀 있다’와 ‘그래서 우리는 이렇게 운영한다’를 분리해 읽습니다. 더 읽을 때는 긍정적인 결과뿐 아니라 검토 시간·유지 부담도 기록한다는 점을 확인하세요. 발표 11장은 검토한 답을 저장하는 선택의 이유를, 9장은 잘못된 문장을 고치고 변경 이유를 남기는 과정을 보여줍니다. 결정 자체가 바뀌었을 때의 대체 이력은 학습 가이드의 보조 사례에서 이어서 읽을 수 있습니다.

6. ALCE 인용 평가 논문

Tianyu Gao 외, Enabling Large Language Models to Generate Text with Citations · 자료 ID S21. 최초 제출 2023-05-24, 여기서는 v2 본문(2023-10-31)을 읽습니다.

읽는 이유: ‘문장이 맞는가’, ‘인용이 문장을 지원하는가’, ‘불필요한 인용은 없는가’를 구별하기 위해 읽습니다. 첫 읽기는 Figure 1, §3의 평가 축, §3.3 Citation Quality입니다. 논문은 citation recall로 진술들이 인용 근거에 의해 지원되는지를, citation precision으로 불필요한 인용을 살핍니다. 구체적인 자동 평가는 NLI 모델의 판단을 사용합니다. §3.3 Citation Quality

지원하는 주장: 링크를 달았다는 외형과 실제 문장 지원은 다른 평가 대상입니다. 지원하지 않는 확장: 자동 함의 판단이 진실 판정의 최종 심판은 아닙니다. 논문의 당시 모델·데이터셋 결과를 지금 도구의 오류율로 읽거나, 우리의 카드 검토를 ‘ALCE를 실행했다’고 부르면 안 됩니다.

읽은 뒤 할 일: 실습에서 근거는 맞지만 문장이 지나치게 넓은 경우와, 문장은 지원되지만 무관한 링크를 더 붙인 경우를 나눠보세요. 사람의 읽기 활동에 평가 관점을 빌린 것입니다. 더 읽기는 §5.3 Retrieval Analysis와 §6 Human Evaluation입니다. 검색 문제·합성 문제·평가 모델의 한계를 어느 층에서 확인하는지 살펴봅니다.

용어를 역할로 구분하기

아래 구분은 이 학습 자료에서 쓰는 설명용 약속입니다. 여러 표준이 함께 정한 단일 데이터 형식이 아닙니다.

용어 이 자료에서의 뜻 섞기 쉬운 것
raw · 원자료 읽은 논문·설명·공지와 그 판을 보존하거나 다시 찾을 수 있게 기록한 것 AI가 쓴 요약을 원문으로 취급하기
source · 자료 카드 저자·제목·판·URL·확인일 등 자료를 다시 찾는 정보 그 자료가 모든 주장을 지원한다는 판정
claim · 주장 지원 여부를 확인할 수 있도록 하나로 쪼갠 문장 두 논문의 내용을 합친 해석을 직접 진술로 표시하기
evidence · 근거 그 주장을 지원한다고 제시한 실제 문장·표·절과 위치 문서 첫 화면 URL만 제시하기
inference · 해석 하나 이상의 근거에서 우리가 이끌어 낸 설명·추론 저자가 실험으로 확인한 결과처럼 말하기
decision · 결정 배경과 근거를 보고 사람이 채택한 행동 자료에서 읽은 사실 자체
schema · 작업 규칙 파일 구조·검토·변경 방법을 적은 약속 AI가 반드시 지킨다는 보장
index · 목차 필요한 페이지를 찾는 입구 시간순 변경 이력
log · 변경 이력 언제 무엇을 왜 바꿨는지의 기록 지금 유효한 설명 전체
diff · 차이 이전 파일과 제안된 파일 사이에서 추가·삭제·수정된 부분 의미 검토까지 완료했다는 증거
graph · 연결 보기 페이지 링크의 관계를 그린 표현 연결이 많을수록 내용이 정확하다는 점수
stale · 낡은 상태 현재 적용 여부를 다시 확인해야 하는 상태 작성일이 오래됐으므로 거짓이라는 판단
conflict · 충돌 같은 대상·조건에서 함께 받아들이기 어려운 진술 대상이나 실험 조건이 다른 결과
superseded · 대체됨 후속 결정이 현행이 되고 이전 이유는 이력으로 남은 상태 원문과 이전 결정의 무조건 삭제

검색·학습 관련 용어는 RAG 원논문, LoRA 원논문, 인용 평가 용어는 ALCE §3.3을 기준으로 다시 확인하세요. ‘근거가 지원한다’는 판정은 자료의 대상·시점·조건이 해당 문장과 맞는지 함께 봐야 합니다.

더 읽고 싶을 때 고르는 경로

주제 수를 늘리기 전에 위 6개 원문의 읽지 않은 부분을 골라 읽는 편을 권합니다. 검색을 구현하려면 RAG의 retriever·generator·training을, 학습을 구현하려면 LoRA의 방법·하이퍼파라미터·평가를, 검증을 설계하려면 ALCE의 자동 평가와 사람 평가를 이어 읽으세요. 이 세 갈래는 서로 다른 질문에 답합니다.

위키가 커졌을 때의 선택은 페이지 수 하나로 결정하기 어렵습니다. 다음 표는 실무 설계 제안이며 이 자료에서 측정한 성능 결과가 아닙니다.

목차에서 필요한 페이지를 못 찾음 제목·분류·별칭·링크가 질문을 반영하는지 분류와 연결 유지
원문을 매번 너무 많이 읽음 파일 검색으로 후보를 좁힐 수 있는지 검색 누락·인덱스 최신성 평가
요약만 보고 범위를 잘못 넓힘 주장에서 원문의 근거 위치로 돌아갈 수 있는지 원문 대조와 검토 시간
같은 설명이 여러 페이지에서 어긋남 기준 개념 페이지와 영향 페이지가 드러나는지 변경 전파와 충돌 검토
오래된 답이 현행처럼 사용됨 적용 시점·판·재검토 조건이 남아 있는지 정기 점검과 담당 배정

목차 탐색·텍스트 검색·의미 검색·구조화된 검색은 필요에 따라 함께 쓸 수 있습니다. 새로운 검색 장치를 붙여도 원자료 보존과 주장 범위 검토의 책임이 사라지지는 않습니다. 도입 효과를 말하려면 실제 질문 집합을 정해 정답 지원, 누락, 수정 시간, 운영 비용을 관찰해야 합니다.
