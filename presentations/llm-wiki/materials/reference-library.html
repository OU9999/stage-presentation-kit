LLM Wiki · 내 자료를 AI와 함께 정리하는 방법

원문 읽기 안내와 용어 모음

LLM Wiki 설계·검색·모델 학습·검토의 일차 근거를 구분해 읽는 안내

이 문서는 링크를 모으는 데서 한 걸음 더 나아가, 어떤 질문으로 원문을 읽고 어디까지 주장할 수 있는지 안내합니다. 먼저 스터디 가이드를 읽고 궁금해진 주제의 원문을 골라도 좋습니다. 준비된 사례를 따라가려면 예제 읽기와 해설, 말로 설명하려면 발표 대본을 이용하세요.

발표의 주제 메모·위키·질문 답은 발표팀이 작성한 설명용 구성 예입니다. 주제 메모도 외부 원문의 발췌가 아닌 자작 설명입니다. 아래 일차 근거의 주장, 우리가 작성한 설명과 활동 설계, 기존 ZIP의 고정 교정 실행을 구분해 읽으세요. 기존 정밀 교정 원문은 2026-10-28, 공개 코드·논문은 2026-10-29, 설계 글과 비교용 공식 문서는 2026-10-31 대조했습니다. 직접 인용 대신 한국어로 의역합니다.

이 발표의 근거를 읽는 기준

LLM Wiki의 출발점은 Karpathy의 설계 글입니다. 지속 문서를 무엇으로 구성하고 ingest/query/lint로 어떻게 유지하는지 읽습니다. RAG·Agentic RAG·모델 학습과의 비교는 각 기술의 논문과 공식 문서에 대조합니다.

이 발표는 같은 주제 메모와 같은 스터디 계획 질문으로 두 구성의 작업 시점·저장 대상·재읽기·유지 부담을 설명합니다. 보편적인 정확도·속도·비용 우위를 측정한 실험이 아닙니다. RAG도 관계와 요약을 미리 만들 수 있고, 위키도 검색을 사용할 수 있습니다. 검색·문서 유지·에이전트 판단·파라미터 학습은 병행 가능한 설계 축입니다.

개인 기록을 다섯 종류로 나누거나 기간별로 회고하는 방식은 선택적인 활용 예입니다. 특정 기록 체계·도구 조합·문서 수는 LLM Wiki의 필수 조건이 아닙니다. 예제의 rules.md는 정리와 검토를 안내하는 작업 규칙이며, 그래프는 문서 연결을 탐색하는 보기입니다.

개인비서와 맥락을 설명하는 근거

OpenClaw의 Memory 문서는 사용자 선호·맥락·결정 등을 마크다운 파일로 남기는 구조를 설명합니다. Hermes 공식 저장소도 지속 기억과 사용자 프로필을 다룹니다. 두 예는 개인비서가 사용자 맥락을 지속해서 읽는 필요를 설명하는 데 사용합니다. 두 도구의 기억 구현을 같은 위키 구조라고 단정하지 않으며, 특정 월의 유행이나 LLM Wiki의 인기 원인을 입증한 자료로 사용하지 않습니다. 확인일은 2026-10-31입니다.

Karpathy Gist의 생성 표시는 2026-04-04입니다. 원문의 날짜와 본문을 확인했습니다. ‘나만의 지식 베이스’와 사람·AI의 역할, 목차·연결은 이 설계의 설명을 바탕으로 합니다.

‘RAG는 DB가 필수’, ‘문서10만개부터 RAG가 우위’, ‘벡터 검색을 쓰면 사람이 원문을 읽을 수 없다’는 단정은 채택하지 않습니다. 작은 위키를 파일과 목차로 시작할 수 있다는 점과, 자료가 커지면 검색·갱신·검토를 함께 설계한다는 점을 설명합니다. 감정·생각·판단을 직접 기록하고 AI 해석과 나누는 방법은 이번 발표가 제안하는 운영 팁입니다.

비교와 도구 역할의 일차 근거

네 방식은 서로 다른 설계 축입니다. 위키 문서는 검색 대상이 될 수 있고, 검색에 에이전트 판단을 붙이거나 모델 적응을 병행할 수 있습니다. 이 병행 제안은 이번 학습 자료의 설계 해석이며 비교 성능 실험 결과가 아닙니다. 주제 메모 예제의 입력·규칙·위키 기대 모양은 확장 학습 팩에서 읽을 수 있습니다. 구판 예제는 별도 부록으로 보존했습니다.

전체 논문을 한 번에 읽을 필요는 없습니다. 아래 ‘첫 읽기’ 구간만 읽고 질문을 적은 다음, 실험 조건이나 수식이 필요한 경우 ‘더 읽기’로 넘어가세요. 각 구간을 이해하는 데 걸리는 시간은 독자의 배경에 따라 달라집니다.

1. LLM Wiki 설계 글

Andrej Karpathy, LLM Wiki 원문 · 자료 ID S1. 이 안내는 고정 revision ac46de1ad27f92b28ac95459c782c07f6b8c964a의 본문을 기준으로 합니다(2026-10-31 대조). 설계·세 작업·선택 도구·Note를 함께 읽고, 댓글과 홍보 링크는 저자 본문과 구분하세요.

읽는 이유: ‘AI에게 문서를 맡긴다’는 말을 실제 저장 대상과 반복 작업으로 바꾸기 위해 읽습니다. 첫 읽기는 The core idea → Architecture → Operations → Indexing and logging → Note 순서입니다. 저자가 제안하는 것은 원자료를 읽어 연결된 Markdown 페이지를 유지하는 설계 패턴입니다. 원자료·위키·schema의 역할, ingest/query/lint, index와 log의 차이를 확인할 수 있습니다. 저자 본문

지원하는 주장: 질문에서 얻은 설명도 파일로 남겨 다음 탐색에 이어 쓸 수 있다는 설계입니다. 지원하지 않는 확장: 모든 RAG가 지식을 축적하지 못한다거나, 위키가 항상 모순을 발견하고 저렴하게 유지된다는 보편적 결론은 이 글로 입증할 수 없습니다. 비교 성능을 검증한 논문이나 공식 표준도 아닙니다.

읽은 뒤 할 일: 스터디 가이드의 학습 예제에서 원자료, 개념 페이지, 질문 페이지를 찾아보세요. ‘규칙에 적어 둔 기대’와 ‘변경 결과에서 확인한 사실’을 다른 색으로 표시해 보면 좋습니다. 더 읽을 때는 원문이 권하는 사람의 요약·수정 검토를 찾아, 자동 유지라는 표현의 운영 조건을 따져보세요.

2. RAG 원논문

Patrick Lewis 외, Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks · 자료 ID S12. 최초 제출 2020-05-22, 여기서는 v4 본문(2021-04-12)을 읽습니다.

읽는 이유: 검색한 자료를 생성에 쓰는 과정과 모델을 학습하는 과정을 분리해 보기 위해 읽습니다. 첫 읽기는 Figure 1과 §2 첫 문단, §2.4 Training입니다. 이 논문은 검색기와 생성기를 결합하며, 검색한 문서를 생성 문맥으로 사용하고 학습도 수행합니다. 따라서 ‘RAG는 학습이 전혀 없다’는 정의로 줄이면 원논문을 잘못 읽게 됩니다. §2 Methods

지원하는 주장: 외부 자료 검색과 생성 모델을 결합하는 방법이 존재합니다. 지원하지 않는 확장: 모든 검색 결과가 관련 있고, 모든 응답이 최신·정확하다는 보장은 아닙니다. §4.3의 Table 4는 특정 생성 과제·비교 모델에 대한 사람 평가입니다. 그 수치를 현재 사용 중인 도구의 품질로 옮기면 안 됩니다.

읽은 뒤 할 일: 선택 심화의 검색 개념 카드에 ‘어디서 가져와 무엇의 입력으로 쓰는가’를 적으세요. 더 읽기는 §4.5의 index hot-swapping과 Broader Impact입니다. 자료 교체의 가능성과 원자료 편향·오류의 위험을 함께 읽습니다. 위키도 필요한 페이지를 검색해 사용할 수 있다는 병행 설계는 이 학습 자료의 해석이며, 해당 조합의 성능 실험 결과가 아닙니다.

3. LoRA 원논문

Edward J. Hu 외, LoRA: Low-Rank Adaptation of Large Language Models · 자료 ID S20. 최초 제출 2021-06-17, v2 본문은 2021-10-16 판입니다.

읽는 이유: ‘저장했으니 AI가 배웠다’는 표현에서 실제로 무엇이 바뀌었는지 묻기 위해 읽습니다. 첫 읽기는 Abstract, Figure 1, §4.1입니다. LoRA는 사전학습 가중치를 고정하고 저랭크 행렬을 학습해 가중치의 변화를 표현합니다. 기본 가중치를 고정한다는 문구만 보고 ‘아무 파라미터도 학습하지 않는다’고 정리하지 마세요. Abstract·§4.1

지원하는 주장: 파일에 메모를 저장하는 일과 학습 가능한 행렬을 최적화하는 일은 구분해야 합니다. 지원하지 않는 확장: LoRA가 모든 작업에서 전체 미세조정보다 낫다거나, 위키를 만들면 LoRA가 필요 없어졌다는 결론은 나오지 않습니다. 초록의 자원 절감 수치는 특정 모델·옵티마이저·비교 조건을 갖습니다.

읽은 뒤 할 일: 스터디 가이드의 비교 페이지에 ‘바뀌는 대상’을 적고, RAG는 ‘검색된 문맥’, LoRA는 ‘학습한 파라미터’에 표시하세요. 이 구분은 두 방법을 배타적으로 선택하라는 뜻이 아닙니다. 더 읽기는 §5의 비교 대상과 Appendix D의 실험 설정입니다. 도입을 검토한다면 논문 이름보다 자신의 과제·데이터·평가 조건을 먼저 정해야 합니다.

4. PROV 출처 정보 개요

W3C, PROV-Overview · 자료 ID S11. 편집자 Paul Groth·Luc Moreau, 2013-04-30 판입니다.

읽는 이유: 출처를 URL 하나보다 넓게 보기 위해 읽습니다. 첫 읽기는 Abstract, Status of This Document, §1 Introduction입니다. provenance는 결과물과 그것을 만든 활동·관여자의 정보를 다룹니다. 이런 정보는 품질과 신뢰성을 평가할 재료가 됩니다. 문서 자체는 비규범 Working Group Note이며 PROV 계열 문서로 가는 안내입니다. Abstract·§1

6. ALCE 인용 평가 논문

Tianyu Gao 외, Enabling Large Language Models to Generate Text with Citations · 자료 ID S21. 최초 제출 2023-05-24, 여기서는 v2 본문(2023-10-31)을 읽습니다.

읽는 이유: ‘문장이 맞는가’, ‘인용이 문장을 지원하는가’, ‘불필요한 인용은 없는가’를 구별하기 위해 읽습니다. 첫 읽기는 Figure 1, §3의 평가 축, §3.3 Citation Quality입니다. 논문은 citation recall로 진술들이 인용 근거에 의해 지원되는지를, citation precision으로 불필요한 인용을 살핍니다. 구체적인 자동 평가는 NLI 모델의 판단을 사용합니다. §3.3 Citation Quality

지원하는 주장: 링크를 달았다는 외형과 실제 문장 지원은 다른 평가 대상입니다. 지원하지 않는 확장: 자동 함의 판단이 진실 판정의 최종 심판은 아닙니다. 논문의 당시 모델·데이터셋 결과를 지금 도구의 오류율로 읽거나, 우리의 카드 검토를 ‘ALCE를 실행했다’고 부르면 안 됩니다.

읽은 뒤 할 일: 선택 심화에서 근거는 맞지만 문장이 지나치게 넓은 경우와, 문장은 지원되지만 무관한 링크를 더 붙인 경우를 나눠보세요. 사람의 읽기 활동에 평가 관점을 빌린 것입니다. 더 읽기는 §5.3 Retrieval Analysis와 §6 Human Evaluation입니다. 검색 문제·합성 문제·평가 모델의 한계를 어느 층에서 확인하는지 살펴봅니다.
