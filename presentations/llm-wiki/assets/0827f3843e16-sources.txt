LLM Wiki: 답을 근거와 연결해 남기기
공개 출처·주장 대응 / Zoom AI 스터디 / 조사 확인일 2026-10-28

이 첨부는 12장 발표(18분)와 질문(2분)의 근거를 찾아보기 위한 자료다.
S*는 실제 외부 조사 출처, C*는 발표 주장이다. E1~E4·EC1~EC2·ED1~ED2는 모두 설명을 위해 만든 합성 예제이며 실제 운영 성과의 증거가 아니다. 합성 자료의 정확한 내용은 decision-example.txt, 시작 양식은 starter-template.txt, 진행은 speaker-guide.txt에 있다.

읽는 방법
- 직접 지원: 원문이 말하는 내용이다.
- 해석: 원문을 읽고 이번 설계의 범위에서 도출한 구분이다.
- 제안: 발표자가 작은 스터디에 적용하도록 만든 작업 방식이다.
- 원문이 어떤 설명을 직접 지원한다는 판단과, 그 방식을 도입하면 효과가 난다는 입증은 다르다. 출처 링크의 존재만으로 문장 전체의 사실성·최신성·정확성이 보장되지는 않는다.

발표 주장과 화면 대응

C01 / 2장 / S1 The core idea, Note / 직접 지원
주장: LLM Wiki는 LLM이 지속적인 Markdown wiki를 구축·갱신하는 지식관리 패턴 제안이다.
안전한 표현: “Karpathy가 공개한 LLM Wiki 아이디어를 출발점으로 봅니다.”
경계: 특정 제품·공식 표준·모든 위키의 정의로 단정하지 않는다.

C02 / 3장 / S1 Architecture / 직접 지원
주장: 원자료 raw, LLM이 작성하는 wiki, 작업 규칙 schema의 세 층이다.
안전한 표현: “원자료는 보존하고 연결된 wiki를 갱신하며, 옆의 규칙 문서가 작업법을 정합니다.”
경계: schema는 raw와 wiki 다음으로 통과하는 산출물이 아니다. 원자료 보존은 해당 설계의 규칙이며 외부 원문이 영원히 바뀌지 않는다는 뜻도 아니다. 규칙 준수는 보장되지 않는다.

C03 / 5장 / S1 Operations, Indexing and logging / 직접 지원
주장: ingest/query/lint와 index/log를 반복 사용과 축적을 돕도록 설계한다.
안전한 표현: “새 자료를 반영하고, 유용한 질문 결과를 남기고, 낡은 주장과 빠진 연결을 점검합니다. index는 찾기, log는 변경 이력입니다.”
경계: 모든 답 자동 저장·모든 모순 검출을 보장하지 않는다. 4·6장의 구체적인 페이지 구성과 사람 검토 후 답 저장은 우리 제안이다.

C04 / 11장 / S1 Architecture / 해석
주장: 이 설계에서 지속되는 것은 사람이 열어 볼 수 있는 wiki 파일이다.
안전한 표현: “파일을 고쳐 저장하는 일과 모델의 가중치를 학습시키는 일은 구분합니다.”
경계: wiki 파일 수정 자체를 모델 재학습으로 표현하지 않는다.

C05 / 11장 / S12 §2 / 직접 지원 + 설계 해석
직접 지원: RAG는 검색한 자료를 문맥으로 사용해 답을 생성한다.
설계 해석: wiki도 필요하면 검색과 함께 쓸 수 있다.
경계: 파일 wiki와 RAG를 배타적인 제품이나 우열 관계로 구분하지 않는다. RAG 전반에 훈련이 없다고 말하지 않는다.

C06 / 6장 / S11 Abstract, Introduction / 직접 지원
주장: 출처 정보는 품질·신뢰성을 판단하는 재료다.
안전한 표현: “어디서, 누가, 어떻게 만든 자료인지 따라갈 단서를 남깁니다.”
경계: 링크를 달았다는 이유만으로 모든 문장이 사실인 것은 아니다. S11은 비규범 Note다.

C07 / 8·10장 / S10 Context, Decision, Status, Consequences / 직접 지원 + 응용 제안
직접 지원: 중요한 결정의 배경·선택·상태·결과를 남기고 대체된 과거 기록을 보존한다.
응용 제안: 스터디 운영 결정에 사용하며 대안·담당·재검토 조건을 덧붙인다.
경계: 자료에서 읽은 사실과 사람이 채택한 행동을 섞지 않는다. ED1/ED2는 가상 결정이다.

C08 / 7장 / S10·S11에서 착안 / 제안
주장: 자료→주장→결정을 나누고 근거 위치·확인일·검토자를 붙여 본다.
안전한 표현: “우리가 검토하기 쉽게 이 세 칸으로 나눠 보겠습니다.”
경계: LLM Wiki·PROV·ADR가 함께 규정한 표준 양식이 아니다. 효과는 측정하지 않았다.

C09 / 6·11장 / S12 Table 4, Broader Impact 및 S1의 설계 제안 범위 / 해석·제안
주장: 근거와 응답을 대조하고 자동 점검의 누락 가능성을 남겨 둔다.
안전한 표현: “자료가 붙어 있어도 이 문장을 정말 뒷받침하는지는 다시 확인합니다.”
경계: 논문의 비교 실험을 현재 제품의 정확도·최신성·비용 보장으로 바꾸지 않는다. 이번 검토 절차의 효과도 측정하지 않았다.

C10 / 9·10장 / 발표자의 운영 방식 / 제안
주장: 새 자료가 오면 관련 주장·결정을 찾아 함께 보고 사람이 승인한 후 기록을 갱신한다.
안전한 표현: “새 정보의 명시적 변경과 적용 범위를 확인하고 관련 페이지와 결정을 다시 봅니다.”
경계: 나중 날짜라는 이유만으로 자동 채택하지 않는다. 모든 연결의 발견·자동 갱신·무검토 승인을 보장하지 않는다.

합성 예제의 위치
4장: E1·E3·E4에서 운영·개념·질문 페이지로 연결.
6장: E4의 질문과 검토 후 남기는 합성 답안.
7~8장: E1 → EC1 → ED1. “매주”는 미지원 확장.
9~10장: E2 → EC2 → ED2. 11월 5일 한 날짜만 20:00에서 20:30으로 변경.
12장: 이 출처 첨부, 합성 결정 카드, 시작 템플릿, 공개 진행 가이드로 연결.

확인하지 않은 것
실제 wiki 운영의 누락률, 시간 절감, 정확도, 유지비를 이번 작업에서 측정하지 않았다. 합성 예제는 실제 앱 구현이나 도입 성과 보고가 아니다. 오답·낡은 정보·연결 누락 가능성은 남는다.
