# LLM Wiki의 DevDay 시각 언어 복원 방향

작성: 2026-10-31 · A 디자인 구현 책임 · 기준: main `92f3c29`의 48장

## 현재 결정과 범위

발표 기본을 `theme: stage`로 복원하고, 19개 독자 SVG의 크림 배경·네이비 면을 역할에 따라 다시 조판한다. SVG root에는 `style="background:#080808"`을 두어 밝은 학습서·Paper 테마·단독 이미지에서도 글자 대비를 보존한다. Stage에서는 같은 검정 무대에 이어지며 전면 크림 사각형이나 큰 네이비 패널을 복원하지 않는다. 48장·본편 35분+Q&A 5분·현재 개념과 자료의 의미를 유지한다. 실습을 새로 넣거나 빼지 않는다. 직접 YouTube 링크와 영상 중심 홍보/사례 표현을 정리하는 최신 사용자 지침은 발표팀이 소유하며, 이 사양의 기존 제목·메모 이름은 대조용 스냅샷이다. 발표팀의 최종 독립 사례 문구를 시각물에도 일치시킨다.

초기 조사는 제품을 읽기 전용으로 진행했다. 이후 root가 A에게 `talks/llm-wiki/assets/expanded/*.svg` 19개와 이 작업의 새 `generate_assets.py` 구현을 승인했다. 이 파일과 `DESIGN_SPEC.json`도 A 소유다. 제품 원고·공통 엔진·CSS·이전 연구는 A가 수정하지 않는다. root가 WORK_LOG·공통 코드·생성물·브라우저 인수를 관리한다.

## 왜 DevDay 스타일이 사라졌는가

테마 적용 실패가 아니라 덱 단위 디자인 방향이 바뀌었다.

- `talks/llm-wiki/slides.md:3`이 `theme: paper`를 명시한다.
- `research/llm-wiki-expanded-20261031/design/DESIGN_BOARD.md:7`은 참고 LLM 강의 09:15의 크림 배경·네이비 위키 면을 관찰했다고 기록한다. 같은 문서의 공통 언어 표가 이 덱을 Paper로 전환한다.
- 같은 작업의 `content/STORY_CONTRACT.md:121`과 `design/HANDOFF.md:19`가 크림/네이비/틸/코랄 언어를 구현 계약으로 유지한다.
- `design/generate_assets.py`의 `save()`가 19개 SVG 모두에 `fill="#F2F0E8"` 전면 사각형을 삽입하고, 색도 CSS 테마와 별도로 하드코딩한다. 원고 테마만 Stage로 바꾸면 검정 무대 안에 크림 도식이 남는다.
- 공통 `DESIGN.md`는 이미 Stage 검정·큰 타이포·넓은 여백·의미색·역할별 정보량 변화를 기본으로 정한다. 덱 전환 때 이 공통 방향과의 대조가 빠졌다.

복원은 팔레트 교체와 함께 화면 역할·텍스트 계층·밝은 면의 이유를 재검토해야 한다.

## 재사용할 공통 원칙

1. 검정 중립 캔버스와 큰 중립 타이포를 기본으로 한다. 색 면적·빈도 수치를 DevDay 공식 규칙으로 만들지 않는다.
2. 선언 → 비교/근거 → 열린 관계도 → 읽을 문서 → 질문으로 역할을 바꾼다. 장 수를 채우기 위한 새 사진·아이콘·도형을 추가하지 않는다.
3. 실제 UI·문서·사진은 원래 표면을 가질 수 있다. 추상 개념을 담는 모든 면을 밝은 문서처럼 그리지는 않는다.
4. 색은 이름·위치·문자와 함께 의미를 연결한다. eyebrow·페이지·연결선·단계번호·상시 장식은 중립이다.
5. 한 화면의 주역은 하나다. 제목과 내부 제목이 같은 뜻이면 발표팀이 확정한 한 쪽을 주역으로 삼고, 나머지는 메타/설명 수준으로 낮춘다. 내용을 지우거나 노트로 옮기는 작업은 발표팀/root 승인 후 수행한다.
6. 기본 조작과 읽기·발표자·전체보기·접근성 계약을 보존한다. 제목/본문을 새 SVG로 평면화해 편집성을 잃지 않는다.

위 원칙은 주제와 독립적인 재사용 기준이다. 아래의 RAG/위키 색 의미, raw/wiki/rules 구조, 15분 진행안·다음 질문은 이 덱의 사례 내용이다.

## 조판 단위와 글자 크기

기준은 1600×900 무대다. SVG는 1500×600 viewBox를 유지한다. 크기는 구현 시작값이며 실제 렌더/글꼴 bbox를 보고 조정한다.

| 화면 역할 | 제목/주역 | 본문 | 배치 |
| --- | --- | --- | --- |
| 표지·큰 선언 | 110–130px | 24–30px | 중앙 단일 초점, 주변 보조 최소 |
| 질문·정의 | 메타 제목 38px, 주역 68–76px | 24–26px | 질문은 2줄 안팎; 긴 정의6은 기존 의미를 보존하고 3줄 수준 |
| 열린 두/세 그룹 | 제목 60–64px, 그룹명 38–44px | 28–32px | 그룹 전체를 본문 영역 중앙에 놓고 큰 하단 빈 공간의 원인을 제거 |
| 개념/동작 도식 | 바깥 제목 54px, 내부 주역 40–48px | 34–38px | 도식이 본문의 대부분. 메타 26–28px |
| 문서/비교표 | 제목 60–64px | 표/문서 28–34px | 한 비교축의 기준선을 맞춤. 줄수와 자료 의미 보존 |

폰트는 저장소의 로컬 시스템 글꼴 스택을 사용한다. 브랜드 글꼴을 추정하거나 원본과 동일하다고 보고하지 않는다. SVG의 메타를 글자 축소로 해결하지 않고 장면별로 의미를 배치한다.

### baseline editorial 14장 → 최종 계획 12장의 실행 선택

현재 `blocks.css`의 editorial은 `grid-auto-rows:minmax(0,1fr)`라 H2 그룹의 내용이 상단에 붙는다. 색/테마만 바꿔서는 중앙의 큰 개념 군이 되지 않는다. A/B와 발표A는 기존 그룹 원문을 유지하는 **범용 opt-in 중앙 조판**에 합의했고 root가 공통 구현을 맡았다. 발표A와 합의한 역할은 message 7, quote 5, media 17, editorial 12, document 6, closing 1이다. 4/13/19/36/48을 중앙 선언으로 바꾸며 13/36이 기존 editorial에서 빠진다.

- 새 범용 `variant: centered`를 editorial에만 적용한다면, parser 허용값·`blocks.js`의 variant/구도 대응·`blocks.css`의 해당 variant 스코프를 함께 다룬다. 읽기는 기존 소스 순서를 유지한다.
- 중앙 변형은 높이를 차지하는 가짜 행을 없애고 그룹 전체를 본문 중간에 놓는다. 그룹별 제목·본문·선은 실제 내용 높이만 가진다. 2열/3열 구조는 유지한다.
- 현재 단일 Markdown 원고 계약에는 native JSON `visual`/`steps`가 compose로 지원되지 않는다. 이번에는 12개 editorial의 소스와 읽기 계약을 유지하며, 9/17/35의 순서·귀환, 22/43의 병렬 조건·위험을 내용 위계로 구분한다. 분류22/43에 순서 화살표를 붙이지 않는다.
- 덱 id·한국어 제목·장번호를 하드코딩한 CSS는 추가하지 않는다. 이미 존재하는 `balanced`를 editorial에 억지 지정하면 현재 fallback 진단이 나므로 사용하지 않는다.

root는 다른 예제 editorial의 기본 동작을 보존하고 1440/960/읽기 화면을 회귀 확인한다. 원고를 별도 native JSON으로 옮기거나 12장을 새 SVG로 만드는 방식은 채택하지 않는다.

## 48장과 19자산의 구체 계약

장별 역할·크기·중심·의미색·변경 경로는 `DESIGN_SPEC.json`의 `slides` 48개에 기록한다. 자산별 재조판은 같은 파일의 `assets` 19개를 따른다. 현행 제목은 대조값이며 새 영상노출 제거 문구가 확정되면 새 텍스트로 연결한다.

중요한 연속 구간은 다음과 같다.

- 10→11→12→13→14: 공통 자료와 질문은 고정한다. 11은 자료→이번 입력→답의 시간 흐름, 12는 같은 자료→저장된 관계→필요한 쪽 재읽기의 지속 구조다. 12를 11의 상자 한 개만 바꾼 그림으로 만들지 않는다. 우열·성능 차이로 표현하지 않는다.
- 19→20→23→25→26→27: 사람의 목적을 큰 문장으로 제시한 뒤, 파일 구조·목적 메모·연결 동작·실제 문서·종합 결과로 역할을 바꾼다.
- 30→31→32→33→34→35: 새 조건은 주황, 바뀐 설명은 같은 위치에 표시하고, 실제로 읽는 입력과 남긴 질문 문서는 별도 역할이다. 마지막 세 동작을 새 저장소 세 개처럼 그리지 않는다.
- 38→39→40→41: 공유 구조→작업 맥락→실제 진행안 발췌→검토·다음 질문으로 이동한다. 40은 밝은 문서가 주역일 수 있고 41은 검정 무대로 복귀한다. 색 복귀 주기를 일반 규칙으로 만들지 않는다.

## 인수와 검토

제품 쓰기 권한이 전달된 뒤 현재 자산을 대체할 때는 이전 연구를 덮어쓰지 않고 새 재생성 소스를 이 작업 아래 보관한다. `assets/expanded/` 경로·SVG title/desc·alt/본문/자료의 이름과 설명은 발표팀 계약과 맞춘다. 두 학습서 전용 자산 `five-layers.svg`·`reflection-layers.svg`도 같은 팔레트/대비로 정돈하되 본편에 새로 넣지 않는다.

필수 검수: 전48 PNG와 중요 원본 크기 시각 확인, 1440/960의 글자·경계·런타임 진단, 390 읽기의 원순서·alt·표/문서 가로 넘침, SVG19의 실제 text bbox/겹침, 11/12 동일입력과 차이, 20의 rules 전역성, 26의 원자료/사람이유/종합 구별, 30~34 조건 변화, 40/41 문서 링크·시간 합계·작성 주체, 46/48 자료 링크. 새 YouTube 노출 제거는 root/발표팀이 발표·읽기·배포자료 전범위에서 별도 확인한다.

이 두 파일은 구현 완료 또는 화면 인수의 증거가 아니다. B 시각 감사의 전체 실독과 상호 질의 뒤 확정하고 root에 전달한다.

## 1차 구현 마감과 후검수 대기

A는 새 `generate_assets.py`와 기존 경로의 SVG19개를 구현했다. 전면 크림 사각형·네이비 큰 관계면을 제거하고, 11은 현재 입력 범위, 12는 열린 저장 관계, 26은 두 문서, 33은 질문 문서, 40은 실제 진행안, 41은 검토 결과의 역할로 재조판했다. 세 주제 메모의 이름과 raw 경로는 발표A/자료B와 직접 대조했다. root 지적에 따라 밝은 학습자료·Paper 선택·단독 재사용에서도 대비를 유지하는 검정 root backing을19개에 넣었다.

발표A/자료B의 직접 반론을 반영해40의 제목·목표·네 활동 행을 등록 `session-plan.md`의 정확한 문구로 맞췄고,33은 raw메모 안에서 목차를 읽는 듯한 문장을 ‘목차에서 개념·비교·계획을 찾아 읽습니다.’로 교정했다. 저장된 질문 문서는 활동을 준비하며 검토한 구성 예이며15분읽기활동 중 위키 파일을 작성한다는 뜻으로 제시하지 않는다.

자체 확인은 Python생성기 문법,19SVG XML/title/desc,구팔레트·영상/실명/타임코드0,새 임시 출력과19개 바이트일치,진행안 발췌문자일치다. root는 실제 Chromium에서19SVG의 bbox경계/글자겹침0을 보고했으며 이후33/40문자delta는최종화면검수에서재확인한다. magick은로컬SVG글꼴목록을해석하지못해실패했고QuickLook은정방형자동크롭이므로이를전체시각인수근거로쓰지않았다.
