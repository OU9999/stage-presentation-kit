## 지금 설명할 수 있는 핵심

LLM Wiki는 원자료를 보존하고 LLM 에이전트가 개념·비교·잠정 종합을 Markdown 위키로 작성하고 계속 갱신하는 방식이다. 특정 완제품의 이름은 아니다. 새 자료 하나를 넣어 새 요약만 늘리는 것보다 기존 개념과 비교를 함께 고쳐 다음 질문의 출발점으로 남기는 것이 목적이다.

사람은 자료·질문·범위와 검토할 사람을 정한다. 파일 도구와 읽기·쓰기 권한이 있는 에이전트가 실제 파일을 읽고 고친다. 읽는 도구는 페이지와 링크를 보는 창이다. 저장 파일의 존재는 모델의 영구 기억이나 가중치 학습이 아니다. 다음 답이 실제로 관련 페이지를 읽었는지 확인해야 한다.

Ingest는 새 자료와 기존 위키를 대조해 관련 설명을 고친다. Query는 저장된 설명과 필요하면 원자료를 읽고 답하며 유용한 답을 다시 연결해 저장한다. Lint는 오래된 설명·조건 차이·누락을 찾아 다시 읽고 고칠 후보를 만든다. 점검 후보를 확정 오류로 취급하면 안 된다.

## 가장 남은 사례

- 고객 A는 월말 정산을 위해 수동 CSV를 원하고, B는 매일 자동 수신을 원한다. 형식이 같아도 요구를 뭉개면 안 된다. 회의 후 예약 전송이 보류됐어도 원래 B 요구는 남기고, 응대에는 출시일이 미확정이라고 말한다. 원래 요구/현재 상태/약속을 나누는 사례가 내 실무 적용 상상에 가장 도움이 됐다.
- 소설에서는 인물의 자기 설명을 확정 동기로 바꾸지 않았다. 인물 페이지의 이전·이후 문장을 나란히 본 장면이 남는다.
- 강의에서는 회귀와 회귀트리가 같은 기준을 쓰는 경우, 분류트리는 다른 기준을 쓰는 경우를 연결했다. 새 정보는 이전 설명의 오류를 꾸며내는 대신 조건과 비교 행을 더할 수도 있다.

## 내 적용과 현재 추정

내가 적은 질문은 발표 준비 메모와 새 피드백을 함께 보고 다음 발표에서 유지·변경할 설명을 묻는 것이었다. 이를 적용한다면 원래 피드백을 보존하고, 주제별 설명·수정 이유·남은 확인을 별도로 유지해 다음 리허설에서 다시 읽고 싶다. 이는 역할 관점의 적용 구상이고 실제 파일 실행 결과는 아니다.

같은 주제를 반복하고 자료가 계속 추가되는 경우에 가치가 클 것이라고 추정한다. 유지 비용은 사라지지 않고 자료가 들어올 때 설명 갱신·중복·근거·경로 검토로 옮겨간다. 작은 자료 묶음과 질문 하나로 시도해 실제 재사용과 수정 부담을 확인하라는 시작 방식에는 확신이 생겼다. 실행 환경을 지금 혼자 구성할 자신은 아직 없다.

## 현재 남은 질문과 돌아가고 싶은 곳

- 가장 궁금한 것은 최소 시작 폴더·작업 규칙 문장·에이전트 실행 한 번의 예다. 일반 요청 문장은 기억나지만 처음 제공할 파일을 어떻게 구성하는지 확인하고 싶다.
- 실제 답이 읽은 페이지와 근거를 어떤 출력으로 확인하는가? 중복 저장이나 관련 페이지 누락을 발견한 뒤 무엇을 승인하는가? Lint 후보를 확정하는 실제 절차도 궁금하다.
- 돌아가고 싶은 곳: 사람/에이전트/읽는 도구 구분과 raw/wiki/schema 구조, 소설 인물 문장의 전후, 에이전트 요청 예문(기억상 5~6장·11장·25장). 이 장번호는 현재 기억이며 다시 조회해 보정하지 않았다.
- 40장 링크는 공개 구현/실험과 파일 교정 예제를 나눠 안내한다. 후속 경로가 있다는 것은 알지만 아직 열지 않아 위 질문이 거기서 해결된다고 미리 판단하지 않는다.

## 유지·변경 우선도

1. 우선 변경 검토: 소설 시작 화면과 강의 시작 화면에서 다음 입력이 발화 예고보다 먼저 보였던 순서. 화면과 말의 시점을 맞추면 전후 변화가 더 잘 전달되겠다.
2. 우선 유지: 고객 사례의 요구·상태·약속 구분, 사람의 확인 역할, 파일 저장과 실제 재읽기의 구별, 직접 질문 한 줄 작성과 작은 검증 시작.
3. 그다음 변경 검토: 작은 시작의 확인 기준을 화면에서도 더 잘 보이게 하기. 회상에 남은 기준은 근거를 다시 찾는지와 잘못된 정리를 고칠 부담을 감당하는지다.
4. 복습 구간이 이어질 때 주의가 내려갔으나 행동 요청으로 회복됐다. 분량을 즉시 줄여야 한다는 결론은 유보한다. 음성 속도와 실제 청중 반응은 검증하지 않았다.
