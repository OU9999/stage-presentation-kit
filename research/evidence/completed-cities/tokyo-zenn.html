OpenAI よりご挨拶

Main Stage | 15:00–15:08(予定 15:00–15:10)
Welcome
登壇:長﨑 忠雄 — OpenAI Japan 代表

開会の挨拶は OpenAI Japan 代表の長﨑さんでした。会場には開発者だけでなく、大学生、研究者、ChatGPT のプロユーザー、AI を使いこなしている企業やパートナーが集まっていて、「これだけ異なるバックグラウンドが集まる会ができるのも、AI が持つ可能性を実感せざるを得ない」と話しました。

OpenAI のミッションは「AGI の実現によって、世界中の人に恩恵を届け、幸せになってもらうこと」で、DevDay もその取り組みの一つだそうです。前日(10月19日)にはスタートアップの創業者向けイベント「OpenAI Founders Day Tokyo」を開き、AI でサービスをどう良くするか、今までにない製品をどう世に出すか、日本のスタートアップが OpenAI と組んで、これまでとはまったく違うコストとスピードで世界に出ていくには何ができるか、を議論しました。今日は「東京から新しいアイデアや参加者どうしのつながりが生まれ、日本のコミュニティから世界が広がっていくこと」を期待している、とのことでした。

日本の AI 活用を示す3つの数字

  • +60%以上:日本の API アクティブアカウント数(前年同期比)
  • 2倍以上:ChatGPT Business と Enterprise を合わせた日本の契約席数
  • 世界2位:Dots のアクティブユーザー数での日本の順位

契約席数の伸びを支えているのは Codex とのことです。Codex は今年の1月・2月から急に伸びていて、その伸びと Business・Enterprise の伸びが強く相関しています。

3つ目の数字の Dots(ドッツ)は、公開されてまだ1か月ほどのエージェントです。長﨑さんの説明では、ChatGPT が「質問すると傍らで手伝ってくれる存在」なのに対し、Dots は自分の目標やゴール、その背景まで理解したうえで、やるべきことをプロアクティブに教えてくれます。長﨑さん自身は初めて使ったとき「AI のレベルが確実に数段上がった」と感じ、それから数週間、仕事の抜けや予定の抜け、経営上の目標設定についての提案を受け続けていて、煩雑な作業から大きく解放される兆しを感じているそうです。日本が世界で2番目にアクティブユーザーが多いことについては「日本のユーザーが新しい技術をいち早く試している証で、この好奇心の高さは世界から見ても日本の大きな強み」と話し、日本法人として使い方やフィードバックを集めて、このエージェント機能を強化していきたいと述べました。

最近出した機能とパートナー

続いて、最近出した機能を簡単に紹介しました。

  • Codex のクラウド版:サンフランシスコの DevDay で発表し、評価が非常に高いです。これまでは PC を開けたまま作業させる必要があったが、クラウドで動くので PC を閉じても作業が続きます。その分、人はもっと付加価値の高いことに時間を使えます。
  • Agents API:自社のアプリケーションや業務システムにエージェント機能を組み込めます。
  • Decisions API:情報の分類や判断の処理を速くします。「まだ使っていない方はぜひ一度試してほしい」。
  • AWS との連携:AWS を使う企業向けに Bedrock Managed Agents ができ、Agents API の中核機能を Bedrock 上で使えるようになりました。Codex も Bedrock 上で使え、デスクトップアプリからも Bedrock 経由でモデルを使えます。

最後に協力企業を紹介しました。この日登壇する GenerativeX と Sakana AI は OpenAI と緊密にやり取りしている顧客で、Accenture、AWS、Recursive は重要なパートナーとして会場の外でデモを出しています。「今後やりたいことや疑問を、ぜひぶつけてほしい」と呼びかけ、基調講演の登壇者を呼び込みました。

東京への歓迎と、要望への対応

Raji さんはまず「ここ東京から始めるのは偶然ではない。東京は世界で最も活気のあるビルダーコミュニティの一つだから」と会場を歓迎しました。前回から多くのものを出してきたが、どれも開発者がいなければ意味がありませんでした。開発者は、OpenAI が考えもしなかった使い道を見つけてくれます。

開発者からは「ほとんど Twitter で」数千件の機能要望が届き、すべて読んで順に対応してきたとのことです。例として、Codex を Linux でも使いたい、同じプロジェクトで複数のフォルダをまたいで作業したい、スマホで Codex を使いたい、という要望を挙げ、いずれも実現したと話しました。「日本語で、あるいは皆さんが使っているツールで、もっとうまく動くべきところがあれば教えてほしい。日本での開発体験を最高水準にしたい」とも述べました。

Dots:常時稼働のエージェントに仕事を任せる

最初の大きなテーマは、数週間前の DevDay で発表した Dots です。発想はシンプルで、必要なときにそこにいて、自分が働いていない時間も含めて一日中、毎日働き、物事を片付けてくれる AI です。「映画で見ていたような AI」に近づくものだそうです。

これまでのバーチャルアシスタントでも予約やチケットの購入はできたが、「この技術が本当にできることに比べれば些細な例」です。Raji さんは「Dots で、AI に対してもっと野心的になってほしい」と言い、Dots を次のように定義しました。

Dots は、驚くほど有能で常時稼働する AI エージェントで、考えつくことなら本当に何でも扱えるように作られている。

remarkably capable, always on AI agents, built to handle really anything you can think of.

Raji さん自身の例では、先週、メールの中にあった税務申告の書類の不整合を Dots が指摘してきました。見ておいてと頼んだわけではなく、Dots が自分から知らせてきたもので、その書類を担当の公認会計士に転送したところ、会計士は Raji さんが気づいたことに驚いていたとのことです。

小さな用事も任せられます。東京から大阪への週末旅行の計画や、家族との夕食の時間探しなどです。一方で Dots は OpenAI で最も強力なモデル Astra で動いているので、主体性の高いチーフ・オブ・スタッフやシニアエンジニアに頼むのと同じように、責任ごと渡せます。挙げられた例は次のとおりです。

  • Slack チャンネルに入ってくるバグをすべて監視し、直し方まで見つける
  • 来年の予算づくりを始め、全チームを予定どおりに進める
  • アプリケーションの性能改善点を見つけて直し、どれだけ速くなったかを示して、レビュー用の PR にする
  • 「サービス終了の前に、うちのアプリをレガシー API から移行させて」。API がアプリや依存関係のあちこちで使われていても、Dots は依存関係をすべて追って変更箇所を洗い出し、コードを書き、テストを実行し、修正を検証して、チームがレビューする PR を出します

Dots はユーザーのアクセス権に従って動き、自分専用のコンピューターを持ち、ブラウザも使えます。今日は1つの Dot から始めるが、将来は Dots のチームを持てるようになるそうです。Dot に電話して話すこともできます。ChatGPT で使える4,000以上のアプリを横断して動き、ユーザーがすでに接続しているプラグインにもすべてアクセスできます。そのあいだもコントロールはユーザーの手にあり、使わせるアプリや computer use の範囲、Dots に許す操作はユーザーが決めます。Astra は「最もアラインメントされたモデル」で、保護機能と基準が組み込まれているとも説明しました。

ChatGPT Space:人とエージェントが一緒に働く場

Dots は個人のコンテキストやワークフローに深く結びついています。一方で、チームやチームメイトの Dots と協働する場も要ります。世の中の生産性ソフトのほとんどは、人とそのエージェントが一緒に働くようには作られていません。それを変えるために発表したのが ChatGPT Space で、自分、チームメイト、自分の Dots、チームメイトの Dots が全員で一緒に働ける場所とのことです。

  • Space はページから始まります。ページでは計画を書く、リサーチをする、画像を作る、データを生成する、何かを作る、といったことができます。
  • ページ上で Dot を呼んで依存関係の追跡を頼んだり、コメントで Dot をタグ付けして作業させたりできます。ページとファイルは Space の中にまとめて置かれ、ドライブのように使えます。
  • ページに指示を与えると「生きた」ページになります。例は「API の Slack チャンネルを見て、私のブリーフィングを最新に保って」。
  • 先週、Space の中でプレゼンテーションを作る機能も入れました。エージェントが読み取り・修正しやすいスライドになり、チームメイトや Dots と ChatGPT の中で共同作業できます。

Dots と Space は ChatGPT Pro、Business Premium、Enterprise の全ユーザーに提供中で、Dots はプランに含まれ、Dots との会話は利用枠を消費しません。エンタープライズ向けには Specialist Dots をプレビュー中で、社内にセットアップしてチーム全体と並んで働く「バーチャルなチームメイト」として、会計、マーケティング、法務などの負荷の高い仕事を担います。ゴールとコンテキストを与えて成果物をレビューし、フィードバックを返すと時間とともに良くなります。OpenAI 社内ではさまざまな問題を投げてきて、多くの職種で驚くほど効果的だったそうです。

Raji さんは、Dots のようなものがモデルとともに人に新しい「超能力」を与えると信じている、と話して前半を締めました。事業を広げる人にも、アクセシビリティを高めたい人にも、自分に何ができるかを発見してほしい、という趣旨でした。

モデル

数週間前に公開した Astra に対し、ユーザーからの要望は「もっと安く、もっと速く」の2つでした。それに応えて DevDay San Francisco で GPT-6.1 Sol を出しました。コストと能力のバランスが良い開発者向けのモデルで、Astra 級の能力を5分の1の価格で提供し、キャッシュ入力は標準の入力から95%割引になります。エージェントがコンテキストを再利用して解法を繰り返し試し、長いタスクをこなすコストがずっと下がるので、「日々の主力(daily workhorse)になると思う」と話しました。

「ときには、本当にときには、最高の知能をとんでもない速さで必要とすることがある」として紹介したのが Ultra Fast です。API、ChatGPT、Codex で使え、既存の Fast(2倍の速度を2倍のコストで提供)をさらに引き上げて8倍の速度、毎秒300トークンを出します。デモでは同じプロンプト「Build a rocket with devday colors」を Ultra Fast と標準版に並べて与え、Ultra Fast のロケットが離陸したときには標準版はまだ作り終わっていませんでした。「今の市場にこんなものはない」。Ultra Fast は Astra で使え、6.1 Sol でも近日使えるようになります。

料金プランでは、利用上限が最も高く ChatGPT で Ultra Fast を使える Pro 500 を新設し、すべてのフロンティアモデルを使える Pro 200 の受付を再開しました。価格帯ごとに知能と能力の最良の組み合わせを出すのが目標とのことです。

Raji さんが「お気に入りの一つ」と言ったのが Decisions API で、パブリックベータになりました。Luna モデルで動き、テキストや画像を評価してアプリの中で使える「判断」にします。Responses API の10倍速く、リクエストのルーティング、画像の分類、アプリで次に取るべき一手の判断のように、レイテンシが重要な用途に向いています。Decisions API がコンピューターを操作する動画を見せ、「この動画は早送りしていない」と念を押していました。モデルの話は「知能、速度、価格、音声、画像のすべてのカテゴリにフロンティアモデルがある。皆さんが作るためのワンストップショップになりたい」とまとめました。

ツール

2つ目の柱は、OpenAI 社内と同じ基盤を開発者に渡すことです。出発点は Codex と Dots を含むすべてのエージェントを動かしている Codex harness で、少ないトークンと速い速度で正確な結果が出るよう効率化してきました。ハーネスはオープンソースで、フォークして中身を見たり、その上に自分のものを作ったりできます。ChatGPT のような数十億人規模の製品を動かすために作ったもので、同じスケールを自分の製品に使える、と説明しました。

  • Codex in Cloud:「皆さんがずっと待っていたもの」。スマホで始めたタスクを、あとでブラウザやデスクトップアプリで、スレッドを失わずに再開できます。実行中に PC を閉じても Codex はクラウドで動き続け、並列実行もできます。
  • Agents API:ハーネス、ホスティング、メモリ管理、マルチエージェントの制御などの中核部品を含みます。Codex や Dots を動かしているのと同じ技術で、パブリックベータになりました。computer use も加わり、エージェントがコンピューターを使ってブラウザを起動し、ページを操作し、テストを実行できます。
  • AWS:AWS を使っているなら OpenAI の全製品を AWS で使えます。Bedrock Managed Agents powered by OpenAI で、AWS のインフラ・アプリ・データのすぐ隣で OpenAI のエージェントを作れ、すべてのフロンティアモデル、Codex、ChatGPT も使えます。
  • Responses API の速度と信頼性:過去1年で利用が100倍に伸びても99.9%(スリーナイン)の信頼性を保ち、最初のトークンが返るまでの時間を45%短縮、ツール呼び出しを30%速くしました。「今の市場で最も高性能で、最も信頼できる API」。

届け方

Codex ハーネスと、Responses API を通じたループ

話は Codex ハーネスから始まりました。ハーネスは、モデルが見る指示とツール、モデルの行動の実行、ステップからステップへ持ち越すコンテキストを管理します。Codex では与えるツールに強いこだわりがあり、たとえばモデルに「コンピューター」を与えました。「人間がコンピューターの使い方を理解できるなら、モデルにも理解できるようにしたかった」という考えです。

動き方は Responses API を通じたループになっています。会話とツールの定義をモデルに送り、モデルがツールの呼び出しを求め、ハーネスがそれを実行して結果を会話に加えます。モデルは何が起きたかを見て、もう1ステップ要るか、ターンを終えてよいかを決めます。これが基本のループです。

長い作業を支えるコンパクション

エージェントが長く複雑なタスクを担うようになると、作業の経過を追い続けることが課題になります。Chatterjee さんはコンテキストを「モデルが次に何をするか決めるときに目の前にある情報」と定義しました。ファイル、実行したコマンド、その結果などで、履歴は増え続けるのにコンテキストウィンドウには上限があります。長いタスクでは、それまでに学んだ大事なことを残しつつ、新しい作業の余地を作らなければなりません。

その対策として製品にコンパクションを組み込みました。コンテキストが埋まってくると、ハーネスが Responses API 経由でコンパクションを要求し、モデルが履歴を小さな「作業状態」にまとめます。重要な発見、決定、未完了の作業を覚えたまま、新しい情報のための余白を持って作業を続けられます。

Codex の特徴は、コンパクションがハーネスとモデルの学習の両方に組み込まれていることだそうです。有用な状態を残すように、また圧縮されたコンテキストから再開するとはどういうことかを理解するようにモデルを学習させました。モデルは「同じタスクを続けている」と分かっていて、必要ならツールで詳細を調べ直せます。これで、コンテキストをいくつものウィンドウにまたいで持ち越し、学んだことの上に積み上げていけるようになりました。


Chatterjee さんの説明をもとに、1ターンのループ、/goal による継続、コンパクションの関係を図にしました。ゴールはターンをまたいで残り、コンパクションはコンテキストウィンドウをまたいで作業を続けさせます。

「続けて」と打ち続ける人間から、ループエンジニアリングへ

長く働けるようになると、次の課題は「仕事が終わるまでやり続けさせること」でした。OpenClaw の作者 Peter Steinberger さんは、これに対処するため同じメッセージを何度も何度も打ち込んでいたそうです(打っていた文面はスライドに出ていた)。「こうしていた私たちは、モデルの外側のループを担い、止まったら動かしていた」。同時に、タスクを最後までやり遂げさせるには何が要るのかを知りたかったそうです。これがループエンジニアリングにつながりました。

以前のモデルは「完了とは何か」の感覚を常に持てていたわけではなく、有用な進捗を出しても1ターンで止まり、タスクを未完了のまま残すことがありました。多くの場合、簡単な声かけでまた動き出しました。この発想を広めたのが Geoffrey Huntley さんの「Ralph ループ」で、プロンプトファイルに対してエージェントを何度も実行する bash のループです。各回は新しいコンテキストで始まり、前回が残したファイルと計画を拾い上げます。この小さなループで長時間作業できたが、その周りに何を置くかを決める必要がありました。

  • 次の実行は何を知っておくべきか
  • 進捗しているかどうかを、どう判断するか
  • いつ止めるべきか

これがループエンジニアリングの考え方だと話していました。

Codex の /goal と、GPT-6 の粘り強さ

このパターンを Codex に取り入れたのが /goal です。/goal は Codex の個々のターンを越えて残る目標で、ハーネスはそれを進行中の会話とは別に保存し、状態を追跡し、エージェントが作業するあいだずっと参照できるようにします。ターンが終わるとハーネスがゴールがまだ有効かを確認し、有効なら元の目標と「続けて」というリマインダーを付けて次のターンを始めます。モデルには、完了と判定する前に目標に照らして自分の作業を確かめるよう指示していて、足りない情報を尋ねることも、本当の障害を報告して止まることもできます。

これは明確な学習の目標にもなりました。残っている作業をモデル自身が認識し、自力でゴールに向かって進み続けられるようにしたかったからです。GPT-6 ではそれを学習させ、モデルは非常に粘り強くなりました。有用なステップを取り続け、結果を確かめ、次の「続けて」を待たずにつまずきを乗り越えていきます。

エージェントを増やすのは、明確な理由があるときだけ

1つのエージェントが作業を続けられるようになったので、次の問いは複数のエージェントにどう分担させるかです。知能が上がったことで、大きな作業の分割、エージェントの並列実行、結果のとりまとめといった調整の多くをモデルが担えるようになりました。

それでも勧めるのは、まず1つのエージェントに明確なタスクと確認の手段を与えることだそうです。GPT-6 系のモデルは、外側のループが「続けて」と言わなくても作業を続け、コンテキストを圧縮し、失敗を押し切って進みます。「多くのタスクではそれで十分なはず。作業の側に明確な理由があるときだけ、エージェントを足すことを勧めたい」。

チームが意味を持つ例として挙げたのは、大規模なリファクタリングと、別々の部分を並行して進められるゲーム開発です。GPT-6 は最初から協働と調整をするよう学習されていて、難しい問題を独立した部品に分けて取り組めます。Ultra を使うと、Codex は自分自身のコピーを作り、コピーと協力して難しい問題に取り組めます。

課題は、作業をどう分けるか、各エージェントが必要とする情報をどう見極めるか、有用な発見をどう他のチームに届けるか、でした。取ったアプローチは、共通のゴールを中心にエージェントをチームに組むことです。

  • 幅と深さの両方:チームごとに問題の異なるバージョンを渡して違うアプローチを試させつつ、各チームが手がかりを追ってゴールまで掘り下げられるようにしました。
  • チームをまたぐやり取り:エージェントはグループ内で通信できるだけでなく、ほかのグループとアイデアや発見を共有し、ほかのグループのエージェントに質問もできました。
  • 重複を避ける:この規模では重複が非常に高くつくので、自分たちの作業が本当に独自のものかを各チームが確かめられるようにしました。
  • 役割の分化:掘り下げが進むにつれ、仮説を探るチーム、その前提に異議を唱えるチーム、実験をするチーム、と必要な作業が変わっていきました。
  • 組み替え:発見が新しい問いを生むと、新しいチームを作るか、既存のチームを有望な方向へ向け直しました。「ゴールは変わらないが、作業の分け方は学ぶにつれて変わった」。

エージェントが強制項のないオイラー方程式(unforced Euler)についての結果を見つけた時点で、全チームをその1つの問題に振り向け、しばらくして解が見つかったそうです。この成果は GPT-6 より強力なモデルを使った、より広い研究の一部で、同じ社内モデルで数学の長年の未解決問題を100個解いたことを最近ブログで公開した、とのことでした。「エージェントが数学と科学のあらゆる分野で新しい発見をしうることを、垣間見せてくれる」。

これまでの経緯と「推論の階層」

OpenAI はこの問題に以前も取り組んでいます。Assistants API では、File Search や Code Interpreter といったツールを備えたホスト型のワークフローを探りました。2023年当時の GPT-4 Turbo は、これらのツールで数秒程度のワークフローを実行できました。今は GPT-6 Astra が、数十種類のツールを数時間から数日にわたって使いこなせます。

推論モデルにはもっと柔軟な基盤が必要で、2025年に Responses API を出しました。高度なエージェント型のワークフローでは、テキスト、画像、推論など、さまざまな種類のコンテンツをモデルとやり取りする必要があったからです。振り返るとこれは強力な基盤になり、Codex や ChatGPT Work といった新しいエージェント型製品を支えました。

登壇者は OpenAI の API を、層を重ねたケーキのような構造、マズローの欲求階層になぞらえた「推論の階層」として説明しました。


登壇者が示した「推論の階層」と、話の中で出てきた年表。Agents API は「皆さんの思い描くことを形にして、プロダクトの可能性を最大限に引き出すためのもの」と説明されました。

なぜ API の裏にハーネスを作り直したのか

当初 OpenAI は、開発者はインフラの多くを自分で管理したいはずだと考えていました。Codex のような優れたハーネスが出る前は、多くの開発者が自作していたからです。2025年には、開発者がすべてを自分で制御しながらエージェントを作れるよう、ローカルで動くハーネスとして Agents SDK を公開しました。

ところが多くのチームと話すと、同じ会話が何度も繰り返されました。作りたい製品ははっきりしていて、業務の流れもエージェントが役立つ場所も分かっています。そのうえで「どう作ればいいか」を聞いてきます。どのツールを使うべきか、エージェントはサンドボックスの中で動かすべきか外か、シークレットはどう管理するか。OpenAI 側は「どんなインフラが欲しいか」と聞き返していたが、相手が求めていたのは、実際にうまくいっている方法を踏まえた具体的な推奨でした。特にはっきりしていた要望は「エージェントの実行と運用を OpenAI に任せるにはどうすればいいか」だったそうです。ツールやデータ、実行環境まで自分で管理したい企業もあるが、だからといってハーネス全体を自分でホストして運用したいとは限りません。

その答えとして、Agents API は「Codex ハーネスを基盤としたマネージドサービス」になりました。開発者はタスク、指示、ツールを定義し、エージェントが操作する環境を選びます。あとは OpenAI がハーネスと関連サービスを動かします。エージェント開発で得た知見やモデルの精度向上に合わせて OpenAI がハーネスを改善し続けるので、開発者はその改善を一つずつ自分で再現しなくてかまいません。

課題1:ハーネスと実行環境を切り離す

Codex のハーネスは、ローカルのコンピューターで動き、ローカルのファイルシステムを読み、ファイルを変更して結果を確かめる、という前提から始まりました。今年の前半、この前提を見直す必要があるという議論になり、コマンドが実際に実行される環境からハーネスを切り離すことにしました。開発者は自分がすでに運用しているサンドボックスで動かしたいかもしれないし、OpenAI にホストしてほしいかもしれません。どちらにしても、クラウドで動くハーネスが任意のサンドボックス環境と通信できる仕組みが要ります。

すると別の問題がすぐ出てきます。たとえばモデルが「ディレクトリ内のファイル一覧を表示して」と求めたとき、そのコマンドを正しいコンピューターに送って結果を素早く返すにはどうするか。セッションにつながっている環境を見つけ、コマンドを送り、結果を受け取ってモデルの処理を続けさせなければなりません。複数の環境がつながるので、コマンドの結果はセッションごとに分けて管理する必要もあります。以前はローカルで済んだコマンドも、毎回この経路を通るようになります。ここ数週間 Agents API を使っている人は、自前のサンドボックスか OpenAI のサンドボックスかを選べたはずで、どちらでもエージェントはターミナルを使って膨大な処理をこなせる、とのことでした。

さらに先日、要望の多かった **API 経由のコンピューター利用(computer use)**を追加しました。OpenAI がホストする環境で Astra が GUI を操作できるようになり、登壇者は「画期的なもの」と表現していました。

課題2:エージェントの作業をユーザーにどう見せるか

エージェントがコンピューターやサンドボックスで動けるようになると、それで製品を作る人はすぐ「エージェントが動いているあいだ、ユーザーに何を見せるべきか」で悩みます。エージェントがたどる道筋は事前に予測できません。プロンプトやツールの結果などさまざまな入力に左右され、実行のたびに別のファイルを開いたり、別のやり方を試したり、作業の一部を別のエージェントに渡したりします。それでもユーザーは、特に長いタスクでは、エージェントが何に取り組んでいるのか、止まっていて助けが要るのかを知りたいはずです。

当初はツール呼び出しとモデルの応答をそのまま渡せば良い UX を作れると考えていたが、実際にはそれ以上が求められました。初期版の Agents API で開発していた社内のあるチームでは、ユーザーとエージェントのやり取りが何往復も続くことが多く、ツール呼び出しや応答を「ターン」ごとに見せたいと考えていました。しかし当初の設計では、それぞれがどのターンに属するかを簡単に知る方法がありませんでした。チーム側で対応関係を記録することもできたが、「それでは、管理を任せるために使い始めたハーネスの一部を自分たちで作り直すことになる」。そこで Agents API のチームが設計を見直し、ターンの情報を API から取れるようにしました。チームは会話の流れを組み立て直すことなく、エージェントの作業をどう表示するかに集中できるようになりました。

「振り返れば当たり前に思えるかもしれないが、ハーネスをサービスとして出すには、こうした判断が何十も要る」。その一つ一つが、どこまで OpenAI に任せられ、どこから開発者が考えるべきか、どんな落とし穴があるかを左右するそうです。

課題3:何時間も続く作業を止めない

長く動くほど履歴が増え、タスクの途中でもモデルのコンテキストウィンドウを超えることがあります。コンパクションはそのために作られたもので、ハーネスが必要な情報を次のコンテキストウィンドウへ引き継ぎ、エージェントが作業を続けられるようにします。これがなければ、長く動くエージェントを作る開発者がそれぞれ履歴の管理を考えなければなりません。

コンテキストのほかにも制約があります。GPT-6 は何日も作業を続けられるが、そのあいだにもサービスのソフトウェアは更新され、サーバーは故障したり入れ替わったりします。普通のクラウドソフトウェアは、リクエストを受けてデータベースにアクセスし、レスポンスを返すまでが1秒以内に終わる前提で作られています。エージェントは何時間も働き続け、途中で追加の指示を受けて進め方を変えることもあります。そのためには複数のサーバーの中からそのユーザーのセッションを特定してリクエストを届けなければならず、Codex が別のコンピューターで動くツールの結果を待っていることもあります。これらはすべてモデルの推論、ストレージ、ツールの呼び出し先など他のシステムにも依存していて、全体で99.9%の信頼性を出すには、それぞれにも同等以上の信頼性が求められます。

Codex がクラッシュしても、サービスの更新でサーバーを入れ替えても、中断したところから正確に再開できなければなりません。エージェントはすでに1時間かけて問題を調べているかもしれないし、二度実行してはいけない操作を済ませているかもしれないからです。そのため、作業の状態を極めて正確に記録し、適切なタイミングでサーバーを入れ替え、スレッドをすぐに再開します。例として挙げたのが、ファイルを編集するコマンドを環境に送った直後に接続が切れた場合です。結果が返ってこなかっただけでは、編集されたかどうか分かりません。再実行すると予期しない結果になりうるので、安全に続けるには、実行環境で何が起きたかに加えて、ハーネスが記録した内容も考慮する必要があります。

03 結果を整理する:重複排除、優先順位付け、担当候補

お客様の現場でも、見つかった問題を整理し、誰が何から直すかを決めるのに非常に時間がかかるそうです。同じ問題なのにチケットが何枚もできる、担当が分からず止まります。そうなると「発見件数が増えても修正が進まない」。これに対して、重複排除、優先順位付け、担当候補の提案で、開発者が手を付けやすい状態を作ります。

  • 重複排除:同じコード上の問題や同じアクセス境界の問題を指しているかをエージェントが確かめ、同じ問題として扱う結果をまとめます。出力には代表となる検出結果と重複のグループが並び、この例では2つの検出結果が1つのグループになりました。開発者には同じ原因をまとめて渡し、調査と修正の重複を減らします。元の検出結果との対応も記録として残し、まとめた根拠を確かめられるようにします。
  • 優先順位付け:サンプルのドキュメントサービス用に作った重大度の基準で分類します。たとえば稼働中のサービスで組織をまたいで機密情報が広く漏れる場合は、この基準では「高」です。影響の大きさを示す重大度と、どこまで裏付けられたかを示す確信度は分けて扱います。コマンドに基準ファイルと検出結果を渡し、分類とその理由を YAML で出させます。YAML ならレビューや、チケットシステムと連携したチケット作成にもつなげられます。今回の結果は「中」です。認証済みの利用者が他の所有者の文書を読めるという不備は確認できたが、本番でどこまで影響するかは確認できていないからです。実サービスではデータの機密性や公開範囲も踏まえて評価し直します。「確認できた問題と、まだ分からない影響を分けて扱うことが重要」。
  • 担当候補の提案:大きなコードベースでは、問題が分かっていても担当チームが分からず止まることがあります。検出結果とソースコードを渡し、Git の履歴などを根拠に担当候補を出します。この例では app.py と documents.py の履歴から候補が出ていました(表示された氏名と連絡先は例示用のもの)。今の担当体制が Git だけで分かるとは限らないので、候補と根拠を見て実際に相談するチームを確かめます。

04 パッチを作り、修正を検証する

検証の流れは、スキャン結果を受け取り、標準の検証をして、そのシステム固有の検証をしてからパッチを作る、という順番です。固有の検証を呼び出すのが「カスタムトリガー」で、スクリプトを実行する、開発環境を起動する、Kubernetes 上でテストする、といったシステムごとの事情に合わせた手順を差し込めます。そのために、環境の準備やテストの実行方法を検証用のプロンプトとして渡しておくことが大事だと話していました。エージェントは使える範囲でその環境を使い、見つかった問題が実際に攻撃として成り立つかを確かめます。修正後は、元の不正アクセスが防げることに加えて、所有者の正常な読み取りを壊していないことも確かめます。

Namazu:オープンモデルを日本に合わせるポストトレーニング

最初に取り組んだことの一つが自社のローカル基盤モデルです。「OpenAI は素晴らしいし、インフラも最先端のモデルもある。でも結局、日本の顧客はローカルで動くモデル、データ主権のある国境の内側で動くモデルを求めている」。そこで、オープンなモデルを日本と日本の文化に合わせ、事実の正確さと中立性を持たせるポストトレーニング技術「Namazu」を開発しました。

オープンなモデルは作り手寄りのバイアスがあることが多い、と Ha さんは言います。「DeepSeek はおそらく中国寄り、Llama は間違いなく Facebook 寄り。実は、当社も使っている OpenAI の GPT-OSS がいちばんバイアスが少ない」。こうしたオープンウェイトのモデルすべてについて Namazu 版を作っていて、最近は Kimi の1兆パラメータのモデルの Namazu 版も作りました。これが社内、プロダクト、企業向けで実際に使っている主力モデルとのことです。ポストトレーニングの過程でナマズが日本の文化を吸収していくのは「外国人の自分が日本に来て、この国について学ぶようなもの」。日本語でのバイブコーディングや、プロンプトがすべて日本語のビジネスレポート作成もこなし、Ha さんの子どもは家で英語を話したがらないので、日本語で算数を練習する公文のようなゲームをバイブコーディングで作ったそうです。

Namazu をもとにしたプロダクトが2つあります。Sakana Chat は純粋なチャットというより検索システムに近く、Web を検索し、日本語のモードごとに調整してあります。標準語のモードがあり、日本語での丁寧な謝り方も学べます(「これはとても難しい」)。大阪弁にも対応しなければならない、とも話していました。Sakana Translate も Namazu がベースで、「ようやく Google 翻訳をやめて Sakana Translate を使える」。どのプロダクトも Ha さん自身が毎日社内で使っているとのことです。

Fugu:モデルを呼び分けるオーケストレーター

個別のモデルである Namazu に対し、Sakana Fugu はオーケストレーターです。モデルルーター自体はよくあるもので、目的はふつうコスト削減にあります。「メールの要約に余計なお金を払いたくはない。安いモデルを使いたいでしょう」。しかし Sakana AI にとっての本当の動機は、日本の企業と政府にレジリエンスを持たせることだそうです。「日本はフロンティアモデルを使えるべきだが、それらのモデルは止められる可能性もある。OpenAI も Anthropic も素晴らしい会社だが、トランプ大統領が大統領令に署名して、お気に入りのモデルを止めるかもしれない」。だから適切なモデルに振り分ける仕組みを作りたかったとのことです。


Ha さんの説明をもとにした Fugu の仕組み。「1人のスーパーヒーローより、アベンジャーズのチーム」とたとえていました。

Fugu 自体も約100億パラメータの LLM で、強化学習で訓練しました。推論の各ステップで、OpenAI の別々のモデル、Anthropic のモデル、Google のモデル、さらには自分自身の別バージョンまで再帰的に呼び出し、タスクの性能を最大にします。LLM の利用ではコストが大きな関心事で、誰もが「トークンエコノミー」を語り、「フロンティア AI の話は減って、パレートフロンティアの上でオーケストレーションしてコストパフォーマンスを最適化する話が増えている」。技術としてのビジョンは、領域やベンチマークやタスクを与えると、そのタスクに強くなるようにモデルを振り分ける最適な方法を見つけ、コストを最小にするシステムだそうです。

公開しているのは2種類で、Fugu Max は出力100万トークンあたり6ドルと安く設定し、同じクラスの多くのモデルを上回ることを狙ってコストパフォーマンスを最適化しています。Fugu Ultra はフロンティアモデルどうしをオーケストレーションし、純粋な性能を最適化します。OpenAI の Astra や、Anthropic の Opus、Fable といったモデルのあいだでオーケストレーションすれば、ずっと良い性能が出ると話していました。

脆弱性は急増し、悪用までの時間は1時間に

今年に入って、AI エージェントがオープンソースのコードを読みながら脆弱性を自動で探すことが盛んになりました。OpenAI は最近、数学の分野でたくさんの論文を出しているが、セキュリティの分野でも AI エージェントによる脆弱性の発見がとても増えているとのことです。CVSS 9.0以上のクリティカルな脆弱性は、2023年が2,355件だったのに対し、2026年は1〜9月の累計で8,222件と、飛躍的に増えています。

題材は Next.js で、ここ2か月で3回ほどクリティカルな脆弱性が出ています。小坂さんが「Next.js を使っている方」「アップデートしたという方」と会場に聞くと、どちらにも手が挙がりました。React Server Components や画像処理の部分の脆弱性で、ログインなしで RCE(リモートコード実行)ができてしまうものも出ていました。「今日帰ったらすぐに会社の Slack に連絡して、アップデートしましょうと言ってほしい。できれば今日中に」。

修正版が出ても放置する人は多いです。小坂さんがこの登壇のために日曜日に npm の1週間分のダウンロードを数えたところ、38%がまだ RCE の脆弱性があるバージョンでした。「開発者はけっこうレイジーなので、世の中には脆弱なサイトがたくさん転がっている」。この状態では、最近出てきたオープンウェイトのモデルなどで攻撃され、情報漏えいにつながります。

さらに、脆弱性が公開されてから攻撃コードが作られるまでの時間(タイム・トゥ・エクスプロイト)は、2018年ごろの論文では60日ほどだったのが、今では数時間、1時間の水準まで縮みました。CVE が出る前に悪用されている例もあります。「ほぼ1時間以内に更新しないと危ない」。しかも過去のパッチの公開は日本時間の深夜1時、2時、3時に集中しています。「彼らは日本時間に合わせてリリースしてくれるわけではない」。そこで、コーディングエージェントを使い、脆弱性が出たら自動で検知して修正版のパッチを当て、リリースしようと考えました。

実際の夜:2時47分の公開から再開まで

今回は Next.js の脆弱性がこの日に出ることを事前に把握していたので、体制を組んで交代で夜中に待機しました。公開は2時47分。社内では Slack のボットが1分に1回、脆弱性のデータベースと自社アプリで動いているライブラリのバージョンを照合していて、クリティカルなものが出るとアラームが上がります。当時、関連するサイトが20件ほど、Next.js の本番サーバーで動いていました。1つずつ見ていては間に合わないので、WAF でリクエストを一括で遮断すると判断し、そのうえで修正をリリースし、E2E テストを自動で走らせて問題がないことを確かめてから再開しました。ここで活躍したのが Codex だそうです。


小坂さんの説明をもとにした、当日の夜の流れ。今回は遮断のルールだけ人が判断し、遮断の操作自体もコーディングエージェントで行いました。

役割分担は、検知はほぼ自動、ネットワークの遮断は人が判断して一括で行い(操作自体はコーディングエージェント)、修正の PR や復旧は AI に任せました。今回は公開日が分かっていたのでよかったが、CVSS 9 クラスの脆弱性が次々に出る中で、必ず予告されるとは限りません。次は、可用性よりも止血を優先し、WAF やファイアウォールの段階で一括で切るところまで自動化したいとのことです。


18:25 「Codex は GX のクラウドの Sandbox 基盤で動いている」。上流の advisory(GitHub・OSV)→ 照合・判定・通知(1分ごとに全 repo の依存と照らし合わせる)→ Cloudflare WAF(公開名を遮断)/ Sandbox 基盤(修正ごとに起動して捨てる)の中で Codex・社内の CLI(結果を JSON で返す)・Skill(修正の手順書)→ GitHub(修正の PR・CI)→ 承認つきリリース(本番の環境へ)。「人がやるのは承認だけ」。

仕組みとしては、オープンソースの脆弱性情報(アドバイザリー)のデータベースに危ないバージョンのリストがあり、GitHub と連携した社内 SaaS で自社のバージョンを管理して1分に1回照合します。問題があればサンドボックスの中で自動的にコンテナが立ち上がり、その中で Codex が動きます。Codex は社内インフラにつながる CLI を持っていて、Cloudflare の WAF を操作したり、PR を出して CI をかけ、通ったらマージしたりできます。

デモでは、社内の SaaS は見せられないので同じ形で作ったものを動かしました。右側は Cloudflare Pages にデプロイしたデモ用の Next.js サーバー、左側は Codex。「脆弱性の診断をしてください」と頼むとスキルが立ち上がり、アドバイザリーのデータベースと照合し、問題があればすぐに WAF のルールを書き換えてブロックします。Cloudflare Pages はビルドとデプロイが速いので、関連するパッケージを更新してビルドし、E2E テストをして、すべて動作を確認できたら WAF のルールを元に戻します。先週の木曜日に小坂さん自身が対応したのと、考え方はまったく同じだそうです。「ここまでやるのか、という話はあるが、世の中の脆弱性がどんどん危険になっているので、こういう体制を組んでいる」。

伝えたかったこと:エージェントが動く環境を設計する

GenerativeX では、アーカイブしたものも含めて約300(296)のリポジトリを管理しています。一つずつ見るのは難しいので、この仕組みで脆弱性を自動で検知し、CI/CD やリリースとつなげて、なるべく安全にサービスを運用しています。

Codex をそのまま使っても開発は速くなります。ただ小坂さんが可能性を感じているのは、Codex が「汎用エージェント」として成り立つことだと話していました。今回なら Cloudflare、GitHub、脆弱性のデータベースが Codex の扱う対象で、それらをすぐに読み出したり、更新したり、遮断したりするものをスキルとして、実体は CLI として作りました。そうすると、開発だけでなく業務全体を自動化する余地が出てきます。「エンジニアリングとしては、エージェントが動く環境自体をちゃんと設計してあげましょう。ここが非常に重要なポイントです」。

もう一つは、ビジネス上の判断のスキル化です。今回は「CVSS 9.0以上ならネットワークを遮断する」というルールだったが、このルールは会社ごとに違います。こうした判断をあらかじめスキルにしておけば、シニアのエンジニアがやってもジュニアがやっても同じ結果が得られます。こうしたプロセスはいきなり進めてもうまくいかないので、継続的に自動化してプロセスをつなげ、エージェントですべてが終わる形へと改善を進めてほしい、と締めくくりました。

Q. (会場からの質問)AI エージェントやプロジェクトの価値を、実際にどう評価すればいい?

Chatterjee:測れるものはいろいろあります。よく測られるのはコストですが、トークン単価を基準にしないことを勧めます。トークン単価は研究所ごと、モデルのシリーズごとに変わりえます。基準にすべきは、満足のいく形でタスクを終えるまでの総コストです。リサーチを終えるのにエージェントが5ターンかかるなら、その全体を測ります。品質の見方もいろいろあり、見つけてほしいツールを見つけたか、人にエスカレーションしてほしい時点でエスカレーションしたか、Sean が話したようなガードレールを守ったか。時間でもコストでも、部分ではなく答え全体を end to end で考えることを強く勧めます。

Ching:原則はそのとおりで、付け加えるなら、作るものによっては評価のためのツールを作るとよいです。別のプロジェクトでも繰り返し使える eval のツールがあれば、継続的に評価できます。OpenAI は6〜7か月ほど前に、いろいろな Web アプリを作るのを助ける「Build Web Apps」というプラグインを出していて、今は Sites のような新しい製品でも同じことができます。そのエージェントの出力を評価するために社内ツールを作りました。たくさんのプロンプトを用意し、異なるやり方で作った Web アプリを横に並べて生成するので、入力を変えながらすべての出力を一貫した枠組みで評価でき、見た目も確かめられます。コスト、性能、能力のベンチマークの面に加えて、見た目はどうか(そのためのルーブリックを作る)、使いやすいか、読み込みは速いか、という実際の使われ方の面があります。「そこは自分のテイストを当てはめられる部分だ」。

Chatterjee:モダリティが違えば、評価の方法も考える必要があります。音声なら、アクセントがどれだけ自然か、話し終えてから正しい答えが返るまでの間がどれだけあるか、声をクローンしているならその声にどれだけ近いか。画像なら、変えたくない部分がどれだけ元のまま残っているか、自社の製品を別のシーンに置いたときに元の製品にどれだけ近いか。

Saito:FDE の立場からビジネス面を補うと、デプロイのプロジェクトではビジネス指標も重視しています。カスタマーサポートの自動化なら、解決までの時間、どれだけ自動化できたか、エラー率、そして特にリアルタイムの場合は、会話が日本語として適切だったか、どれだけ自然に感じられたか。こうした指標で、AI エージェントのシステムが業務に実際の価値をもたらしているかを測っています。

Q. OpenAI 自身は、自社の技術でどう変わった?

Chatterjee:数か月前に知ったことですが、今の OpenAI の開発は「prototype first」です。プロダクトの要件をまとめたり文書をたくさん書いたりする代わりに、作るべきだと思うもののプロトタイプをいきなり作り、社員全員がテスターになって試します。従来のエンジニアリング・プロダクト・デザインの三角形の考え方からすると大きな変化です。面白い統計として、そうしたプロジェクトのうち本番に至るのは10件中2件です。失敗率は高いですが、何が実際に機能するかについて有益な情報が得られています。営業チームではもともとエージェントを使っていましたが、エージェントへの信頼がかなり築かれ、インバウンドの問い合わせから、注文書を送って返ってくるまでの調達のやり取りまで任せられるようになりました。能力と信頼を少しずつ築きながら、社内のプロセスを考え直しています。

Ching:私のチームは OpenAI の開発者向けドキュメントをすべて管理していて、従来の開発者向け製品に限らず OpenAI の製品群全体を見渡せる新しいサイト learn.openai.com も作りました。新しい API の機能、SDK の更新、Codex の機能と、出るものが多く、出荷が速くなるほどドキュメントを保つ手間は増えます。スピードを保ちながら品質と一貫性をどう保つかが、重視している大きな指標です。そこでチーム向けのツールを作りました。以前は、ほかのチームがドキュメントを更新したいときに GitHub の PR を出してもらい、こちらがコードを読み、デプロイのプレビューを見て何が変わったかを把握していました。作ったツールでは変更点がすべてハイライトされ、どこを変えたかを目で見て確かめられます。さらに各 PR に対してスキルやプラグインが自動で走り、ベストプラクティスのチェックや、いわゆる de-slop(質の低い文章の除去)のようなことをします。自分たちの知識を組み込んだ自動チェックを走らせれば、人のレビューが必要なときもその時間はずっと短くなり、チームは本来のタスクに集中できます。このループはほぼどんなユースケースにも当てはまります。

Saito:FDE では、リクルーター向けに採用のループを作りました。ダッシュボードの更新、候補者探し、面接の日程調整などを1つのループで自動化し、今では1人のリクルーターが以前の2〜3倍の候補者を扱えます。こうしたループで大事なのは、ガバナンスの話に戻りますが、エージェントが必要なシステムやデータにアクセスし、必要な操作をできるようにして、実際に効果を出せるようにすることです。OpenAI はエージェントにアクセスを許すことにもともと寛容で、組織の中でエージェントが効果を出せるよう信頼を築くことが大事だと思います。

Q. 日本と日本の開発者は、どんな強みを持っている?

Chatterjee:強みを生かしてほしいです(play to your strength)。日本の文化はとても精密で、細部にこだわります。新しいシステムを作るときにそれがよく生きます。エージェントをこう作ったら結果がどうなりうるかを、数手先まで考えられます。作るときは、よく知っている顧客の課題、よく知っている領域から始め、作ったあとに成功がどんな姿になるかも考えることです。何が良いものかを知っていることの価値は、いくら強調してもしきれません。自分の業界やドメインの専門性は AI プロダクトにとてもよく生きます。解こうとしている課題を押さえ、細部への注意を各ステップや eval に当てはめれば、すばらしいプロダクトを作れるはずです。

Ching:付け加えることはあまりありません。私のチームはオンラインでとても活発で、サンフランシスコにいても多くの日本の開発者がオンラインでつながってくれています。もっと共有し、交流し、何が変わっているかについて良い会話をしてほしいと思います。

Q. エージェントの時代にキャリアを考える開発者へ、助言を

Chatterjee:ドメインの専門性に戻ります。AI が今どれだけ有能で、これからさらに有能になっても、その分野で質の高い仕事とは何かを見極めるテイストと判断力の重要性は、ますます高まります。ドメインと課題を深く理解しているほど、エージェントの時代に成功しやすいです。もう一つは、好奇心を持ち、恐れないことです。これらのツールは新しいことを試す力を大いに与えてくれるので、試して何が生まれるかを見てほしいです。

Ching:それが核心で、付け加えるなら、先ほどの「オンラインで積極的に」を繰り返したいと思います。世界中の開発者と仕事をしていて気づくのは、多くの人が才能も知識もあり、すばらしいことをしているのに、世界の反対側で何が起きているかは正確には知らないということです。今は、顧客の課題を解くプロトタイプや本番のアプリまで作り、安全な形でオンラインで共有してフィードバックをもらうのに絶好の時期です。そのループは非常に強力で、手早いものにも野心的なものにも効きます。若い頃の自分にもそう言いたいです。

Chatterjee:付け足させてください。Corey が言ったことは今すぐできます。you can just do things、OpenAI はこれを強く信じています。今夜の目標を立ててほしいと思います。このあとのレセプションで話したい人を3人見つけて、自分が作っているものを共有し、相手が何を作っているかを聞きます。そうすれば、この会場を出る前に小さなコミュニティができます。
