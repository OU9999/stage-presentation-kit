# DevDay 디자인 의도 복원 — 회의 결과

2026-10-28 · 디자인팀·엔지니어링팀 직접 회의, 총괄 통합

**새 Markdown 작성 경로에 기존 STAGE의 구도·주역·장간 리듬을 충분히 연결하지 못했다.** 검정 배경과 시스템 글꼴을 재사용한 것만으로 기존 디자인이 유지됐다고 평가한 판단은 부족했다. 기능 보존과 디자인 충실도를 별도 검증해야 했다.

[현재 실제 화면 비교](comparison.html) · [직접 회의록](MEETING.md) · [디자인 종합](design/synthesis.md) · [엔지니어링 종합](engineering/synthesis.md)

## 무엇이 달라졌나

기존 CSS/시각화 코드는 Markdown 구현 전과 바이트가 같다. 새 두 원고12장은 모두 `layout:blocks`로 생성되며 제목·세로 본문의 한 배치만 사용한다. 이전에 고른 큰 선언·자료 분할·두 수치·편집형 C안은 새 일반 Markdown의 기본 작성 흐름에 연결되지 않았다.

| 실제 관찰 | 디자인에 미친 영향 |
| --- | --- |
| 새 첫 장·이미지 장·표 장이 모두70px 제목과 동일한 본문 흐름 | 한 주장을 크게 말하는 장과 근거를 읽는 장의 위계/정보량 변화가 약함 |
| 이미지230px 높이 상한, 대시보드 실표시 약258×193px | 화면이 주역인 장에서도 작은 삽화처럼 보임. 파일 로드 성공과 청중의 자료 가독성은 다른 기준 |
| 기존 중앙 표지·두 수치·C안의 footer는 숨김, 새 세 장은 모두 표시 | 장 역할에 따른 정보 절제도 연결되지 않음. 출처/가상 안내는 footer와 별도로 보존해야 함 |
| 기존 visual 제목은74px이고 plot/80%가 크게 배치됨 | 모든 제목을130px로 바꾸는 것으로 해결할 수 없음. 상대 면적과 역할이 중요 |

같은1440×1000에서 기존4장·새3장을 캡처했다. 원고와 주제는 서로 달라 이 비교를 동일 내용의 A/B 실험이나 복원안의 효과 검증으로 주장하지 않는다. [실측](evidence/observations.json), [기존 코드 보존/새12장 경로](evidence/code-baseline.json)에 근거가 있다.

## 두 팀이 합의한 복원 방향

**Markdown 내용은 한 번 작성하고, 필요한 장에만 작은 시각 선택을 더한다.** 기본 조판을 개선하면서 기존 STAGE의 표현 원리를 새 원고에 연결한다.

| 장의 역할 | 복원할 표현 | 작성 부담 |
| --- | --- | --- |
| 선언·전환 | 큰 주장, 넓은 여백, 선택적 의미색과 읽히는 보조 안내 | 일반 제목/문단 + 필요한 장에 한 줄 선택 |
| 표·코드·자료 | 원자료가 읽힐 면적, 주장과 자료의 위계 | 원문 그대로. 표를 차트로 추측하지 않음 |
| 주역 미디어 | UI/사진에 넓은 면적, 명시적 주역과 보조 설명 | 기존 이미지/alt/설명을 재입력하지 않음 |
| 두 수치 | 값·단위·대상 라벨의 큰 대비 | 명시 선택 + 정확2행의3열 Markdown 표 + 출처/범위1문단 |
| C안 편집 요약 | 주역 결과물과 보조 자료, 다른 크기·매체 자체 표면 | H2별 이미지/인용/문단 묶음 + 대표 하나 표시 |

모든 장에 새 주석을 요구하지 않는다. 프로젝트 profile을 한 번 선택하고, 일반 원고의 기본 개선과 선언1장/주역 화면1장 정도의 선택 효과를 나눠 확인하는 경로다. C안과 두 수치도 매번 JSON으로 다시 작성하게 두지 않는다. 기존20양식은 정밀 호환 경로로 유지한다.

색은 의미 단위·범주·자료 정체성을 위해 쓴다. 모든 장을 한 색이나 같은 카드로 통일하거나, 자료가 없는 칸에 가짜 수치·문서·아이콘을 채우지 않는다. C안의 정확12슬롯 복제보다 관련 결과물의 주역/보조 관계를 우선한다.

## 실제로 필요한 연결 작업

현행 `heading? + blocks` 의미 트리를 유지하고 시각 선택이 그 노드/그룹을 참조하게 한다. parser가 선택을 제어 정보로 인식하고 명시 검증을 거친 뒤 blocks 범위의 renderer가 표현을 바꾼다. 읽기는 같은 원문 전체를 문서 흐름으로 표시한다. 기존 layout의 좁은 필드에 일반 본문을 평탄화하거나 CSS 클래스를 덮어쓰는 방식은 채택하지 않았다.

회의에서 쓴 `stage-view`/`stage-primary`와 message/evidence/media/pair/editorial은 **아직 미구현인 설계 가안**이다. 현재 parser에 그대로 쓰면 literal 본문이 되며 H1 앞에서는 제목 승격까지 막는다. 실제12입력은 성공7/명시거절5였고, root도 별도 임시 프로젝트에서 재실행했다. [현재 API 재현](engineering/evidence/view-probe.json)은 앞으로 구현할 기능의 성공 증거가 아니다.

선택은 장 첫 내용 앞 단독1줄, 대표 표시는 해당 H2 바로 앞이라는 선호 계약을 합의했다. 중복·오타·legacy 혼용·잘못된 binding/대표 선택은 원고 위치 오류와 마지막 정상본 보존으로 처리한다. 내용을 버리거나 다른 역할로 조용히 바꿔 성공으로 보이지 않게 한다.

pair에서는 원표 header·모든 rich 셀·출처/가상 성격이 발표에도 각1회 실제로 보여야 한다. 원표와 큰 값을 중복 표시하거나 read/aria에만 숨기는 것은 실패다. 표시 문자열은 원문 그대로 유지하고 비율/합계/단위를 추정하지 않는다. editorial의 대표 자료도 원위치에서 면적만 바꾸며 실제 보이는 읽기·DOM·키보드·read 순서를 유지한다.

## 권장 구현 순서와 완료 조건

1. 동일 원고·동일 자산의 현재/기본 조판 개선/선택1~2장 버전을 나란히 렌더한다. 우선 큰 선언·넓은 자료·주역 화면의 차이를 복구한다.
2. 같은 원고에서 두 수치와 C안 자료 그룹을 연결한다. 세 역할만 만든 상태를 전체 복원 완료로 판정하지 않는다.
3. 다른 주제 두 원고의 전체보기를 보고 장 역할·정보량 변화·주역 세부 가독성을 검수한다. 긴 한국어·큰 값·복합 단위·긴 표/코드·이미지 실패도 포함한다.
4. 제목1회·원문/inline/셀/코드/링크/alt/출처의 누락·중복0과 순서, 390px native 읽기·표/코드 국소 스크롤, source 진단·build/reload·전체보기/발표자·기존 양식 회귀까지 확인한다.

정확한 폰트·격자·면적 수치, 실제 pair DOM/헤더 연결, 복합 그룹·매체 지원 한도와 locale/값의 세부 허용 규칙은 동일 원고 시안에서 정한다. **이번 완료 산출물은 원인 확인과 두 팀의 복원 설계 합의다.** 제품·원고·배포에 복원 코드를 적용한 상태로 보고하지 않는다.

## 검토와 인계

디자인 실무자 둘이 시각 감사/작성 서사를, 엔지니어링 실무자 둘이 현재 API 감사·12입력 재현/작성·이행 계약을 작성하고 상대 초안을 직접 반례로 수정했다. 두 매니저는 R1/R2에서 반대안·binding/URI 경계·표 헤더/출처·자료 순서·이행 정책을 직접 교환해 상호 수신 확인했다. 총괄은7실제화면·코드 보존·12입력 재실행·최종 문서/링크와 제품 불변을 검증했다. 최종10문서의 로컬 링크131개·비교 HTML 참조17개 누락0, PNG7개1440×1000, 재현 원본12개·성공 JSON7개·content SHA2개·제품 SHA7개 일치를 확인했다. 최종 상태는 [WORK_LOG](../../WORK_LOG.md), 검증 근거는 [통합 기록](integration-receipt.json)에 보관한다.
