## 매니저 판단

확인한 차이는 **공통 검정 무대는 남았지만, 일반 Markdown에서 화면 역할과 콘텐츠 면적을 바꾸는 경로가 빠졌다는 것**이다. 기존 중앙 메시지의 130px 타이포와 넓은 빈 공간, 두 수치의 대비, 자체 표면이 다른 편집형 결과물, 넓은 근거 도표가 각각 별도 위계를 만든다. 새 표지·이미지 목록·표는 모두 같은 제목 크기와 본문 시작점을 갖는다. 새 이미지 목록의 실제 대시보드 크기는 약 258×193px로 작아, 이미지가 근거 또는 시연의 주역이 되기 어렵다.

제목 70px 자체는 모든 장에서 틀린 값이 아니다. 기존 visual 제목도 74px다. 복원 판단은 제목 크기 하나가 아니라 주장·근거·미디어의 상대 면적과 장 사이의 밀도 변화로 해야 한다. 표를 그대로 읽는 장과 긴 설명의 문서 흐름은 유지할 가치가 있다.

초기 JSON의 `footer: true`는 DOM 노드 존재만 가리켰다. 기존 중앙 메시지·quiet 장에서 푸터가 실제 보인다고 해석하지 않도록 총괄에 직접 지적했고, 총괄이 `footer:{nodePresent,visible,display,visibility}`로 보강했다. 보정본에서 기존 표지·편집요약·두 수치의 footer는 `display:none`, 새 세 장과 기존 visual은 `display:flex`임을 다시 읽어 확인했다. 편집 요약·수치 장의 출처 문장은 일반 footer와 구분해 보존한다.

## 엔지니어링과 대조한 의사결정

1. 일반 Markdown 의미 트리를 유지하고 view가 노드 경로·범위를 참조하는 최소안을 선택했다. 현행 legacy 어댑터는 정밀 호환 경로로 유지한다. 기존 class/고정 bento 슬롯을 blocks에 직접 붙이지 않고 토큰·위계를 재사용하며 새 view를 격리한다. 별도 AST 플랫폼·player/build 전면 변경은 선행하지 않는다.
2. 무선택 기본은 글폭·행간·자료 면적을 개선하되 역할을 자동 분류하지 않는다. 프로젝트 profile을 한 번 선택하고 필요한1~2장만 명시 힌트를 더하는 이행을 선호한다. 원고 자동 수정·모든 장 주석·새 추천 UI는 필수에서 제외한다. H1-only 후보 제안은 자동 적용을 허용하는 근거가 아니다.
3. 기본 세 역할만으로 C안·두 수치까지 복원되지는 않는다. 이를 JSON 재작성 과제로 남기지 않고 같은 표의 pair 및 H2 자료 그룹의 editorial을 선택 확장으로 연결한다. 세 역할 단계와 전체 복원 완료를 구분해 보고한다.
4. pair는 한3열표·2행·한 후속문단의 초기 구조, 모든 header/rich 셀/출처의 발표1회 실제 표시를 합의했다. C는 H2 바로 앞 대표 marker 하나와 원고 위치의 면적 차이를 선호하며 보이는 읽기/DOM/키보드/read 순서를 모두 유지한다. 숫자 추출·단위 추정·성과 해석·12개 칸 강제는 하지 않는다. 세부 schema·DOM·font/grid·복합 입력 한도는 후속 시안의 결정값이다.
5. 같은 원고·같은 자산·같은 viewport의 전후 화면과 의미 대조를 인수 조건으로 합의했다. 이번 서로 다른 주제의 PNG는 결함 범위의 근거이며 후보 성공 증거가 아니다. 기본/힌트1~2장/7장 내용 편집안을 구분해 검증한다.

## 두 매니저의 실제 R1/R2 교환

R1에서 디자인은 CSS 일괄 확대·legacy JSON 강제를 반례로 기각하고 AST+작은 view를 제안했다. 엔지니어링은 이를 수용하면서 기존 blocks의 구조를 존중하는 view 격리와 canonical URI/발행 URL resolver의 범위 축소를 수정 제안했다. 디자인이 두 수정을 모두 수용하고 R1 합의를 확인했다. 현재 정상 발행 URL 변경을 원고 손상으로 취급하지 않는다.

R2에서 엔지니어링은 장 시작 단독 힌트·엄격 오류·pair/editorial의 입력 구조·한 번의 profile 이행·동일 원고 시각 게이트를 제안했다. 디자인은 frontmatter/장 구분 뒤 첫 내용 앞이라는 위치, legacy 혼용/primary 오용/미지 키 오류, header의 rich children 보존, C의 H2 경계와 마지막 문단 소속·보이는 순서를 추가했다. 엔지니어링이 수정 모두를 수용한 답변을 보냈고 디자인이 최종 수신을 확인했다. 일방적인 문서 합의를 두 팀 합의로 표시하지 않았다.

명시 구조 부적합은 `source:line` 오류와 마지막 정상본 유지로 처리하고 silent fallback은 하지 않는다. 실제 길이·면적 넘침은 원문 유지·진단·작성자 분할로 다룬다. pair의 N/A·약값·선행0·복합단위는 표시 원문을 유지하고 빈 단위는 보존한다. C의 대표가 뒤에 있으면 원래 그 위치에서 면적만 바꾼다. `stage-view`와 `stage-primary`는 현재 지원 구문이 아니며 이번 합의는 향후 구현의 선호 계약이다.

최종 종합에는 구현 순서를 ① 제어 분리/schema/binding, ② profile의 기본 개선과3역할, ③ pair/editorial 연결, ④ 동일 원고의 의미·시각·390px read·기존 덱 검수로 기록했다. 실제 DOM/header 연결·locale/값 허용 목록·그룹 수/복합매체·font/grid/면적은 시안 후 결정할 값이다. 이번에 제품 복원이 완료됐다고 보고하지 않는다.

## 취합 검수 범위

두 실무자의 [시각 감사](visual-audit.md)와 [서사·작성 제안](story-proposal.md)을 실제 읽었다. A는 보존 원리와 현재 차이 9개를 작성했고 B는 기존 product-notes 문장·표·코드·링크의 순서를 유지하는 7장 편집 예시와 작은 역할 선택을 제안했다. 기존 원고 파일에 이 예시를 적용하지 않았다.

실무자 직접 반례 교환은 취합에 실질 영향을 주었다. A의 ‘이미지+목록 자동 split은 순서를 바꿀 수 있다’는 지적을 B가 수용해 넓은 자료와 원문 순서를 기본으로 삼았다. A의 ‘H1과 blockquote가 함께 있는 장은 무엇이 주역인가’라는 반례로 B는 5장의 message 선택을 제거했다. B의 ‘작은 가상 삽화를 확대해도 근거 타당성은 생기지 않는다’는 반례를 A가 받아들였다. 이는 자동 분류가 잘못된 의미를 만들 수 있는 경계로 엔지니어링에 전달한다.

매니저는 초안의 중첩 code fence가 Markdown 예시를 중간에 닫는 문제를 지적했고 B가 바깥 다섯 백틱·안쪽 기존 세 백틱으로 수정했다. `markdown-it`로 회의용 Markdown 예제가 하나의 fence이며 실제 code와 마지막 장을 함께 포함함을 독립 확인했다. ‘한두 장만 선택하면 된다’는 권고와 여러 역할을 보여 주는 전체 7장 예시도 구분하도록 교정했다.

최종 [취합](synthesis.md)을 실제 읽고 세 역할의 복원 범위와 C/두 수치의 간단 그룹 후보·미결정 경계를 확인했다. 두 실무자는 모두 `completed`이며 파일 편집 종료와 매니저에게 소유권 인계를 직접 확인했다. 인계 후 매니저가 종합의 ‘모든 장130px를 금지’라는 모호한 문장만 ‘모든 장을130px로 일괄 변경하지 않음’으로 명료화했다. 실무자 초안의 내용은 추가 수정하지 않았다.

1차 문서4개의 Markdown 링크는 로컬 경로77개 누락0, 행 끝 공백0을 독립 확인했다. R1/R2 뒤에는 종합과 매니저 검수 두 파일만 갱신했고 최종4문서의 로컬 링크82개 누락0·행 끝 공백0을 다시 확인했다. 두 실무자 초안의 해시는 1차 인수본과 같다. 총괄의 RESULT.md·MEETING.md도 읽어 실제 회의·미구현 가안·후속 시각검증의 경계가 위 합의와 일치함을 확인했으며 정정 요청은 없다.

제품 변경이 없고 이번 산출물은 문서뿐이므로 제품 테스트·새 브라우저 회귀를 반복 실행하지 않았다. 현재 제품 변화의 시각 QA 또는 미래 복원안의 실제 렌더 통과를 주장하지 않는다. 두 실무자는 종료를 유지하며 추가 조사·하위 작업은 배정하지 않았다. 디자인 매니저의 최종 문서 편집도 종료하고 총괄에게 인계한다.
