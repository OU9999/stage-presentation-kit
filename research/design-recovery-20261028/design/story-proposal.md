# Markdown 원고의 의미를 지키는 디자인 복원 서사안

작성: `/root/design_manager/story_designer` · 2026-10-28 · 독립 실질 초안. 제품 구현·원고 변경·브라우저 조작·commit/push는 하지 않았다. 이 문서의 새 표기와 7장 예시는 **회의용 제안**이며 현재 parser에서 작동한다는 뜻이 아니다.

## 판단과 실제 확인

Markdown 작성 흐름을 유지하면서 장마다 **기억할 문장 / 읽을 근거 / 볼 화면 / 회수할 결과** 중 무엇이 주역인지 선택하게 한다. 자유로운 Markdown을 20개 구조화 양식의 JSON으로 다시 쓰게 하는 방식은 기본 작성 경로로 삼지 않는다. 본문이 많을 때는 이를 먼저 지우거나 요약하지 않고 넓은 증거 장 또는 명시적인 장 분할을 권한다.

직접 `view_image`로 본 공통 근거는 [기존 큰 메시지](../evidence/old-message.png), [기존 C 편집형 결과](../evidence/old-editorial.png), [기존 두 수치](../evidence/old-metric-pair.png), [기존 native 시각자료](../evidence/old-visual.png), [새 표지](../evidence/new-opening.png), [새 이미지+목록](../evidence/new-image-list.png), [새 표](../evidence/new-table.png)와 [과거 C 시안](../../review-20261023/design/proposal-desktop-c.png)이다. 공통 [측정 기록](../evidence/observations.json)은 1440×1000, stage 1344×756으로 같지만 원고와 주제가 다르다. 이 비교는 출력 문법 차이의 관찰이며 같은 원고의 효과 검증이 아니다.

보존된 DevDay [20:30 큰 문장](../../evidence/devday/keynote-20m30.png), [20:00 주장과 도표](../../evidence/devday/keynote-20m00.png), [36:00 실제 작업 화면](../../evidence/devday/keynote-36m00.png), [47:50 여러 결과의 회수](../../review-20261023/research/evidence/general/keynote-live-47m50.png)도 직접 열었다. 문장·도표·실제 화면·혼합 요약이 맡는 역할과 면적이 달라지는 것을 확인했다. 새 영상 재생·외부 사이트 관찰이나 공식 서체·토큰 검증은 하지 않았다. `old-message`의 실제 양식은 cover/130px이며 statement126px의 직접 증거로 사용하지 않는다.

- 큰 메시지에서는 시선 중심이 두 줄 주장과 한 의미색에 모인다. 새 표지는 제목+본문의 같은 왼쪽 문서 흐름에 가상 자료 안내까지 같은 본문 위계로 놓인다. 안내를 삭제하는 대신 주장의 아래에 충분히 읽히는 보조층을 둬야 한다.
- 새 이미지+목록에서는 이미지만 약258×193px이고 세 목록이 그 아래로 이어진다. 이미지가 실제 근거라면 작아서 세부를 읽기 어렵다. 그러나 이 이미지가 단순 삽화라면 자동으로 확대해 차트처럼 읽게 만드는 것도 잘못이다. 이미지의 역할 선택이 필요하다.
- 새 표는 표의 관계와 전체 문장이 실제로 유지되어 있다. 이를 chart나 큰 수치로 바꾸는 것은 디자인 복원의 필수 조치가 아니다. 표 자체를 주요 증거로 읽게 하는 넓은 무대가 적합하다.
- 기존 C안은 한 프로젝트의 표지·관찰·인용·실행 UI가 서로 다른 표면과 크기로 연결된다. 모든 장을 타일로 채우거나 자료가 없는 원고에 가짜 문서·수치를 만들어 넣는 근거가 아니다.

함께 읽은 근거는 [DESIGN.md](../../../DESIGN.md)의 한 장 역할·중앙 변형·C 편집형 원칙, [2026-10-23 디자인 종합](../../review-20261023/design/synthesis.md)의 주역과 보조·자산 자체 표면, [2026-10-25 글 배치](../../type-layout-20261025/synthesis.md)의 읽기 폭·원문 줄바꿈·모바일 native 흐름, [2026-10-24 시각자료 사양](../../visual-redesign-20261024/design/final-spec.md)의 열린 wide/split·동일 원본 표다. `blocks.css`는 70px 제목·30px 본문·230px 이미지 상한과 세로 흐름 하나를 사용한다. 두 `talks/*/slides.md`는 이미지·목록·표·코드·인용·링크를 일반 Markdown으로 명확하게 쓰며, `examples/devday-compositions/content.js`는 선택 구조화 자료에서만 C안·두 수치 등 역할을 명시한다.

## 권장안: 안전한 기본 + 작은 시각 선택 + 선택적 정밀 양식

기본은 원문 DOM 순서와 의미를 보존하는 Markdown 장이다. 아무 힌트도 없는 기존 원고는 갑자기 다른 구조나 의미로 분류하지 않는다. 여백·읽기 폭·자료 최대 크기 같은 공통 기반은 개선할 수 있지만 문장 삭제, 숫자 추출, 표의 chart 전환, 목록의 범주화는 하지 않는다.

선택 힌트는 장의 **시각 표현만** 바꾼다. 회의용 표기는 `<!-- stage-view: message -->`, `<!-- stage-view: evidence -->`, `<!-- stage-view: media -->` 세 가지를 제안한다. 실제 이름·parser 연결·지원 범위는 엔지니어링과 합의해야 한다. 이 표기는 현재 지원 구문이 아니다. 제목·본문은 일반 Markdown 그대로 쓰고 좌표·폭·폰트·아이콘·별도 `content.js`를 요구하지 않는다. 각 힌트는 없어도 문서를 읽을 수 있는 주석이며 일반 Markdown 도구의 본문 의미를 바꾸지 않는다.

| 선택 | 발표에서 하는 일 | 원고에 요구하는 것 | 안전 경계 |
| --- | --- | --- | --- |
| 기본 | 제목과 본문을 자연스럽게 읽고 표·코드는 넓게 배치 | `#`, 문단, 목록, 표, 코드 등 기존 Markdown | 내용 형태를 보고 메시지/수치/차트로 임의 승격하지 않음 |
| `message` 가안 | 첫 H1을 큰 중심으로 두고 보충문을 낮은 위계로 유지 | 장당 선택 주석 하나. 긴 본문이면 source:line으로 부적합 안내 | H1과 인용 중 주역을 자동 추론하지 않음. 보충문·화자·출처·가상 안내를 숨기지 않음. 길면 축약 대신 분할 권고 |
| `evidence` 가안 | 표·코드·이미지와 설명이 읽을 면적을 확보 | 주석 하나. 필요하면 image 우선/설명 우선 등 시각 변형은 제품이 제공 | DOM 순서는 그대로. 설명이 독립 질문인지 모르면 자동 split하지 않음 |
| `media` 가안 | 이미지 한 개나 실제 작업 화면이 넓은 주역 | 주석 하나 + 기존 이미지 문법·alt | 전체 UI는 contain, 사진은 선택 crop. alt를 설명 대신 화면에 강제 출력하지 않음. 제목·캡션을 버리지 않음 |
| 정밀 양식 | 실제 수치 두 개·정량 chart·편집형 결과모음처럼 의미가 명시된 자료를 재사용 | 기존 명시 layout/구조화 데이터의 복사 가능한 스타터 | 일반 원고를 자동 변환하지 않음. JSON/12슬롯은 선택 경로이며 기본 문법 아님 |

`evidence`는 코드·표를 무조건 2열로 만드는 이름이 아니다. 넓은 자료를 기본으로 삼고, 원문에서 독립 자료와 설명의 경계가 분명할 때만 선택적으로 나눈다. 전체 시선은 제목→먼저 쓴 자료→나중에 쓴 설명 순서를 따른다. grid 배치가 DOM 또는 접근성 순서를 바꾸면 채택하지 않는다.

작성자가 반드시 새 힌트를 모든 장에 붙일 필요는 없다. 기본 원고를 붙여넣고, 큰 선언 한 장과 주역 화면 한 장을 선택하는 것만으로 장간 리듬이 생겨야 한다. 기존 `title`, 문단, 링크, 이미지 경로를 별도 시각 설정에 중복 작성하게 하지 않는다.

최소 선택 예시는 기존 6장 중 1장에만 `message`를 선택하고 나머지는 일반 Markdown으로 두는 것이다. 실제 화면 한 장이 분명할 때만 그 장에 `media`를 더한다. 아래 7장 예시는 역할 후보를 비교하기 위한 **여러 장 선택 예시**이며, 모든 주석을 써야 하는 최소 양식이 아니다. `message`의 기본 주역은 H1이라는 가안을 두므로 H1과 blockquote가 함께 있는 5장은 기본 장으로 남긴다. 인용 자체를 주역으로 만드는 선택은 후속 검토 사항이다.

## 7장 서사와 짧은 원고 예시

아래는 기존 `product-notes`의 의미를 설명하는 **미구현 회의용 7장 원고 예시**다. 기존 6장의 문장·표·코드·인용·링크 순서를 유지하고, 마지막 장의 맺음 문단을 별도 7장으로 나눈 편집안이다. 7장 제목만 새로 제안했으며 원고 파일에는 적용하지 않았다. 역할별 효과는 아직 렌더 검증하지 않았다.

| 장 | 서사 역할 | 시각 주역 | 이 장에서 말할 한 문장 |
| --- | --- | --- | --- |
| 1 | 시작의 약속 | 큰 선언, 아래의 짧은 맥락과 가상 자료 안내 | 관찰과 다음 행동을 같은 원고에 남긴다. |
| 2 | 무엇을 볼 것인가 | 실제 자료로 채택할 이미지와 뒤따르는 3개 관찰 원칙 | 해결책보다 먼저 실제 행동을 본다. |
| 3 | 어떤 근거로 판단할 것인가 | 넓은 표, 읽을 수 있는 열 이름·행 | 관찰과 다음 행동을 구분한다. |
| 4 | 작은 작업의 구체성 | 넓은 코드와 설명 | 원문과 코드 안의 구분선을 보존한다. |
| 5 | 회고의 관점 | 원래 인용과 설명을 함께 읽는 기본 장 | 만든 것보다 이해한 것을 이야기한다. |
| 6 | 실제 다음 행동 | 순서 있는 링크 목록 | 같은 질문으로 작은 변경을 다시 본다. |
| 7 | 맺음과 복귀 | 짧은 마지막 문장 | Markdown 하나에서 발표와 읽기를 함께 확인한다. |

바깥 5백틱은 문서에 원고를 표시하는 울타리이고, 원고 내부의 JS 코드는 기존 3백틱 그대로다. 실제 원고 예제 전달 때는 parser가 코드 안 `---`를 장 구분으로 보지 않는 기존 계약을 유지한다. 2장의 SVG는 현재 가상 대시보드이며 결과를 입증하는 실데이터가 아니다. 무엇을 읽어야 할지 확인하지 않은 상태에서 확대만으로 근거가 생겼다고 판단하지 않는다.

선택적인 8장 결과 회수는 실제 프로젝트의 완성 문서·실행 화면·관찰 사진이 있을 때 추가한다. 큰 결과물 하나와 보조 UI 하나를 중심으로, C안처럼 자산의 자체 면을 살린다. 작성할 자료가 없으면 7장으로 끝낸다. 임의의 12개 타일, 수치, 장식 아이콘을 채우는 과제는 만들지 않는다.

## 채택하지 않을 안과 반례

| 안 | 장점 | 기각 또는 제한 이유 |
| --- | --- | --- |
| blocks의 모든 제목만 크게·중앙으로 | 수정이 적음 | 표·코드·목록이 읽을 면적을 잃고 모든 장의 역할이 다시 같아짐. 긴 한국어 제목도 불리함 |
| 모든 원고를 20종 legacy layout/JSON으로 전환 | 기존 무대 재사용이 쉬움 | 일반 표·코드·링크·중첩 목록을 의미 손실 없이 다시 작성하기 어렵고 원고 수정 지점이 늘어남 |
| Markdown 구조를 보고 완전자동 분류 | 새 문법이 없음 | 표의 숫자는 큰 성과값이라는 보장이 없고, 목록은 범주가 아니라 순서일 수 있음. 이미지도 근거/삽화/전체 UI가 다름 |
| 원문은 읽기에만 두고 발표에서는 요약/숨김 | 화면 밀도를 쉽게 줄임 | 누가 무엇을 없앴는지 원고에서 알 수 없고 발표의 의미·가상 안내·출처가 달라질 수 있음 |
| 모든 결과를 C안 bento로 | 다양한 표면과 컬러를 회수 | C안은 한 프로젝트의 편집된 자료 관계가 전제. 일반 설명문에 채울 수 있는 보편 wrapper가 아님 |
| message 하나만 보면 빈 공간은 실패라는 판단 | 화면을 더 채우게 됨 | 기존 큰 메시지·두 수치의 여백 자체가 시선을 정하는 기능. 자료 없는 장식으로 채우지 않음 |

장기적인 완전자동 분류가 필요하다면 적용 전에 후보만 보여 주고 작성자가 장 단위로 선택하게 해야 한다. 기본 동작으로 silently 적용하지 않는다.

## 원문·읽기·편집 계약

1. Markdown이 유일한 내용 권위다. 발표 DOM은 파생 표현이며 현재 원고 수정·build/dev/reload 흐름을 유지한다. 생성물 화면 편집을 원본 저장으로 오인하게 만들지 않는다.
2. 제목·본문 노드·문단·목록 순서·표의 header/셀 대응·code raw text/언어·blockquote·링크 목적지·이미지 alt/경로가 원문과 같아야 한다. `strong`이 의미 강조인 것과 단순 색 선택을 혼동하지 않는다.
3. `message`에서도 일반 본문과 가상 자료 안내·출처가 읽혀야 한다. 이를 notes 또는 appendix로 자동 이동하지 않는다. 현재 새 모드에서 미지원인 notes/role/sourceDownload 등을 이번 디자인 제안으로 지원한다고 주장하지 않는다.
4. read는 시각 힌트를 벗겨도 같은 논리 순서와 전체 내용을 유지한다. 모바일은 native 문서 흐름과 충분한 글자 크기·표/코드의 국소 스크롤을 사용한다. 16:9 축소만으로 390px 읽기를 통과 처리하지 않는다.
5. 넘침은 원고 위치와 이유를 알리고 작성자가 장을 나눈다. 자동 축소·말줄임·본문 삭제로 조용히 통과시키지 않는다. 보조 텍스트는 낮은 위계여도 실제 표시·대조 가능한 크기를 유지한다.

## 후속 승인 시 시각 검증 기준

- 같은 Markdown·같은 자산·같은 viewport에서 현재/후보를 나란히 확인한다. 문구를 바꾼 7장 편집안은 별도 서사안으로 표시하고 단순 CSS 효과로 주장하지 않는다.
- 메시지/표/코드/이미지+목록/인용/마무리의 최소 6역할을 비교한다. 메시지는 한 주장이 먼저, 근거 장은 읽어야 할 셀·코드·UI가 먼저, 결과 회수는 주역 1개와 보조 자료의 관계가 먼저 보여야 한다.
- 본문은 별도 정규화 비교로 누락·중복·순서 변경 0을 확인한다. 표의 raw 값과 코드 안 구분선·링크·줄바꿈도 대조한다.
- 실제 긴 한국어·긴 단위·긴 URL·12행 표·긴 코드·이미지 실패·표나 이미지 없는 message 반례를 확인한다. 특정 예제 길이만을 기준으로 고정 수치를 정하지 않는다.
- 1440×1000 동일 화면에서 잘림·겹침·주역 자료의 의미 있는 세부 가독성을 확인하고, 390px read에서 본문 가로 넘침 0·native text·국소 표/코드 스크롤·링크 이동·source 순서를 확인한다.
- 기본 원고와 힌트 원고 둘 다 build/reload/read/발표자·전체보기에서 유지되는지 후속 엔지니어링 단계에서 확인한다. 이번 회의에서 제품 구현·모바일 실기·효과 검증을 완료한 것은 아니다.

## 독립 초안 이후 교차 검토 기록

A의 초기 메시지는 이미지+목록 자동 split이 원고 읽기 순서와 충돌할 수 있다는 반례를 제기했다. 이 반례를 받아 기본은 자동 split하지 않고, 선택 표현에서도 DOM/읽기 순서는 유지하며 넓은 자료를 먼저 쓰도록 권고했다. A의 실질 초안 `visual-audit.md`를 읽고 5장의 H1과 blockquote 중 주역이 모호하다는 추가 반례를 수용했다. `message`는 첫 H1 주역이라는 가안으로 제한하고 5장은 기본 장으로 바꿨다. B는 삽화 확대가 곧 근거 확보가 아니며 표 자체가 적절한 증거일 수 있다는 반례를 A에게 직접 보냈고, A는 수용·반영한다고 답했다.
