# 디자인팀 복원 방향 종합

초안 취합: `/root/design_manager/story_designer` · 최종 회의 반영: `/root/design_manager` · 2026-10-28. [A 시각 감사](visual-audit.md)와 [B 서사·작성안](story-proposal.md)을 읽고, 엔지니어링 매니저와 R1/R2 직접 제안·반례·수정·상호 수신 확인을 마친 결과다. 아래는 **미구현 선호 계약**이며 제품 구현·기존 원고 변경·commit/push·배포를 수행한 결과가 아니다.

## 결론과 원인

기존 DevDay 참고 디자인을 복원하려면 검정 배경을 더 진하게 만들거나 모든 제목을 크게 하는 것이 아니라, **한 문장의 선언 → 읽을 근거 → 주역 화면 → 관련 결과의 회수**라는 장의 역할과 면적 변화를 일반 Markdown 작성 흐름에 다시 연결해야 한다.

현재 일반 Markdown은 의미를 보존하면서도 전부 `layout:blocks`로 출력된다. `blocks.css`의 70px 제목·30px 본문·230px 이미지 상한·세로 흐름 하나로는 기존 cover/statement의 큰 선언, 열린 visual의 근거, media의 주역 UI, metric-pair의 두 값, C안의 불균등 결과 요약을 선택할 수 없다. 기존 20양식과 팔레트 자체는 남아 있으므로 현재 근거가 가리키는 원인은 디자인 자산 삭제보다 **새 원고 경로와 시각 역할의 연결 부재**다.

R1에서 두 팀은 현재 `heading? + blocks`를 단일 내용 권위로 유지하고 작은 view가 노드 경로·범위를 참조하는 안을 선택했다. 기본 CSS의 글폭·행간·자료 면적도 개선하되 모든 제목130px·이미지 상한 일괄 해제는 표/코드/긴 본문을 해치므로 해법으로 삼지 않는다. 일반 원고를 기존 JSON으로 강제 이행하는 안도 표 혼합 거절과 중복 작성 때문에 기각했다. 기존 토큰·위계는 재사용하되 새 view는 blocks 안에 격리하며 고정 bento 슬롯을 그대로 붙이지 않는다. 별도 AST 플랫폼·player/build 전면 재작성은 선행 조건이 아니다.

[엔지니어링 실제 재현](../engineering/parser-view-audit.md)과 [12입력 결과](../engineering/evidence/view-probe.json)는 현재 `stage-view`가 literal 문단이며 H1 앞에 놓으면 제목 승격도 막는 것을 확인했다. JS의 `slide.view` 미지 키가 검증을 통과해도 app은 이를 소비하지 않는다. 아래 예시를 현재 작동하는 원고 문법으로 안내해서는 안 된다. 제어 지시문 분리·엄격 schema·노드 binding·renderer 연결이 함께 구현돼야 한다.

## 채택할 방향과 아직 남는 간극

1. **일반 Markdown 기본**: 원래 순서와 의미를 유지하고 글폭·행간·자료 면적을 개선한다. 표·코드가 좁아지는 일괄 중앙정렬은 하지 않는다. 기본값만으로 모든 원고의 역할을 정확히 알 수 있다고 주장하지 않는다.
2. **작은 장 단위 선택**: `message / evidence / media`를 기본 선택으로 합의했다. message는 유효한 첫 H1을 주역으로 삼고 보충문·가상 안내·출처를 남긴다. evidence는 넓은 자료이며 자동 split/chart가 아니다. media는 하나로 특정된 주역 이미지에 큰 면적을 주고 UI는 contain을 기본으로 한다. 문장·표·alt·링크를 다시 쓰지 않는다. `stage-view` 표기는 **현행 parser 미지원인 회의용 표기**다.
3. **간단한 그룹을 쓰는 선택적 확장**: 위 세 역할만으로 두 수치와 C안의 결과 요약이 복원되지는 않는다. 이를 매번20양식 JSON으로 쓰게 하면 작성 부담이 남는다. R2에서 표 한 번을 참조하는 `pair`, H2 자료 그룹과 대표 하나를 참조하는 `editorial`을 선호 계약으로 합의했다. 아래 구조와 보존 조건을 구현·시각 검증해야 하며 세 역할만 완료하면 전체 복원 완료로 부르지 않는다.
4. **기존 정밀 양식 유지**: 데이터 chart·시스템 도식·기존20양식을 필요한 작성자가 계속 쓸 수 있게 한다. 기본 원고를 모두 이 경로로 돌려보내지 않는다.

최소 작성 예시는 기존 6장 중 선언1장에만 선택을 넣고 나머지는 일반 Markdown으로 두는 것이다. 실제 화면이 주역인 경우1장만 추가 선택한다. [B의 전체7장 원고](story-proposal.md)는 여러 역할을 비교하는 확장 예시이며, 모든 장 주석이 필수인 최소 문법이 아니다. 예시의5장 인용은 H1과 인용 중 주역이 모호해 기본 장으로 남겼다. 7장 원고는 기존 product-notes의 맺음 문단을 따로 나눈 편집안이며 원고 파일에는 적용하지 않았다.

### R2 선호 계약: 작은 힌트와 엄격한 실패 정책

지시문은 frontmatter 또는 장 구분 뒤 **첫 내용 앞의 단독 한 줄** `<!-- stage-view: message -->` 형식을 선호한다. 기본3역할 외 pair/editorial은 선택 확장이다. 코드·인용 속 예문은 제어로 해석하지 않는다. 내용 줄 위치를 유지하며 지시문을 의미 AST와 분리해 첫 의미 H1이 한 번만 소비되는 계약을 지킨다.

중복·오타·잘못된 위치·미지 enum/키·잘못된 binding·명시 legacy layout과 혼용·editorial 밖 primary·명시 구조 부적합은 `source:line` 오류와 복구 안내를 내고 마지막 정상 산출물을 유지한다. 조용히 기본/다른 역할로 바꾸거나 본문을 덜어내지 않는다. 실제 렌더에서 길이·면적이 넘치면 원문을 보존한 채 진단하고 작성자가 나눈다. 정확한 lexer/schema 값은 후속 구현에서 이 계약을 충족하도록 확정한다.

### R2 선호 계약: 두 수치와 편집 요약의 간단 그룹

**두 수치:** 명시 pair 선택에서만 H1은 선택 사항으로 두고, 대상/값/단위 순의 한3열표·정확히2데이터행·바로 뒤 한 범위/출처 문단을 참조하는 초기 구조를 합의했다. 계산 없는 표시 view로 raw 문자열과 rich children을 그대로 사용한다. 선행0·약24·N/A·복합단위도 임의 Number 변환·합계·전환율·성과 해석을 하지 않는다. 빈 단위는 보존하고 빈 값·여러 표·추가 설명의 결합은 적합성 진단 대상이다.

header3개·모든 셀의 rich inline·출처·가상 성격을 **발표에도 각각 한 번 실제로 표시하고 접근 가능하게** 남긴다. header/설명을 read 또는 aria에만 숨기면 실패이며 원표와 별도 큰 값을 중복 읽게 하는 방식도 피한다. header 이름의 locale/별칭 허용값, 정확한 DOM과 header 연결, 긴 값의 적합성은 후속 시안에서 정할 값이다.

미구현 선호 표기와 내용 예시:

```markdown
<!-- stage-view: pair -->
| 대상 | 값 | 단위 |
| --- | --- | --- |
| 모아 둔 아이디어 | 24 | 개 |
| 연결한 작업 | 6 | 가지 |

양식 설명용 가상 수치 · 실제 측정 결과가 아닙니다.
```

이 표를 보고 자동 변환한다는 뜻이 아니다. **명시 pair 선택이 없으면 일반 표**다. 후속 문단을 출처라고 내용으로 추측하지 않고 위 입력 경계로 참조한다. 범위를 벗어나는 입력은 위치 진단한다. 원문 수치·라벨·단위·출처를 JSON 필드에 재입력시키지 않는 것이 목표다.

**편집 요약:** 각 H2부터 다음 H2 전까지의 이미지/인용/문단을 한 자료 그룹으로 참조하고, `<!-- stage-primary -->`를 대표 H2 바로 앞에 붙이는 방식을 선호 계약으로 합의했다. 순번은 앞 그룹 삽입에, 제목 참조는 rename에 취약하므로 피한다. 첫 H2 전은 공통 안내, 마지막 H2 뒤 문단은 마지막 그룹에 남기며 마지막 문단을 공통출처로 추정하지 않는다. 원매체 표면과 면적 차이를 살리고12칸이나 특정 자산 수를 강제하지 않는다.

미구현 선호 표기와 내용 예시:

```markdown
<!-- stage-view: editorial -->
<!-- stage-primary -->
## 완성한 기록

![프로젝트의 실제 완성 문서](./report.png)

관찰에서 다음 행동까지 한 문서로 묶었습니다.

## 다음 행동

> 첫 화면에서 해야 할 일을 먼저 보여 줍니다.

다음 검토에서는 이 안내를 같은 질문으로 확인합니다.
```

제목·이미지·문단은 한 번만 작성한다. 대표0/복수·빈 그룹·주역 모호는 진단한다. 뒤 그룹이 대표여도 원래 위치에서 면적만 달라지며 **보이는 읽기 순서·DOM·키보드·read 순서를 원고와 같게** 유지한다. 대표를 앞쪽 grid로 끌어오지 않는다. 위 예시는 두 그룹의 최소 후보이며 C안12슬롯을 완성했다는 주장이 아니다. 허용 그룹 수·복합매체·긴 본문·UI의 실제 가독성과 정확한 격자는 후속 시안으로 정한다.

두 선택의 인수 조건은 **원문 중복0 / 원고·보이는 읽기·read 순서 보존 / 사실 추론 금지 / 명시적 선택 / 기존 일반 표·본문과의 비간섭 / 넘침 진단**이다. 간단한 문법 합의만으로 구현 가능·호환·작성 편의·시각 복원이 검증됐다고 보고하지 않는다.

### R2 합의: 무주석 원고의 이전과 자동성

| 방안 | 얻는 것 | 남는 위험·확인 질문 |
| --- | --- | --- |
| 프로젝트에서 복원 profile 한 번 선택 + 명시 장 선택 | 무주석도 글폭·행간·자료 면적 개선, 필요한1~2장만 작은 선택 | 채택. 기존 원고를 자동 수정하지 않고 기존 blocks/legacy 기준과 미리보기로 비교 |
| 구조가 매우 단순한 H1-only 장의 후보 제안 | 명확한 선언을 발견할 수 있음 | 자동 적용하지 않음. 새 추천 UI는 이번 최소 구현의 필수가 아니며 필요할 때 후속 선택 |
| 위치/표/숫자/목록/이미지를 보고 폭넓게 자동분류 | 입력 부담은 작음 | 첫/마지막 장 자동 cover/closing을 포함해 채택하지 않음. 작성자가 선택하지 않은 의미를 만들 위험 |

profile은 출력 스타일 이행이며 notes/공개 role/내용 재작성과 무관하다. 정확한 설정명·버전값은 후속 구현에서 정한다. 무선택 기본 개선과 힌트1~2장 선택의 효과를 따로 검증한다. 모든 장 주석·원고 자동 재작성·새 추천 UI를 요구하지 않는다. 기존 두 원고와 정밀20양식은 비교 기준으로 보존한다.

## 후속 구현 순서와 완료 판정

1. parser의 제어 힌트 분리·줄 위치 보존, 명시 view schema·적합성·노드 binding과 마지막 정상본 보존부터 구현한다. 현재 미지 키 통과나 CSS 클래스 추가를 지원 완료로 간주하지 않는다.
2. blocks에 한정한 복원 profile의 기본 글폭·행간·자료 면적과 message/evidence/media를 연결한다. 내용은 현재 heading+blocks 한 번으로 두고 read는 원래 흐름을 유지한다. 원고 URI와 발행 URL resolver를 구분하며 현재 정상 asset rewriting을 결함으로 취급하지 않는다.
3. 같은 AST에서 pair와 editorial을 선택하는 작은 표/그룹 계약을 연결한다. 수치·제목·이미지·출처를 별도 JSON에 다시 쓰게 하지 않는다. 두 선택이 빠진 단계는 기본3역할 개선으로 보고하며 C/두 수치까지 전체 복원됐다고 하지 않는다.
4. 같은 원고·자산·viewport의 기본/후보를 실제 렌더하고 아래 의미·시각·모바일·기존 덱 검수를 모두 마친다. 7장 서사 편집안은 내용이 달라 별도 비교로 표시한다. 실제 시안에서 DOM/header 연결·locale·복합 그룹 범위·font/grid/면적 값을 결정한다.

## 유지할 원고 계약과 후속 검수

- Markdown이 유일한 내용 권위다. 제목1회·문단·목록·표 header/셀·코드 raw text/언어·인용·링크·alt·명시 줄바꿈을 보존한다. 발표에서 숨긴 본문을 read에만 남기는 정책을 자동 도입하지 않는다.
- 선택 배치가 시각적 위치를 바꾸더라도 DOM·키보드·read의 논리 순서는 원고와 같아야 한다. 표의 숫자 추출, 목록의 범주화, 개념도의 실측그래프화는 금지한다.
- 보조 안내·출처·가상 자료 성격은 읽을 수 있게 남긴다. 큰 선언 때문에 필요 정보를 제거하지 않는다. 넘침은 source:line 진단과 작성자 분할로 해결한다.
- 후속 승인 시 같은 원고·자산·viewport의 현재/후보를 비교한다. 짧은 선언, 긴 한국어+설명, 이미지+3목록, 표, 코드 안`---`, 제목+인용, 두 수치, 결과요약을 각각 확인한다. 전체보기에서 역할·밀도 변화도 확인한다.
- 390px read의 native 문서 흐름·본문 가로 넘침0·표/code 국소 스크롤·링크와 전체 내용 보존, 기존 quiet/중앙/표지metadata/editorial/visual 회귀를 후속 검수한다. PDF는 향후 출력 범위에 포함할 경우 별도로 검증하며 이번 회의 필수 완료로 확장하지 않는다.

## 직접 교차 협의와 인계

A는 실제 시각 원리·9개 차이·검수 기준 초안을, B는 역할·최소작성 계약·7장 전체 원고·반대안 초안을 각각 먼저 작성했다. 이후 직접 읽고 아래 반례를 주고받았다.

| 보낸 사람 → 받은 사람 | 반례 | 반영 결과 |
| --- | --- | --- |
| A → B | 이미지+목록 자동 split이 원고 순서와 충돌 | B는 기본 자동split을 빼고 선택시DOM/read순서 불변으로 제한 |
| B → A | 작은 이미지가 항상 확대 대상은 아님. 가상 삽화 확대가 근거 타당성을 만들지 않음 | A는 이미지 역할 확인을 추가하고 무조건 상한 해제 해법을 배제 |
| A → B | H1과 blockquote가 함께 있는5장 message의 주역이 모호 | B는 message 기본주역H1 가안을 명시하고5장을 기본장으로 변경 |
| 양쪽 → 취합 | 세 역할로 C안·두 수치까지 해결됐다고 말하면 작성 부담 과소평가 | 간단 그룹 후보와 미확인·직접회의 안건을 별도 기록 |

두 실무자의 편집 종료와 소유권 인계 뒤 디자인·엔지니어링 매니저가 직접 R1/R2를 진행했다. R1에서 엔지니어링은 blocks 격리와 URI resolver 범위 수정을 제안했고 디자인이 수용했다. R2에서 엔지니어링의 작은 힌트·pair·editorial·이행·검증 제안에 디자인이 위치/혼용 오류·header rich 보존·그룹 경계·보이는 순서 조건을 추가했고 엔지니어링이 모두 수용했다. 마지막 수신도 서로 확인했다.

선호 계약과 구현 순서는 합의했으나 실제 parser/view 구현, 동일 원고 시안, 정확한 DOM·격자·서체/면적·locale·복합 그룹 범위, 제품 회귀·모바일 실기는 아직 미확인이다. 이번 회의는 방향 합의 완료이며 실제 제품 복원 완료가 아니다. 제품 구현·기존 원고 변경·Git 전달은 수행하지 않았다.
