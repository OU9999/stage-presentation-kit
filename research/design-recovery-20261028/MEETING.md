# DevDay 디자인 의도 복원 — 두 팀 직접 회의

2026-10-28 · 총괄 `/root` 기록 · 기준 HEAD `cdb88b4`

사용자는 새 Markdown 발표에서 기존 OpenAI DevDay스러운 디자인이 사라졌다고 지적하고 디자인팀·엔지니어링팀의 내부 회의 결과를 요청했다. 디자인 실무자2명·매니저가 먼저 시각/작성 초안을 작성했고 엔지니어링 실무자2명·매니저가 구현 경계와 실제 재현을 검토했다. 그 뒤 두 매니저가 서로 직접 제안·반례·수정·수신 확인을 진행했다. 제품 구현·현재 parser 지원 구문과 이번 미구현 설계 합의는 구분한다.

근거: [디자인 종합](design/synthesis.md), [엔지니어링 종합](engineering/synthesis.md), [현재 화면 비교](comparison.html), [현재 API 실제 재현](engineering/evidence/view-probe.json).

## R1 — 원인과 복원 구조

**디자인 제안.** 검정 무대와 팔레트는 남았지만 일반 Markdown에서 장 역할과 면적·정보량 변화를 선택하는 연결이 없다. 기본 조판을 개선하고 같은 본문에 작은 시각 선택을 추가한다. 모든 제목을130px로 만드는 안, 이미지 상한을 무조건 해제하는 안, 모든 원고를 기존20양식 JSON으로 다시 쓰게 하는 안은 각각 표/코드·삽화/근거·작성 중복 반례로 기각한다.

**엔지니어링 반례와 수정.** 현재 후보 `stage-view`는 literal 문단이 되며 H1 앞에 두면 제목 승격까지 막는다. 모델에 미지의 view 키가 통과해도 app가 읽지 않는다. 따라서 parser 인식·명시 schema·노드 binding·실제 renderer 연결을 함께 설계해야 한다. 현재 `heading? + blocks`를 단일 내용 권위로 재사용하고 view는 참조만 추가한다. 기존 message/bento 클래스·고정 슬롯을 일반 AST에 바로 덮어쓰면 호환과 내용 보존을 해칠 수 있으므로 토큰·위계·매체 표면을 재사용하고 새 표현은 blocks 경계로 격리한다.

**디자인의 수용·재수정.** 새 blocks view 격리를 수용했다. canonical URI 보존은 현재 정상적인 발행 URL 변환을 막는 요구로 확대하지 않고 원고 URI/출력 복사·resolver 경계로 좁혔다. 빌드 전면 재작성은 복원의 전제에서 뺐다.

**상호 합의·수신 확인.** 두 매니저가 위 원인과 최소 구조를 직접 확인했다. 무주석 기본은 보수적인 조판 개선, 의미 추론 없는 작은 시각 선택을 권고한다. 자동 분류가 필요하면 적용 후보를 제안하는 수준으로 제한한다. 동일 원고·동일 자산·동일 viewport에서 실제 렌더 비교를 마친 뒤 디자인 복원 완료를 판정한다.

## R2 — 작성 계약·이행·시각 인수 조건

**엔지니어링 선호안.** 작은 directive를 내용 AST와 분리하고 현행 heading+blocks에 참조만 더한다. 명시 선택의 부적합을 조용히 다른 구도로 대체하지 않는다. pair는 한 표와 한 문단의 제한 shape로 시작하고 editorial은 H2 그룹과 대표 하나를 원본으로 삼는다. profile을 프로젝트에서 한 번 선택해 이행하며 자동 원고 수정이나 추천 UI를 필수로 만들지 않는다.

**디자인의 반례·수정 요청.** pair에서 큰 값2개만 남기면 header·rich inline·출처를 발표에서 숨기게 된다. 원표와 큰 값을 동시에 표시하면 같은 셀을 중복 읽는다. 표시 전용 값을 Number로 바꾸면 N/A·선행0·약24·원문 단위가 달라질 수 있다. C안의 뒤쪽 대표 그룹을 앞으로 옮기면 실제 보이는 순서와 키보드/DOM/read 순서가 어긋난다. 공통 안내·출처의 결합 범위도 자동 추정하면 안 된다.

**수정 합의.**

| 항목 | 두 팀이 상호 수신 확인한 선호 계약 |
| --- | --- |
| 작은 선택 | 장의 첫 내용 앞에 단독1줄로 쓴다. code/인용 속 예문과 구분하고 첫 H1·원줄 위치를 유지한다. `stage-view` 표기와 message/evidence/media/pair/editorial 이름은 미구현 설계용 가안이다. |
| 명시 오류 | legacy 혼용·중복·미지키/enum·잘못된 binding/primary는 source:line 오류로 알려 마지막 정상 산출물을 유지한다. silent fallback으로 선택을 바꾸지 않는다. |
| 무주석 기본·이행 | 프로젝트 profile을 한 번 opt-in하고 무선택 기본 조판 개선과 선택1~2장의 역할 개선을 별도 비교한다. 무주석 원고를 자동 message로 바꾸거나 원고를 자동 수정하지 않는다. 역할 추천 UI는 필수 구현이 아니다. |
| pair 입력 | 대상/값/단위의 한3열 표·정확2개 데이터 행·바로 뒤 출처/범위1문단의 제한 shape를 우선한다. 모호한 추가 표/열/설명은 진단하고 일반 본문 경로를 안내한다. |
| pair 표시 | header의 rich children·모든 셀·출처/가상 성격이 발표에서도 실제 텍스트로 각1회 보이고 접근되어야 한다. read나 aria에만 남기거나 원표+큰 값으로 중복 표시하면 실패다. raw 표시가 기본이며 연산·단위/비율 추정은 하지 않는다. 빈 단위는 그대로, 빈 값은 진단한다. 세부 locale/값 허용 규칙은 후속 명세다. |
| editorial 입력 | H2부터 다음 H2 전까지를 그룹으로 묶고 대표 H2 바로 앞에 primary marker를 정확1개 둔다. 첫 H2 전 안내는 공통 내용, 마지막 H2 뒤 문단은 마지막 그룹에 속한다. 공통 출처를 자동 추정하지 않는다. |
| editorial 표시 | 대표는 원위치에서 면적/위계만 바꾼다. 보이는 읽기 순서·DOM·키보드·read 순서를 유지하고 실제 자산의 자체 면을 살린다. 자료나12칸을 만들어 채우지 않는다. |
| 완료 판정 | 같은 원고·자산·viewport의 현재/기본개선/선택1~2장 버전을 비교한다. 의미 노드의 누락/중복0, 전체보기의 역할·밀도 변화, 390px read, source 진단·build/reload·복제·legacy 회귀를 함께 확인한다. |

엔지니어링 매니저가 디자인의 수정 요청을 수용해 직접 회신했고 디자인 매니저가 최종 수신을 확인했다. 양측 모두 위 계약을 종합·검수 문서에 반영하기로 했다.

## 구현 순서와 후속 결정

1. 기존 원고와 같은 자산의 비교 기준을 만들고 일반 본문 기본 조판을 개선한다. 새 선택을 인식하는 parser·명시 검증·내용 참조·scoped renderer를 함께 연결한다.
2. 선언/넓은 자료/주역 미디어를 한두 장만 선택해 기존의 크기·면적·여백 변화가 돌아오는지 실제 렌더한다. 본문/출처는 그대로 유지한다.
3. pair와 H2 기반 editorial을 같은 Markdown에서 표현하는 경로를 검증한다. 세 역할만으로 C안·두 수치까지 복원 완료라고 보고하지 않는다. 기존 정밀20양식은 호환 경로로 유지한다.
4. 다른 주제 두 원고·긴 한국어·표/코드/미디어·전체보기·발표자·모바일 읽기를 통과한 후 디자인 복원 완료를 판정한다.

실제 DOM/헤더 연결·폰트/격자/면적 수치·복합 그룹/매체의 지원 한도·세부 locale/값 허용 규칙은 동일 원고 시안과 구현에서 정한다. 이 회의는 미래 구문이 현재 작동하거나 복원 시각 검증을 이미 통과했다는 뜻이 아니다. 제품·기존 원고·Git HEAD/배포는 유지하며 이번 결과는 검토/설계다.
