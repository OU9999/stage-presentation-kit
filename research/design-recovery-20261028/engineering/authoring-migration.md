# Markdown 작성 부담과 디자인 복원 이행안

2026-10-28 · `/root/engineering_manager/performance_auditor` · 기준 `cdb88b421d5a2fc018fe0269713e1ba16d4d8b20`

## 판단

**기본 Markdown의 화면을 개선하고, 한두 장의 시각 선택만 추가하는 경로를 우선한다.** 기존 20양식 JSON은 정밀 호환 경로로 유지하되 큰 선언·근거·미디어를 얻기 위해 일반 원고를 다시 쓰게 하지 않는다. 다만 `message/evidence/media` 세 역할만으로 두 수치와 C안 편집 요약이 복원되지는 않는다. 단일 원고의 표·자료 그룹을 참조하는 별도 선택 계약이 필요하다. 아래 구문·schema·자동 범위는 전부 **미구현 회의 가안**이며 제품 변경이나 채택 확정을 뜻하지 않는다.

## 현행 작성 경로와 부족

| 현재 가능한 경로 | 실제 비용과 한계 | 복원안에서 유지/변경할 것 |
| --- | --- | --- |
| 일반 Markdown → blocks | 첫 의미 H1·본문 AST를 보존하지만 [parser](../../../scripts/markdown-document.cjs#L142)와 [app](../../../app.js#L427)이 같은 blocks 흐름으로 연결한다. [blocks.css](../../../blocks.css#L2)는 70px 제목·30px 본문·이미지230px 상한을 공통 적용한다. | 문법·내용 권위는 유지. 같은 흐름만 제공하는 화면 계약을 보완한다. 글자 크기 하나가 원인 전부는 아니다. |
| 명시 stage layout/JSON → 기존 양식 | [legacy 분기](../../../scripts/markdown-document.cjs#L82)는 기존 필드 어댑터로 다시 파싱한다. metric-pair는 items의 value/unit/label, C bento는 preset/variant/type별 필드·현재 고정 슬롯을 알아야 한다. 일반 표·코드·혼합 본문을 그대로 view만 바꾸는 API가 아니다. | 기존 원고와 정밀 표현을 유지. 일반 MD를 JSON과 두 번 관리하는 기본 경로로 삼지 않는다. |
| 디자인의 작은 stage-view 힌트 | 현재 지원되지 않는다. A의 [실제 재현](evidence/view-probe.json)에서 H1 앞 주석은 literal 문단이 되어 첫 H1 승격까지 막고, H1 뒤에서도 본문으로 남았다. | 새 제어 문법을 인식·검증하고 내용 AST와 분리해야 한다. 단순 주석 삽입·view 속성 추가만으로 작동한다고 안내하지 않는다. |
| 발표와 read | [builder](../../../scripts/stage.cjs#L174)는 같은 deck을 content.js로 쓰고 index/read가 이를 읽는다. [참조 처리](../../../scripts/stage.cjs#L69)는 AST/legacy URI를 발행 URL로 바꾼다. | read의 전체 의미·순서·링크/alt는 계속 보존. URI 변경은 MD 원본 수정이 아니지만 새 canonical 모델은 원고 URI와 발행 URL resolver를 구분한다. |

root [observations.json](../evidence/observations.json)과 [비교 화면](../comparison.html)은 기존4장/새3장의 현재 출력을 확인한 근거다. 동일1440×1000이지만 원고·주제가 달라 복원안 효과의 통제 A/B가 아니다. 기존 표지의 실제 양식은 cover/130px이며 기존 visual 제목74px도 있으므로 모든 제목을130px로 키우는 해법은 근거와 맞지 않는다. footer는 노드 존재와 가시성을 구분한다. quiet의 footer 생략이 출처·가상 자료 안내 생략을 허용하지 않는다.

## 최소 계약: 내용은 한 번, view는 참조만

제안 흐름은 `원고 → 제어 힌트 분리 + canonical AST → view 적합성/노드 binding → 발표 표현`이며 read는 같은 canonical AST를 문서 흐름으로 렌더한다. canonical AST는 첫 H1을 포함한 내용 순서·inline·표·코드·이미지/링크·source 위치를 한 번 보존한다. 현재 `heading? + blocks`의 노드를 그대로 참조하는 최소안도 가능하며 내용 트리를 중복 생성할 필요는 없다. view는 `kind`와 해당 노드/그룹 참조만 갖고 value·label·출처·본문을 복사해 별도 작성 권위로 만들지 않는다. node 참조는 한 build 안의 식별이며 영구 slide ID를 선행 요구하지 않는다.

- 힌트는 정확한 위치·허용 값·중복·잘못된 조합을 검증한다. code fence/일반 예문 속 비슷한 문자열은 제어 힌트로 해석하지 않는다. 미지원/부적합 선택은 source:line과 복구 방법을 알려 마지막 정상 산출물을 유지한다. 조용히 무시하거나 내용 일부를 버려 통과시키지 않는다.
- `presentation view`와 현재 HTML의 `data-view=read/present` 모드, 미지원인 공개 `role/notes` 기능을 구분한다. 디자인 힌트가 노트·부록 공개 기능을 도입하지 않는다.
- 발표 DOM의 원문·논리 순서를 유지한다. 의미상 같은 노드를 view용 wrapper에 넣을 수 있지만 원표와 큰 수치를 동시에 중복 읽게 하거나 대표 그룹을 DOM 앞쪽으로 옮기지 않는다. read는 원표/원그룹·문단을 그대로 렌더한다.
- 기존 styles/visual의 토큰·큰 주장·값/단위/라벨 위계·매체 자체 표면을 재사용하되 새 blocks view에 한정한다. 전역 `.slide-title`, bento preset 또는 quiet 규칙을 한꺼번에 바꾸지 않는다. 현재 model은 주입한 view 속성을 통과시켜도 소비하지 않으므로 명시 schema와 app/view renderer 연결이 필요하다.

## 세 역할의 범위와 적합성

| 선택 가안 | 최소 입력·효과 | 부적합 반례 |
| --- | --- | --- |
| 무선택 기본 | 보수적 본문 흐름·읽기 폭·자료 면적 개선. 모든 장 주석 불필요 | 표/이미지의 존재만으로 chart·hero·분할을 자동 선택하지 않음 |
| message | 첫 H1을 주역으로, 보충문·출처·가상 안내를 읽을 수 있게 유지 | 제목+인용 중 주역 모호, 긴 문단/표 동반. 제목을 크게 한 뒤 나머지를 감추지 않음 |
| evidence | 원표·코드·자료가 읽을 면적 확보 | 코드/표를 무조건2열로 분할하거나 숫자를 추출하지 않음 |
| media | 작성자가 선택한 실제 화면/이미지의 큰 면적, UI는 contain | 여러 이미지 중 대표 추정, 임의 crop, alt를 캡션처럼 강제 표시, 목록 밀어내기 |

이 선택은 한 주장/자료/화면의 무대를 제공한다. 두 값의 관계나 여러 결과물의 편집 단위는 입력에 별도로 명시되지 않으므로 세 역할만으로 C안/두 수치 문제까지 해결됐다고 보고하지 않는다.

## 두 수치: 표 한 번과 출처 한 번

선호 후보는 **명시 수치 view + 정확히2개 데이터 행의 대상/값/단위 표 + 경계가 분명한 출처/범위 문단**이다. 아래 제어 표기는 이름을 비교하기 위한 가안이며 현재 지원 구문이 아니다.

```markdown
<!-- stage-view: pair -->
# 연결한 결과

| 대상 | 값 | 단위 |
| --- | --- | --- |
| 모아 둔 아이디어 | 24 | 개 |
| 연결한 작업 | 6 | 가지 |

양식 설명용 가상 수치 · 실제 측정 결과가 아닙니다.
```

발표는 지정한 두 셀의 원문을 값/단위/라벨 위계로 보여 주고 read는 원표와 문단을 유지한다. **표시 문자열 확대와 숫자 파싱/연산은 별개**다. 계산이 필요 없는 초기안은 원문 표시를 우선하며 `9,876,543.2`·`0`·선행0·음수 부호를 Number로 변환해 다시 쓰지 않는다. 수치 적합성을 검사한다면 허용하는 표기만 명시적으로 검사하고 raw 문자열은 그대로 둔다. 통화/백분율/기간을 추정하거나 합계·비율·좋음/나쁨을 계산하지 않는다.

표현 변화는 행을 두 값의 배치로 바꾸는 범위다. **원표 header(대상/값/단위)·모든 셀 원문/rich inline·출처/가상성격은 발표에서도 각각 한 번 실제로 표시되고 접근 가능해야 한다.** header나 설명을 read에만 두거나 aria-label로만 대체하면 원문 숨김을 다시 도입한 것이므로 실패다. 정확한 DOM/표 접근성 표현은 후속 설계로 남기되, 원표와 확대값을 둘 다 중복 렌더하는 방식도 피한다.

셀에 `**24**`·링크·각주 성격의 inline이 있으면 원셀 children을 렌더 참조하고 plain 값은 적합성 검사의 파생값으로만 쓴다. 초기 renderer를 text-only로 제한한다면 복합 inline 선택을 source 위치로 진단해야 하며, 문자열 추출로 의미를 몰래 없애면 안 된다.

| 반례 | 선택 계약의 처리 가안 |
| --- | --- |
| 3행·여러 표·추가 열·헤더 불명확 | 정확히 어느 표/열인지 진단. 첫2행만 취하거나 남는 열을 삭제하지 않음 |
| 빈 값·N/A·대시 | 0으로 채우지 않음. 일반 표는 그대로 유효하고 pair 적합성은 별도 진단 |
| `24개` 값+`개` 단위·`약24`·`2~3`·범위/각주 포함 값 | suffix를 떼거나 parseFloat로24/2를 만드는 것 금지. 원문을 그대로 표시할 허용 범위 또는 pair 부적합을 명시적으로 결정해야 함 |
| `건/주`·`명/100명`·서로 다른 단위 | 단위를 문자열로 보존하고 양쪽을 임의 비교/정규화하지 않음. 긴 단위·라벨은 줄바꿈/넘침 검증 |
| 출처 문단2개·표 사이 문단·여러 시점/대상 | 인접 첫 문장을 자동으로 출처로 단정하지 않음. 초기 shape를 한 표+한 문단으로 제한하거나 그룹 경계/참조를 추가하는 대안 중 회의에서 결정 |
| 가상 수치/설명용 예시 | 그 성격을 발표에서도 실제로 읽을 크기로 유지. footer 숨김과 함께 사라지면 실패 |

비교 후보는 (1)표+한 문단의 제한 shape, (2)명시 그룹 경계 안의 표+여러 설명, (3)기존 metric-pair JSON이다. (1)은 가장 작지만 복합 출처를 담기 어렵고 (2)는 유연하나 구분 문법이 늘어난다. (3)은 즉시 가능한 호환 경로지만 표/JSON 동시 재입력을 기본으로 만들면 작성 요구를 놓친다. pair의 정확한 값 허용 문법·출처 경계·오류/경고 severity는 미결정이다.

## C 편집 요약: H2 자료 그룹과 대표 하나

선호 후보는 **H2부터 다음 H2 전까지의 image/blockquote/문단을 한 관련 자료 그룹으로 참조**하고, 대표 그룹 하나만 작성자가 표시하는 방식이다. 다음 표기도 미지원 가안이다.

```markdown
<!-- stage-view: editorial -->
# 관찰을 다음 행동으로

<!-- stage-primary -->
## 완성한 기록

![완성 문서](./report.png)

관찰과 다음 행동을 같은 문서로 묶었습니다.

## 다음 행동

> 첫 화면에서 해야 할 일을 먼저 보여 줍니다.

다음 검토에서 같은 질문으로 확인합니다.
```

대표 표식을 그룹 바로 앞에 두면 제목/파일명에서 대표를 추론하지 않고 그룹 이동 시 선택도 함께 옮길 수 있다. 대안인 `primary=2` 같은 순번 선택은 주석 하나로 짧지만 앞 그룹 삽입 시 가리키는 대상이 조용히 달라질 수 있다. 제목 문자열/새 수동 id 참조는 rename·중복 제목 부담이 있다. 정확한 marker·그룹 경계는 아직 미결정이다.

발표는 대표의 면적과 매체 자체 면을 살리되 **원고/DOM/키보드/read 순서는 유지**한다. 뒤의 대표를 앞쪽 grid로 당겨 읽는 순서까지 바꾸지 않는다. read는 H2와 원그룹 전체를 그대로 보여 준다. H2 이전/이후의 전역 설명·출처도 누락하지 않는다. 대표0/2개, 빈 H2, 이미지+인용의 주역 모호, 동일 이미지 재사용, 그룹 수 증가·긴 본문은 source 위치로 적합성을 진단한다.

고정12칸·가짜 수치/문서/UI·자료 자동 축약은 요구하지 않는다. 현 [bento preset](../../../deck-model.js#L28)의 고정 슬롯을 그대로 이 후보에 적용하면 적은 자료를 채워 넣는 과제가 된다. 기존 C안의 위계/표면 원리는 재사용하지만 자유 그룹 renderer가 현재 C안과 같은 결과를 낸다는 증거는 없다. 적은2그룹·여러매체·대표가뒤인경우의 실제 시안이 필요하다. 이번 단순 그룹이 정량 visual·복잡한 도식까지 대신한다는 주장도 하지 않는다.

## 무주석 원고의 이행·반대안·검증

권고는 새 기본 디자인 profile을 프로젝트에서 한 번 선택하고 기본 원고의 읽기 폭·자료 면적을 개선한 뒤, 기존6장 중 선언1장과 주역 화면1장 정도에만 선택을 더하는 것이다. profile 이름/버전/설정 위치는 제안이다. 현재 config/원고를 자동 재해석하거나 모든 장의 주석 작성을 요구하지 않는다. legacy20양식과 기존 blocks 기준을 보존할 이행 버전을 두고, 변경 원고·힌트·출력 차이를 미리보기에서 검토한다.

| 반대안 | 채택하지 않는 이유 |
| --- | --- |
| 모든 제목130px·모든 이미지 상한 일괄 해제 | 표/코드/설명 면적과 긴 한글을 해치고 역할별 밀도 차이를 만들지 못함 |
| 전부 legacy JSON으로 이행 | 같은 본문·표·이미지·출처 중복 작성과 의미 손실 위험. 선택적 호환 경로로만 유지 |
| 일반 표→chart·숫자→hero·목록→범주 자동 추론 | 작성자가 명시하지 않은 사실/관계/역할을 만들어냄 |
| 첫/마지막 장 자동 cover/closing·H1-only 자동 적용 | 위치/짧음만으로 의도 확정 불가. 후보 제안은 가능하지만 묵시적 적용은 별도 승인 없이 하지 않음 |
| 본문은 read에만 남기고 발표에서 삭제/요약 | 가상 안내·출처·화자·근거가 달라짐. 내용 보존 계약 위반 |
