## 결론과 재사용 범위

현 AGENTS의 디자인 선독·현재 화면·`--require-approved` 세 규칙은 유효하며 폐기할 이유가 없다. 좁은 보완점은 **DESIGN 안의 핵심 방향을 현 발표 디자인 절의 첫 항목에 직접 요약하고, 위임·복구 때 그 방향과 현재 검수 상태가 함께 전달되도록 하는 것**이다. 내용 참고자료의 스타일이 기본값을 바꾸고, 기술 검사만으로 완료를 설명했던 기존 실패 경로에 대응한다. 문구를 늘리거나 파일 이름을 바꾸는 것만으로 준수를 보장할 수는 없다. 최종 통합 결정에 따라 기존 WORK_LOG 절과 사용자 제공 로그4항을 파일 맨 앞의 원문 prefix 그대로 보존하고, 발표에 한정한 위임·복구의 추가 문구는 디자인 절에 둔다. 파일 전체 절 순서는 바꾸지 않는다.

기존 [확정안](../design-governance-20261102/research/RESEARCH.md)과 [문서 운영 조사](../design-governance-20261102/research/documentation-practices.md)를 읽어 재사용했다. 이번에는 같은 시각 문헌·영상·26장 감사를 다시 조사하지 않았다. [DESIGN](../../DESIGN.md), [검수 안내](../../DESIGN-REVIEW.md), 현 AGENTS·WORK_LOG 상단과 작성 진입점을 직접 대조했다. 기존 연구의 “DESIGN 210행, AGENTS 로그4규칙”은 **보완 전 상태의 관찰**이다. 현행 DESIGN은 145행이며 AGENTS는 로그4+디자인3규칙이므로 과거 관찰을 현재 사실로 되풀이하지 않는다.

## 현 7규칙의 gap과 최소 변경 위치

외부 공식 사실은 “문맥을 작게·명확하게 전달하고 필요한 근거를 다시 읽는다”는 운영 사례다. 아래의 Stage 기준, 현 디자인 절 첫 항목의 핵심 요약, 인계 항목과 검사 시나리오는 **이 프로젝트의 실패 이력에 근거한 판단**이다. 외부 업체가 발표 디자인의 정답이나 AGENTS 필수 문구로 정한 사실이 아니다.

| 현 규칙 | 판정 | 최소 보완 또는 유지 이유 |
| --- | --- | --- |
| 1. 목표·현재 지침·담당·미완료·결정을 WORK_LOG 하나에 기록 | 유지 | 현재 상태의 단일 출처로 충분하다. 별도 상태 로그·새 양식을 만들지 않는다. |
| 2. 새 지침을 진행 작업과 대조·갱신 | 유지 | 최신 사용자 지시의 반영을 맡는다. 매번 재승인을 묻는 규칙으로 바꾸지 않는다. |
| 3. 결정·결과 기록, 영향 담당자에게 직접 통지 | 원문 유지 | 일대일 전달은 이미 요구한다. 발표 위임에 필요한 내용은 디자인 절의 조건부 항목으로 명시한다. |
| 4. 압축·인수인계 후 WORK_LOG 재독 | 원문 유지 | 상태 복구만으로 시각 기준·미승인 범위가 들어왔다고 보장하지 않는다. **진행 중인 발표 작업일 때** DESIGN 관련 절과 현 검수 상태도 확인하는 연결은 디자인 절에 둔다. |
| 5. DESIGN 선독, 변경·보존 범위, 사용자 우선·입력 문법 | 유지+앞 핵심 | 현재 연결은 필요하고 충분히 유효하다. 다만 기준 전문을 열기 전에도 놓치면 안 될 Stage 방향과 내용 출처의 권한 경계를 바로 앞에 짧게 둔다. |
| 6. 현재 원고·스타일·runtime·자산의 실제 화면·이유, 기술/시각 분리 | 유지 | 현재 실패에 직접 대응한다. hash/manifest/명령 전체는 검수 안내에 남긴다. |
| 7. 승인 보고는 require-approved 통과한 명시 범위, needs-changes 구별 | 유지 | 보고의 의미를 명시한다. 일반 check 통과를 승인으로 잘못 확대하지 못하게 한다. |

권고하는 정확 문구와 위치는 아래와 같다. 실무자는 AGENTS·DESIGN·WORK_LOG를 편집하지 않으며 엔지니어링팀이 채택 범위를 결정한다.

1. 기존 `# 작업 로그 관리` 절과4항을 AGENTS 파일 맨 앞의 원문 prefix 그대로 둔다. 현 `# 발표 디자인 작업` 절의 첫 항목으로, 선독 규칙 바로 앞에 다음 **한 핵심 규칙**을 추가한다. 절 전체를 재배치하지 않는다.

   > 별도 디자인 변경 지시가 없으면 Stage의 검정 바탕·큰 타이포·넓은 여백·한 시각 중심을 유지한다. 장의 역할에 맞는 밀도·구도 변화와 실제 자료의 고유색·표면을 보존하며, 내용 참고자료의 색·레이아웃을 기본값 변경 권한으로 삼지 않는다.

2. 디자인 절에 다음 위임·복구 항목을 추가한다. 기존 로그4항에는 덧붙이지 않는다. 완료 조건을 전달하여 기술 검사만으로 끝나는 해석을 줄이고, 일반 작업에서 DESIGN 전체를 매번 읽으라는 의무를 만들지 않는다.

   > 발표 작업을 위임할 때는 최신 지시·목표·변경/보존 범위·적용할 디자인 핵심과 예외·현재 검수 상태·완료 조건·미완료 담당과 다음 행동을 직접 전달한다. 압축·인수인계 후 진행 중인 발표 작업을 재개할 때는 WORK_LOG와 DESIGN의 관련 절, 해당 범위의 현재 검수 상태를 확인한다.

3. 기존 선독 규칙의 “발표를 작성·수정하기 전에”를 “발표 원고·자산·공통 스타일/runtime을 작성·수정하기 전에”로 구체화한다. 공통 렌더 입력의 변경을 디자인 영향 밖으로 오해하지 않게 하는 범위 명료화다.

초기 검토의 디자인 절 전역 앞 배치안은 준수 개선 효과가 미측정이고 이 보강에 불필요하므로 철회했다. 현 디자인 절 첫 항목의 직접 핵심으로 오류 감지를 돕고자 하지만 DESIGN과 요약이 달라질 유지 위험도 생긴다. 따라서 전체 색상표·역할표·타임코드·검수 schema는 복제하지 않는다. “검정 배경만 맞추면 승인”이라는 축소를 막기 위해 밀도·구도와 실제 자료 고유면까지 같은 요약에 포함한다. 이 장단점은 이 프로젝트의 운영 판단이며 효과 크기를 측정한 실험 결과는 아니다.

## 위임·복구 때 필요한 최소 내용

새 인계 파일이나 필드를 강제하지 않는다. 기존 직접 메시지와 WORK_LOG의 최신 항목으로 다음을 전달하고 받는 사람이 필요한 원문을 읽으면 된다.

- 최신 지시와 이번 산출물·소유권: 발표 수정인지, 지침 연구인지, 교정 명세인지 구분한다.
- 변경할 범위와 보존할 의미·자료: 원고·그림·대본·원문 보관을 의미 없이 삭제하지 않는다.
- 적용할 디자인 핵심과 정본 경로, 이미 허용된 예외: 내용 출처만으로 테마 권한을 만들지 않는다. 이미 승인·위임된 변경을 다시 질문하지 않는다.
- 현재 화면·판정의 범위, 완료 조건과 남은 담당·다음 검수: 정지화면21승인/5개선필요를 전체 제품 승인으로 바꾸지 않는다. 근거가 stale이면 재확인한다.

새 하위 담당자는 부모의 기억이나 파일 존재만 믿지 않고 현재 로그·관련 DESIGN 절·담당 범위를 확인한다. 인계자는 전체 대화·문헌을 복사하지 않고 결정과 미완료를 선별한다. 이 규칙은 문맥 유지 책임을 명확히 하지만 실수0을 보장하지 않는다.

## 직접 인계와 남은 작업

독립 초안은 공식 고정본문·시점·현7규칙 대조를 먼저 마쳤다. 이후 실무 A의 [초안](agent-instructions.md) 전문을 직접 읽고 상호 반론했다. A와 매니저가 지적한 앞 배치의 효과 미측정 한계를 수용했다. A의 완료 조건·원고/자산/공통 스타일/runtime 범위 명시를 채택했고, A는 B의 밀도·구도 변화와 자료 고유면을 핵심 요약에 포함하는 반례를 수용했다. 초기에는 로그3에 위임·로그4에 복구를 덧붙이는 대안을 합의했으나, root의 통합 결정으로 그 대안은 철회했다. 이후 root의 최신 배치 결정도 반영하여 WORK_LOG 절과 사용자 로그4항을 파일 맨 앞의 원문 prefix 그대로 유지하고, 현 디자인 절 첫 항목의 핵심 요약과 조건부 위임·복구만 추가하는 안을 최종 권고한다. 전역 절 재배치 권고는 철회했으며 A에게 직접 통지했다. 합의는 [실무 취합](contributor-synthesis.md)에 남긴다.

후속 엔지니어링팀의 구현 여부와 최소 문구 선택은 매니저 확정안을 따른다. 제품·원고·runtime·자산·기존 감사·CLI와 AGENTS·DESIGN·WORK_LOG는 이 담당자가 편집하지 않았다. 본문은 문헌·지침 연구의 결과이며 새 화면 판정·모델 준수율 실험·제품 전체 테스트를 수행한 결과가 아니다. 매니저와 root가 공유한 운영 snapshot의 정확 모델 `gpt-6.1-sol` / `high` / `fork_turns=none`을 사용했으며 이 현재 모델 선택은 10월 정책 근거와 구별한다.
