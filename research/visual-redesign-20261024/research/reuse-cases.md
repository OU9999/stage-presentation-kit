# 다른 주제로 바꾸는 네 가지 수용 사례

2026-10-24 · 리서치 매니저 직접 작성

아래는 가상 서비스의 작업·지원 경험 자료다. 금융 지표나 실제 성과를 사용하지 않는다. **후속 구현에서 그대로 시험할 목표 선언**이며 아직 현재 제품이 이 입력을 지원한다는 뜻은 아니다. `layout: visual`과 작은 `visual` 설정으로 장을 구성하는 방향은 엔지니어링 매니저와 직접 논의했다. 최종 필드명은 구현 계약에서 확정하되, 이 수량과 수정 흐름을 유지해야 한다.

## A. 12주 코호트 없이 7점 추세

```js
{
  layout: "visual",
  title: "작업을 끝내는 흐름이 달라졌습니다.",
  visual: {
    kind: "line",
    labels: ["1주", "2주", "3주", "4주", "5주", "6주", "7주"],
    values: [65, 65, 70, 70, 74, 75, 80],
    unit: "%",
    focus: 6
  },
  notes: "가상 서비스의 주별 작업 완료율. 실제 성과·인과 효과가 아닙니다."
}
```

7개 값은 작성자가 이미 계산한 측정값이다. 이 장을 위해 인터뷰·퍼널·일정·역할 데이터나 W13 메타를 입력하지 않는다. 끝점 강조는 마지막 값 80%에서 나오며 원고의 별도 숫자 필드에 다시 입력하지 않는다. `focus`가 인덱스인지 키인지는 최종 계약에서 명확히 정하고, 선택 영역이 없으면 임의의 서로 다른 항목 합계를 만들지 않는다.

원시 인원에서 계산하려면 `values`를 아래 한 쌍으로 **교체**한다.

```js
numerators:   [78, 91, 91, 112, 111, 135, 136],
denominators: [120, 140, 130, 160, 150, 180, 170]
```

같은 비율 65·65·70·70·74·75·80%가 나온다. 전체 집계를 제공한다면 754/1,050 = 71.8%이며 주별 표시값 평균 71.3%로 대신하지 않는다. 직접 값과 계산 입력을 동시에 주는 모호한 설정은 진단한다. 분모 0이나 누락은 0%로 꾸미지 않고 계산 불가로 남긴다. 단위 `%`가 붙은 직접 값이 전부 발생률인 것은 아니므로 모든 경우를 0–100으로 제한하지 않는다.

## B. 네 범주 대신 지원 문의 다섯 범주

```js
{
  layout: "visual",
  title: "문의는 어디에 모였을까요?",
  visual: {
    kind: "composition",
    labels: ["탐색", "작성", "공유", "설정", "기타"],
    values: [8, 12, 10, 6, 4],
    unit: "건",
    focus: 1
  },
  notes: "가상 지원 문의 40건의 대표 분류. 사용자 발생률이 아닙니다."
}
```

다섯 값 합계 40건에서 20·30·25·15·10%를 계산한다. 사용자는 합계와 비율을 따로 적지 않는다. 범주 하나를 더 쓰려면 라벨·값 한 쌍만 추가하며 네 개라는 기존 개수를 맞추기 위해 서로 다른 범주를 합치지 않는다. 음수 구성비는 의미 오류로 진단하고, 총합 0은 빈 자료로 분명히 표시한다. 문의 건수와 고유 사용자 수를 같은 분모로 바꾸어 말하지 않는다.

## C. 계정 퍼널과 무관한 두 단계 흐름

```js
{
  layout: "visual",
  title: "요청에서 답변까지, 간단하게.",
  visual: {
    kind: "flow",
    items: ["요청 접수", "답변 완료"]
  }
}
```

선형 순서는 배열 자체가 나타낸다. `registered/started/drafted/activated` ID, 프로젝트 공유 정의, 네 단계 수, 인터뷰 원인 참조가 필요하지 않다. 두 요소와 그 사이 관계가 무대에서 충분히 크게 보여야 한다. 이 화살표는 인원·전환 확률·인과 효과를 암시하지 않는다.

## D. 같은 방식으로 다섯 단계

```js
{
  layout: "visual",
  title: "누가, 어디서 다음 행동을 이어갈까요?",
  visual: {
    kind: "flow",
    items: ["문제 등록", "담당 선택", "해결안 작성", "답변 전송", "확인 완료"]
  }
}
```

두 단계 예제에서 `items`만 교체한다. 다섯 단계이므로 웹에서 줄을 나누거나 읽기 모드에서 세로로 펼치는 것은 정상적인 레이아웃 대응이다. 수량을 거절하거나 글자를 계속 줄이는 방식으로 해결하지 않는다. 분기선을 명시하는 확장 입력을 쓰는 경우에만 그 연결의 참조 ID를 검사한다.

## 수정량으로 확인할 편의

| 사용자가 하려는 일 | 목표 조작 | 하지 않아도 되는 일 |
| --- | --- | --- |
| 첫 도표 만들기 | 스타터를 복사하고 한 장의 제목·데이터 블록 수정 | 350줄 코호트 프로젝트 해독·명령 실행·SVG 편집 |
| 7주→8주 | 라벨·값 한 쌍 추가 | 기간 ID·메타·퍼널 끝값 갱신 |
| 5범주→다른 5범주 | 라벨·원시 값 교체 | 합계·백분율·범례 숫자 수동 계산 |
| 2단계→5단계 | `items` 배열 하나 교체 | 여정·인터뷰·과제 ID 동기화 |
| 장을 골라 새 발표 구성 | `slides` 배열에서 필요한 선언만 복사·삭제·재배치 | 고정 12장 전체 생성·관련 없는 자료 입력 |

완료 검증에서는 실제 다른 주제의 `content.js` 하나로 이 네 장을 붙여 넣고 `file://`에서 확인한다. native 제목·라벨과 편집/내보내기, 같은 입력에서 나오는 펼쳐 읽는 표, 390px의 순서와 가독성을 함께 본다. PDF나 인쇄 결과는 이번 수용 기준이 아니다.
