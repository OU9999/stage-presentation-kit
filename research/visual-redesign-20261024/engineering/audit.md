# 웹 발표 작성 구조 감사

2026-10-24 · 직접 검토 `/root/engineering_manager` · 초기 토론 단계

이 감사의 기존 코드·줄 수·실행 결과는 기준 커밋 `ab96f16`을 대상으로 한다. 아래 전용 생성기/데이터 경로는 재설계에서 제거될 수 있는 과거 코드 위치이며 현재 사용 안내가 아니다.

## 결론

현재 예제는 잘못된 숫자를 막는 검증과 특정 가상 실험의 작성 규칙을 한꺼번에 강제한다. 여덟 그림을 SVG 파일로 만들고 그 파일을 이미지 양식에 넣기 때문에 작성 경로와 화면 구성이 함께 굳어졌다. **그림을 발표의 직접 데이터로 받아 같은 무대에서 렌더링하고, 사용자는 content.js 하나를 수정한 뒤 새로고침하는 흐름**으로 바꾸는 것이 우선이다.

PDF 사용 여부와 이 문제의 원인은 구분한다. 이번 감사는 웹 발표를 기준으로 했으며 PDF 생성·출력용 제한을 새 계약의 기준으로 삼지 않았다. 제품 코드는 수정하지 않았다.

## 재사용 실패를 실제로 확인한 사례

[legacy-constraints.json](legacy-constraints.json)은 현재 입력을 복사해 현행 validator를 직접 실행한 결과다. 원본은 바꾸지 않았다.

- 7개 시점: 12개 필수 제약에 걸린다.
- 5개 범주: 합계를 유지해도 4개 필수 제약에 걸린다.
- 2단계 흐름: 노드·path가 4개여야 한다는 오류가 난다.
- 5단계 흐름: 수량과 고정 ID 순서에 걸리며 다섯 번째 ID에는 undefined를 기대하는 오류까지 나온다.
- 실제 업무 자료: fictional=false가 거절된다.

이것들은 웹에서 그림을 그리는 데 필요한 제약이 아니다. 새로운 계약의 최소 수용 사례는 [입력 제안](contract-proposal.md)의 7점·5범주·2/5단계다.

## 구현 선택

우선은 공통 visual 어댑터와 DOM 기반 HTML/SVG 렌더러를 권고한다. 이미 app.js가 createElementNS로 아이콘·도형을 만들고 있어 같은 실행 방식으로 연결할 수 있다. [MDN createElementNS](https://developer.mozilla.org/en-US/docs/Web/API/Document/createElementNS) 본문을 새로 확인했으며 SVG namespace의 요소를 DOM으로 만들 수 있다. 별도 XML 문자열 파서·SVG 파일 생성·React 전환은 전제조건이 아니다.

Apache ECharts도 실질적인 대안으로 한정 검토했다. 공식 문서는 필요한 차트·component만 등록하는 번들과 [SVG/Canvas 렌더러 선택](https://echarts.apache.org/handbook/en/best-practices/canvas-vs-svg/), [부분 import 구성](https://echarts.apache.org/handbook/en/basics/import/)을 제공한다. React가 필수인 구조는 아니다. 로컬 배포 번들을 키트에 포함하는 접근도 검토할 수 있으나 이번 감사에서 설치·번들 크기 측정·성능 비교는 하지 않았다.

현재 권고는 라이브러리의 일반적인 우열이 아니라, 디자인 프로토타입의 배경 없는 line·HTML funnel·직접 라벨 matrix와 간단한 flow를 한 계약으로 구현할 수 있다는 판단이다. 복수 축·대규모 상호작용·복잡한 label layout이 실제로 필요해 직접 renderer가 커진다면 같은 visual 입력 뒤에 ECharts 어댑터를 붙일 수 있다. 사용자에게 두 엔진의 옵션을 모두 익히게 하지 않는다. 최종 선택은 프로토타입·재사용 사례와 대조한다.

공식 문서는 TaskSpace 9의 매니저 전용 p2에서 직접 확인했다. 기술 도입·제품 구현·새 테스트 작성·브라우저 제품 검증을 완료한 단계는 아니다.
