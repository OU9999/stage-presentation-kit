# 본질·동기·다양한 사례의 제품 반영 계약

2026-10-29 · manager 확정안. 근거와 직접 논쟁은 [MEETING](./MEETING.md), 40행의 제목·핵심·출처·권고 구도는 [SYNTHESIS §4](./SYNTHESIS.md#4-권고40장과182분-경로), 기계로 읽는 진행은 [core-route.json](./core-route.json)을 따른다. 이 계약은 원문·사례 연구를 제품 원고로 옮기는 범위다. 실제 LLM 실행·조직 도입·청중 효과의 완료를 뜻하지 않는다.

## 고정할 설명과 경계

첫 부분에서 다음 순서를 실제로 보여 준다: **정의 → 해결하려는 반복 문제 → 저장되는 개념·비교·종합 → LLM과 사람의 역할 → 구조와 ingest/query/lint → 서로 다른 세 사례**. 공용 노트 비유는 정의를 대신하지 않는다. 없애거나 한 장/짧은 말로만 보조한다.

발표용 정의는 ‘LLM이 원자료 사이의 개념·비교·연결을 Markdown 위키로 작성하고 계속 갱신해, 다음 질문이 이전 정리에서 출발하도록 하는 지식관리 방식’이다. 특정 완제품·공식 표준으로 표시하지 않는다. 등장 동기는 저자가 풀려는 반복 재종합·유지 부담으로 설명한다. 모든 RAG·현재 파일 업로드 제품에 축적이 불가능하다고 일반화하거나 역사적 최초성을 주장하지 않는다.

LLM은 파일을 다루는 에이전트 환경에서 위키를 실제 작성·유지하는 역할이다. 사람은 자료·범위·질문·분석 방향을 고르고 필요한 결과를 검토한다. 수동 claim 승인·ADR·pending·Node 반영은 우리가 택한 운영/실습 방식이며 패턴의 필수 정의가 아니다.

5/8장과 대본에 파일과 현재 문맥의 경로를 짧게 넣는다. 에이전트가 관련 raw/wiki를 찾아 읽어 현재 문맥에 넣고 도구로 Markdown을 수정한다. 다음 질문은 저장된 페이지를 다시 찾아 읽는다. 파일 저장으로 모델에 영구 기억이나 자동 파일 접근이 생긴다고 묘사하지 않는다. 파일 갱신과 가중치 학습의 구별은 한 장/짧은 문단이면 충분하며 RAG/LoRA 강의로 주제를 다시 바꾸지 않는다.

원자료는 보존, 위키는 갱신, schema는 전체 작업을 안내하는 규칙으로 그린다. ingest는 새 요약만 만드는 일이 아니라 기존 개체·개념·비교·잠정 종합도 갱신한다. query는 관련 위키를 읽고 유용한 답을 페이지로 남기는 귀환을 보인다. lint는 낡은 설명·상충·고립·빠진 개념/연결을 점검한다. 고정된 선형 폴더 순서나 모든 문제의 자동 발견을 약속하지 않는다.

## 사례와 근거 수준

- **소설 독서 10~12장:** 1장과 3장의 메모, 인물·신뢰 주제·장 요약, 배신에 관한 질문 답을 연결한다. 서하의 자기 설명을 확정 동기로 바꾸지 않고 읽은 범위·미확인을 유지한다.
- **고객 요구 13~15장:** 월말 수동 다운로드와 매일 자동 수집을 비교하고 새 회의로 상태·FAQ를 갱신한다. 요구를 지우거나 출시 약속으로 바꾸지 않는다. 후속 질문은 고객 B에게 지금 무엇을 말할지다.
- **강의 메모 16~18장:** 회귀/회귀트리의 공유 개념에서 분류트리의 새 기준과 비교로 확장하고 질문의 종합을 저장한다. 이전에 없던 오류를 지어내 교정했다고 설명하지 않는다.

각 사례는 **입력 → 여러 위키 페이지의 변화 → 후속 질문에서 읽을 것 → 새 답의 저장/새 자료에 따른 재갱신**이 보여야 한다. 세 사례는 ‘가상 자료로 만든 적용 예’라고 화면과 대본에서 밝힌다. 입력·전후파일·질문 저장의 자세한 문장은 연구 examples 3개를 따른다.

원저자 제시 용도/관찰한 공개 구현/논문 실험/우리가 만든 적용 예라는 네 라벨을 구별한다. Microsoft 사례는 고정 코드에서 확인한 등록·LLM enrichment·query 경로만 설명하며 `/save` handler가 안내만 하는 한계를 유지한다. 설치·실행 성공이나 Microsoft 조직 도입으로 말하지 않는다. 코드 위키 변형의 해시 차이는 변경 신호이지 의미 오류/자동 교정 인증이 아니다.

논문은 §3의 탐색 설계와 §6의 실제 평가를 구분한다. 실제 wiki arm은 59문항 전체에 같은 고정 section과 질문 대상 자료가 주어져 문맥 선택 실패 단계가 없다. RAG는 21벡터 중 5개를 검색한다. 따라서 같은 코퍼스/LLM이라는 이유로 표현만의 공정 비교라고 하지 않는다. 단일 코퍼스·답변 1회·LLM judge·비용 미측정이며 학생 학습성과 실험도 아니다. 발표에는 수치 경쟁 차트를 넣지 않고, 수치는 학습자료에서 이 조건과 함께만 다룬다.

저자의 유지비·누락·규모에 관한 낙관적 표현을 보편 보장으로 채택하지 않는다. 출처 링크는 문장 지원/진실을 대신하지 않는다. 영문 직접 인용은 추가하지 않는 방향이며 기존 12단어를 포함해 출처당 총 25단어 이내다. 원문 전문·댓글·홍보를 복제하지 않는다.

## 40장·시간·참여·이동

SYNTHESIS의 40행을 반영한다. 핵심은 1~28장 연속 1,080초, 40장 Q&A 120초로 총 20분이다. 29~39장은 별도 선택 심화이며 추가 555초 배분안이다. 실제 낭독과 청중 반응은 미측정이다. 시간표·장 제목·말하기·전환·자료 링크를 함께 고친다. 긴 제목은 같은 의미로 줄일 수 있으나 구조/시간 변경은 manager와 core-route를 함께 갱신한다.

28장에 `#40`으로 가는 ‘질문과 적용 이야기’, 40장에 `#29` 공개 구현/실험과 `#34` 기존 교정 실습 진입, 39장에 `#40` 복귀를 둔다. 발표 중 바로 이동은 실제 슬라이드 안의 `#N` 링크로 제공한다. 자료의 `../slides.md#N`은 읽기 화면 참고 링크이며 즉시 발표 이동과 구별한다.

13장에서는 실제 두 상담 입력을 동등하게 보여 주고 ‘같은 요청으로 묶어도 될까요?’를 잠깐 생각하게 한다. 생각할 틈은 해당 장 35초 안에 포함하고, 구분 이유는 14/15장에서 회수한다. 정답을 미리 표시하지 않는다. 24장은 자기 질문 작성 20초와 선택 공유를 포함한 60초다. 무응답이면 질문을 간직하고 다음 장으로 간다. 자동 집계·입력 저장이나 별도 웹 투표 기능을 만들지 않는다.

## 시각과 파일 인터페이스

40장을 동등 3열 텍스트/작은 캡션으로 반복하지 않는다. 큰 선언·의미 있는 사진 전환·기존 DevDay blue/green/orange/purple·짧은 실제 구성 파일 발췌·관계도·전후 변화·Zoom 질문을 목적에 맞게 섞는다. 한 장의 주장은 하나다. 미실행/비보장 각주를 모든 장에 반복해 내용을 가리지 말고 자료 첫머리와 해당 증거 장에 정확하게 둔다. 긴 조건·근거·파일 내용은 대본과 자료로 옮긴다.

도식 본문은 원본 기준 24~30px 이상을 목표로 하고 주요 라벨은 가능하면 32px 이상으로 만든다. 글자 축소로 맞추지 않는다. 작은 도식만으로 핵심을 전달하지 말고 같은 장의 본문/alt/자료에서도 읽을 수 있게 한다. root가 최종 PNG를 실제 열어 읽고 좁게 교정을 요청한다. 경고/넘침 0을 가독성 판정으로 대신하지 않는다.

B가 다음 새 SVG를 단독 작성하고 A가 정확한 경로로 사용한다. 기존 원자료 구조 그림은 필요하면 재사용하며 기존 사용 자산을 임의 삭제하지 않는다.

## 2단계 소유와 개시 조건

연구 A/B는 각각 실제 최종 교차 후 연구 파일 편집 종료를 통지했다. manager가 이 계약과 core-route를 작성한 뒤, A/B의 명시 수신과 root 통보를 완료하고 별도의 source 개시 메시지를 보낸다. 그 전에는 제품 읽기 전용이다. 인수한 연구 파일은 이후 원고 상태를 소급해 덮어쓰지 않는다.

- **A / karpathy_design_reviewer:** `talks/llm-wiki/slides.md`, `materials/speaker-script.md`, `assets/speaker-guide.txt`, 주제 `README.md`. 실제 이야기·대본·경로·시간표를 작성하고 제품 취합을 맡는다.
- **B / evidence_cases_engineer:** 새 SVG 6개와 사례 txt 3개, `materials/{index,study-guide,workshop,reference-library,demo-log}.md`, `assets/CREDITS.md`. 근거·사례·학습 심화와 새 시각물 정합을 맡는다.
- **manager:** 이 새 engineering/의 회의·계약·최소 검수 근거만 소유한다. 실제 실물·정적 구도·임시 빌드/참조·대본 시간을 독립 검수한다.
- **root:** WORK_LOG·최종 생성물·브라우저 TaskSpace108·Git/commit/push·Pages. 기존 사용자 Space와 서버는 보존한다.

공통 runtime/CSS/엔진·다른 주제·과거 연구·고정 demo 원본/ZIP은 변경하지 않는다. demo-log의 model_invoked:false·고정 승인안·검사 단위와 ZIP의 실제 내용은 보존하고 새 LLM 실행으로 소개하지 않는다. 외부 repo/skill 설치·실행도 하지 않는다.

## 직접 검수와 인수 기준

A와 B는 소유 파일의 초기 실물을 먼저 만든 뒤 서로 실제 읽고, 도식 방향·사례의 인용/해석·새 원고/대본·자료 링크/번호/시간을 직접 교차한다. 같은 파일 동시 편집은 0이다. 소유 밖 수정은 해당 담당자에게 근거와 제안을 직접 알린다. 최초로 모든 자산 링크가 해결되는 체크포인트를 manager/root에 알려 root PNG 검수를 병행한다.

필수 확인은 40장, 자료 6개, 핵심+Q&A 1,200초의 계산, route/장번호·제목·anchor·출처/사례 라벨·새 txt3/SVG6·원문 총 인용·고정 demo/ZIP 불변, 실제 현재 Markdown의 임시 빌드·planner 경고·참조 폐쇄다. 새 unit test나 runtime 변경으로 내용 검수를 대신하지 않는다. 최종 source 해시와 양 writer 편집 종료를 root에 인계한 뒤 별도 디자인/청중 관점 후검수와 공개 전달을 잇는다.
