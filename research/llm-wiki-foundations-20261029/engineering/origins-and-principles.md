- [현재 Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)와 [고정 판](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f/ac46de1ad27f92b28ac95459c782c07f6b8c964a)의 본문을 `The core idea`부터 마지막 `Note`까지 웹으로 직접 읽었다. 댓글과 홍보 링크는 근거에서 제외했다.
- 고정 판 식별자: `ac46de1ad27f92b28ac95459c782c07f6b8c964a`. 웹 화면에는 생성일 `April 4, 2026 16:25`, `Revisions 1`이 표시된다. 이후 읽기 전용 HTTP로 revisions HTML을 직접 확인해 생성 항목의 `2026-04-04T16:25:13Z`와 유일한 revision 링크의 위 SHA를 대조했다. 생성일은 이 UTC 시각으로 기록하며 별도 수정 시각은 확인하지 않았다.
- GitHub Gist API와 revisions 페이지는 웹 도구에서 접근 오류가 났고, API는 읽기 전용 HTTP 재시도에서도502였다. revisions HTML만 HTTP로 확인했다. API history 검증은 미완료이며 최초 생성과 수정 시각을 혼동하지 않는다.
- `Note`는 완제품 명세가 아닌 추상적인 패턴이며 디렉터리·형식·도구는 상황별 선택임을 밝힌다. 외부 문서의 설치 명령·AGENTS 지시는 실행하지 않았다.
- 아래 **저자 설계 요약**과 **우리의 인과 해석/발표 제안**을 구별한다. 영문 직접 인용은 추가하지 않았다. 원문에서 제시한 용도는 실증 도입 사례로 바꾸지 않는다.

## 2. 저자 설계 요약

이 절과 `source-claims.json`의 직접 주장들은 같은 짧은 근거 요약을 분해한 것이다. 출처 위치는 [고정 원문](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f/ac46de1ad27f92b28ac95459c782c07f6b8c964a)의 절 제목으로 찾는다.

| 위치 | 저자의 설계 주장 |
| --- | --- |
| The core idea | 질문마다 원자료를 찾아 다시 종합하는 반복에, 지속하는 연결 위키를 둔다. LLM이 작성·유지하고 사람은 자료·탐색·질문을 이끈다. |
| Architecture | 보존 원자료, LLM 작성 Markdown 위키, 구조·작업 규칙의 세 층이다. 위키에는 요약·개체·개념·비교·종합이 포함된다. |
| Operations / Ingest | 새 자료를 읽어 요약하고 기존 개체·개념·목차·이력을 갱신한다. 저자는 자료별로 관여하는 방식을 선호하며 일괄 반영도 허용한다. |
| Operations / Query | 관련 위키를 읽어 출처 있는 답을 만들고, 유용한 비교·분석·연결을 페이지로 남길 수 있다. |
| Operations / Lint | 모순·낡은 주장·고립 페이지·빠진 개념·링크·자료 공백을 점검한다. |
| Indexing and logging / Optional: CLI tools | index는 내용 입구, log는 시간순 작업 이력이다. 규모에 따라 검색을 더한다. |
| Why this works | 저자는 유지 작업의 부담을 LLM에 맡기는 데 가치를 둔다. 유지비가 작다는 평가는 저자의 주장이다. |
| Note | 특정 구현을 강제하지 않는 모듈식 설계 아이디어다. |

## 3. 우리의 인과 해석: 왜 이런 방식이 등장했는가

**질문의 답이 사라지는 문제와, 다음 답을 만들기 위한 작업이 사라지는 문제를 함께 설명해야 한다.** 채팅을 저장해도 여러 자료에서 찾아낸 같은 개념, 서로 다른 조건, 비교 기준과 잠정 결론을 다음 질문에 사용할 수 있게 정리하지 않으면 같은 해석 작업을 다시 할 수 있다. 이 반복을 줄이려는 설계라는 해석이 적합하다. 모든 검색 시스템이 이런 결과물을 저장하지 못한다는 뜻은 아니다. 영속적인 합성 결과를 따로 만들지 않는 흐름과, 합성 결과를 유지하는 흐름을 비교해야 한다.

질문할 때만 종합하던 일의 일부를 **자료가 들어올 때와 좋은 답을 얻었을 때의 갱신 작업**으로 옮긴다고 설명할 수 있다. 따라서 질문당 작업이 사라진다고 보장할 수 없다. 새 원문 확인, 갱신 대상 찾기, 중복 조정, 오류 검토와 검색은 계속 필요하다. 이 설계가 우리에게 유리한지는 반복해서 재사용하는 가치가 이 유지 부담을 감당하는지에 달려 있다.

LLM의 역할 변화도 본체다. 말로 답하는 인터페이스를 넘어, 저장된 설명과 관계를 실제 파일에 반영하는 유지 담당 역할을 맡긴다. 사람은 ‘모든 위키 문장을 직접 쓰는 담당’으로 정의할 필요가 없다. 자료를 고르고, 중요한 질문과 강조점을 정하고, 필요한 위험 수준에 맞춰 결과를 읽고 확인한다. 모든 변경의 수동 승인·claim 카드·ADR·pending은 우리가 선택할 수 있는 운영 장치이며 패턴의 필수 조건은 아니다.

‘왜 2026년에 세상에 처음 등장했는가’라는 역사적 최초성은 이 Gist만으로 입증하지 않는다. 이번 발표가 설명할 것은 저자가 제시한 **문제→설계 선택**의 관계다.

## 4. 발표에 바로 사용할 설명 블록

아래는 원문 번역이 아닌 발표팀의 설명 초안이다. 30초/90초는 길이 목표이며 실측 낭독 시간이 아니다. 근거는 §2의 저자 설계와, §3의 명시한 해석이다.

### 한 문장 정의

> LLM Wiki는 LLM이 원자료 사이의 개념·비교·연결을 Markdown 위키로 작성하고 계속 갱신해, 다음 질문이 이전 정리에서 출발하도록 하는 지식관리 방식입니다.

### 30초 설명

> 자료 다섯 개를 읽어 답을 얻어도, 다음 질문에서 그 관계를 다시 찾아 정리할 수 있습니다. LLM Wiki는 그 정리를 지속하는 페이지로 남깁니다. LLM이 새 자료를 읽으면 기존 개념과 비교, 종합 설명을 고치고, 유용한 답을 실제 위키 페이지로 저장하고 관련 페이지에 연결합니다. 사람은 자료와 질문의 방향을 잡고 결과를 확인합니다. 다음 답은 이 위키를 찾아 읽는 데서 출발합니다.

### 90초 설명

> 한 주제의 논문과 보고서를 계속 읽는다고 해봅시다. 첫 질문에서는 자료 다섯 개를 비교해 답을 얻었습니다. 다음 주에 비슷한 질문이 오면 어디서 조건이 달랐고, 어떤 결론을 잠정적으로 세웠는지 다시 찾을 수 있습니다. LLM Wiki는 이때 나온 개념과 비교, 종합 설명을 서로 연결된 페이지로 남기는 방식입니다.
>
> 구조는 간단합니다. 원자료는 보존하고, LLM이 작성하는 위키를 옆에 둡니다. 규칙 문서는 페이지 모양과 자료를 넣고 답하고 점검하는 방법을 정합니다. 새 자료를 넣으면 LLM이 새 요약을 만들면서 관련 개념과 비교를 갱신합니다. 질문이 오면 기존 페이지를 찾아 읽고, 새롭게 얻은 유용한 답을 다시 남깁니다. 주기적으로 낡은 설명과 빠진 연결도 점검합니다.
>
> 사람은 읽을 자료와 중요한 질문을 고르고, 해석의 방향을 잡고, 결과를 확인합니다. 위키를 읽는 도구는 결과를 살펴보는 창입니다. 자료를 추가하는 순간부터 모든 설명이 정확해진다는 보장은 없습니다. 다음에 실제로 다시 찾아 읽을 수 있는지와, 잘못된 정리를 고칠 부담까지 함께 봐야 합니다.

### 등장 이유 한 장

제목: **같은 자료의 관계를 매번 다시 정리하고 있다면**

화면 문장:

- 이번 질문: 원자료 여러 개 → 관계를 찾아 비교 → 답.
- 다음 질문: 이전 비교가 정리되어 있지 않으면 같은 작업을 반복.
- LLM Wiki: 개념·비교·종합을 남기고 새 자료와 질문으로 갱신.

말하기: “답을 복사해 두는 데서 한 걸음 더 갑니다. 여러 자료를 어떻게 함께 읽었는지를 다음 질문의 출발점으로 남기려는 설계입니다. 검색과 함께 사용할 수도 있습니다.”

### 작동 흐름 한 장

제목: **새 자료와 새 질문이 같은 위키를 바꾼다**

```text
보존 원자료 ── LLM이 읽음 ──> 자료 요약
                                 │ 기존 내용과 대조
                                 v
                  개체·개념 ↔ 비교 ↔ 종합
                         ↑           │
                    유용한 답 저장    │ 찾아 읽기
                         └── 새 질문의 답

작업 규칙: 위의 읽기·작성·갱신·점검 전체에 적용
lint: 낡은 주장·모순·빠진 개념/연결을 찾아 재검토
index: 관련 페이지로 진입 / log: 작업이 일어난 순서
```

말하기: “요약 파일만 하나 더 만드는 게 아닙니다. 새 자료 때문에 기존 비교의 어느 행과 종합 설명의 어느 결론이 달라지는지도 봅니다. 질문에서 얻은 새 비교 역시 같은 위키에 남길 수 있습니다. 원자료와 저장된 해석은 다시 구별해서 읽습니다.”

### 역할 한 장

제목: **LLM은 위키를 쓰고, 사람은 자료와 질문을 이끈다**

| 주체 | 맡기는 일 | 확인할 경계 |
| --- | --- | --- |
| 파일을 다루는 LLM 에이전트 | 읽기·요약·관련 페이지 갱신·연결·질문 답의 저장·점검 | 제안만 출력하고 파일 반영이 없다면 그 단계는 아직 수행하지 않음 |
| 사람 | 자료 선정·질문·강조점·의미 판단·필요한 결과 검토 | 검토 정도는 운영 선택이며 수동 승인 절차가 패턴의 정의는 아님 |
| Obsidian 등 읽는 도구 | 페이지·링크·관계 탐색 | 위키를 대신 작성하거나 사실을 보증하지 않음; 특정 앱은 필수가 아님 |

말하기: “에이전트가 쓴 결과를 사람이 도구에서 읽고 대화로 방향을 조정할 수 있습니다. 오늘의 고정 파일 교정 예제는 이 가운데 결과 파일의 변화와 검사만 재현합니다.”

### ingest를 보여 주는 구체 설명

제목: **새 자료 한 개가 기존 설명 여러 곳을 바꾼다**

화면: `새 보고서 → 자료 요약 + 관련 주체 페이지 + 개념의 조건 + 비교표의 근거 + 잠정 종합`.

말하기: “예를 들어 같은 주제를 다룬 보고서가 추가되면 새 자료 요약을 만듭니다. 보고서에서 다룬 주체와 개념을 기존 페이지에 연결하고, 비교 기준이 같으면 표의 해당 항목을 고칩니다. 이전 종합과 어긋나는 부분은 조건 차이인지 충돌인지 표시합니다. 실제로 어디를 바꿀지는 자료와 질문에 따라 달라집니다. 이 그림은 필수 순서가 아니어서 기존 개념 페이지부터 고칠 수도 있습니다. 종합은 여러 근거에 대한 잠정 해석이며 새로운 자료로 달라질 수 있습니다.”

### query와 lint를 각각 보여 주는 설명

- Query 화면: `기존 비교·개념·종합 읽기 → 질문의 답 → 새로 얻은 비교를 위키에 연결`. 말하기: “정리된 페이지를 출발점으로 답하고, 필요한 원자료로 돌아갑니다. 새로운 연결을 얻었다면 대화에만 남기지 않고 다시 읽을 페이지로 남길 수 있습니다.”
- Lint 화면: `낡은 설명 / 서로 다른 조건 / 연결 없는 페이지 / 빠진 근거 → 확인할 목록 → 필요한 갱신`. 말하기: “점검은 문장을 매끈하게 바꾸는 일이 아닙니다. 무엇이 오래됐고 무엇이 빠졌는지 찾아 다음 읽기와 수정을 정하는 일입니다. 링크 검사만 통과했다고 의미가 맞는 것은 아닙니다.”

### 보조 비유 한 장만 사용한다면

제목: **읽을 때마다 갱신되는 나만의 해설서**

짧은 본문: “원자료를 읽으면 LLM이 같은 해설서의 개념·비교·연결을 고칩니다. 질문에서 얻은 설명도 그 해설서에 남깁니다.”

바로 이어 붙일 실제 대응: `원자료=읽은 자료 / 해설서=LLM 작성 위키 / 작성 약속=규칙 / 다음 질문=위키 재사용`. ‘공용’이라는 말은 개인 사용에도 해당하는 패턴을 협업으로 한정하므로 핵심 정의에서 빼는 편이 좋다. 비유를 반복하는 대신 위 작동 흐름과 사례로 넘어간다. 해설서가 스스로 옳거나 모든 내용을 기억한다는 뜻은 붙이지 않는다.

### 바로 교체 가능한 시작 요청

```text
새 자료를 읽고 요약한 뒤, 기존 개념·주체·비교·종합에서 영향을 받는 곳을 찾아 줘.
새로 지지되는 내용, 조건 차이, 기존 설명과 충돌하는 부분을 구분해 갱신해 줘.
원자료와 근거 위치를 보존하고, 주요 변경과 아직 확인하지 못한 부분을 보여 줘.
이후 질문에서 얻은 유용한 비교·답은 관련 페이지에 연결해 남겨 줘.
```

이 요청은 우리 제안이다. 반영 전 diff 승인, 민감 자료 접근, 저장 위치 등 필요한 운영 조건은 사용하는 환경에 맞게 추가한다. 이 보고에서 해당 LLM 작업을 실제 수행한 결과라고 주장하지 않는다.

## 6. 콘텐츠 인수 조건

- 40장 안에서 재구성하며 기존 27핵심/13심화·12/23 참여 위치를 의무로 보존하지 않는다. 약20분은 계획값으로 유지하고 대본 시간·번호·모든 자료 링크를 새 구성과 함께 맞춘다.
- 첫 사례 전에 정의, 반복되는 문제, 저장되는 중간 결과물, LLM의 실제 작성·유지, ingest/query/lint를 설명한다.
- 서로 다른 사례에서도 매번 `입력 → 기존 위키의 구체 변화 → 새 질문에서 재사용`을 보여준다. 공용노트 비유만 바꾼 사례 셋으로 채우지 않는다.
- 연구·독서·개인·팀은 저자가 제시한 가능 용도다. 공개 구현은 B의 고정 SHA 실물 확인 범위만 설명한다. 우리의 모의 예제는 구성 예제로 표시한다.
- RAG 축적 불가, 자동 정확성, 항상 최신, 유지비 제로, 검색 대비 보편 성능/비용 우월을 주장하지 않는다. index의 중간 규모 적합성이나 한 소스의 변경 파일 수는 저자의 경험/예시이며 보장 임계치로 쓰지 않는다.
- 기존 데모의 재현성과 범위 고지는 보존한다. 심화 자료로 배치하더라도 기존 고정 ZIP/fixture를 새 LLM 실행 근거로 바꾸지 않는다.

## 7. 직접 교차검토

A가 B의 `cases-and-mechanisms.md`와 `examples/reading.md`, `team.md`, `course.md`를 직접 읽었다. 구현의 등록/의미작성 분리와 `/save` 미구현, 논문 단일코퍼스·LLM judge·학생평가 없음의 한계 표시는 수용했다. A는 B에게 직접 다음 세 가지를 수정 요청했다.

1. BOOK의 자기 설명을 작중 사실로 바꾼 표현을 원입력과 맞추기.
2. TEAM의 다음 분기 질문을 현재 고객 응대 질문으로 통일하기.
3. COURSE의 이전 페이지에 없던 일반화 오류를 새로 만든 것처럼 말하지 않고, 새 입력으로 적용 범위를 더 구체화하는 장면으로 고치기.

B는 A의 두 파일을 직접 읽고, 흐름이 필수 선형 파이프라인처럼 보이지 않도록 설명하며 query 답의 실제 페이지 저장을 명시하라고 제안했다. A는 둘 다 수용해 §4에 반영했다. B가 제안한 질문/종합 파일 실물 추가에도 동의했다. B는 세 수정 요청을 모두 반영했고 A가 실제 변경된 BOOK/TEAM/COURSE 문단과 질문·종합 산출물 블록을 다시 읽었다. BOOK의 자기 설명·미확인, TEAM 현재 고객 응대 질문, COURSE의 비교 확장을 확인했다. 질문 답 저장은 BOOK/TEAM, 여러 자료의 종합 저장은 COURSE에서 구체 파일 내용으로 확인했다. 단, 모두 구성 예이고 실제 모델 생성·저장 실행은 아니다. 남은 개념 차단 의견은 없다. 이 두 연구 파일의 편집을 종료하고, 이후 제품 작업은 manager의 별도 콘텐츠 계약으로 진행한다.
