# STAGE 디자인 가이드

새 발표의 내용 정본은 `talks/주제/slides.md`이며, 빌드가 `content.js`와 발표·읽기 화면을 만듭니다. Markdown 작성은 [MARKDOWN-FIRST.md](MARKDOWN-FIRST.md)를 따릅니다. 기존 JavaScript 직접 입력 방식에서는 `window.PRESENTATION`을 편집하며 [CONFIG.md](CONFIG.md)의 계약을 사용합니다. 시각 구현의 현재값은 공통 [styles.css](styles.css), Markdown 조판 [blocks.css](blocks.css), 시각자료 [visual.css](visual.css)와 관련 렌더러·자산을 함께 확인합니다.

## 권한과 사용법

**최신 사용자 지시가 우선입니다. 별도 변경 지시가 없으면 Stage의 검정 바탕·큰 타이포·넓은 여백·한 시각 중심을 유지합니다.** 이 문서는 STAGE의 디자인 정본이며, 행사 랜딩페이지가 아니라 실제 발표 세션의 구도와 정보량 변화를 참고합니다. OpenAI의 공식 발표 규정은 아닙니다.

새 작업은 아래 원칙과 역할별 판단을 읽고, 바꿀 내용·시각 범위·보존할 자료를 정하는 데서 시작합니다. 새 내용 출처의 색이나 레이아웃이 기존 시각 기준을 자동으로 대체하지 않습니다. 기본값을 바꿀 때는 사용자 지시 또는 프로젝트의 예외 이유, 적용 범위, 되돌아갈 기준과 검수 영향을 기록합니다. 임시 실험을 다음 발표의 영구 기본값으로 승계하지 않습니다.

문서의 세 층을 구별하세요. **원본 관찰**은 특정 프레임에서 실제 본 것, **프로젝트 결정**은 STAGE가 선택한 재사용 원칙, **구현값**은 현재 CSS·입력 계약입니다. 원본의 공식 글꼴·HEX·제작 기술을 추정해 구현값의 권위로 삼지 않습니다. 입력 세부는 CONFIG·작성 안내, 조사 근거는 연구, 목표·담당·미완료·결정은 [WORK_LOG.md](WORK_LOG.md)에서 관리합니다.

## 먼저 지킬 원칙

1. **한 장의 역할과 시각 중심을 정합니다.** 기억할 메시지, 주장을 받치는 근거, 관계를 읽는 그림, 실제 결과물, 시연, 다음 행동 중 무엇이 주역인지 먼저 말할 수 있어야 합니다.
2. **메시지·근거·시연의 밀도와 리듬을 바꿉니다.** 큰 한 문장 뒤에는 근거를 충분히 크게 보여주고, 실제 화면을 볼 때는 설명의 비중을 낮춥니다. 모든 장을 제목+동등한 본문 열로 맞추지 않습니다.
3. **관계를 실제 크기로 읽게 합니다.** 도표의 단위·출처, 문서의 필요한 구절, UI의 행동 영역, 도식의 연결을 볼 수 있게 배치합니다. 빈 공간을 채우기 위한 박스와 설명은 추가하지 않습니다.
4. **매체의 고유 표면과 의미색을 보존합니다.** 사진·작품·실제 UI·문서의 색은 콘텐츠입니다. 중립 무대 위의 밝은 문서나 색 노드는 허용하며, 색만으로 구분하지 않습니다.
5. **가독성과 의미를 함께 지킵니다.** 긴 한국어를 계속 축소하기보다 읽는 순서와 설명 위치를 정리합니다. 원자료·좋은 그림·맥락을 삭제하는 일을 간소화의 기본 해법으로 삼지 않습니다.
6. **현재 판의 실제 화면으로 판정합니다.** 잘림·누락·빌드 검사는 필요하지만 주장과 근거의 연결, 위계, 가독성, 연속 흐름의 시각 승인을 대신하지 않습니다.

같은 구도를 이어 쓰며 문구·근거를 단계적으로 추가할 수 있습니다. 레이아웃 연속 N장, 색 면적·빈도, 장수 최소화 같은 합격 할당량은 두지 않습니다. 카드·네모·컬러·밝은 면도 전면 금지하지 않습니다. 구도는 해결할 이해 문제로 선택합니다.

## 역할별 판단과 허용 반례

| 장의 역할 | 먼저 보일 것과 읽는 순서 | 판단 예 |
| --- | --- | --- |
| 짧은 메시지·전환 | 기억할 한 문장 또는 이름 → 짧은 보충 | 중앙 메시지는 라벨·번호를 덜어낼 수 있습니다. 모든 장에 중앙 정렬을 적용하지 않습니다. |
| 근거·비교 | 주장 → 하나의 도표·비교축 → 단위·출처 | 같은 축으로 비교하며 도표에 충분한 면적을 줍니다. 실제 수치·기간·출처를 밝히고 가상 예제를 성과로 바꾸지 않습니다. |
| 관계·과정 | 출발 대상 → 연결·변화 → 결과 | 선·정렬·거리·의미색으로 관계를 드러냅니다. 설명을 반복해 그림과 경쟁시키지 않습니다. 단계적 설명에는 같은 구도가 유효합니다. |
| 실제 자료·결과물 | 읽어야 할 구절·행동 영역 → 자료의 정체성·출처 | 밝은 문서면을 유지할 수 있습니다. 활동안·개념도·실제 실행 결과를 구별하고, 작은 전체 화면으로 가독성을 통과시키지 않습니다. |
| 시연·전체 미디어 | 실제 화면·영상 → 필요한 짧은 안내 | 설명은 직전 메시지와 노트에 둘 수 있습니다. 방송의 발표자 합성 화면을 발표 양식에 복제하지 않습니다. |
| 다음 행동 | 청중이 지금 할 한 행동 → 예시 → 보조자료 | 시작 요청과 자료 탐색 링크의 위계를 나눕니다. 원문·부록 접근은 보존합니다. |

현재 LLM Wiki 재점검의 화면 반례를 함께 봅니다. 이는 특정 장수를 다음 발표에 강제하는 규칙이 아닙니다.

- [8장](research/design-governance-20261102/evidence/before/slide-08.png)과 [9–11장을 포함한 보드](research/design-governance-20261102/evidence/before/contact-09-16.jpg): media가 이어져도 입력 상자·열린 관계·연결·두 문서로 기하가 달라집니다. layout 이름의 반복만으로 실패 판정하지 않습니다. - [17–24장 보드](research/design-governance-20261102/evidence/before/contact-17-24.jpg): 어려움·직접 판단·활용·장점·주의가 같은 동위계 3열로 놓일 때 각 장의 차이와 읽는 순서가 드러나는지 확인합니다. 17장의 현상·대응·쓰임과 18장의 사람 책임은 위계를 재검토할 대상입니다. 반면 19장의 동등한 활용처, 21장의 병렬 동사로 된 이점, 22장의 대등한 위험 차원은 3열이 역할에 맞는 허용 사례입니다. 내용을 일괄 삭제하거나 모든 3열을 금지하지 않습니다.
- [20장](research/design-governance-20261102/evidence/before/slide-20.png): 밝은 활동안 자체가 대상입니다. 읽어야 할 부분을 크게 유지하고 활동 배분을 생성 시간 실측이나 실행 성과로 설명하지 않습니다. [24장](research/design-governance-20261102/evidence/before/slide-24.png)은 첫 요청과 보조 링크의 위계를 검토합니다.

## 사진·문서·UI·열린 시각자료

사진 모음은 같은 프레임만 맞추지 말고 피사체 크기·시선·행위·조명·배경의 관계를 검토합니다. SF의 사진 6열은 원본 관찰이며 모든 모음의 수량 규칙이 아닙니다. 사진이 주역이면 큰 제목과 하단 캡션을 덜고 짧은 상단 설명으로 묶을 수 있습니다. 스톡 사진 속 인물을 행사 참가자나 실제 사례로 소개하지 않으며 [자산 크레딧](assets/CREDITS.md)을 유지합니다. 원본의 통일 촬영 시리즈까지 재현했다고 주장하지 않습니다.

UI·문서는 `contain`으로 필요한 전체 내용을 보일지, 읽을 영역을 별도로 확대할지 결정합니다. 사진의 `cover`는 피사체가 잘리지 않는 초점과 크롭을 함께 봅니다. 전체 미디어의 짧은 캡션은 피사체를 피합니다. 이미지마다 어두운 덮개·회색조·단색 틴트를 일괄 적용하지 않습니다. 의미 있는 대체 텍스트와 필요한 크레딧을 작성하고 데이터에는 출처를 둡니다. 스트립의 `zoom`은 디지털 표시 확대이며 렌즈나 광학 줌의 재현이 아닙니다. 세부 입력은 [이미지 항목](CONFIG.md#이미지-항목)에 있습니다.

혼합 타일은 자료마다 폭·높이·역할을 달리하며 주역을 먼저 읽게 합니다. `seoul`·`recap`의 슬롯·격자·거터·라운드는 STAGE 구현 계약입니다. 서울·도쿄 현장 사진에서 공식 CSS를 추출한 값이 아닙니다. 아이콘월과 두 수치의 직접 근거는 서울이며 도쿄·벵갈루루에서도 동일 화면을 확인했다고 합치지 않습니다. 앱 로고 대신 자체 아이콘을 사용합니다. Figma 기반 `mosaic`은 독자 작품 모음이며 DevDay 혼합 타일의 충실한 복제가 아닙니다. [원본/구현 보드](research/visual-implementation.html), [서울 조사](research/seoul-devday-visual-research-20261023.md), [도쿄·벵갈루루 조사](research/completed-cities-visual-research-20261023.md), [구현 비교](research/visual-implementation-diff-20261023.md)를 연결합니다.

편집형 구성은 표지·인용·주제·발견·다음 행동을 한 이야기로 잇습니다. 작은 타일에는 한 인용·행동·짧은 발견을 두고, 읽어야 할 긴 UI·데이터는 따로 크게 보여줍니다. 파형·과정은 개념을 나타내며 실제 측정값·성과 그래프가 아닙니다. `24 → 6 → 3` 같은 서로 다른 단위를 전환율이나 인과로 설명하지 않습니다. 글자는 편집 가능한 요소로 남기며 매번 SVG나 아이콘 키를 작성할 필요가 없습니다. [C안 판단](research/review-20261023/design/synthesis.md), [입력 계약](CONFIG.md#c안처럼-한-이야기로-엮기), [다른 주제 예제](examples/editorial-starter.js)를 참고합니다.

`visual`은 메시지·자료에서 가져온 핵심값·plot을 열린 무대에 놓습니다. 모든 자료를 사진 프레임·불투명 면·같은 테두리로 감싸지 않습니다. wide는 넓은 plot과 간결한 메시지, split은 주장·큰 값과 해당 plot의 연결을 강조합니다. 짧은 흐름은 메시지와 관계를 가까이 묶습니다. 숫자 사본을 만들지 않고 focus 자료를 사용하며, 자료 길이·범주·단계 수는 실제 입력을 따릅니다. 작은 SVG 축소만으로 모바일 가독성을 통과시키지 말고 같은 입력의 상세 읽기 표·범례도 확인합니다. [시각자료 사양](research/visual-redesign-20261024/design/final-spec.md), [직접 입력](CONFIG.md#시각자료-visual)에 상세 계약이 있습니다.

지원 양식·항목 수·필드의 정본은 [양식과 수량](CONFIG.md#양식과-수량)입니다. 선언·표지·섹션·마무리는 중앙 또는 왼쪽 정렬을 선택하고, 순서가 중요한 자료에는 순서가 보이는 구도를 사용합니다. 예를 들어 `mosaic`의 빈 칸 채우기는 시간·단계 비교에 적합하지 않을 수 있으며 모바일에서는 입력 순서를 유지합니다. 현재 예제의 장수나 자산 개수를 다음 발표의 의무로 삼지 않습니다.

## 한국어·타이포와 읽기

큰 주장·근거·보조 설명의 읽는 순서를 크기·굵기·밝기·간격으로 만듭니다. 어절을 유지하고 제목의 의도한 줄바꿈을 보존합니다. 긴 제목·수치·단위는 실제 폭에서 확인합니다. 수치와 단위가 넘치면 먼저 전폭 행·줄바꿈을 검토하고 필요한 요소만 국소 조정합니다. 편집 중인 노드와 원본 내용을 다시 만들어 사용자의 수정을 잃지 않게 합니다.

발표는 1600 × 900 논리 캔버스를 비율대로 축소합니다. 일반 양식의 안전 여백과 글자 크기는 구현 시작값이며 원본 발표 실측값이 아닙니다. 중앙 메시지·전체 미디어·긴 설명·넓은 도표는 역할에 맞는 다른 크기와 폭을 사용하므로 모든 제목에 하나의 숫자를 강제하지 않습니다. 구체 수치·전후 판단은 [타이포 비평](research/type-layout-20261025/discussion.md), [채택 배치](research/type-layout-20261025/manager/final-decision.md), [비교 화면](research/type-layout-20261025/index.html), [배치 스타터](examples/text-layout/index.html), 현재 CSS를 참고합니다.

외부 글꼴 요청 없이 운영체제의 한국어 글꼴을 사용합니다. macOS의 Apple SD Gothic Neo, Windows의 맑은 고딕 등 실제 환경에 따라 폭과 개행이 달라집니다. 발표할 기기의 실제 크기에서 읽어야 할 문장·도표·문서를 확인합니다. 입력 오류·분량 경고는 내용을 몰래 삭제하거나 계속 축소하는 수단이 아닙니다. [점검과 복구](CONFIG.md#점검과-복구)에 따라 문장·항목을 나누고 읽기 화면의 전체 의미도 확인합니다.

발표 모드는 16:9 화면, 읽기 모드는 문서 재배치를 사용합니다. 비교·도표·데모·단계·이미지 모음·결과물·범주·혼합 타일·두 수치의 모바일 읽기는 한 열을 사용하며 아이콘월은 중앙 문장 뒤에 입력 순서의 아이콘을 펼칩니다. 전체 보기·발표자 미리보기는 원래 구도를 유지합니다. 이는 구현 의도이며 모든 기기의 검증 완료를 뜻하지 않습니다. 긴 표·셀의 자체 스크롤과 상세 표도 실제 읽기 크기에서 확인합니다. PDF 장수·인쇄 결과를 웹 발표의 자료 수량 제약으로 사용하지 않습니다.

## 모션과 접근성

모션은 읽는 순서를 보조하는 짧은 선택 효과입니다. 모든 내용과 숫자는 기본적으로 완성 상태이며 관객 발표 모드의 비편집 화면에서만 움직입니다. 효과 대상이 없으면 정적으로 표시합니다. 숫자 count-up·수동 단계 공개·무한 반복을 추가하지 않습니다.

읽기·편집·전체 보기·발표자 미리보기와 시스템 모션 줄이기에서는 효과를 끕니다. 읽기 모드의 JavaScript 이동도 설정을 따릅니다. 기본 fade·rise·stagger·chart의 정확한 시간·거리·지연은 [모션 입력 계약](CONFIG.md#모션-선택)과 [모션 사양](research/color-motion-20261024/design/motion-spec.md)에 있습니다. 이 값은 원본 영상의 컷·지속 시간·easing 측정값이 아닙니다. [개발 검토](research/color-motion-20261024/engineering/synthesis.md)에 따라 기존 HTML/CSS/JavaScript를 사용합니다. 색 이외의 라벨·위치·단위, 의미 있는 대체 텍스트·출처와 함께 완성 화면을 확인합니다.

## 변경과 현재 판 검수

작업 시작에 읽은 DESIGN 버전과 대상 원고·자산·공통 스타일/runtime, 바꿀 범위, 예외, 보존할 의미·자료를 확인합니다. 기존 발표의 역할 맵은 재사용하고 변경 장·영향받는 흐름을 갱신합니다. 작은 문구 수정마다 전체 역할 맵을 새로 쓰지는 않습니다.

| 변경 | 필요한 시각 확인 |
| --- | --- |
| 원고·배치·링크 | 변경 장의 실제 크기, 앞뒤 흐름, 전체 보드, 영향을 받는 읽기 화면·행동 |
| SVG·사진·문서 | 자산 원본과 실제 배치 크기, 읽어야 할 부분·관계·크롭, 필요 상세 읽기 |
| 공통 CSS·렌더러·테마·모션 | 영향받는 대표 양식, 긴 한국어·수치, 밝은 UI·문서, 사진, 다른 주제, 읽기·모션 줄이기와 기존 기능 |

검토 기록에는 읽은 DESIGN revision, 대상 입력과 관련 자산·공통 CSS/runtime fingerprint, 대상 장·모드·viewport, 증거 경로, 검토자·판정·이유를 대응시킵니다. 원고 해시가 같아도 SVG·스타일이 바뀌면 근거가 오래될 수 있습니다. 전체 보드는 밀도와 흐름, 개별 원본은 위계와 세부 가독성에 사용합니다. 실제 발표 기기·다른 화면 크기·모션을 확인하지 못했다면 범위를 명시합니다.

기준만 바뀌고 제품 입력이 같으면 기존 캡처를 새 기준으로 직접 다시 읽을 수 있습니다. 캡처 당시 기준과 재검토 기준의 fingerprint를 구별하고 재검토자·범위·이유를 기록합니다. 캡처의 옛 기준 해시를 덮어쓰거나 이전 승인을 자동 승계하지 않습니다. 제품 입력이 바뀌면 영향 화면을 다시 캡처합니다.

| 판정 | 의미와 후속 행동 |
| --- | --- |
| 승인 | 실제 확인 범위에서 기준 충족 이유가 있습니다. 그 입력·근거가 유효한 범위에만 적용합니다. |
| 개선 필요 (`needs-changes`) | 문제와 보존·교정 명세가 있습니다. 재점검 기록 완료와 제품 시각 승인을 구별하며, 미구현 교정은 승인으로 바꾸지 않습니다. |
| 미확인 | 필요한 실제 화면·기기·판정이 없습니다. 다음 담당과 확인 행동을 남깁니다. |
| 오래된 근거 | 검수 뒤 관련 입력·자산·runtime·기준이 바뀌었습니다. 이전 판정은 이력으로 남기고 영향 범위를 다시 검토합니다. |

기술 검사와 시각 판정을 따로 보고합니다. 자동 검사는 대상·증거 파일의 실재, 최신성, 범위와 상태의 대응을 확인할 수 있지만 실제로 보았는지와 판단의 옳음을 증명하지 못합니다. 기록 생성 시 승인을 자동으로 부여하지 않습니다. 개선 필요 기록의 유효성 검사와 시각 승인 완료 경로를 구별합니다. 기능 검사는 변경 영향에 맞게 수행하며 과거 테스트 개수·예제 장수를 현재 의무나 승인 증거로 사용하지 않습니다.
