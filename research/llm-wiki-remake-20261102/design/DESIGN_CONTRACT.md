## 구현 결정을 가르는 원칙

실제 리메이크의 단위는 색이나 레이아웃 이름이 아니라 이해 문제다. 한 장의 기억할 말, 관계를 읽을 대상, 다음 행동의 우선순위가 전후에 어떻게 달라지는지 구현과 화면으로 설명할 수 있어야 한다. 전26장의 역할과 흐름을 재검토하되 이미 적합한 장을 바꾸기 위한 변경은 요구하지 않는다. 이전21장 승인은 새 입력·새 흐름으로 자동 승계하지 않는다.

4장의 필요 맥락/위키 지원, 19장의 세 활용처, 21장의 세 장점, 22장의 세 위험은 병렬 구도가 성립하는 반례다. 8–11장의 media 연속은 검색 상자·열린 관계·갱신·두 문서라는 기하와 역할로 판단한다. 같은 양식 연속 수, 밝은 면 비율, 색 개수, 최소 장수는 합격 조건이 아니다. 1·25·26장의 저밀도 대비를 보존하며 모든 장에 관계도나 3열을 강제하지 않는다.

우선 기존 Markdown `compose`와 `stage-group primary`를 이용한다. `primary: true`를 썼다는 사실은 위계 해결의 증거가 아니다. 현재 `variant: centered`는 일반 editorial과 별도의 크기·간격을 적용하므로 실제 화면을 확인한다. 새 공통 런타임·만능 양식을 추가하기 전에 기존 입력·그룹 재배치·별도 개선 SVG로 풀 수 있는지 확인한다. 공통 코드를 바꿀 필요가 생기면 원인·영향·다른 주제와 읽기 회귀 범위를 먼저 root에 전달한다.

## 실제 검수와 반복

1. 엔지니어링팀은 전장 명세와 보존 계약을 확인하고 제품을 구현한다. 변경 경로·의미 대응·국소 기술검사·관련 대본 동기화를 제출한다. 작성자와 검토자의 역할을 구분한다.
2. root는 빌드 후 최신 원고·스타일·runtime·자산 전체 입력 hash와 실제 브라우저 캡처를 묶는다. 발표1440×1000 및960×900에서 전26장의 원본 PNG/전장 보드/manifest, 읽기1440 및390 폭에서 전체 내용과 관련 링크의 실제 화면·행동을 제공한다. 캡처 때의 실제 viewport·DPR·stage 크기를 함께 남긴다. 읽기는 문장·링크·표·이미지 접근을 각각 확인하며 SVG를390폭에 단순 축소한 상태를 가독성 통과로 쓰지 않는다. 핵심9도식과 새 개선 도식에서 필요한 관계·문구를 실제로 읽을 수 있는지, 원본 확대 또는 동등한 native 설명에 접근할 수 있는지 확인한다. 새 기능 자체를 의무로 삼지 않고 발견한 실제 이해 문제를 푸는 최소 범위를 구현팀과 정한다.
3. 재개한 디자인 A/B는 구현 설명을 받아도 독립적으로 실제 화면을 먼저 읽고, 전26장과8–11/16–22/23–26의 연속 흐름, 바뀐 SVG 원본과 실제 contain 크기, 한국어 개행·관계·링크를 판정한다. 축소 보드만으로 작은 본문을 승인하지 않는다. 기술 경계·이미지 누락0은 별도 기술 증거다.
4. 개선 필요는 대상 장/모드/크기, 화면 근거, 문제, 반드시 보존할 의미, 수용 조건을 직접 엔지니어링 매니저에게 전달한다. 구현한 최신 입력과 화면을 다시 확인한다. 정책이 모호하거나 오판을 유도했다면 해당 문구·실제 오작동·최소 교정안을 root에 전달하고 문서 교정 후 같은 제품으로 재검증한다. 기준을 낮추거나 기록만 채워 승인하지 않는다.
5. 최종은 **제품 시각 승인**과 **AGENTS/DESIGN 제작 적합성 승인** 두 판정을 명시한다. 제품 승인은 최신 입력의 해당 장·모드·크기에 대해 `--require-approved`를 통과한 범위에 한정한다. 정책 승인은 이번 실제 제작과 독립 반례에서 지침이 권한/위계/자료 보존/검수 범위를 충분히 유도했다는 근거에 한정한다. 미래 모든 발표의 오류0이나 현장·모션·청중 이해 효과를 보장하지 않는다.

기존 기록은 이력으로 보존하고 새 판의 기록을 별도로 남긴다. 검수 도구는 현재 한 기록당 한 mode/viewport를 대응하므로 크기·모드가 다른 검토는 별도 기록으로 만든다. hash 갱신만으로 과거 승인을 재사용하지 않는다. 현재 모든 구현 후 판정은 아직 미확인이다.
