# LLM Wiki 리메이크 — 독립 수용 기준과 반증 계약

2026-11-02 · 독립 비평 B `/root/remake_design_manager/independent_critic`

이 문서는 구현 전에 작성한 수용 기준이다. **새 본편과 AGENTS/DESIGN의 제작 적합성 모두 아직 승인하지 않는다.** 기존 정지 화면의 21장 승인·5장 개선 필요는 출발 근거이며 새 판의 승인이 아니다. 이번 사용자의 실제 리메이크 지시가 이전 감사의 ‘본편 교정은 범위 밖’을 대체한다. 기준을 낮추거나 교정 명세의 완성을 제품 승인으로 바꾸지 않는다.

## 독립 초안에서 확인한 근거

직접 읽은 정본은 루트 [AGENTS](../../../AGENTS.md), [DESIGN](../../../DESIGN.md) 145행, [검수 안내](../../../DESIGN-REVIEW.md), [기존 감사](../../design-governance-20261102/design/LLM_WIKI_AUDIT.md), [10월 정책 연구](../../agent-design-policy-202610/RESEARCH.md), 현재 [26장 원고](../../../talks/llm-wiki/slides.md)와 [대본 시간표](../../../talks/llm-wiki/materials/speaker-script.md)다. 입력 문법 중 `compose`, `stage-group.primary`의 기존 지원도 [MARKDOWN-FIRST](../../../MARKDOWN-FIRST.md)에서 확인했다. `primary`는 위계 구현 수단이지 선택만으로 합격시키는 표지가 아니다.

`view_image`로 기존 [1–8](../../design-governance-20261102/evidence/before/contact-01-08.jpg), [9–16](../../design-governance-20261102/evidence/before/contact-09-16.jpg), [17–24](../../design-governance-20261102/evidence/before/contact-17-24.jpg), [25–26](../../design-governance-20261102/evidence/before/contact-25-26.jpg) 보드와 **4·10·17·18·19·20·21·22·24장 원본 PNG**를 직접 보았다. 새 영상·문헌조사를 하지 않았다. 원본 프레임을 재사용하는 프로젝트 판단과 특정 발표의 공식 제작 규정을 구별한다. 현재 root의 [캡처 재사용 확인](../before/capture-reuse.json)은 기존 제품 동일성의 운영 근거이며 새 화면의 승인은 아니다.

독립 관찰은 다음과 같다.

- 10장의 문제는 media 연속 수가 아니라 외부 제목·내부 선언·하단 과정 안내가 서로 떨어져 경쟁하는 데 있다. 입력 세 메모와 세 연결 대상의 기하 자체는 유용하다.
- 17장은 현상·질문·쓰임이 같은 크기의 세 범주로 보인다. 18장은 사람이 정하고 적는 내용과 AI정리 구분의 무게가 같다. 크기만 조금 바꿔도 관계가 여전히 안 읽히면 교정되지 않은 것이다.
- 20장의 밝은 문서와 네 시간 구간은 읽히는 좋은 대상이다. 바깥의 ‘실제 결과’와 작은 비실측 주의 사이의 간극, 문서 설명의 반복을 고쳐야 한다. 밝은 면을 제거할 이유가 없다.
- 24장의 요청문은 이미 큰 면으로 주역이다. 보조 링크의 성격을 구별하면 되며 새 버튼·별도 행동 표지를 의무로 추가할 이유가 없다.
- 4장의 지원 라벨, 19장의 대등한 활용처, 21장의 병렬 이점, 22장의 대등한 주의 범주는 유효하다. 이것들을 동위계라는 이유로 모두 바꾸면 오히려 판단을 잃는다.

## 두 승인과 판정의 의미

| 대상 | 승인에 필요한 실제 근거 | 승인으로 대신할 수 없는 것 |
| --- | --- | --- |
| 새 본편 | 현 입력에 대응하는 전26장 두 발표 크기, 읽기 두 크기, 장별 및 연속 판단과 현행 검수 명령 결과 | 기존21장 승인, 검정 배경, SVG 원본만 확대, build·경계 검사 성공 |
| AGENTS와 DESIGN의 제작 적합성 | 실제 이번 제작에서 권한·보존·역할·위임·복구·현재판 판정이 작동했는지 구체 사례로 대조하고, 재현되는 모호성/충돌이 해결됨 | 지침 파일 존재, 팀 합의, 단어 존재 검사, 제품이 한 번 보기 좋다는 사실 |

제품의 `approved`는 명시한 장·모드·viewport·입력에만 적용한다. `needs-changes`에는 보이는 문제·보존할 의미·수정할 이해 문제·담당/다음 행동을 남긴다. 화면이 없거나 필요한 읽기 경로를 확인하지 않았으면 `unreviewed`다. 입력이 달라졌으면 과거 판정은 이력으로 남기며 새 캡처를 요구한다. 정책 판정은 별도 서술 기록으로 남기며 기존 제품용 CLI가 정책 품질을 판정한다고 설명하지 않는다.

## 보존 수용 기준

현재26장 주제·전체 논리와 1–25장35분/Q&A5분 배분안을 유지한다. 시간표는 발언 계획이며 실제 리허설 실측으로 바꾸지 않는다. 제목 변경은 대본 시간표·장별 표제·speaker-guide 및 관련 안내와 맞춘다. 제목을 바꾸기 위해 장별 핵심 의미를 버리지 않는다.

본편9도식은 3·5·8·9·10·11·14·16·20장의 의미·관계로 확인한다. 전체19도식, 원문48장·원대본, 데모·학습자료, 사용자 [test.md](../../../talks/llm-wiki/test.md)는 원본을 보존한다. 기존 SVG를 개선할 경우 원본을 덮어쓰지 않고 `talks/llm-wiki/assets/remake/`에 새 파일을 만든다. 본편은 새 자산을 참조할 수 있으며 부록/원본 접근과 출처를 유지한다. 원고의 의미 보존, 원본 파일 보존, 새 화면의 읽힘을 각각 확인한다.

특히 사람의 목적·감정·생각·판단·선택 이유와 원문/내 기록/AI요약·해석 구분을 축약 과정에서 잃지 않는다. RAG와 위키의 병용·검색 필요, 위키 관리비용, 간단한 노트/검색 대안도 남긴다. 문장을 대본으로 옮기더라도 청중이 해당 장에서 읽어야 할 핵심 관계를 감추지 않는다.

## 연속 흐름과 실제 크기

전26장 보드로 정의→비교→연결/활용→목적/판단→한계/첫 행동의 진행을 본다. 개별 PNG로 각 장의 실제 읽는 중심을 확인한다. 특히 3–6의 필요/구조/분담, 7–11의 비교와 다른 기하, 12–14의 읽기/갱신, 15–19의 선택 이유와 사람 책임, 19–22의 실제 문서와 이점/위험, 23–26의 첫 행동/종결을 이어 본다.

8–11의 media 이름 반복은 실패가 아니다. 실제 기하·주역·내용 관계가 구별되는지가 기준이다. 17/18 교정 후 19/21/22가 역할에 맞는 병렬로 여전히 읽히면 유지한다. 구도를 바꾸기 위한 구도 변경, N장마다 색/사진 추가, 최소 장수·레이아웃 수·색면 비율은 합격 기준에 없다.

| 확인 범위 | 필요한 실제 확인 | 통과의 한계 |
| --- | --- | --- |
| 발표1440×1000·DPR1 | 전26장 PNG/보드, 실제 stage 크기 대응, 제목·관계선·자료 본문·출처 위계 | 무대에서의 거리/프로젝터/청중 이해는 미측정 |
| 발표960×900·DPR1 | 전26장 같은 순서, 필수5장과 긴 표/코드/밝은 문서/9도식의 실배치 읽힘 | 브라우저를 확대하거나 SVG만 따로 크게 본 것으로 대체 불가 |
| 읽기1440·390 폭 | 전체26장 내용·원순서·자료/출처/부록 링크, 표·코드 스크롤과 이미지 의미의 접근 | viewport마다 원본 슬라이드 구도를 고정 유지할 의무는 없음 |

글자 크기 한 숫자로 승인하지 않는다. 두 발표 크기에서 핵심 문장·필요 도식 라벨/관계·20장 목표/네 구간/비실측 표기·24장 요청4행과 지원 링크를 실제로 읽을 수 있어야 한다. 작은 출처가 부차적이라는 이유로 찾을 수 없을 만큼 약해져서는 안 된다. 중요한 한국어 어절/표제의 의도치 않은 단절·겹침·잘림을 직접 본다.

390폭 읽기에서 SVG가 축소돼 관계를 못 읽는다면 generic alt만으로 통과시키지 않는다. 같은 의미의 인접 설명·읽을 수 있는 상세 문서 경로·원본 확대 등 실제 제공된 경로를 열어 필요한 대상/관계를 확인한다. 이미지 확대 접근만 제시했다면 실제 조작/내용을 확인하고 그 범위로 판정한다. 전체 내용이 사라진 이미지를 ‘모바일은 원래 작음’으로 승인하지 않는다. 링크는 보이는 존재와 실제 로컬 목적지·원격 href/작동 확인 범위를 구별한다.

root가 이번 준비 단계에서 제공한390×844의 [10장 읽기](../before/reading-390-slide10.png)와 [20장 읽기](../before/reading-390-slide20.png)를 B도 `view_image`로 직접 보았다. 10장의 제목/짧은 과정은 native 문장으로 읽히지만 그림 속 대상/관계 글자는 매우 작고,20장도 문서의 세부 글자는 작지만 `15분 활동 진행안 읽기` 링크가 본문에 있다. figure에 원본 확대 링크가 없다는 DOM 관측은 root에게 전달받은 사실이며 B가 직접 브라우저 조작한 결과는 아니다. 새 판에서는10장의 관계를 읽을 수 있는 경로와20장의 연결된 실제 문서 내용을 직접 열어 확인해야 한다. 이 구체 위험을 포함해 기존9도식과 새 SVG 모두 필요한 관계를 읽을 수 있는지 확인한다. 실제로 막힌 경로는 동등한 native 설명이나 원본 접근 등 최소 해결을 검토하며, 문제가 없는 도식까지 일괄 새 기능으로 바꿀 의무는 없다.

공통 CSS/runtime 변경이 생기면 이 덱뿐 아니라 영향받는 다른 주제의 대표 양식·긴 한국어·밝은 문서·읽기·모션 줄이기까지 검토 범위를 넓힌다. 기존 compose/primary와 덱 전용 자산으로 해결되면 그 범위의 검사를 적용한다. 효과를 새로 넣지 않아도 되며 모션 승인으로 확대하지 않는다.

## 구현 후 독립 검토에 필요한 인계

root가 최신 전체 입력 hash와 두 발표 크기 전26장 PNG/보드·manifest, 읽기1440/390 전체 내용/링크 근거를 제공하면 독립 검토를 재개한다. 각 발표 크기는 현재 도구 계약에 맞게 별도 검수 기록으로 대응한다. 읽기 근거·판정은 실제 지원 형식을 확인해 별도로 연결하며 presentation-stage-only 검사의 성공을 읽기 승인으로 확대하지 않는다.

독립 검토자는 최신 원고/수정자산/대본과 화면을 함께 읽고, 필수5장을 전후로 대조하며 나머지21장도 새 판으로 본다. 화면 입력이 일치하는지 확인한 뒤 구체 이유를 쓰고 승인/수정/미확인으로 판정한다. 양 실무자가 제품과 지침을 각각 판단하고 매니저가 충돌을 해결한다. 수정 요구가 남으면 담당이 수정하고 영향 장·인접 흐름·읽기 경로를 새 화면으로 다시 확인한다. 모든 명시 제품 범위가 승인되고 `--require-approved`가 통과한 뒤에만 그 범위의 제품 승인을 보고한다.

## 상호 검토와 취합

독립 수용 기준의 실질 초안을 먼저 작성하고 A의 [REMAKE_SPEC](REMAKE_SPEC.md) 전문과 매니저의 [DESIGN_CONTRACT](DESIGN_CONTRACT.md) 전문을 실제 읽었다. A도 B와 매니저 초안 전문을 읽고 다음 반론을 직접 교환했다.

- A→B:12장의 세 측면을 화살표로 쓰면 필수 절차로 바꿀 수 있다. B는 수용해 장별 표의 개념별 분리·목차/원자료 재읽기·관계 보완을 대등한 세 측면으로 고쳤다.
- B→A:명세 마감의 `960×900 영향 장`은 root/매니저의 두 크기 전26장 계약보다 좁다. A가 수용해 전26장 두 발표 크기와 읽기1440/390의 전체 내용/접근으로 맞췄다.
- B→A:10장의 요약↔개념/계획 표기를 그대로 양방향 화살표로 구현하면 원본의 방향 없는 연결선보다 강한 의미를 주장할 수 있다. A가 수용해 관계를 문장으로 적고 새 양방향 화살표를 필수로 삼지 않음을 명시했다.
- B→A:18장 후보에서 `내가 적는다`만 남으면 원문의 `목적은 내가 정한다`가 약해질 수 있다. A가 수용해 후보에 `목적은 직접 정하고`를 명시하여 자기결정과 기록을 함께 보존했다.
- 양측:17의 질문→18의 직접 책임은 quote 조판을 연속 재사용해도 실질 전개가 있으므로 허용한다. 18의 구체 항목은 보조 크기라는 이유만으로 실패시키지 않고 두 실제 크기에서 필요한 말이 읽히는지 판정한다. 24의 H3는 코드보다 클 수 있으므로 라벨 존재만으로 해결을 판정하지 않는다.

B는 A의 반론 반영 최종 전문과 매니저 계약 전문을 다시 읽고, 세 파일의 보존·최소 교정·실화면 범위·모바일 의미 접근·승인 구분에 남은 충돌이 없음을 확인했다. A의 작은 읽기 절은10장의 관계 설명/상세 경로,20장의 전체 native 문서 열기,나머지7도식의 의미 접근을 구체화하며 generic alt나 파일 존재만으로 합격시키지 않는다. 초기 계약의 상호 검토·취합은 완료했다. **실제 구현, 최신 화면의 독립 제품 검수, 실제 제작에 근거한 AGENTS/DESIGN 적합성 판정은 다음 단계로 남아 있다.**
