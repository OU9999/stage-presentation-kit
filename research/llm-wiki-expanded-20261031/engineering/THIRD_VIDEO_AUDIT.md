## 기존 48장에서 보존할 기술 계약

1. RAG는 필요한 외부 자료를 찾아 생성에 사용하는 패턴, Wiki는 지속 지식 문서를 작성·갱신하는 층. 둘은 병행 가능.
2. RAG도 관계·요약·결과를 축적할 수 있고 Wiki도 목차·파일/의미 검색을 사용할 수 있음.
3. 문서 갱신·현재 입력 문맥·모델 파라미터 학습 구분. ‘모델이 새로 학습 불가능’은 모든 학습 방법에 대한 보편 명제로 옮기지 않음.
4. 입력과 원자료 보존·작성 주체·해석·근거·읽은 범위를 구분. Markdown 사용만으로 토큰/비용/정확도가 항상 개선된다고 주장하지 않음.
5. ingest/query/lint는 같은 위키로 돌아오고, 실제 읽은/바뀐 파일을 확인해야 함. 목차·메모리가 존재한다는 사실만으로 최신 문맥이 읽혔다고 확정하지 않음.
6. 다중 에이전트·여러 설정 파일·훅·SQLite·Discord·클리핑 도구는 개인 구현의 선택. 필수 설치/규격으로 확대하지 않음.
7. 여러 검토자의 합의는 근거 대조의 대체물이 아님. 실제 산출물·원문·조건과 대조.

## 새로 강화할 계약

### 골드 데이터와 사람의 입력

- 골드는 원문의 화자가 쓰는 목적 관련 선별 자료·경험·생각의 표현
- 라벨이 붙은 gold truth, 검증된 정답, 데이터 품질의 인증으로 해석 금지
- 목적과 최종 쓸 결과를 정한 뒤 필요한 자료를 고름
- 사람의 직접 메모·판단과 AI가 작성한 정리를 구분해 읽고, 함께 사용할 때도 출처·작성 주체를 남김
- 이번 팩의 예시 위키는 발표팀이 작성한 기대 모양이며, 실제 모델 실행의 산출물로 허위 표기하지 않음

### 질문에서 실제 사용할 결과로

- 기존 `wiki/syntheses/study-plan.md`는 현재 판단·계획의 입력층
- 그 계획과 관련 개념/비교를 재읽고 ‘15분 스터디 진행안 한 쪽’이라는 실제 검토 가능한 별도 예제 산출물 제작
- 산출물 검토에서 목적·근거·시간 배분·작성 주체·미확인 조건을 확인
- 검토 후 결과·바꾼 이유·다음 확인을 다시 위키에 연결
- 샘플 산출물이 존재하는 것과 실제 스터디에서 유용했던 것은 구분

### 공유 공간의 네 질문

- 맥락: 어떤 자료·현재 판단·조건을 공유하나?
- 요청: 무엇을 어떤 기준으로 만들어 달라고 하나?
- 논의: 어떤 대안·근거·수정이 있었나?
- 결과: 실제 무엇이 남았고 어디까지 확인했나?

네 개 파일을 반드시 만들라는 표준이 아니라 공유 작업을 이어 읽는 질문으로 소개. 한 사람·한 에이전트의 작업에도 적용 가능.

## 새 발표 전문가팀과 직접 교차

Sol/xhigh 리드·청중 전문가의 37~41장 전환안에 기술적으로 동의: 학습→공유 공간→맥락/요청/논의/결과→1쪽 진행안→검토와 결과/이유 저장. 이 구간 합계 235초를 유지해 본편 35분·Q&A 5분 유지.

첫 입력은 세 영상의 읽기 메모로 통일하고, 15분 미니 활동에서는 그중 두 개를 골라 읽는 조건을 분명히 하면 모순이 없음. 2분 목적+4분 선택 메모 읽기+5분 연결/근거 확인+4분 후속 질문/남은 확인은 배분 예로 적절. 설치·모델 응답·새 시스템 구축까지 15분에 완주한다는 약속은 하지 않음.
