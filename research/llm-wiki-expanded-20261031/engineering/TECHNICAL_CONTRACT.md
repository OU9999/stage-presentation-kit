# 확장 발표 기술 계약

## 기술적 중심

LLM Wiki는 LLM이 원자료의 개념·개체·비교·종합을 연결된 문서로 지속 작성하고 갱신하는 패턴. 새 자료를 기존 설명에 통합하고, 다음 질문에서 필요한 쪽을 찾아 다시 읽으며, 유용한 결과도 다시 연결한다.

파일 형식, 정정의 정확성, 모델 학습 경계 하나가 전체 주제를 대신하지 않게 한다. 이번 본편의 주인공은 지속되는 지식 문서와 그것을 유지하는 LLM이다.

## 24장 판에서 확대할 내용

| 24장 판의 편중·빈곳 | 새 본편에서 설명할 대상 | 화면의 실제 행동 |
| --- | --- | --- |
| RAG/LoRA를 구별하는 한 비교가 중심 | 왜 흩어진 개인 지식에 지속 정리층을 두는가 | 같은 사람이 두 번 묻는 질문과 이미 남긴 관계 |
| 파일 두 개와 개념·비교만 강조 | 자료 요약·개체·개념·비교·종합·질문과 목차/로그의 다른 역할 | 같은 자료가 역할이 다른 여러 문서에 연결 |
| 인제스트를 한 쪽 반영으로 설명 | 새 자료 하나가 기존 여러 페이지에 미치는 영향 | 입력→개념 적용 범위·비교 기준·현재 계획 변경 |
| 후속 질문이 모델 학습 오해 교정 | 실제 필요한 새 판단·계획·비교에 이전 종합 재사용 | 관련 페이지 읽기→답/계획→검토 뒤 저장 |
| lint가 점검 목록 한 장 | 낡은 계획·빠진 연결을 찾고 수정·재읽기 | 이전 계획과 새 조건 대조, 수정 이력 |
| 비용·확장성을 짧게 지나감 | 입력시 정리·갱신 부담과 질문시 검색·재종합 부담 | 언제 어떤 일이 드는지, 병행 가능성 |
| 목적 한 줄만 제시 | 저장 이유·본인 맥락·쓰고 싶은 결과가 분류와 종합을 바꿈 | 같은 자료라도 다른 목적의 문서 강조 |

## 본편에 있어야 할 특징

| 특징 | 설명에서 필요한 내용 | 오해 방지 |
| --- | --- | --- |
| 지속성 | 정리 결과가 채팅 밖 문서로 남음 | 저장만으로 모든 다음 요청에 자동 주입 아님 |
| 연결성 | 자료 사이 개념·조건·비교가 드러남 | 링크 수·그래프 모양이 의미 정확도의 증거 아님 |
| 다중 페이지 | 자료별 요약과 주제별 설명을 함께 유지 | 모든 자료가 항상 일정 개수 파일을 바꾸는 규칙 아님 |
| 갱신 | 새 정보·관점이 관련 기존 설명도 보완 | 보편 정의를 임의 목적에 맞춰 뒤집지 않음 |
| 재사용 | 관련 쪽을 읽고 새 질문에 종합 | 이전 답을 무검토 복붙하는 동작과 구분 |
| 사용자 맥락 | 목적·범위·활용 의도가 정리를 이끔 | 거대한 개인 프로필·24시간 수집 필수 아님 |
| 원자료·출처 | 원자료를 보존하고 주장 근거로 돌아감 | 보존된 원자료가 항상 참이라는 의미 아님 |
| 목차·로그 | 찾아갈 입구와 변경 이유·시점 구별 | 하나가 다른 하나를 대신하지 않음 |
| 역할 분담 | 사람이 자료·질문·범위를 정하고 LLM이 작성·연결·갱신 | 사람이 모든 페이지를 직접 작성해야 하는 정의 아님 |
| 세 작업 | ingest/query/lint가 같은 위키에 돌아옴 | 자동 완전 유지·무오류 보장 아님 |
| 검색 조합 | 목차·파일 검색·의미 검색을 필요에 맞게 사용 | 무검색·벡터DB 금지 같은 규격 아님 |
| 결과 형태 | 답·표·계획·발표 등으로 활용 가능 | 모든 산출물이 무조건 위키 현행본이 되지는 않음 |

## 같은 원자료·같은 질문으로 비교하는 두 장

공통 질문 예: ‘다음 AI 스터디에서 LLM Wiki를 어떻게 시도할까?’

### 기본 RAG 흐름의 예

- 화면 문구: **이번 답에 필요한 근거를 찾는다**
- 흐름: 같은 원자료→질문에 맞는 근거 검색→현재 입력에서 종합→이번 답
- 말하기: 지금 질문에 필요한 근거를 찾아 생성 모델에 넣는 흐름. 무엇을 찾고 어떻게 합치는지 설계가 필요함
- 범위: 이해를 위한 기본 검색-생성 예. 모든 RAG 시스템의 저장 기능·관계 정리·입력시 종합을 금지하는 정의가 아님

### LLM Wiki 흐름의 예

- 화면 문구: **이미 정리한 관계를 다시 읽는다**
- 흐름: 같은 원자료를 반영→개념·비교·종합 문서에 관계를 유지→필요한 쪽을 찾아 읽기→이번 답과 유용한 결과의 갱신
- 말하기: 이전 이해를 문서로 남겨 다음 탐색의 출발점으로 활용. 필요한 원자료도 다시 확인
- 범위: 파일 갱신·범위 검토·검색 누락·문맥 한계와 비용이 남음

공통 하단: **검색과 지식 정리는 함께 쓸 수 있습니다.**

### 비용 비교의 정확한 축

| 시점 | 기본 검색-생성 예 | 위키를 유지하는 예 |
| --- | --- | --- |
| 입력·변경시 | 자료 정제·분할·색인/갱신 | 원자료 읽기·관계 종합·관련 문서 갱신·검토 |
| 질문시 | 근거 검색·선별·현재 답 종합 | 관련 쪽 검색·재읽기·현재 답 종합·필요시 원자료 대조 |
| 유지시 | 검색/생성 평가·색인·접근 정책 | 설명 최신성·중복/모순·연결·검색·접근 정책 |

정량 비용·정확도·속도 우위는 이번 예제로 입증하지 않음. 새 자료가 들어올 때 관계를 미리 정리하려는 설계 의도를 설명한다.

## 네 방식은 서로 다른 축

| 방식 | 중심 작업 | 주로 사용하는/바꾸는 대상 |
| --- | --- | --- |
| RAG | 외부 자료를 찾아 생성에 사용 | 검색된 근거와 현재 입력 문맥 |
| Agentic RAG | 검색 시점·도구·방식·반복을 에이전트가 결정 | 검색 계획과 현재 입력 문맥 |
| 파인튜닝 | 학습 예제로 모델 동작 조정 | 모델 파라미터·학습 가능한 어댑터 |
| LLM Wiki | 연결된 지식 문서 지속 작성·갱신 | 개념·비교·종합 등 지속 문서 |

위키를 검색 대상으로 삼거나, 위키를 읽는 에이전트가 검색 계획을 세우거나, 조정한 모델을 함께 쓸 수 있다. 신구 세대·우열·택일 비교 금지. RAG 원논문에도 학습이 있으므로 ‘RAG에는 학습이 없다’로 전부 정의하지 않는다.

## 중심 예제에 대한 직접 교차 의견

video_curriculum의 두 실제 영상 읽기 메모→LLM Wiki 개념/검색 개념→RAG 비교→스터디 계획을 중심 예제로 채택하는 안에 동의.

- `raw/brian-video.md`, `raw/yongdam-video.md`: 실제 영상의 시간별 자가 의역, 설명과 기술적 교정을 구분
- `wiki/concepts/llm-wiki.md`, `retrieval.md`: 정의·작동·서로 연결되는 조건
- `wiki/comparisons/rag-vs-wiki.md`: 같은 질문·동일 축의 비교
- `wiki/syntheses/study-plan.md`: 우리 목적과 제약을 반영한 현재 계획
- 새 `raw/study-retro.md`: 실제 스터디 실행 결과가 아닌 **가상 조건·질문**으로 명시
- 새 입력 뒤 개념의 ‘우리 적용 범위’, 비교의 ‘선택 기준’, 종합의 ‘현재 계획’을 각각 갱신
- 중요한 구분: 입문자·시간 같은 새 조건은 LLM Wiki의 보편 정의를 바꾸지 않음
- 목차/로그/관련 질문도 갱신해 탐색과 이유가 이어지게 함
- lint 예는 낡은 계획·빠진 연결의 수정으로 보여주고, 기술 오류 반박만으로 발표를 채우지 않음

## 원문 발언을 그대로 옮기지 않을 표현

| 영상 취지·일반화 위험 | 새 발표 문구 |
| --- | --- |
| RAG는 새 자료마다 전체 재색인 필요 | 문서별 갱신도 가능하며 실제 비용은 설계에 따라 다름 |
| RAG는 자료 사이 관계를 축적 못함 | 기본 검색-생성 예와 대비한 지속 문서의 가치; GraphRAG처럼 관계·요약을 미리 만드는 구현도 존재 |
| 위키에는 검색 기능 없음 | 필요한 페이지를 찾는 방법은 목차부터 검색 도구까지 다양 |
| 문서 10만 개가 공식 경계 | 자료량·질문·검색 품질·권한·갱신 비용으로 판단 |
| 특정 두 제품 필수 | 문서를 보는 도구와 파일을 쓰는 에이전트의 한 조합 |
| 위키가 기업에서 항상 더 좋음 | 목적·자료·접근 범위·검토와 유지 부담으로 검토 |
| 로컬 모델이면 보안 문제 모두 해결 | 실행 위치와 별개로 누가 어떤 원자료와 파생 문서를 읽을지 정해야 함 |
| 더 비싼 모델로 모든 개인기록 처리 필수 | 이번 목적과 공개 자료 몇 개로 시작 가능 |
| 그래프가 온톨로지의 완성 | 연결을 탐색하는 보기이며 분류·연결 규칙은 별도로 설명 |
