## 전달된 원리와 주장

LLM Wiki는 파일을 읽고 쓸 수 있는 LLM 에이전트가 여러 원자료에서 개념·비교·연결·잠정 종합을 Markdown 페이지로 작성하고 계속 갱신하여, 다음 질문이 그 페이지를 다시 찾아 읽게 하는 방식이다(2·4·5·8장). raw는 보존 입력, wiki는 갱신 설명이며 schema는 두 영역 전체에 적용할 규칙이다(6장). ingest/query/lint는 한 위키를 유지하는 서로 다른 작업이고 고정 파이프라인이 아니다(7~9·23장). 가중치 학습이나 모든 모델의 자동 기억을 약속하지 않는다(5·8장).

세 가상 적용 예는 인물/주제 해석, 고객 요구/현재 상태, 강의 개념/기준 비교를 남기고 다음 질문에 재사용하는 같은 구조를 전달한다(10~19장). 새 자료는 확정 사실만 늘리는 것이 아니라 미확인과 조건 차이, 보류 상태를 보존하도록 한다. 중요한 문장과 실제 읽음을 확인하고, 다시 쓸 가치와 유지 부담을 자기 질문으로 판단하라는 주장까지 이어진다(20~22·26장). 설계 설명이며 실제 모델 실행이나 효과 검증 결과라고 읽히지 않는다.

## 주의와 남은 질문

- 20·27장 및 기본2~4 안내에서 '실제 읽은 파일 확인'이 자기보고인지 도구 실행 기록까지 대조하는지 목적지를 읽고 확인할 필요가 있다.
- 25·27장의 내 자료 작성 경로는 위치·권한·규칙을 포함해 구체적이다. 다만 아직 목적지를 안 읽었으므로 개인 도구의 첫 실행/복구 성공 여부나 안내의 완결성은 판단할 수 없다.
- 27장의 같은 크기 세 카드는 개념 이해/실제 파일 에이전트 작성/고정 파일 교정을 분류한다. 레이블과 대본으로 구별되지만 시각적 동등함이 효력 동등으로 확대되는지 연결 내용과 함께 최종 점검할 것이다.
- 소설에서 자기 설명을 확정 동기로 바꾸지 않는 점(11~12), 접수 요구를 약속으로 바꾸지 않는 점(14~15), 예의 기준을 전체로 넓히지 않는 점(17~18·21)은 화면/대본 차원에서 일관된다. 실제 구성 파일도 이 범위를 지키는지 아직 미확인이다.
- 비교가 검색 일반의 한계라는 식의 과장 문구는 현재 관찰 범위에 없다(3·20장). 성능·비용 비교를 증명했다는 주장도 없다.

## 미감과 서사 독립 판단

큰 한 문장→역할/구조 도해→세 사례의 갱신과 질문→한계→자기 질문→시작 경로의 순서로 새 개념이 공개된다. 4장 도해를 23장에 회수하고 책상 사진을 26장에서 다시 사용해 처음의 읽기 경험으로 돌아온다. 검정 배경과 제한된 강조색, 표·선·카드의 반복으로 시각 규칙이 일관된다. 2장 정의는 길지만 첫 질문 뒤 바로 구체적 동작을 고정하는 이익이 크다. 27장의 큰 카드 세 개는 읽는 순서가 선명하나 여러 링크가 몰려 말로 구분하는 대본이 중요하다. 화면과 대본만으로 추가 제품 수정이 반드시 필요한 결함은 현재 식별하지 못했다. 이는 청중 이해도나 발표 시간의 입증이 아니다.
