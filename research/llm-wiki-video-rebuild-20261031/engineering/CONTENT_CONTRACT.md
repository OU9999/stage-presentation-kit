## 핵심 한 문장

LLM Wiki는 LLM이 원자료를 읽어 개념·비교·종합을 연결된 문서로 작성하고 갱신해, 다음 질문에서 그 정리를 다시 읽어 활용하는 지식관리 패턴.

## 같은 질문으로 비교

| 방식 | 중심 작업 | 주로 달라지는 대상 | 다음 요청에서 사용하는 것 |
| --- | --- | --- | --- |
| RAG | 필요한 외부 자료를 검색해 답 생성 | 검색 인덱스·현재 입력 문맥 | 검색된 자료와 질문 |
| Agentic RAG | 에이전트가 검색 필요·질문·도구·반복을 결정 | 검색 계획과 현재 입력 문맥 | 도구로 모은 근거와 질문 |
| 파인튜닝 | 예제와 학습으로 모델 동작 조정 | 모델 파라미터 또는 학습된 어댑터 | 조정된 모델; 외부 검색과 함께 사용 가능 |
| LLM Wiki | 원자료의 관계와 종합을 문서로 유지 | 지속되는 연결 문서 | 필요한 위키 페이지와 원자료 |

- 분류 축이 서로 다름: 검색 전략·모델 적응·지식 저장을 묶어 비교한 교육용 표
- 위키는 RAG의 검색 대상이 될 수 있고, 위키 에이전트는 agentic retrieval을 쓸 수 있음
- 위키 저장은 모델 가중치 학습과 구별; 파일의 설명을 다음 요청에 다시 읽혀야 활용 가능
- RAG 시스템에 답 저장·요약 계층이 없는 것은 정의상의 필수가 아님

## 화면에서 보여줄 단일 사례

권고: AI 스터디 노트를 한 질문으로 묶기. 원논문 텍스트는 짧게 의역하고 전체 복제 금지.

1. 질문: ‘우리가 만든 위키를 고치면 모델도 학습되는 걸까?’
2. 원자료 A: 검색 결과가 생성 모델 입력에 들어간다는 RAG 읽기 메모
3. 원자료 B: LoRA에서 학습 가능한 행렬을 조정한다는 읽기 메모
4. 위키: `concepts/retrieval.md`, `concepts/model-adaptation.md`, `comparisons/context-vs-weights.md`
5. 다음 질문: ‘우리 스터디의 최신 정정은 어디에 반영할까?’
6. 답: 먼저 위키 문장을 고치고 그 페이지를 찾아 읽기. 모델을 따로 학습시켰다는 의미는 아님
7. 새 자료: 실제 사용 도구의 검색·파일 읽기 방식 확인; 개념 페이지와 비교 페이지를 함께 갱신
8. 사람 확인: 저장한 답이 원자료를 지원하는지 재읽고 문장 수정; 링크가 있는 사실만으로 참으로 판정 금지

실제 출력으로 소개할 수 있는 것은 이번에 실제 실행·기록한 내용뿐. 파일 편집 예시는 ‘설명용 구성 예’, 기존 ZIP은 ‘고정 교정 실습’으로 명시.

## 표현 교정 계약

| 피할 일반화 | 발표용 문구 |
| --- | --- |
| RAG는 문서마다 전체 재색인 필요 | 변경 문서만 갱신할 수도 있으며 구현에 따라 비용이 달라진다 |
| RAG는 단순 문자열 검색 또는 벡터DB뿐 | 필요한 외부 자료를 찾아 생성에 쓰는 패턴; 검색 방식은 다양 |
| RAG는 학습이 없다 | 위키 파일 갱신과 모델 파라미터 학습은 다른 작업 |
| 위키는 검색이 필요 없다 | 작을 때 목차로 시작하고 커지면 검색을 함께 쓴다 |
| 위키는 모순을 자동으로 모두 해결 | LLM이 갱신·점검하고 사람이 중요한 결과를 확인한다 |
| 위키가 더 싸고 정확하다 | 반복하는 질문에서 가치가 있는지 실제 자료로 비교한다 |
| Obsidian+Claude Code 필수 | 파일을 쓰는 에이전트와 문서를 읽는 도구의 한 조합 |
| 그래프가 AI의 기억 자체 | 파일 간 연결을 탐색하는 보기 방식 |
| 모든 자료를 넣으면 나를 이해한다 | 목적과 질문을 먼저 정하고 필요한 자료부터 선택한다 |
