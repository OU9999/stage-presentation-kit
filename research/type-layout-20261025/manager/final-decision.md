# 제품 적용 결정

담당: 디자인 매니저 `/root/design_manager`. 두 실무의 실제 독립 시안과 두 차례 상호 비평을 바탕으로 한 STAGE의 독자 결정이다. Apple/OpenAI/Anthropic 이름을 제품 preset으로 만들지 않는다. 공식 장면은 [A 근거](../apple-openai/sources.md)·[B 근거](../anthropic/sources.md)에 관찰 범위를 구분했다.

## 사용할 구조

- **선언/표지:** 하나의 큰 문장 블록과 보조 설명. 기존 `align`과 title 배열의 명시적 줄바꿈을 우선한다. 현재 예제의 `align:center`를 왼쪽으로 바꾸지 않는다. 연사·날짜도 보존한다.
- **넓은 증거(wide):** 위쪽에 주장과 제한된 수치 열, 아래에 전폭 차트. A의 넓은 증거를 채택하되 음수 margin으로 숫자를 끌어올리는 초안은 기각한다. copy/hero/plot을 명시적인 grid 영역으로 두고, hero 열은300px로 제한해 제목 폭이 값의 길이에 종속되지 않게 한다.
- **설명과 근거(split):** 왼쪽 약38–40%에 주장·설명, 오른쪽에 수치+레이블과 해당 차트. B의 관계 묶음과 상단 정렬을 채택한다. 수치를 왼쪽 아래 멀리 떼어 두거나 제목보다 위에 띄워 두지 않는다. 기존 `composition:'split'`을 재사용한다.
- **설명+짧은 흐름도:** 4개 단계와 같은 관계는 전폭으로 유지한다. 모든 도식을 좁은 오른쪽 열에 세로로 넣던 B 초안은 기각한다. 긴 설명이 필요한 장에서만 split을 선택한다. 외곽 장식 패널은 만들지 않는다.

## 글폭·정렬·간격

1600×900의 기존 무대 기준 권고다. 아래 값은 원본 회사의 측정값이 아니다.

| 역할 | 데스크톱 기본 | 390px 읽기 |
| --- | --- | --- |
| visual 주장 | wide74px/1.18, 최대15em; split64px/1.2, 최대11em | 35px/1.26 |
| 설명 | 26px/1.55, wide36em, split 열 너비 이내 | 18px/1.65 |
| 긴 본문 | 전폭 읽기 영역,30px/1.65,34em 이내 | 18px/1.7 |
| 수치·단위·레이블 | 수치128px, 단위40px·중립색, 레이블22px | 수치80px, 단위26px, 레이블16px |
| 흐름도 단계 | 38px/1.4 | 24px/1.45 |
| 상세 표 | 원본에서 생성 | 실제 HTML16px, 지역 스크롤 |

주장→설명은24px, 글 묶음→증거는40px를 기본으로 둔다. 단위/기간/출처는 주장을 방해하지 않는18px/1.5의 작은 조건으로 묶고, 도표가 이미 단위를 명확히 제시하는 경우 같은 단위만 별도 큰 간격으로 반복하지 않는다. 이때 작성자가 입력한 설명·기간·출처를 삭제하지 않는다. 본문은 `word-break:keep-all`과 긴 토큰의 `overflow-wrap:anywhere`를 조합한다. 문장을 의미 없이 줄이거나 고정 문자수로 반려하지 않는다.

## 긴 값과 긴 문장

숫자+단위 **전체 한 줄**의 실제 폭을 측정한다. 제한 열보다 길면 숫자를 제목 쪽으로 밀어 넣지 말고 전폭의 독립 행으로 옮긴다. 숫자의 일부를 자르거나0으로 대체하지 않는다. 먼저 공간을 확장하고 모바일에서는 단위를 별도 줄로 분리한다. 극단적으로 긴 한 수치의 행 조정은 국소적으로만 하며 모든 글을 일괄 축소하지 않는다. 변경/resize 후 재평가해도 편집 중인 DOM 원문을 초기화하지 않는다.

긴 한국어는 먼저 전폭의 읽기 폭과 줄바꿈을 확보하고, 본문을 제목과 다른 크기·행간으로 둔다. 입력된 title 배열/줄바꿈은 보존한다. 무제한 텍스트가 한 발표 화면에 들어간다는 보장은 하지 않으며, 읽기 모드에서 전체 원문을 이어 읽을 수 있어야 한다. 모바일은 무대 축소본 대신 글→수치/레이블→그림→상세표 순서로 재배치한다.

## 최소 수정 파일과 순서

1. `visual.css`: wide/split 명시 grid, 독립된 제목 읽기 폭, 상단 정렬, 설명/조건 간격, 흐름도 글 크기, 390px 문서 흐름을 먼저 적용한다. 현재 테마의 `--slide-*`를 유지한다.
2. `app.js`: 필요한 경우에만 수치+단위 한 줄에 클래스와 폭 검사용 hook을 추가한다. 원고/레이블/숫자 계산 경로와 native 편집 필드는 재사용한다. 기존 `.visual-copy`, `.visual-hero`, `.visual-plot`만으로 grid를 바꿀 수 있으므로 새 렌더러나 큰 API는 필요 없다. `scaleStages()`의 render/resize 경로와 입력 후 `scheduleDiagnostics()`에서 DOM만 재평가하고 rawDeck을 바꾸지 않는다. overview/presenter 복제도 같은 최종 배치를 얻어야 한다.
3. `styles.css`: 공통 제목의 한국어 줄바꿈/긴 토큰 처리 등 다른 레이아웃에서도 필요한 작은 규칙만 조정한다. 기존 명시적 중앙정렬·배열 title·cover metadata를 이기지 않게 한다.
4. 제품 반례 검수 후 기존 배포 사본/버전 참조를 현재 프로젝트 방식으로 갱신한다. 시안의 임시 편집 버튼·재생 UI를 이식하지 않고 기존 저장/표/내보내기/motion을 유지한다.

## 검수 범위

실무의 두 라운드 기록과 매니저의 최종 독립 브라우저 검수는 [취합](../synthesis.md)·[토론](../discussion.md)·`final-browser.json`에 남긴다. 제품 적용·저장/내보내기 회귀는 이 독립 시안 검수와 구분하며 총괄의 후속 통합 검수에서 완료한다. 이번 범위에 PDF·새 브랜딩·프레임워크 교체는 없다.
