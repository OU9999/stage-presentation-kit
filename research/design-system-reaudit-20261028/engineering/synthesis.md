## 판정

## 추가 색 판정: 팔레트 보존과 새 예제 전달은 다름

사용자가 기존 좋은 DevDay 참고 컬러 사용도 예제에 없다고 추가 지적했다. 매니저가 정적으로 확인한 현재 경로는 [FRONT](../../../scripts/markdown-document.cjs#L10)에 tone 없음, 일반 장 생성에 tone 없음, [StageBlocks](../../../blocks.js#L28)의 허용 attrs에 palette/tone 없음, [strong/em](../../../blocks.css#L18)의 색은 기본 중립 `--slide-accent`다. root computed 기록에서도 새 두 덱의 strong은 `rgb(232,232,229)`이다. 이미지 안의 파랑/사진색이 있는 사실은 원고에서 의미색을 작성·재사용하는 경로의 대체물이 아니다.

반면 [기존 토큰](../../../styles.css#L50)의 orange/purple/blue/green/yellow·Paper 대응색, item tone·native palette는 남아 있다. model/app에는 slide tone 검증과 data-tone 적용도 이미 있으므로 전체 색 엔진을 다시 만들 문제가 아니라 일반 원고의 작성 입구·의미 표현·기본 예제에 연결할 문제다. 실제 pair의 값은 blue/orange이고 단위는 중립이며 category 색은 라벨/아이콘에 대응한다. root의 최종14관찰은 강조 자식까지 측정해 주황/보라와 Paper 대응색도 확인했다. 이는 STAGE 구현값이지 공식 OpenAI HEX 규격이 아니다. 색 token의 존재나 제목 부모의 중립 computed color만으로 강조 자식의 색까지 판정하지 않으며 이 관찰을 대비/WCAG·관객 독해 통과로 확대하지 않는다.

**색 역할 전달은 필수 후속이다.** 선언의 저자 의미 단위·수치와 중립 단위/출처·범주 색+라벨/위치·사진/UI 고유색·중립으로 돌아오는 연속 리듬을 실제 서로 다른 서사에서 재현해야 한다. 매 덱 모든 색을 채우거나 색 개수를 늘리는 과제가 아니다. Paper 등 기존 테마 대응·실제 대비도 영향 범위에서 확인한다.

FRONT에 tone 하나를 추가하거나 기본 accent를 한 색으로 교체하는 것만으로 완료하지 않는다. strong/em 활용·tone binding·작은 저자 선택은 시안 후보이며 정확한 문법/API를 먼저 고정하지 않는다. 임의 감정/성과색 추론·슬라이드별 색 순환·수치 단위/출처까지 일괄 착색은 해법으로 삼지 않는다. 작성자가 새 일반 MD에서 JSON/HTML/CSS를 반복 작성하지 않고 이 색 역할을 얻는지 실제 수정 작업으로 검수한다.

## 앞선 복원 합의의 수정

이전 팀 선호를 사용자 확정 요구로 고정하지 않는다.

- **profile 의무와1~2hint 충분성 폐기:** 먼저 무선택 기본을 인수한다. 선택은 필요한 제어 수단이며 실제 필요한 수/재입력/수동 조정은 작성 작업에서 확인한다.
- **모든 header 가시1회·표시 중복0의 기계적 규칙 폐기:** 구조 라벨 통합과 정보성 조건을 구분한다. native55% hero+plot처럼 같은 원본의 유익한 반복은 허용하되 별도 수치 권위·불일치·버그성 H1 복제는 막는다.
- **모든 보이는 위치=원고 순서 규칙 폐기:** C04의 실제 주역은4번째다. 비선형 주역/면적과 DOM/read 논리 순서를 구분한다. 현재 kit mosaic 샘플이 실제 역전했다는 뜻은 아니며 CONFIG/packMosaic의 일반 빈칸 메움 허용을 별도 근거로 쓴다. 절차·시간·인과/정량 관계는 보존한다.
- **source1문단·3열2행·H2 고정 그룹은 가안으로 환원:** 두값과 조건/출처의 연결은 명확해야 하나 자연 원고의 복수 문단·추가 표행·매체 묶음을 실제 작성해 지원 범위와 비용을 결정한다.
- **모든 표현 부적합 hard error 재검토:** unsafe 구문/필수 자산/모호 binding과 공간 부족을 구분한다. 보이는 warning+온전한 원문 fallback은 손실 방지 후보이며 **build 성공이나 fallback은 release의 발표 가독성/미감 합격이 아니다.** silent 누락·추론은 허용하지 않는다.

사실/관계와 조판 자동성도 나눈다. AST 길이/형태·비율·마지막 위치를 조판 입력으로 쓰는 후보는 비교할 수 있다. 이를 저자 의도 단정·새 맺음 문구 생성·조건/링크 숨김·표를 성과 chart로 바꾸는 추론과 동일시하지 않는다. 기존 [명시 분자/분모 계산](../../../deck-model.js#L136)의 `n/d*100`, [원분자/분모 표 보존](../../../visual.js#L365)·focus/hero/plot 재사용은 유지한다.

단일 원고와 read 전문·값/단위/대상/기간/조건/가상·실측 성격/인용 귀속/링크 목적/사실인 순서는 보존한다. 표현상 구조 라벨 통합·비선형 위치·강조 반복·저자가 명시한 투영은 검토 가능하되 변경을 보여 주고 원문에 추적 가능해야 한다. 중요한 조건을 read/aria에만 두는 우회나 무단 요약/숨김을 구현한 것은 아니다.

## 직접 교차 검토와 한계

A/B는 각각 실질 초안을 쓴 뒤 상대 전체 문서·통제 generator/관찰을 읽었다. A는 mosaic 실제 샘플/일반지원의 구분·C4번째 주역·native 반복을 전달했고 B가 반영했다. B는 마지막 위치를 조판에 쓰는 것까지 금지하면 자동성과 사실을 혼동한다는 반론을 보냈고 A가 수용했다. A는 완전한 원문 fallback도 긴표/code의 발표 합격은 아니라는 반례를 보냈고 B가 build 손실 방지와 release 인수를 분리했다. 기존 명시 계산/조건 보존·기본 시안 우선·작은 표현 책임·실제 작성 작업으로 판단함에 합의했다.

R1에서 디자인 매니저가 필수/시안/유지와 색 전달 실패를 제안했고 엔지니어링은 단순 tone/accent 변경으로 완료할 수 없음·원문 fallback의 손실방지와 release 독해 인수 분리를 반론했다. 디자인이 두 보강을 수용했다.
