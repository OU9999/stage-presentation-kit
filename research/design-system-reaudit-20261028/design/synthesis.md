# 전면 감사 디자인팀 종합과 후속조치 판정

초안 취합 B `/root/design_manager/story_designer` · 최종 판정회의 반영 `/root/design_manager` · 2026-10-28. [A 시각 시스템 감사](visual-system-audit.md)와 [B 이전 합의 반대 검토](proposal-counterreview.md)를 독립 작성·교차 검토한 뒤 엔지니어링 매니저와 R1/R2를 직접 교환하고 상호 수신 확인했다. 사용자의 추가 컬러 지침도 필수 축으로 통합했다. 제품·원고·기존 연구는 읽기 전용이며 새 구현·commit·배포는 수행하지 않았다. 아래는 후속 필요/범위/담당/종료의 최종 판정이며 정확한 새 문법·시안의 성공 판정은 아니다.

## 판정

**후속조치가 필요하다.** 문제는 새 두 원고의 작은 이미지 몇 장에 그치지 않는다. 기본 작성 경로가 기존 STAGE의 시선 중심·자료 면적·정보량·색의 역할·매체 편집·장간 전환을 제공하는지 인수하지 않은 시스템 문제다. 기존 코드와20양식이 남아 있고 기능 검사210개가 통과했다는 사실은 새 기본 경험의 미감 보존을 입증하지 못했다.

이전 복원 회의는 원인을 올바르게 좁혔지만, 실제 동일 원고 시안을 보기 전에 표현을 제한하는 parser 계약에 빨리 합의했다. 모든 header의 가시1회, source1문단, H2 그룹, 모든 보이는 순서 동일, 엄격한 hint 실패, profile opt-in+선택1~2장으로 충분하다는 조건을 사용자 요구처럼 유지해서는 안 된다. 해당 조건은 아래와 같이 수정 또는 폐기한다.

## 확인한 범위와 증거

## 컬러 전달 실패와 필수 후속

사용자는 “기존의 좋은 OpenAI DevDay 컬러들 사용도 예제에는 전혀 없네?”라고 추가 지적했다. [색 inventory와 실제3probe](../evidence/color-inventory.json)를 읽어 새12장의 tone0·ordinary strong AST 유지·frontmatter tone 거절·legacy tone 지원을 확인했다. `blocks.css`의 strong/em는 기본 중립 `--slide-accent`를 사용한다. [실제 자식 요소의 색 측정](../evidence/color-browser.json)에서도 새 두 장의 strong는 `rgb(232,232,229)`이고 기존 선언 강조는 주황·수치42는 초록·단위%는 중립으로 분리된다. 부모 제목 색이나 token 존재를 실제 강조색으로 오해하지 않았다. 새 예제에서 이미지 자체의 색은 남지만 선언·수치·범주의 색 사용법이 일반 작성 경로로 전달되지 않았다.

기존 색은 삭제되지 않았다. 추가 보드의 product-launch02/03 주황, engineering-review07 파랑, workshop02 보라/03 범주색, photo-story05·kit05 노랑, 기존 native와 C의 값/범주·사진/UI 고유색이 유지 자원이다. 현재 Stage의 orange `#FF7A3D`, purple `#A080FF`, blue `#24A8FF`, green `#69CF82`, yellow `#EDCF66`과 Paper 대응색은 **STAGE 구현값이며 공식 OpenAI HEX가 아니다.** 팔레트 교체보다 새 원고에서 이 역할을 얻는 경로와 예제를 복구해야 한다.

| 실제 서로 다른2서사의 필요한 지점에서 확인할 역할 | 인수 조건 |
| --- | --- |
| 선언의 선택색 | 저자가 강조한 의미 단위를 선명하게 보여 주며 모든 제목·본문·메타를 같은 색으로 칠하지 않음 |
| 수치와 중립 단위 | 선택 값·비교의 색과 단위·출처·공통 구조의 중립 위계를 유지. 색으로 좋음/나쁨이나 성과를 발명하지 않음 |
| 범주색과 라벨 대응 | 색·범주 이름·위치의 대응이 유지되며 색만으로 구분하지 않음 |
| 사진·UI 자체의 색 | 원매체의 표면·컬러를 보존하고 강제 틴트/회색화·공통 accent로 덮지 않음 |
| 중립으로 돌아오는 리듬 | 컬러 장과 차분한 장의 전환이 실제 이야기·정보량에 맞음. 매장 색 순환이나 고정 등장 빈도는 요구하지 않음 |

두 팀은 tone 키 하나 허용·기본 accent 한 색 교체·토큰 존재만으로 이 조건을 통과했다고 하지 않기로 했다. strong/em 활용은 작은 작성 후보지만 정확한 binding/문법은 시안 후 정한다. 새 일반 Markdown의 실제 수정 작업에서 JSON/HTML/CSS를 반복 작성하지 않고 색 역할을 얻는지 검증해야 한다. 모든 색을 매 덱 채우거나 색 개수로 점수화하지 않으며 Paper 등 기존 테마 대응과 실제 대비도 영향 범위에서 확인한다.

## 후속 설계 방향

**기본값부터 회복한다.** 단일 원고의 구조·길이·매체 비율에 맞춰 제목/본문 폭·단계적 위계·자료 면적·공통 메타를 조판한다. 이것을 table→성과 chart나 숫자→개선율 같은 사실 추론과 혼동하지 않는다. 무선택 H1+quote에서는 어느 하나를 자동 주역으로 단정하지 말고 균형 조판과 작은 저자 선택을 비교한다. role 이름과 문법을 먼저 늘리는 방식은 피한다.

**좋은 기존 표현 자원을 새 원고에 연결한다.** 큰 선언·선택 의미색·중립 단위·열린 근거·실제 UI·사진의 자체 색·C의 주역/보조 관계는 유지한다.20양식 JSON을 매번 배워야 기본 결과가 나오면 작성 목표를 충족했다고 보지 않는다. 두 수치/편집 요약의 간단 그룹은 후보지만, header 노출이나 H2 수를 채우는 과제를 새 의무 문법으로 확정하지 않는다.

**자료 권위와 표시를 분리한다.** 원고/원표/코드/링크/조건은 추적 가능한 단일 권위다. 발표의 크기·묶음·비선형 위치·같은 값의 유익한 반복은 표현 선택이다. 전문이 너무 길어 발표용 투영이 필요한 경우 저자가 무엇을 덜어내는지 통제하고 read 전문·핵심 조건을 보존하는 작은 옵션을 검토한다. 자동 숨김이나 새 노트/부록/편집기 프로젝트로 범위를 확대하지 않는다.
