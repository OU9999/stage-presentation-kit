## 발표에 쓸 수 있는 문장

1. **출처**: “이 문장을 어디서 가져왔고, 누가 언제 어떻게 바꾸었는지 함께 남기면 다시 확인하기 쉽습니다.” S11의 개념을 바탕으로 한 실무 제안이다. W3C가 아래 템플릿을 요구한다고 말하지 않는다.
2. **결정**: “자료가 말하는 것과 우리가 선택한 것은 구분해 둡니다. 선택에는 이유와 부작용, 현재 상태를 붙입니다.” S10의 형식을 일반 스터디로 응용한 제안이다. 사실 확인으로 선택이 자동 확정되지는 않는다.
3. **갱신**: “새 자료가 오면 덧붙이기만 하지 않고, 영향을 받는 주장과 결정을 찾아 다시 봅니다.” 운영 제안이다. 자동으로 모든 관련 문서가 갱신된다는 보장은 없다.
4. **검색과 정확도**: “RAG는 관련 자료를 찾아 답 생성에 쓰는 방식입니다. 검색 결과가 붙어 있어도 주장과 근거를 다시 대조합니다.” 앞 문장은 S12 직접 지원, 뒤 문장은 검토 제안이다. 논문의 제한된 비교 평가를 모든 응답의 정답 보장으로 확대할 수 없어 ‘검색하면 정답’이라는 보장으로 읽을 수 없다.

## 하나로 이어지는 합성 실습 계약

**명시 문구: 아래 모임·공지·날짜·결정은 설명을 위해 만든 합성 예제이며 실제 사례가 아니다.** 현실의 Zoom 기능이나 요금제 주장이 들어가지 않게 모임 운영 공지만 사용한다. 조사 source ID S1~S12와 구별해 예제 자료는 E1/E2, 주장 EC1/EC2, 결정 ED1/ED2로 구분하며 모두 E로 시작한다.

질문: “다음 AI 스터디는 몇 시에 시작하나요?”

- E1, 가상 운영 공지 1판, 작성 2026-10-20: “11월 5일 AI 스터디는 오후 8시에 시작한다.”
- EC1: “11월 5일 시작은 오후 8시.” 근거 E1의 시작 시각 문장. 상태는 1판 확인. LLM이 만든 “매주 오후 8시”는 반복 주기를 말한 근거가 없으므로 미지원으로 표시한다.
- ED1, 가상 결정, 2026-10-21: 참석자 안내 혼선을 줄이기 위해 1판 기준 오후 8시 안내를 사용한다. 상태 accepted. 결과: 안내 준비가 쉽지만 공지 변경 시 재검토가 필요하다. 담당은 가상 운영자 민지.
- E2, 가상 운영 공지 2판, 작성 2026-10-27: “이번 11월 5일 모임은 오후 8시 30분으로 변경한다.” 기존 1판을 지우지 않는다.
- 변경 처리: EC1을 과거 1판 기준으로 표시하고 EC2 “11월 5일 시작은 오후 8시 30분”을 E2에 연결한다. 2판의 명시적 변경 문구 때문에 이 날짜에 새 시간을 적용한다. 다른 날짜까지 바꾸지 않는다.
- ED2, 가상 결정, 2026-10-28: 2판에 맞춰 이번 모임 안내를 오후 8시 30분으로 교체한다. ED1은 superseded by ED2로 연결한다. 결과: 기존 초대장도 점검한다. 이전에 초대장을 실제로 바꾸었다고 발표하지 않는다.

핵심 계약은 ‘새 자료 → 영향 주장 확인 → 범위/충돌 표시 → 사람이 변경 승인 → 이전 결정과 새 결정 연결’이다. 이 절차는 발표용 운영 제안이며 LLM Wiki의 공식 표준이라고 표현하지 않는다. 결정이 승인되기 전에는 proposed, 근거가 부족하면 미확인 상태를 유지한다.

## 한계와 오해 방지

- 출처 링크는 사실을 자동 보증하지 않는다. 해당 문장이 해당 주장과 범위·시점까지 맞는지 확인한다.
- 오래된 자료라는 이유만으로 틀렸다고 단정하지 않는다. 적용 시점과 후속 자료가 있는지 확인한다.
- 최신 날짜 하나만으로 충돌을 해결하지 않는다. 예제는 2판에 ‘이번 날짜의 변경’이 명시되어 있어 범위를 정할 수 있다.
- 일반 지식 노트, RAG, LLM Wiki, ADR은 역할이 다르다. 이 연구의 ADR·PROV 응용 템플릿은 실무 제안이다.
- RAG 논문의 비교 결과는 해당 논문 조건이다. 현재 제품의 품질·정확도·비용 수치로 전용하지 않는다.
- 모임 예제는 실제 정책·현실의 도입 효과·정량 성능 근거가 아니다.

## 직접 교차 검토

독립 초안 작성 후 A가 직접 검토했고, B도 A의 llm-wiki-primary.md와 S1 본문을 직접 대조했다. A가 제안한 지식 축적 연결·답 저장·확인일 표기를 반영했다. 초기 운영 공지 사례는 [최종 합의](synthesis.md)에서 E3 읽기 메모·E4 질문 메모가 연결되는 스터디 준비 위키로 확장했다. 최종 사례와 주장 ID는 취합 문서가 기준이다.

S12의 한계 위치는 실제 확인한 v4 §4.3 Table 4의 factuality 평가와 Broader Impact의 외부 자료 한계로 통일했다. Table 4에는 두 모델 모두 낮게 평가된 경우가 있으며 모든 응답의 정답을 보장하는 결과가 아니다. 이 연구에서 현재 제품의 품질은 측정하지 않았다. A의 최종 3문서 교차 검토와 관리자 검수가 완료되어 이 파일의 편집을 종료한다.
