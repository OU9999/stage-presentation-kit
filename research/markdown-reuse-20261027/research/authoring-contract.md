# 간단한 Markdown 원고와 STAGE 재사용 계약 초안

2026-10-27 · `/root/research_manager/vite_researcher` · 기준 HEAD `835453787bd3fdf75837a618674e6fb20828ee7a`

## 권고

**새 작성 흐름은 `slides.md`를 주 원본으로 삼고, 평범한 제목·문단·목록·이미지·링크·코드·인용·표를 먼저 지원한다.** 작성자가 20개 레이아웃의 JSON 필드를 알아야 시작하는 구조를 기본으로 삼지 않는다. 기존 STAGE 색·글꼴·타이포·구도를 재사용하는 기본 본문 구도를 제공하고, 필요한 장만 명시적으로 기존 레이아웃을 선택한다. Node 빌드·watch 미리보기·CI는 이 흐름의 가능한 도구다. 이전 `content.js` 직접 편집과 file 재생 요구는 legacy 입력·portable 출력의 호환 비용으로 분리한다.

첫 구현 후보는 **Markdown 파일 편집 + 자동 미리보기**다. 이것으로 사용 목적을 충족하면 React 편집 UI는 추가하지 않는다. 기존 React 작성기 우선 권고는 이번 요구에 그대로 적용하지 않으며, 모노레포·플러그인 체계보다 일반 문법 보존과 공통 스타일의 최소 확장에 집중한다.

이번 초안은 **제안 계약**이다. 아래 일반 Markdown 문법과 6장 원고가 현재 compiler로 모두 동작한다는 뜻이 아니다. 제품·기존 원고·빌드 출력은 수정하지 않았고 새 문법을 구현하지 않았다.

## 현행 지원과 제안의 차이

[현재 가이드](../../../MARKDOWN.md)와 [compiler](../../../scripts/markdown-deck.cjs)의 `parseSlide():115`, `parseMarkdown():239`, [제품 예제](../../../examples/product-launch/slides.md)·[사진 예제](../../../examples/photo-story/slides.md), 기존 Markdown 테스트를 읽어 대조했다. 아래는 코드 관찰이다.

| 작성 요소 | 현재 지원 | 새 일반 원고 계약 제안 |
| --- | --- | --- |
| 장 구분 | fence/주석 밖의 단독 `---`로 분리, 빈 장 오류 | 같은 명시 구분 유지. heading 수나 글자 수로 장을 자동 분할하지 않음 |
| 발표 정보 | flat frontmatter `id/title/theme/speaker/date/footer`만 허용; 일반 YAML 아님 | 모두 선택. 가장 작은 원고는 frontmatter 없음, 필요하면 `title` 한 줄. 프로젝트 설정에서 기존 STAGE 기본값 제공 |
| 제목 | 본문 전의 `#`만; 연속 `#`는 제목 배열/줄바꿈. `##` 이하는 오류 | 장의 첫 `#`는 장 제목, `##` 이하 제목은 본문 계층. 새 모드에서 반복 `#`로 줄바꿈하지 않으며 명시 hard break 사용 |
| 문단 | layout에 따라 subtitle/caption/attribution 등 한 필드로 합침 | 문단 노드와 순서 보존. 긴 글을 임의 subtitle·notes로 재분류하지 않음 |
| 목록 | `-`만 `demo.steps`로 변환. 그 외 layout·번호/`*`/`+` 목록 오류 | 기본 unordered/ordered list, 목록 항목 안 inline 보존. 중첩도 문서 계층으로 보존하되 발표 넘침은 진단 |
| 이미지 | 특정 image/media/demo/gallery/mosaic/results layout에서만 허용 | 독립 image block·alt·경로를 유지. 이미지+목록도 한 장의 원문 순서대로 허용. 기본 contain, 크롭은 명시 예외 |
| 링크·강조·inline code | 일반 inline 해석 없음; 기호 그대로 표시 | link/emphasis/strong/code를 구조로 보존. 코드는 표시용이며 실행하지 않음 |
| 일반 code fence | `stage` JSON fence 외에는 오류 | 언어 표시를 선택적으로 받아 원문·공백·줄바꿈 보존. 코드 속 `---`는 장 구분 아님. 문법 강조는 선택 도구 |
| `>` 인용 | 오류; quote layout은 `#`를 quote, 문단을 attribution으로 매핑 | blockquote를 그대로 표시. 인용 다음 문단을 자동으로 저자/출처로 해석하지 않음 |
| pipe table | 오류 | 헤더·셀·정렬을 가진 표로 지원. 숫자 같아도 임의 차트로 변환하지 않음 |
| raw HTML | 일반 문장에서 문자로 표시; stage 주석만 별도 해석 | 원고 내 임의 HTML/JS 실행은 일반 계약 밖. 코드로 표시하거나 명시적인 미지원 진단 |
| stage metadata/JSON | 기존 layout별 필드·중복/누락 검증 | 고급 호환 경로로 유지. 일반 본문과 충돌하면 원문 위치를 알리고 실패; 조용히 덮어쓰지 않음 |

현재 예제의 `layout: cover/image/demo`나 `stage` JSON은 현 compiler에 필요한 설정이다. 이를 없애도 지금 그대로 출력된다고 설명해서는 안 된다. 반대로 새 일반 문법을 위해 기존 20개 양식과 `StageVisual`을 버릴 필요도 없다.

## 원본과 표현 모델

1. **원고 모델:** Markdown을 heading/paragraph/list/image/link/code/quote/table의 문서 blocks로 파싱한다. 블록과 inline의 순서, 원본 파일·행 범위, 안정 식별자를 유지한다. 이 모델은 특정 layout의 `subtitle`이나 `items`를 작성자가 직접 채우는 계약과 구분한다.
2. **발표 투영:** 기본은 제목+원문 순서의 본문 구도다. 기존 `styles.css`의 제목/설명 위계·읽기 폭·한국어 줄바꿈·의미색을 재사용한다. 특정 레이아웃을 요청한 경우에만 adapter가 기존 deck-model 필드로 변환하고 검증한다.
3. **본문 표현의 실제 빈칸:** 현 20개 layout은 임의 code·quote·table·image+list를 모두 담는 범용 blocks 필드가 없다. 일반 본문 renderer/모델 확장이 필요하다. 표현할 수 없는 노드를 subtitle 문자열로 평탄화하거나 삭제해 기존 모델에 억지로 맞추지 않는다. 확장 크기와 adapter 설계는 엔지니어링 검토 대상이다.
4. **공유 읽기 투영:** 같은 blocks에서 문서형 읽기 화면을 만든다. 발표 장 순서와 제목·문단·표·코드·링크·alt를 보존하고 읽기 폭과 넘침 정책만 바꾼다. 발표용 그림이 native 데이터에서 생성되면 기존 StageVisual의 동일 자료 표를 재사용한다.

새 범용 본문 구도는 새로운 브랜드 스타일을 만드는 작업이 아니다. [타이포 제품 결정](../../type-layout-20261025/manager/final-decision.md)의 제목·설명 분리, 한국어 줄바꿈, 원문 보존, 긴 수치의 독립 공간 원칙을 적용한다. 이미 있는 `stage/paper/midnight` theme와 글꼴·색 토큰을 우선 재사용한다. 코드/일반 표 등 현재 없는 의미 노드의 스타일은 기존 토큰으로 최소 보완하며, 이를 이미 구현된 기본 양식으로 표시하지 않는다.

**레이아웃의 자동 추론 범위를 작게 둔다.** 첫 장이라 cover, 마지막이라 closing, 큰 숫자라 metric, 표라 chart, 여섯 항목이라 bento라고 추측하지 않는다. 기본 본문 구성은 입력 순서로 결정하고 독자가 읽는 순서를 바꾸지 않는다. 스타일 preset은 프로젝트에서 한 번 고르는 기존 STAGE 설정 묶음이며 장마다 CSS·격자·색상 수치를 쓸 의무가 아니다. `theme: stage`는 현재도 존재하지만 새 프로젝트 preset 선택 UI/설정은 아직 제안이다.

## 일반·선택 확장·고급 경로

| 층 | 작성자가 알아야 하는 것 | 경계 |
| --- | --- | --- |
| 일반 | Markdown과 장 구분 `---`; 필요할 때만 frontmatter | 일반 6장 원고에는 `stage` JSON·UI 속성·좌표·AI 입력 불필요 |
| 선택 확장 | 해당 장의 작은 `<!-- stage ... -->`에서 명시 layout, 필요한 노트/공유 역할 등 | 기존 `cover/image/quote` 등을 요청할 때만 사용. 새 blocks→layout 변환 조건을 문서화하고 불일치는 진단 |
| 고급 | 기존 `stage` JSON으로 visual·bento·metric-pair 등 구조 자료 | 현재 schema와 검증 재사용. 일반 사용자에게 모든 런타임 필드를 문법으로 노출하지 않음 |

예를 들어 한 장을 명시적으로 기존 image 구도로 표시할 때 `layout: image`를 선택하고 제목+이미지+캡션만 허용할 수 있다. 같은 장에 목록도 있으면 “image adapter는 목록을 담지 못함; 기본 본문 구도 사용 또는 장 분리”를 알린다. 자동 삭제·서로 다른 원본 필드 덮어쓰기·숨은 JSON 생성은 하지 않는다. 이는 **새 adapter의 제안**이며 현 compiler의 이미지+목록 지원을 뜻하지 않는다.

발표자 notes·공유 전용 보충 설명·appendix는 선택 확장이다. 첫 구현의 일반 원고가 이를 몰라도 동작해야 한다. 역할 표식·공개 투영·저장 방식은 한 계약으로 정의하고 “HTML 주석이면 비공개”라고 간주하지 않는다. 공개 읽기에서는 notes 제외를 기본 제안으로 두되 **원본 Markdown 다운로드/저장소 공개에는 notes가 들어갈 수 있으므로 원본 제공은 별도 opt-in**으로 둔다. 공개본 Markdown을 제공한다면 공개 투영에서 새로 생성하고 원본과 구분한다.

## 제안 원고: 일반 문법으로 쓰는 6장

아래는 `talks/reuse-demo/slides.md`라고 가정한 **새 계약의 예시**다. 현재 compiler는 2장의 `##`/목록, 3장의 기본 이미지, 4장의 코드, 5장의 인용, 6장의 표를 이 조합으로 컴파일할 수 없다. 첫 장만 특별 cover로 추론하지 않고 모두 같은 STAGE 기본 본문 스타일을 사용한다. 자료·수치는 가상이다. 상대 이미지 경로는 원고 위치 기준이며 기존 자체 제작 자산을 가리킨다.

````md
---
title: 한 원고로 발표하고 공유하기
---

# 한 원고로 발표하고 공유하기

발표할 문장과 공유할 근거를 같은 Markdown에서 관리합니다.

---

# 작성자는 내용부터 씁니다

## 이번에 지킬 약속

- 제목과 핵심 문장을 먼저 적습니다.
- 원고 순서와 내용은 출력에서도 유지합니다.
- 장이 길면 미리보기에서 확인하고 직접 나눕니다.

---

# 화면과 설명을 함께 둡니다

![자체 제작한 가상 업무 화면](../../assets/examples/dashboard.svg)

- 같은 화면을 발표와 읽기에서 사용합니다.
- 그림을 자동으로 잘라 중요한 내용을 숨기지 않습니다.

자료의 성격은 [크레딧 안내](../../assets/CREDITS.md)에서 확인합니다.

---

# 코드도 원고의 일부입니다

아래 문자열의 `---`는 새 장을 만들지 않습니다.

```js
const separator = `
---
`;
const title = "발표와 공유";
console.log(title, separator);
```

코드를 실행하지 않고 원문 그대로 보여줍니다.

---

# 짧은 문장을 인용합니다

> 자료는 한 번 쓰고,
> 필요한 화면에서 다시 읽습니다.

가상 팀 회고를 설명하기 위한 예시 문장입니다.

---

# 자료와 다음 행동을 남깁니다

| 작업 | 이전 | 제안 |
| --- | --- | --- |
| 원고 위치 | 여러 파일 | Markdown 한 원본 |
| 발표와 공유 | 별도 수정 | 같은 원고에서 생성 |

1. 원고를 고칩니다.
2. 미리보기를 확인합니다.
3. 선택한 공개본을 공유합니다.

[기존 작성 안내](../../MARKDOWN.md)와 새 문법의 차이를 먼저 확인합니다.
````

이 예시의 `id`·theme·연사·날짜는 생략했다. 다중 발표의 실제 식별자는 프로젝트 manifest가 source 상대 경로와 안정 deck id를 연결하며 원고 제목과 분리한다. manifest는 발견한 원고에서 도구가 관리할 수 있고 일반 작성자가 새 설정 파일을 직접 쓸 필요는 없다. 동일 basename의 `slides.md`가 여럿이어도 충돌하지 않아야 한다. 명시 원고 `id`가 있으면 manifest와 대조하고 중복은 실패시킨다. 장 id는 저장/직접 링크가 필요할 때 manifest/source mapping에 고정하며 제목 문자열만으로 만들지 않는다. 기존 `#n` 링크는 이행 중 호환 별칭으로 유지할 수 있다. 세부 manifest 형식과 장 이동 시 id 유지 방식은 엔지니어링에서 확정한다.

## 작성·미리보기·공유·수정 계약

- **단방향 기본:** Markdown 원본 → 문서 blocks/검증 → 발표·공유 읽기·선택 portable 출력이다. `content.js`는 생성 산출물 또는 legacy 직접 입력이며 새 Markdown 원본과 동시에 수정하는 두 번째 원본이 아니다.
- **최소 frontmatter:** 문서 정보가 없으면 최초 제목에서 표시 제목을 얻고 기존 `stage` theme를 사용한다. 원본 식별자는 제목 추론과 별개다. 현행 flat frontmatter의 작은 범위를 유지하고 프로젝트 단위 기본값으로 반복을 줄인다. 일반 YAML 전체 지원 여부를 암묵적으로 약속하지 않는다.
- **일관된 수정:** 원고 저장 후 watch/preview가 갱신된다. parser·누락 미디어·adapter 오류는 원본 파일/장/행을 가리키고 마지막 정상 산출물을 보존한다. 해당 watch/진단 UI는 제안이며 현재 기능 완료가 아니다.
- **화면 편집:** Markdown 역저장이 구현되기 전에는 read-only 또는 명시적인 임시 draft로 둔다. `content.js` 다운로드를 Markdown 저장으로 부르지 않는다. source map 기반 patch·충돌 검사·저장 완료 표시가 구현돼야 영속 화면 편집으로 승격한다. 원본/브라우저 동시 변경 시 자동 덮어쓰지 않는다.
- **분량과 읽기:** 넘치면 장/원본 위치를 진단하고 작성자가 장을 나눈다. 임의 문장 삭제·숨김·자동 장 증가·읽기 어려운 축소로 맞추지 않는다. 긴 코드·표는 공유 읽기에서 스크롤로 전체를 보존하고 발표에서는 길이 경고를 제공한다. 발표 시 자체 스크롤 허용 여부와 좁은 화면 동작은 엔지니어링 검증에서 확정한다.
- **예측 가능한 자산:** 이미지·문서 링크는 원고 폴더 기준으로 해석하고 출력 위치가 바뀌어도 같은 자료를 가리키게 만든다. 현재 compiler의 미디어 재계산·존재 검사는 재사용하되 일반 링크와 publish copy 목록까지 확장해야 한다. 이미지 alt·출처 링크를 보존한다.
- **공개 구분:** 슬라이드/읽기용 공개 artifact와 원본 Markdown 공개를 구분한다. 원본 공개가 선택되지 않으면 source 파일을 artifact에 자동 포함하지 않는다. 별도의 PUBLIC Git 원본에 이미 있는 파일을 artifact 선택으로 비공개로 만들 수는 없다.

## 엔지니어링이 재현할 반례와 인수 기준

| 반례/입력 | 필요한 결과 |
| --- | --- |
| 제목+이미지+목록+링크 한 장 | blocks 순서·alt·목록·클릭 가능한 링크를 발표/읽기에 보존; image layout으로 자동 축소하지 않음 |
| 코드 fence 안 단독 `---`·한글·들여쓰기 | 장 수 불변, 코드 원문 보존, 실행 없음 |
| 일반 표 30행·긴 코드 | 원고/읽기 전체 보존, 발표 넘침의 위치 진단; 자료 삭제·차트 자동 변환 없음 |
| `#` 반복으로 줄바꿈하던 기존 원고 | legacy parser 경로의 이전 출력 보존; 새 문법과 버전/명령 경로를 명시해 조용한 의미 변경 방지 |
| `talks/a/slides.md`, `talks/b/slides.md` | deck id·출력 경로·브라우저 상태가 충돌하지 않음 |
| 원고의 장 제목 변경/순서 이동 | 제목에 종속되지 않는 장 id 정책과 기존 직접 링크의 호환 규칙 확인 |
| 동일 필드를 Markdown+stage JSON에 중복 | 파일/장/행을 알리는 오류; 원문과 이전 산출물 보존 |
| notes가 있는 원본의 웹 공유 | 공개 투영에 notes 미포함, source 다운로드는 별도 opt-in; PUBLIC 원본 존재 여부는 별개로 안내 |
| Markdown 변경과 브라우저 draft 동시 발생 | 원본을 자동 덮어쓰지 않고 source revision 불일치 표시 |
| raw HTML/지원 밖 확장 | 실행·조용한 소실 없이 명시적 처리/진단 |

새 원고 모드와 기존 Markdown 모드는 parser 버전/진입 명령 또는 프로젝트 설정으로 분리한다. 현재 원고를 새 parser로 자동 재해석하지 않는다. 일반 Markdown 샘플의 동작, legacy 출력 바이트/의미 호환, 다중 문서 id·자산 독립성, 두 공개 투영의 원문 일치는 구현 후 검증할 항목이며 이번 초안에서 통과한 결과가 아니다.
