## 1~10장 화면 관측 후 기록 — 동결 1

- 역할 관점의 관심: 2장의 “메모는 남았는데 어느 문장이 근거일까”는 동료에게 설명을 인계할 때 다시 링크를 뒤지는 상황과 맞는다. 이는 내 역할에 따른 적용 추론이며 발표가 실무 효과를 측정한 것은 아니다.
- 이해가 덜 된 부분: 8장에서 LLM이 Markdown을 유지한다는 설계는 알겠지만, 10장은 사람이 승인한 수정안을 Node가 적용한다고 한다. 오늘 체험으로 자동 연결의 쓸모까지 판단할 수 있는지는 아직 모르겠다. `raw`, `wiki`, `schema`라는 표기와 “고정 승인 교정안”을 기억해야 해서 설계와 데모의 관계를 한 번 더 정리하고 싶다.
- 질문: 기존 팀의 Markdown/PR 리뷰에 어떤 파일 하나를 추가하면 출발할 수 있는가? 원자료와 읽기 메모가 모두 보존 대상이면 잘못된 읽기 메모는 어떻게 고치는가? 답을 찾는 방식 자체는 어디서 다루는가? 이 질문들은 화면만으로 답을 확정하지 않는다.
- 주의가 떨어질 위치: 4장의 두 질문 예고, 5장의 세 단어, 6장의 다섯 단계가 연달아 나온다. 각각 뜻은 다르지만 아직 실제 파일을 못 본 상태에서 “다음 질문에 다시 쓴다”는 약속이 세 번 누적되는 느낌이다. 5와 6의 큰 글자는 기억에는 남고, 둘 다 길게 설명하면 진입을 기다리게 된다.
- 화면 관측: 2장의 세 줄은 한 번에 읽힌다. 3장은 세 역할이 서로 다른 줄에 있어 비교하기 쉽다. 8장은 원자료→위키와 하단 규칙이 구별되지만 하단 규칙의 점선이 위키 쪽으로만 이어져 규칙이 위키에만 적용되는지 잠깐 묻게 된다. 대본은 전체 작업에 적용한다고 명시하므로 발언을 들어야 해소된다. 10장의 사람/Node 두 열은 실제 실행 범위를 분명히 한다.
- 다음 구간에서 확인하고 싶은 것: 링크가 달린 한 문장이 실제로 어떻게 바뀌고, 변경 이유를 어디에 남기는지. 미래 대본 선노출이 있으므로 이것을 순수한 예측으로 취급하지 않는다.

## 31~40장 화면 관측 후 기록 — 동결 4

`slides.md` 31~40장, 정제 `block-4.md`, PNG 31~40을 개별 직접 확인했다. 따라서 화면 01~40 및 대본 말하기 40구간의 누락은 없다. 아래 회상을 쓰기 전 추가 자료나 상대 결과를 보지 않았다.

- 중심 메시지: 원문을 보존하고, LLM에 초안/연결 후보를 부탁하고, 사람이 근거와 변경을 확인해 검토한 설명을 다음 질문으로 이어가자는 운영 습관이다. 32장의 역할 구별과 36~38장의 시작 요청·검토 규칙·유지 부담이 직접 지원한다.
- 행동으로 남길 것: 이미 읽은 자료를 고르고 한 질문을 적어, 근거 한 곳을 확인한 다음 동료 한 명과 고칠 문장을 읽어 볼 수 있겠다. 34~37장의 행동 지시로 출발점은 생긴다. 이것이 내 업무 자료에서 실제로 성과를 낼지는 아직 판단하지 못한다.
- 질문이 해소된 것: 32장과 36장은 오늘 고정 승인 데모와 앞으로 LLM에 부탁할 일을 구별한다. 검토자는 37장에서 정하라고 하므로 “사람 역할이 없다”는 결론은 맞지 않는다. 다만 대기 항목 재검토 주기와 채택 기준의 세부는 내 팀에서 정해야 할 것으로 남는다.
- 화면/기억: 31장의 62.5%와 37.5%가 가장 큰 숫자라 비율을 기억하게 되지만, 내 역할에서는 기존 5쪽/새 3쪽과 검사의 한계가 더 중요하다. 대본은 정확도 점수가 아니라고 명시하지만 화면에는 성능 지표 같은 큰 비율이 떠 있다. 33장은 읽기→질문→점검 순서와 되풀이한다는 제목이 맞는다. 34장은 사진으로 숨 돌리는 장이며 작은 하단의 “자료 3개·질문 1개·검토자 1명”을 발표자가 읽어줘야 행동 단위가 남는다.
- 참여 부담: 35장의 20초 안에 자료 제목 둘, 연결 질문, 근거 위치까지 새로 찾는 것은 어렵다. 이미 1장에서 떠올린 자료와 30장의 두 자료를 기억하고 한 줄 질문만 적는다면 가능하겠다. 대본의 “질문 하나가 남으면 충분”을 먼저 말하면 빈칸을 채워야 한다는 압박이 줄 것 같다. 실제 참여 시간은 측정하지 않았다.
- 집중이 끝까지 가는 이유/부담: 36장의 시작 요청은 복사할 수 있어 유용하다. 반면 31~38장에도 실행 한계와 검토 필요가 여러 차례 나오므로 후반이 새로운 체험보다 이미 들은 원칙의 정리로 느껴질 수 있다. 39장과 40장의 두 경로는 더 읽을 자료가 있다는 안정감을 준다. 실제 다운로드나 실행은 하지 않았다.
- 다음 모임 기대: “질문 하나와 근거 위치 하나를 가져와 같이 읽기”로 이어지면 참가할 이유가 있다. 자동 지식 정리 도구의 성공 시연을 기대하고 왔다면 오늘의 고정 승인 파일 데모만으로 기대가 충족되지는 않을 것이다. 후자는 역할 기반 기대 차이의 추론이다.

## 자료를 다시 보지 않고 적은 자기 말 회상 — 동결

초기 대본 미래 선노출을 포함한 에이전트의 회상이다. 실제 참가자의 기억 측정·학습 평가로 해석하지 않는다.

1. **LLM Wiki란:** 자료 원본 옆에 사람이 다시 읽고 고칠 수 있는 연결된 설명 파일을 두고, LLM으로 초안과 연결 후보를 만들며, 검토한 결과를 다음 질문의 입력으로 남기는 방식으로 이해했다.
2. **기존 메모와 다른 점:** 읽었다는 흔적이나 링크만 보관하는 데서 더 나아가 어떤 문장을 어떤 범위에서 말할 수 있는지, 무엇을 바꿨고 왜 바꿨는지 찾아가게 한다. 기존 메모에도 같은 규칙을 적용할 수 있을 것 같지만, 특정 앱에서 어떻게 하는지는 오늘 확인하지 않았다.
3. **원문→주장→결정 연결:** RAG 원문에서 학습 절차를 더 읽어 넓은 주장을 고치고, 그 경험을 이전 저장 이유와 함께 읽어 검토된 답과 보류 답을 나누는 결정을 만들었다. 이전 결정은 새 결정으로 대체됐다는 표시를 남긴다.
4. **내 자료로 시작:** 같은 주제의 자료 몇 개와 답하고 싶은 질문 하나를 골라 근거 위치를 붙인 설명을 만든다. LLM에는 변경안과 이유를 부탁하고, 적용 전에 다른 한 사람과 읽는다. 미지원 부분은 다음 확인을 적어 따로 둔다.
5. **남는 의문:** 실제 LLM이 어느 파일을 빠뜨리는지 어떻게 찾아낼까? 파일이 많아졌을 때 사람이 연결 영향을 얼마나 감당할까? pending은 누가 언제 다시 보며, 어떤 조건에 현행이 될까? 오늘은 이 부분의 성능이나 비용을 입증한 발표로 이해하지 않았다.

## 회상 뒤 대본 재대조 — 보완이며 초기 기록은 보존

회상 저장 후 대본의 시간표와 8·14·18·22·25·32·34~38장을 다시 읽어 “설명되지 않음”과 “설명됐지만 구체 운영은 미정”을 구별했다. 심화자료는 열지 않았다.

- **검토자 없음이라는 비판은 성립하지 않는다.** 37장 실제 발언은 “다음 모임 전에 실제 파일을 읽을 사람도 정합니다.”이다. 남는 것은 개별 pending 항목의 담당/기한/보류 해제 기준이며, 이것을 모든 스터디에 정해줘야 한다는 뜻은 아니다. Q&A에서 우리 운영에 맞춰 물을 문제다.
- **검색 필요를 숨기지 않는다.** 18장은 “저장했다는 사실과 다음 답이 읽었다는 사실은 서로 다른 확인 항목”, 25장은 “답이 읽은 파일과 빠뜨린 근거를 사람이 확인”, 38장은 “파일 위키와 검색은 병행”을 말한다. 따라서 자동 기억/검색 대체의 허위 약속이라고 판단할 근거는 없다. 실제 LLM의 읽기 누락을 확인하는 체험까지는 제공되지 않는다.
- **모든 파일을 손으로 유지하라는 지시로 확정할 수 없다.** 32장의 LLM 초안/수정안 역할과 36장의 diff 요청이 있다. 다만 현재 데모에서는 사람이 승인안을 작성했으므로, 실제 모델을 붙였을 때의 작업량/난도는 검증되지 않는다.
- **34장 세 자료와 35장 두 자료는 모순이라기보다 시작 묶음과 짧은 참여의 차이다.** 그러나 “세 자료 중 지금 떠오른 두 개만”이라는 전환은 없어서 자기가 적을 개수를 잠깐 확인할 수 있다. 35장 작성 시작 전에 그 한 문장을 보태면 된다.
- **역사/외부 출처의 진위를 이번 역할 평가로 새 검증하지 않았다.** 7·30장의 화면 인용과 발표자의 번역·설계/역사 아이디어라는 제한, 13·15장의 근거 위치, 27장의 Nygard 형식 응용을 관찰했다. 출처의 실제 지원 범위 검증은 별도 독립 작업이다. 이번 제안은 발언 전달과 화면 근거에 한정한다.

## 40장 유지·설명 참여 30분·가벼운 Zoom 스터디에 대한 독립 판단

**조건부로 목적에 맞는다.** 주제는 도구 도입 성과보다 “다음 질문에 다시 읽을 근거와 이유를 남기는 습관”이다. 실무 역할에서는 22장의 재사용 입력, 25장의 보류 이유/다음 행동, 26~27장의 대체 결정과 비용을 얻어 갈 수 있다. 반면 실제 LLM의 검색·갱신 흐름까지 보고 바로 배치하려는 요구에는 충분하지 않다. 이 판단은 역할 기반 예상이며 발표 성과 측정이 아니다.

대본 표에서 1~10장에 7분, 11~20장에 8분40초를 배정해 Q2는 15분40초에 열린다. 이 배분은 제목의 핵심인 “다음 질문 재사용”을 후반에 기다리게 한다. 40장을 유지한 채 앞부분의 설명 깊이를 줄이고 핵심 전환을 확실히 읽는 편이 낫다. 현재 시간표는 합계 추정이며 내가 낭독하거나 리허설한 값이 아니다. 각 화면을 읽고 Zoom 채팅을 기다리는 실시간 변동은 이 평가에서 알 수 없다.

## 두 역할 직접 대조와 취합 — 초기 기록 이후 보완

manager가 A/B의 4구간과 teachback 동결을 확인한 뒤에만 [A 보고서](./first_time.md)를 읽었다. A `/root/audience_review_manager/first_time`에게 관측·근거·제안·다음 작업을 직접 보냈고, A도 B 보고서를 읽은 뒤 차이와 보완 제안을 직접 돌려주었다. 아래는 에이전트 두 역할의 대조이며 실제 사람 둘의 반응이나 관객 통계가 아니다. B는 대본 11~40장까지 초기 선노출됐고 A는 11장 본문/12장 제목 및 시간표가 선노출됐다는 한계가 달라, 두 결과를 동일한 맹검 절차의 재현으로 취급하지 않는다.

| 논점 | 공통 관측 | 역할 차이와 보존할 판단 |
| --- | --- | --- |
| 진입·리듬 | 3~6장의 약속이 길게 이어지고, 15~17장 같은 일반화가 반복된다. 19장 여덟 이름은 한 번에 기억하기 부담스럽다. | A는 diff/해시 같은 말에도 풀이를 기다린다. B는 코드 형식은 익숙하나 실제 변경/다음 판단으로 빨리 넘어가길 바란다. 기술 풀이를 전부 늘리기보다 역할별 한 문장을 넣을 문제다. |
| 재사용의 유익 | 22장 실제 입력 문장, 24~27장 현행/보류/대체/비용이 제목의 약속을 구체화한다. | B는 특히 결정의 원래 이유와 대체 상태가 협업 인계에 쓸모 있다고 추론했다. A는 새 질문에서 무엇을 가져오는지 이제 보였다는 이해를 강조했다. |
| 내 자료로 시작 | 32장의 역할과 36장 요청문은 가져갈 결과물이다. 35장 20초에 자료둘/질문/근거를 다 새로 쓰기는 빠듯할 수 있다. | **B는 기존 Markdown/PR 검토에 질문 하나와 동료 검토를 붙여 시작할 수 있다고 판단했다. A는 원리를 이해해도 채팅에서 파일을 지정하고 읽히고 수정안을 확인한 뒤 어디 저장할지 막막하다.** 최소 기록을 줄이는 제안만으로 A의 도구 시작 공백은 해소되지 않는다. |
| 운영 의문 | 자동 검색·기억·정확도 향상은 관찰하지 않았고 대본도 그렇게 주장하지 않는다. | A는 최초 파일 입력/저장 순서가 우선이다. B는 pending 담당자·재검토 주기·해제 조건과 연결 영향 검토 비용이 우선이다. 서로 다른 준비도와 관심이며 하나의 결핍으로 합치지 않는다. |
| 참여·화면 | 12·23장 B가 뚜렷하다. 31장 큰 구성비는 파일 수의 의미보다 비율을 앞세운다. | 보류 이유 한 단어를 선택적으로 쓰게 하는 안에는 양측이 동의했다. 8장의 규칙 점선이 위키 쪽으로만 향한다는 관측은 B가 제시했고 A의 독립 초기 관측으로 소급하지 않는다. |

직접 대조 뒤 후속으로 정리한 논점은 다음과 같다.

1. **40장은 유지하면서 발언 깊이를 조정한다.** 두 역할 모두 장수 자체를 결함으로 결론내리지 않았다. 5~6/15~16/28~30장의 반복 부연을 줄이고, 19장의 기호는 예시 이름임을 알리며 22장의 세 입력과 24~27장의 정책 문장을 보호한다. 35장 작성20초도 보호한다. 구체 절약 분량은 실제 낭독 후 정해야 하며 임의의 실측 수치를 만들지 않는다.
2. **36장의 도구 첫 동작은 A의 별도 요구로 보완한다.** “자료 두 개 지정→연결된 노트 읽기 요청→읽은 파일·근거·수정안 확인→승인 저장”이라는 앞으로 해볼 구성 예시 한 줄을 제안한다. 이는 현재 모델 실행 결과나 특정 제품 기능 검증이 아니다. B의 최소 기록 제안과 함께 제시하되 서로 대신하지 않는다.
3. **23장 참여에는 보류 이유의 선택 입력을 더한다.** 한 글자만 보내도 참여할 수 있고, 이유를 쓰고 싶은 사람은 한 단어를 더 쓰게 한다. 정답 선택을 근거 검토 능력의 증거로 보고하지 않는다.
4. **34→35장 전환은 과제 범위를 먼저 좁힌다.** “세 자료 중 두 개만, 질문 하나가 남으면 충분”을 먼저 말한다. 근거 위치를 바로 못 찾으면 다음 모임 행동으로 넘겨도 된다고 안내하는 안이다.
5. **B의 운영 의문은 후속 모임 안건이다.** 검토자 한 명 지정은 이미 37장에 있으므로 새 누락으로 과장하지 않는다. 담당자/주기/해제 기준의 세부는 자기 팀 자료로 시작한 뒤 비용을 보며 정할 실무 질문이다.

최종 독립 판단은 유지한다. **자료 공유와 판단 이유를 남기는 가벼운 스터디에는 유익하다. 실제 모델의 검색/갱신 성과를 보고 즉시 운영 준비를 마치려는 목적에는 한계가 있다.** A의 첫 도구 동작 공백과 B의 운영 부담 의문을 따로 다루면 이 차이를 솔직하게 전달할 수 있다.
