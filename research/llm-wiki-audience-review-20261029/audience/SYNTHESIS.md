# 현재 40장 발표의 독립 모의청중 종합

현재 자료는 **근거를 붙인 노트와 판단을 다음 질문에 재사용하는 방법을 나누는 Zoom 스터디 발표로 유익하다.** 22장과 24~27장에서 실제로 어떤 기록을 다시 읽고 저장 정책을 바꾸는지가 드러난다. 처음 듣는 사람이 LLM Wiki를 짧게 정의하고 자기 도구에서 곧바로 시작하도록 돕기에는 LLM 역할의 구체화가 늦고, 중간의 파일 식별자와 반복 설명이 부담이 된다. ‘충분히 재미있고 잘 전달될 것’이라는 완료 판정은 사람 리허설 없이 내릴 수 없다.

## 판단 범위

두 에이전트가 각각 LLM Wiki를 처음 듣는 AI 스터디 학습자(A), 검색·공유·결정 기록에 관심 있는 개발자/스터디 참석자(B)를 맡았다. 실제 관객 반응, 대표 표본, 실측 집중도·학습 향상·낭독 시간은 아니다. 두 역할 모두 `gpt-6.1-sol/high/fork none`이며 동일 모델이라는 한계도 있다. 모델 배정과 직접 대조 경로는 [MEETING.md](./MEETING.md)에 남겼다.

초기 대본 추출에서 A는 11장 발언·12장 제목과 시간표, B는 이후 전체 대본/시간표에 선노출됐다. 상대·과거 평가·심화자료는 초기 판단과 자기 말 회상 동결 전 읽지 않았다. 이후 10장 단위 화면 관측과 정제 발언 입력을 사용했다. 따라서 이는 **독립 역할 기반 워크스루**이며 완전 블라인드 최초 시청 반응이나 기억 실험이 아니다. manager의 공통 로그 과거 이력 노출도 별도 기록했다.

대상은 main `a5b558c36b41ed92a4132b303a77f3ad1a287e27`, 원고 SHA256 `7dbd19ffdf942f22af8bec54af10fac7835a06469360b99bdb783a2dca077c28`, 대본 SHA256 `c8ed063f8a6369a1a1db0b4e06288b436c2772fe6fa566499351c7832baaaed8`다. manager는 원고 전문·대본 40구간·source 동일 직전 PNG40개를 개별로 직접 확인했다. A는 10장 보드4개와 19/22/24/31/35 개별 화면, B는 PNG40개 개별 화면을 확인했다. 기능 테스트 통과 수는 이 판단의 근거로 쓰지 않았다. 제품 변경은 하지 않았다.

두 역할이 비슷한 말을 했다는 사실은 결과의 통계적 확실성을 높이지 않는다. 각각의 독립 기록을 보존하고, 화면/발언에서 지원된 이해와 자기 업무로의 적용 추론을 구분했다. 전문은 [A](./first_time.md), [B](./practitioner.md)에 있다.

## 유지할 좋은 점

1. **작은 오류 문장을 실제 변경 결과까지 따라갈 수 있다.** 13장의 원문 대조, 16장의 승인 기록, 17장의 삭제/추가 두 열은 각기 다른 검토 단계를 보여준다. 17장 발언의 “바뀐 한 문장을 나란히 읽으면 어떤 일반화를 버렸는지”라는 목적을 화면이 지원한다. 반복을 줄이더라도 최종 변경 한 문장은 남길 가치가 있다.
2. **제목의 약속이 구체적으로 성립하는 구간이 있다.** 22장은 ‘링크가 있어도 일반화가 틀릴 수 있다 / 다음 답에 쓰려면 고친 파일을 다시 읽는다 / 모든 답을 현행에 모으려 했다’를 한 화면에 둔다. 대본은 이를 “처음에 왜 모든 답을 모으려 했는지도 함께” 읽는다고 설명한다. 24~27장은 그 결과를 현행·pending·D1→D2와 검토 비용으로 보여준다. A/B 모두 이 구간을 핵심 유익으로 남겼다.
3. **불확실성과 시작 행동을 남긴다.** 25장의 보류 이유/다음 행동, 26장의 과거 맥락 보존, 38장의 가치/유지 부담은 무조건적인 도입 권유를 피한다. 35장은 자기 질문을 쓰게 하고, 36장의 세 줄 요청은 복사할 시작점이다. 이 점을 유지하면 발표 뒤 토론이나 다음 모임으로 이어갈 재료가 있다.

## 우선순위 3개 — 제품 수정이 아닌 후속 제안

| 순위 | 문제와 직접 근거 | 구체적 대안 | 확인할 결과 |
| --- | --- | --- | --- |
| 1 | **LLM Wiki의 작업 장면을 앞에서 구체화한다.** 8장 발언은 “LLM이 원자료를 읽어 연결된 Markdown 페이지를 유지”한다고 하지만 10장은 고정 승인안을 Node가 적용한다. 구체적인 LLM/사람 분담은 32장, 요청 문구는 36장에 나온다. A/B 모두 설계와 오늘 데모의 관계를 앞에서 다시 묻고 A는 종료 후에도 자기 채팅 도구의 파일 작업 순서를 모른다고 남겼다. | 8~10장에 ‘자료 두 개를 읽기 → LLM의 설명/연결/수정 후보 → 사람이 근거 대조 → 승인한 파일 갱신 → 다음 질문에서 다시 읽기’의 한 예를 붙인다. 32장의 분담을 앞에서 짧게 예고한다. 오늘 본 화면은 사람이 준비한 결과라는 경계는 명확히 한 번 정하고 필요한 곳에 짧은 상태 표기로 유지한다. 실제 실행을 추가한다면 사용 도구·입력 파일·반환/저장 결과를 직접 확인한 뒤 구분해 제시한다. | 초심자가 10장 뒤 ‘LLM이 할 일, 사람이 할 일, 오늘 실제 실행한 일’을 자기 말로 나눌 수 있는가. |
| 2 | **19장 관계도의 기억 부담을 줄인다.** 화면에 C1/Q1/Q2/D2와 index/log/D1/pending 8개 이름이 함께 나온다. 40초 발언은 이 관계와 자동 영향 발견의 한계를 함께 설명한다. 20장은 D1→D2를 이미 언급하지만 D1의 구체적인 원래 이유는 22/26장에서 풀린다. | 3 | **참여가 자기 판단을 남기게 하고 앞부분의 기다림을 줄인다.** 4~6장은 연속 예고이고, 11장 발언부터 ‘범위가 같을까요’라고 힌트를 준 뒤 12장은 B를 고른다. 23장은 화면/발언이 이미 ‘근거 부족’이라고 밝히고 B를 초록으로 표시한다. A/B 모두 답이 쉽게 보이고 25초가 기다림이 될 가능성을 예상했다. 자기 질문을 실제 쓰는 35장은 시간표상 26:20이며 자료 두 제목·질문·근거 위치를 20초에 요구한다. | 앞 예고의 발언을 짧게 하고 실제 한 문장 예를 앞당긴다. A/B 입력은 유지하되 12장에는 ‘과도한 단어 하나’, 23장에는 ‘보류 이유나 다음 확인 한 줄’을 선택적으로 붙인다. 선택 색으로 정답을 먼저 알리지 않는다. 35장은 “질문 하나가 남으면 충분”을 작성 전에 말하고, 첫 장부터 자료 두 개를 준비하게 하거나 제목/질문만 쓰고 근거는 다음 모임에 찾게 한다. | 한 글자 선택 외에 청중이 실제 남긴 이유/자기 질문이 있는가. 무응답이면 대본의 안전한 진행 분기를 쓰되 참여 성공으로 보고하지 않는다. |

31장의 62.5%/37.5%는 화면에서 가장 큰 숫자다. A/B 모두 실제 파일 구성보다 성능 지표를 먼저 떠올릴 수 있다고 보았다. 대본은 파일 수·링크·보존 검사와 의미/검색/시간 성과를 정확히 구분하므로 허위 수치 문제로 판정하지 않는다. 시각 검토팀에는 ‘5쪽+3쪽=8쪽’ 원값이 핵심으로 남는지, 구성비의 현저성이 발표 메시지에 필요한지 확인하도록 전달한다.

## 40장·30분과 가벼운 Zoom 스터디의 적합성

40장을 유지하는 선택은 메시지·비교·도식·참여·직접 문장 읽기로 장면을 나누는 데 쓸 수 있다. 장수만으로 길거나 짧다고 판정하지 않는다. 대본은 1~39장 설명/참여 30분, 40장 별도 질문 2분을 배분했으며 실제 리허설 시간은 아니다.

현재는 8장 구조 설명까지 4:40, 첫 채팅이 8:00, 제목의 핵심인 Q2 시작이 15:40, 자기 질문 작성이 26:20에 배치된다. 가벼운 스터디라는 목적에서는 첫 실제 파일까지의 예고와 같은 오류·경계의 반복이 부담 후보이고, 반대로 19장의 8개 관계는 짧은 시간에 몰린다. 원고를 빨리 읽어 30분에 맞춘다고 해결되는 문제는 아니다. 시간 초과 시 Q2/보류/대체 결정과 자기 질문 작성은 유지하고, 원문 절·LoRA 부연·JSON 필드·확장 운영법을 자료로 넘길 대본의 선택을 실제 낭독으로 확인할 필요가 있다.

A는 도구를 통한 실제 시작 안내가 부족해 입문 체험의 완결성을 낮게 보았고, B는 검토할 한 질문을 정하는 실무 토론의 시작으로는 행동 가능성을 보았다. 이 차이를 하나의 만족도나 합격 점수로 합치지 않는다.

## 사람 리허설에서 확인할 질문 3개

1. 10장 뒤 자료를 가리고 “LLM Wiki는 무엇이고, LLM·사람·오늘 Node 데모는 각각 무엇을 하나요?”라고 묻는다. 실제 답을 기록해 역할 구별이 전달되는지 본다.
2. 22~27장 뒤 “Q2가 예전 기록 중 무엇을 왜 가져왔나요? 현행에 못 넣은 문장은 무엇을 더 확인해야 하나요?”라고 묻는다. 코드 이름 암기보다 이유와 연결이 남는지 본다.
3. 35장의 안내대로 자기 자료 제목·질문·근거 위치를 적어 보게 한 뒤 “어디에서 멈췄고 다음 모임 전에 무엇을 할 수 있나요?”라고 묻는다. 실제 작성물·걸린 시간·막힌 이유를 기록하고, 발표자가 추측한 참여와 구별한다.

## 인계 상태

A/B 초기 구간과 회상은 동결했고 양방향 직접 교차 검토·B의 논점 취합·사후 대조와 최종판단을 완료했다. A/B와 manager 전원 편집 종료했다. 이후 보완은 원래 관측 뒤에 덧붙였다. manager는 새 공개 PNG 중8/19/22/31/35장도 직접 대조해 핵심 화면 판단을 유지했다. 청중→디자인 직접 인계는 신규 디자이너의 독립 초기 판정 뒤 root가 연결한다. 종료/인계 계약은 MEETING에 기록했다.
