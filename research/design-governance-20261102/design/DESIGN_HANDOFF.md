# 디자인 기준과 현재판 검수 — 후속 구현 계약

2026-11-02 · 디자인 매니저 `/root/design_manager` · 기준 HEAD `2a95f37`

이 계약은 [리서치 확정안](../research/RESEARCH.md)을 [기존 DESIGN 정본](../../../DESIGN.md)과 [현재 26장 audit](LLM_WIKI_AUDIT.md)에 연결한다. 이번 디자인팀 산출은 기준 재구성과 현재 화면의 판정·교정 명세다. 본편 교정을 구현했다고 보고하거나 개선 필요 판정을 승인으로 바꾸지 않는다. 최신 사용자 지시가 우선이며 Stage는 명시적 변경 전의 기본값이다.

## 후속 구현에서 지킬 결정

- 새 발표의 원고는 `talks/<id>/slides.md`다. 생성 `content.js`를 원고 정본으로 안내하지 않는다. legacy JavaScript 직접 입력은 별도 경로로 설명한다.
- 내용 참고자료는 주제·사실·그림의 출처다. 그 자료의 배경·색·구도를 기존 시각 기준 대신 기본값으로 승계하려면 변경 이유·영향·명시적 예외 또는 사용자 지시를 기록한다.
- 디자인은 한 장의 역할·주역·읽는 순서, 메시지/근거/시연의 밀도 변화로 판단한다. 검정·의미색·레이아웃 빈도·장수·도식 수만으로 판정하지 않는다.
- 실제 문서·UI·사진의 밝은 면과 고유색은 허용한다. 8–11장의 서로 다른 관계도 연속과 20장의 밝은 활동안은 금지 규칙의 반례로 보존한다.
- 현재 26장·본편9도식·19그림 부록·48장 원문·대본·자료 접근을 보존한다. 이번 범위를 전면 재작성·대량 삭제로 확대하지 않는다.

## 검수 기록이 표현해야 할 내용

파일 형식과 명령 이름은 엔지니어링팀이 정한다. 다음 대응을 검사할 수 있어야 한다.

| 항목 | 필요한 내용과 판정 경계 |
| --- | --- |
| 대상 | 발표 id·원고 경로·현재 원고 fingerprint, 필요한 생성 대상 |
| 읽은 기준 | DESIGN 경로·revision/fingerprint, 적용한 예외와 근거 |
| 화면 입력 | 공통 CSS/JavaScript·렌더링/빌드 입력·관련 자산의 경로와 fingerprint. 원고가 같아도 자산·runtime 변경을 놓치지 않음 |
| 변경 영향 | 바뀐 원고/자산/공통 코드/기준과 대상 장·인접 흐름·확장 회귀 범위 |
| 화면 근거 | 실제 존재하는 캡처/보드·manifest 경로와 fingerprint, 모드·viewport·관련 장, 캡처와 측정의 대응 |
| 검토 | 검토자·기준 적용 시점·실제로 본 범위·판정·구체 이유·미완료 교정과 다음 담당 |
| 기술 결과 | 생성물 일치·기능/경계 검사와 시각 판정을 별도 결과로 기록 |

원고와 자산은 이번 검수 범위의 실제 파일을 열거한다. 누락 파일을 과거 해시만으로 통과시키지 않는다. 기준 문서·원고·runtime·자산·증거 파일의 실재와 현재 fingerprint가 기록과 맞는지 확인한다. 검토 범위와 판정의 장 대응도 확인한다. 기록 파일의 존재만으로 통과시키지 않는다.

기록 생성은 입력과 범위를 준비할 수 있지만 사람의 승인 상태나 판정 이유를 자동으로 만들지 않는다. 자동 검사는 사람이 이미지를 실제 보았는지, 디자인 판단이 옳은지 증명하지 못한다. 수동 판정과 root의 독립 확인 책임을 유지한다.

## 상태와 완료 조건

| 상태 | 의미 | 자동 확인에서의 취급 |
| --- | --- | --- |
| `approved` / 승인 | 명시한 현재 범위를 직접 보고 기준 충족 이유를 제시 | 현재 입력·근거가 맞는 범위만 승인. 전체 승인으로 확대 금지 |
| `needs-changes` / 개선 필요 | 실제 화면의 문제와 보존·교정 명세가 있음 | 유효한 재점검 기록. 제품 시각 승인 완료와 구별 |
| `unreviewed` / 미확인 | 필요한 화면·모드·판정이 아직 없음 | 미확인 범위·담당·다음 행동을 보고 |
| `stale` / 오래된 근거 | 검토 후 관련 입력이나 기준이 달라짐 | 이전 이력 보존, 현재 승인 재사용 금지 |

‘재점검 기록이 완전하고 최신인가’와 ‘제품이 시각 승인됐는가’를 별도로 확인한다. 전자는 정직한 `needs-changes` 기록을 허용한다. 후자는 해당 범위가 현재 `approved`여야 한다. 성공 메시지에서 이 두 결과를 하나의 통과로 합치지 않는다. 구현된 명령이 없다면 문서만으로 존재한다고 보고하지 않는다.

DESIGN만 바뀌고 제품 바이트가 그대로인 경우, 기존 캡처를 새 기준으로 다시 읽을 수 있다. 이때 캡처 당시 기준 fingerprint와 실제 재검토 기준 fingerprint를 구분하고 재검토자·범위·이유를 명시한다. 파일의 해시를 새 값으로 덮어써서 재검토한 것처럼 처리하지 않는다. 제품 입력이 바뀌면 영향 화면을 다시 캡처한다.

## 변경에 따라 확인할 범위

| 변경 | 필요한 확인 |
| --- | --- |
| 특정 원고·문구 | 해당 장과 앞뒤 흐름, 전체 보드의 역할 변화, 필요한 읽기 화면 |
| SVG·이미지 | 원본과 실제 배치 크기, 읽어야 할 부분·대체 텍스트·출처, 해당 장과 인접 흐름 |
| 공통 CSS/runtime | 대표 양식·긴 한국어·밝은 실제 UI/문서·사진·다른 주제·읽기·모션 줄이기 및 기존 기능의 영향 범위 |
| DESIGN 기본값/판정법 | 영향 장의 새 기준 대조, 예외와 기존 판정 재사용 범위 명시 |

사소한 변경마다 26장 맵을 다시 작성하지 않는다. 기존 역할 맵을 유지하고 무효화된 범위와 흐름을 갱신한다. 반대로 원고 SHA 하나가 같다는 이유로 공통 CSS·자산 변경을 생략하지 않는다.

## 현재 인수와 남은 일

현재 제품 입력은 원고 SHA256 `6df65ff95f74d48df3845d212d4bd36b111980e077d9ff332299c9bba7728b09`의 26장이다. 캡처 당시 입력은 [before 입력 해시](../evidence/before/input-hashes.json), 캡처/측정은 [manifest](../evidence/before/manifest.json)에 보존한다. 입력 해시는 111항이며 `talks/llm-wiki/` 실제98파일과 공통13파일을 포함한다. 디자인팀 종료 검산에서 이 중 DESIGN만 재구성으로 바뀌고 나머지110파일은 같으며 누락은 없다. 저장소 루트 `test.md` 부재와 실제 `talks/llm-wiki/test.md`를 구별한다.

root가 screenshot과 측정의 viewport 대응을 보강한 뒤, 매니저는 확정된 4개 contact sheet와 4·10·17·18·20·24장 원본을 다시 열어 확인했다. 모드는 `presentation-stage-only`, viewport1440×1000·DPR1, 실제 stage PNG는1344×756이며 각 관측과 같은 invocation의 캡처가 대응한다. 보관된 DevDay 23:00·24:15·48:30 및 Codex20:00 프레임도 직접 열었다. 최초 영상은 이번에 새로 재생하지 않았다. 현재 정지 화면 범위의 위계·관계·자료 정체성 판단이며, 발표 현장·전 기기·청중 이해도 실험·전체 모션 검증을 수행한 것은 아니다.

현재 audit의 정지 화면 판정은 21장 승인, 10·17·18·20·24장 개선 필요다. 4장은 필요→지원의 표제가 관계를 이미 구별하므로 승인하며 선택 제안만 남긴다. 19·21·22장의 병렬 범주·동사는 3열 유지의 구체 근거다. 24장의 요청문은 이미 주역이며 보조자료 두 행의 성격·위계만 보완 대상으로 한정한다.

후속 엔지니어링팀의 **이번 실행 범위는 작업 진입점과 검수 근거 최신성·승인 상태 분리**다. 실제 검증 명령·결과·미완료를 root에 인계한다. 본편5장 교정은 이번 작업 밖의 추후 발표 수정 권고이며, 다음 발표 수정 담당자가 [audit 명세](LLM_WIKI_AUDIT.md)의 보존 조건·주역·읽는 순서에 따라 적용하고 화면을 재검토한다. 이 권고를 이번 요청의 미완료 구현으로 보고하지 않는다. 기술 검사에서 경계 초과·이미지 누락이 없다는 결과는 현재 시각 판정을 대체하지 않는다.

양 실무자는 독립 초안 뒤 상대의 전체 파일을 직접 읽고 반론·합의를 완료했으며 편집을 종료했다. 매니저도 최종 DESIGN145행과 audit142행 전체를 다시 읽었다. 인수한 DESIGN SHA256은 `75e405eb4d1695fc5b4d5301d9393a2b3a0f938a3288dd3c9807e2845ca90817`, audit SHA256은 `5af3802bafcca71a7f9490c0c6d96a8260818a7ccf4a0648b3a34123dd6f6265`다. 매니저 검산에서 26행은 승인21/개선필요5로 대응했고 세 디자인 문서의 로컬 링크93개는 모두 실재하며 줄 끝 공백은 없었다. 문서 변경이므로 제품 전체 테스트를 반복하지 않았다.
