## 결론

최초 기준은 사라진 문서가 아니라 **후속 작업에서 효력을 잃은 기준**이었다. 현재 [DESIGN.md](../../../DESIGN.md)는 이미 210행이며 실제 DevDay 세션의 메시지·근거·시연, 정보량과 시선의 변화, 의미색과 매체 고유색을 기록한다. 그런데 새 참고자료의 시각 언어가 작업별 계약의 기본값이 되고, 그 기본값이 다음 작업으로 승계됐다. 원고·SVG·공통 CSS가 바뀔 때마다 현재 판을 최초 기준과 다시 대조하는 인수 연결이 약했다. 새 DESIGN 파일을 만들거나 검정 테마만 고정하는 처방으로는 이 경로를 막지 못한다.

이번 권고는 **기존 정본의 권한과 사용법을 앞에 놓고, 작성 진입점에서 읽도록 연결하며, 현재 입력과 실제 화면 검토를 묶는 것**이다. 최신 사용자 지시가 우선하며 Stage는 명시적 변경 전의 기본값이다. 현재 26장을 전면 재작성하거나 필요한 그림·설명을 일괄 삭제하는 요청으로 확대하지 않는다. 디자인팀은 아래 위험 구간에 판정을 내리고, 엔지니어링팀은 근거의 최신성·누락·상태를 확인한다. 자동 검사에 미감의 판정을 맡기지 않는다.

## DESIGN 현행화 구조와 audit 판정 규약

디자인팀은 기존210행의 근거를 보존하면서 다음 순서로 사용 목적을 앞당긴다. 이는 새 정본을 하나 더 만드는 제안이 아니다.

1. 권한·적용 범위·읽는 법: 사용자 최신 지시, 현재 프로젝트 기본값, 예외/실험, 원본 관찰의 관계.
2. 핵심 시각 원칙: 한 장의 역할·시각 중심·밀도/리듬·큰 근거·열린 관계·매체 고유면·한국어 가독성.
3. 색·타입·면의 실제 역할: 값의 출처와 CSS 대응, 구현값과 원본 실측값의 구별.
4. 역할별 구도 선택: 짧은 선언·단일 근거·관계 설명·실제 자료·시연·다음 행동. 지원 입력의 문법은 작성 안내/CONFIG로 연결.
5. 재발 사례와 허용 반례: paper 승계·설명 평준화·옛 판 인수 재사용과 밝은 실제 문서·유효한 연속 관계도의 대비.
6. 변경·검수 계약: 시작 때 기준/범위 확인, 변경 영향별 화면 확인, 현재 판의 명시적 판정과 근거 갱신.
7. 출처·미확인·관련 문서: 기존 영상 타임코드와 조사, 입력 계약, 운영 로그, 현재 발표별 audit 연결. 과거 테스트 개수·예제 장수는 현재 의무와 분리.

현재26장 전체 audit는 장별 `역할/핵심 메시지/증거 또는 대상/주역/판정/이유/화면 근거`를 대응시킨다. 이번 전체 재점검 뒤 사소한 변경마다26행을 새로 쓰게 하지 않고 기존 맵을 재사용하며 영향 장과 흐름을 갱신한다.

| 개선 필요 | 실제 화면과 구체 문제·보존/교정 명세가 있음 | 유효한 재점검 완료이며 제품 시각 승인과 구별. 이번 요청의 완료를 본편 전면 리디자인까지 확대하지 않음 |
| 미확인 | 필요한 실제 화면/기기/판정이 아직 없음 | 확인한 것처럼 보고하지 않고 다음 담당·행동 명시 |
| 오래된 근거 | 검수 뒤 관련 원고·자산·runtime·기준이 변경됨 | 이전 판정 이력은 보존하고 현재 승인을 재사용하지 않음 |

예방 검증은 ‘유효한 개선 필요 판정’과 ‘승인’을 구별해야 한다. 재점검 기록을 검사하는 경로는 정직한 개선 필요 기록을 허용하고, 시각 승인을 요구하는 별도 완료 경로에서는 승인이 없는 상태를 통과시키지 않는다. 기록 생성 도구가 승인 상태를 자동으로 쓰게 하지 않는다. 구체 파일 형식·명령은 후속팀이 가장 작은 범위로 결정한다.

## 후속팀 실행 계약

| 우선 | 담당·산출물 | 완료 조건 |
| --- | --- | --- |
| P0 | 디자인팀: 기존 DESIGN 정본 재구성, 현재 LLM Wiki 역할 맵과 장별 판정 | 첫머리에 권한·읽는 법·변하지 않는 방향·허용 변형을 둠. 원본 관찰/프로젝트 판단/현재 구현을 구분하고 구식 수량은 정리. 현재26장 전장 흐름과 위 위험 장의 승인/교정/미확인을 근거 이미지에 연결 |
| P0 | 디자인팀: 필요한 교정 명세 | 각 수정이 해결하는 이해 문제·주역·읽는 순서·보존 문구/그림·검수 크기를 적음. 필요한9도식과19부록·48장 원문·대본·내용을 보존. 전면재작성이나 삭제 없이 해결 가능한 범위부터 제시 |
| P0 | 엔지니어링팀: 작성 진입점 연결 | 사용자 최신지시가 우선임을 보존하며 AGENTS·README·MARKDOWN-FIRST·스타터에서 DESIGN의 역할과 변경/검수 흐름에 접근 가능. 연구 전체를 각 문서에 복사하거나 기술 설정을 제품 청중 UI에 노출하지 않음 |
| P0 | 엔지니어링팀: 작은 검수 기록과 최신성 확인 | 읽은 DESIGN revision, 대상 원고/공통 runtime/자산 fingerprint, 변경 범위, 캡처 모드/viewport, 증거 경로, 검토자·판정·사유를 대응. 필수 입력이 바뀌면 기존 승인에 stale/재검토 필요를 표시. 형식·최신성·상태를 검사하며 자동 미학 점수는 만들지 않음 |
| P0 | 총괄+디자인: 현재 판 인수 | 기술 통과와 시각 판정을 두 항목으로 보고. 실제 보고하는 모든 승인 상태는 현재 fingerprint에 유효. 미확인을 승인으로 바꾸지 않음. WORK_LOG에 결정·결과를 root가 기록하고 영향 담당자에게 직접 전달 |
| P1 | 디자인+엔지니어링: 변경 영향별 회귀 | 원고만 바뀌면 해당 장+앞뒤 흐름·전장보드·필요 읽기; SVG면 원본/실제 배치 크기·필요 상세 읽기; 공통 CSS/runtime면 대표 양식·긴 한국어·실제 밝은 UI/문서·이미지·다른 주제·읽기·기존 기능의 영향 범위. 변경이 무효화하는 검증을 선택 |

재발 시 기존 정본을 계속 덧붙여 비대하게 만들지 않는다. DESIGN은 현재 기준·판단법, CONFIG/MARKDOWN-FIRST는 입력 계약·작성법, 연구는 관찰·비교·결정 근거, WORK_LOG는 목표·담당·미완료·결정의 단일 운영 로그를 맡는다. 발표별 역할 맵/검토 기록은 품질 근거이며 별도 상태 로그가 아니다.

다음 검증은 ‘사람이 검토했다고 쓴 파일이 있다’만 확인해서도 안 된다. 최소한 대상 파일·증거 파일의 실재와 최신성, 명시적 검토 범위와 판정의 대응을 확인한다. 자동 검사는 사람이 실제 보았는지나 판단이 옳은지를 증명하지 못하므로, 디자인 인수 책임과 총괄의 독립 화면 확인은 남는다.

## 금지할 오해

- 검정 배경·초록색·같은 도식 수가 DevDay 승인이라는 규칙을 만들지 않는다.
- 카드·네모·밝은 문서면·컬러를 전면 금지하지 않는다. 실제 대상의 고유면과 무관한 반복 박스를 구분한다.
- 레이아웃 연속 N장·색 면적·장수·텍스트 수치에 합격 할당량을 두지 않는다. 단계적 설명에는 같은 구도가 유효할 수 있다.
- 원고 간소화를 좋은 시각자료·맥락 삭제와 동일시하지 않는다. 화면 설명·대본·자료의 역할은 구분하되 접근 경로와 의미를 보존한다.
- 자료 링크·표·빌드 성공·이미지 로딩 성공을 주장 지원·가독성·시각 승인과 동일시하지 않는다.
- 최초 영상의 정지 프레임 관찰을 전편의 애니메이션·색빈도·원본 제작기술 확인으로 확대하지 않는다.

## 팀 산출·검증·남은 판단

두 실무자의 초기 조사와 직접 반론·합의는 [시각 계보 조사](visual-baseline.md), [문서 운영 조사](documentation-practices.md), [실무 통합](contributor-synthesis.md)에 있다. 매니저가 기존 원문·코드·최신 캡처·공식 외부 본문을 직접 읽고 이 확정안을 작성했다. 모델은 세 담당 모두 root의2026-11-02 05:24 UTC 공식 release/runtime snapshot을 공유한 `gpt-6.1-sol` / `high` / `fork_turns=none`이며, 범위가 고정된 수집보다 판단·반론·통합이 주된 업무라 선택했다. 현재 리서치 산출물만 변경하며 제품·원고·DESIGN·AGENTS·WORK_LOG는 직접 수정하지 않았다.

리서치가 확정한 것은 문제 경로·적용 원칙·후속팀 수용 기준이다. 현재26장의 최종 시각 승인·구체 교정 채택·예방장치 구현은 후속 디자인/엔지니어링팀과 총괄 담당이다. 이번 문헌/분석 변경에는 제품 전체 테스트를 반복하지 않았으며, 실제 제품 변경 뒤 영향에 맞게 실행해야 한다.
