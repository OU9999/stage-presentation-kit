# 작은 LLM Wiki 만들기

[발표24장](../slides.md#24)에서 적은 질문 한 줄을 가져오세요. 기본 실습은15~20분의 계획이며 실제 소요를 측정하지 않았습니다. RAG·LoRA의 정밀 교정 실습은 아래의 **별도20~30분 심화**입니다. 모두 끝내야 참여한 것으로 보지 않습니다.

## 기본 실습: 내 자료에서 작은 순환 만들기

목표는 파일 수가 아니라 **입력→관련 여러 페이지 작성·갱신→후속 질문에서 읽기→유용한 답 저장→새 자료 재갱신**을 설명하는 것입니다. 파일 읽기/쓰기 도구가 있는 LLM 에이전트가 입력과 위키를 현재 문맥에 읽고 작성하도록 할 수 있습니다. 직접 편집하거나 종이로 설계해도 됩니다. 어느 방식을 썼는지 결과에 남기며, 제공된 문장을 모델의 실제 수행 결과로 표시하지 않습니다.

### 1. 사례 하나와 질문 하나 고르기

| 선택 | 입력·출력 실물 | 이어갈 질문 |
| --- | --- | --- |
| 독서 | [장 메모/인물/주제/답 txt](../assets/examples/reading.txt) | 왜 배신으로만 볼 수 없을까? |
| 팀 | [상담/회의/요구 비교/답 txt](../assets/examples/team.txt) | 고객 B에게 지금 무엇을 말할까? |
| 강의 | [단원 메모/개념/종합 txt](../assets/examples/course.txt) | 무엇이 같고 다른가? |

세 자료는 모두 가상 구성 예입니다. 자기 자료로 옮길 때는 접근 가능한 입력과 읽은 범위를 정합니다. 실제 자료가 없다면 한 예를 골라 아래 팀 사례처럼 흐름을 연습하세요. 전체 세 사례 해설은 [학습 가이드](./study-guide.md#세-가지-적용-예)에 있습니다.

### 2. 입력과 이전 위키를 나누기

아래는 가상 팀 사례의 실제 연습 문장입니다.

```markdown
# raw/call-a.md
월말 정산을 위해 화면에서 CSV를 수동 다운로드하고 싶다.
# raw/call-b.md
매일 대시보드를 갱신하려고 CSV를 자동으로 받고 싶다.
```

```markdown
# wiki/concepts/export.md — 이전
A는 월말 수동 다운로드, B는 일별 자동 수집을 요청했다.
출력 형식은 같지만 목적·주기·자동화 범위는 다르다.
우선순위와 출시일은 미정이다.
근거: raw/call-a.md, raw/call-b.md
연결: comparisons/export-requests.md
```

연습: 입력의 사실과 위키의 비교를 다른 색으로 표시하세요. LLM에게 맡긴다면 자료 요약·내보내기 개념·요구 비교를 함께 쓰고 근거를 연결하게 합니다. 모든 상담을 같은 요청 한 줄로 합치지 않았는지 확인합니다.

### 3. 새 입력을 관련 여러 페이지에 반영하기

```markdown
# raw/planning-meeting.md — 새 입력
이번 분기는 수동 CSV의 범위를 검토한다.
예약 전송은 운영 비용 검토가 남아 보류한다. 출시일은 미확정이다.
```

```markdown
# wiki/concepts/export.md — 갱신 후
A와 B의 요청은 별도 요구로 보존한다.
수동 CSV는 범위 검토 중이고 예약 전송은 보류 중이다.
어느 기능도 이 자료만으로 출시일을 약속할 수 없다.
근거: raw/call-a.md, raw/call-b.md, raw/planning-meeting.md
연결: comparisons/export-requests.md, questions/what-to-tell-b.md
```

연습: source 요약, 내보내기 개념, 요구 비교의 상태, FAQ, index/log 가운데 무엇을 왜 고칠지 적으세요. 입력과 관련 없는 페이지까지 억지로 바꿀 필요는 없습니다. 회의의 우선순위를 고객 요구 자체의 삭제로 바꾸지 않습니다.

### 4. 다음 질문의 답을 실제 페이지로 남기기

```markdown
# wiki/questions/what-to-tell-b.md
B의 일별 자동 수집 요구는 접수되어 있다.
예약 전송은 운영 비용 검토가 남아 보류 중이다. 출시일은 미확정이다.
다음 확인: 일별 수동 다운로드도 B의 업무를 해결하는가?
근거: raw/call-b.md, raw/planning-meeting.md
연결: concepts/export.md, comparisons/export-requests.md
```

연습: 답을 쓰기 전에 어떤 파일을 실제로 읽었는지 적으세요. 답을 내보내기 개념·비교와 연결해 다음 질문에서 찾을 수 있게 합니다. B의 후속 상담이 오면 비교와 이 답의 어느 문장을 다시 볼지 표시합니다. 이 codeblock은 가상 응대 초안이며 실제 고객에게 발송한 기록이 아닙니다.

### 5. 작은 점검과 해설

다음을 한두 문장으로 확인하면 기본 실습을 마칠 수 있습니다.

- 원자료와 LLM/사람이 쓴 설명은 어디서 구분하는가?
- 새 입력 때문에 기존 페이지 두 곳 이상에서 무엇이 달라졌는가?
- 다음 질문이 어느 파일을 찾아 현재 문맥에 읽는가?
- 유용한 답을 어느 페이지에 저장하고 다시 연결했는가?
- 아직 모르는 내용과 새 자료가 오면 다시 볼 곳은 무엇인가?

해설: 팀 사례에서는 출력 형식만 같다고 두 요구를 합치지 않고, 회의 뒤 상태와 응대 범위를 함께 바꿉니다. 독서는 인물의 말·서술 사실·독자의 해석을 나눕니다. 강의는 공유 개념에 새 기준을 연결하고 적용 범위를 넓히되 모든 트리로 일반화하지 않습니다. 이 경계가 유지되는지 source와 위키를 함께 읽습니다. 링크 검사 통과가 의미 검토를 대신하지 않습니다.

## 기술 스터디 심화: 주장·근거·파일 교정

이하20~30분은 별도 계획입니다. RAG·LoRA의 원문, 가상 읽기 메모, 질문·결정·날짜를 구별하며 실제 지원 범위를 대조합니다. codeblock은 직접 만들 가상 위키 경로입니다. AI는 선택 사항이며 직접 작성도 가능합니다. 이 수동 검토 흐름은 LLM Wiki의 필수 정의가 아닙니다.

[고정 데모 ZIP](../demo/llm-wiki-demo.zip)은 사람의 승인안을 Node로 적용·검사한 보조 실습입니다. 실제 모델 호출이나 자동 의미 검증이 아닙니다. [실행 기록](./demo-log.md)과 범위를 확인하세요.

## 1. 원문을 찾을 수 있는 읽기 메모 만들기

### 입력

첫 자료는 [RAG 논문 v4의 §2 Models·Generator](https://arxiv.org/html/2005.11401v4#S2)입니다. 검색된 문서가 생성에 어떻게 쓰이는지 찾습니다. 두 번째 자료는 [LoRA 논문의 Abstract](https://arxiv.org/abs/2106.09685v2)입니다. 무엇이 고정되고 무엇이 학습되는지 찾습니다. 두 논문은 서로 다른 방법과 실험을 다루므로 성능 숫자를 뽑아 우열표를 만들지 않습니다.

아래 메모를 복사하고 실제 읽은 위치와 자신의 확인일을 적으세요. 원문에 접근하지 못했다면 확인일에 오늘을 적어 ‘검토 완료’로 표시하지 말고 `접근 못 함, 제공된 메모만 읽음`이라고 씁니다. 읽은 범위를 정직하게 남기는 것도 실습의 일부입니다.

```markdown
# RAG 읽기 메모

- 기록 ID: X-R1 — 가상 학습자의 메모
- 실제 자료: Lewis 외, RAG, v4(2021-04-12)
- URL: https://arxiv.org/html/2005.11401v4
- 읽은 위치: §2, 특히 §2.3 Generator
- 확인일: [직접 확인한 날짜 또는 미확인]
- 자기 말 요약: 검색한 문서를 생성의 입력에 활용한다.
- 더 알아볼 질문: 이 논문에는 학습 단계도 있는가?
```

```markdown
# LoRA 읽기 메모

- 기록 ID: X-R2 — 가상 학습자의 메모
- 실제 자료: Hu 외, LoRA, v2(2021-10-16)
- URL: https://arxiv.org/abs/2106.09685v2
- 읽은 위치: Abstract
- 확인일: [직접 확인한 날짜 또는 미확인]
- 자기 말 요약: 사전학습 가중치를 고정하고 추가한 저랭크 행렬을 학습한다.
- 더 알아볼 질문: 기본 가중치가 고정돼도 학습이라고 부르는 이유는?
```

### 진행

각 메모에서 원문에서 확인한 설명 한 줄과 자신이 궁금한 질문 한 줄을 다른 항목으로 남깁니다. 원문 설명을 읽고 떠올린 생각을 모두 ‘논문 결론’에 넣지 마세요. 스터디에서 여러 자료를 모을 때 이 구분이 다음 사람이 읽을 출발점이 됩니다.

운영 규칙도 짧게 만들어 둡니다. [LLM Wiki 원문](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)의 원자료·위키·운영 규칙 구분을 참고한 실습용 약속이며 공식 템플릿이 아닙니다.

```markdown
# 이 위키의 작업 규칙

- raw의 읽기 메모는 원문과 구분하고 URL·판·읽은 위치를 적는다.
- 위키의 핵심 주장은 직접 지원과 해석을 나눈다.
- 질문의 답은 근거를 대조한 뒤 현행 답으로 표시한다.
- 새 근거가 오면 관련 개념·비교·질문의 변경안을 먼저 본다.
- 의미가 바뀐 이유는 log에 적고, 선택이 바뀌면 결정을 연결한다.
```

### 기대 결과와 해설

읽기 메모가 두 개 있고 그 메모에서 실제 원문으로 돌아갈 수 있어야 합니다. URL만 복사해둔 상태보다 어느 판의 어떤 부분을 읽었는지 적은 상태가 검토에 적합합니다. 규칙은 AI가 할 일을 약속한 문서입니다. 이후 파일에 근거 위치가 빠져 있다면 규칙에 적혀 있어도 실제 결과를 고쳐야 합니다.

## 2. 주장 두 개와 비교 한 개 만들기

### 진행

RAG 메모에서 한 주장, LoRA 메모에서 한 주장을 뽑아 개념 페이지에 적습니다. 각각 한 문장으로 써보세요. “검색 문서를 사용하고, 항상 정확하며, 비용도 낮다”처럼 서로 다른 주장을 한꺼번에 묶지 않습니다.

```markdown
# 검색 문맥과 답 생성

- 주장 ID: X-C1
- 문장: RAG 논문의 모델은 검색된 문서를 생성에 활용한다.
- 종류: 직접 지원
- 근거: https://arxiv.org/html/2005.11401v4 의 §2
- 범위: 해당 논문에 설명된 모델 구조
- 검토 상태: [직접 원문 대조 후 적기]
- 비교: [검색과 모델 적응](../comparisons/retrieval-vs-adaptation.md)
```

```markdown
# 모델 적응

- 주장 ID: X-C2
- 문장: LoRA는 기본 가중치를 고정하고 추가한 저랭크 행렬을 학습한다.
- 종류: 직접 지원
- 근거: https://arxiv.org/abs/2106.09685v2 의 Abstract
- 범위: LoRA 논문이 설명하는 적응 방식
- 검토 상태: [직접 원문 대조 후 적기]
- 비교: [검색과 모델 적응](../comparisons/retrieval-vs-adaptation.md)
```

비교 페이지에는 아래의 같은 질문을 적용합니다. 빈칸을 채울 때 파일 저장·검색·모델 적응이 배타적인 세 제품이라고 가정하지 마세요. 함께 설계할 수 있는 서로 다른 역할로 봅니다.

```markdown
# 검색과 모델 적응 비교

| 질문 | 위키 파일 갱신 | 검색을 이용한 생성 | LoRA 적응 |
| --- | --- | --- | --- |
| 직접 바꾸는 대상 |  |  |  |
| 다음 답에 반영되는 경로 |  |  |  |
| 사람이 확인할 대표 항목 |  |  |  |

- 설계 해석 X-I1: [함께 쓰는 가상 예를 한 문장으로]
- 이 조합의 운영 성능: 이 실습에서 측정하지 않음
```

### 예시 답과 해설

첫 행에는 ‘설명·연결 파일 / 자료·색인·검색과 생성 흐름 / 학습 가능한 추가 행렬’을 적을 수 있습니다. 둘째 행에는 ‘필요한 파일 다시 읽기 / 관련 문서 검색 후 문맥에 사용 / 학습 결과를 적용한 모델로 추론’을 적을 수 있습니다. 셋째 행에는 ‘위키의 주장 범위·중복·링크·이력 / 검색 누락·관련성·답의 지원 / 학습 데이터·목표·평가·적용 대상’을 적을 수 있습니다. 이 구분을 읽고 “검토한 위키를 검색해 문맥으로 쓰고, 모델 적응은 별도 목표와 평가로 검토한다”라는 가상 설계를 제안할 수 있습니다.

마지막 문장은 두 논문을 합쳐 얻은 우리의 설계 해석입니다. 두 논문이 이 조합으로 스터디 품질이 개선됐다고 실험한 직접 근거처럼 표시하면 안 됩니다. 비교 표는 설계 질문을 정리하는 도구이고, 실험 결과의 대체물은 아닙니다.

## 3. 질문에 답하고 유용한 결과를 다시 저장하기

### 입력 질문

“위키 파일을 고치면 모델도 그 내용을 학습하나요?”

### 진행

개념 두 개와 비교 페이지를 읽고 3~5문장으로 답하세요. 첫 문장은 질문에 직접 답하고, 다음 문장은 다음 질문에 어떻게 반영되는지 설명합니다. 마지막에는 두 논문의 기전만으로 답할 수 없는 질문을 남깁니다. 원문을 추가로 읽었으면 어느 위치인지 적습니다.

AI를 사용한다면 아래 요청을 복사할 수 있습니다. 모델이나 도구가 로컬 파일을 읽을 수 없다면 필요한 내용을 함께 제공하고, 실제로 읽은 범위를 구분하게 합니다.

```text
질문: 위키 파일을 고치면 모델도 그 내용을 학습하는가?
사용할 자료: 지금 만든 두 개념 페이지와 비교 페이지.
원문에 접근할 수 있으면 실제 확인한 위치를 표시하라.
파일 저장, 질문할 때 문맥 읽기, 학습 가능한 매개변수의 갱신을 구분하라.
답의 직접 지원 부분과 설계 해석을 분리하라.
자료로 알 수 없는 부분은 열린 질문으로 남겨라.
검토 전에는 답을 검토 완료로 표시하지 마라.
```

아래 틀로 답을 저장합니다. 링크가 많다는 이유만으로 좋은 답이라고 판단하지 말고, 핵심 문장과 근거가 대응하는지 읽습니다.

```markdown
# 위키 수정은 학습인가

- 질문 ID: X-Q1
- 상태: 초안 / 검토 완료 중 선택

## 답

[3~5문장]

## 근거와 해석

- 직접 지원: [주장과 원문 위치]
- 설계 해석: [우리가 설명한 파일 흐름과 병행 설계]

## 남은 질문

[우리 자료·도구에서 별도로 확인해야 할 것]

## 연결

- [검색 문맥](../concepts/retrieval.md)
- [모델 적응](../concepts/parameter-update.md)
- [같은 기준으로 비교](../comparisons/retrieval-vs-adaptation.md)
```

### 예시 답과 해설

“이 예제에서 위키 수정은 저장된 문서를 고치는 일입니다. 다음 답변에 반영하려면 AI가 수정된 파일을 읽을 수 있어야 합니다. 모델의 학습 가능한 매개변수를 갱신하는 일과는 구분합니다. RAG의 검색 문맥과 LoRA의 학습 대상을 비교하면 서로 다른 경로임을 볼 수 있습니다. 우리 자료에서 필요한 파일을 제대로 찾는지는 별도로 확인해야 합니다.”

이 답은 ‘위키 저장은 모든 종류의 학습을 대신한다’는 결론을 만들지 않습니다. 또한 RAG와 LoRA가 서로 함께 쓰일 수 없다고 말하지 않습니다. 검토할 때는 개념 페이지의 원문 위치를 실제로 대조한 뒤 상태를 바꾸세요. 이 과정을 통해 query는 일회성 대화로 끝나지 않고, 검토한 답과 남은 질문을 다음 읽기에 연결합니다.

## 4. 새로 읽은 근거로 잘못된 표현 고치기

### 입력: 검토할 잘못된 초안

다음 문장을 비교 페이지에 썼다고 가정합니다. 일부러 오류를 포함한 연습 문장이므로 현행 개념으로 외우지 마세요.

```markdown
## 초기 비교 메모 — 검토 전

외부 파일을 쓰는 시스템은 학습하지 않는다.
기본 모델 가중치가 고정돼 있으면 아무 파라미터도 학습하지 않는다.
```

이제 [RAG §2.4 Training](https://arxiv.org/html/2005.11401v4#S2.SS4)을 추가로 읽고, [LoRA Abstract](https://arxiv.org/abs/2106.09685v2)를 다시 봅니다. RAG 원논문이 학습을 포함하는지, LoRA에서 무엇이 학습되는지 확인하세요. 새 자료를 읽었다는 이유로 초기 메모의 반대 문장인 “외부 파일을 쓰면 항상 학습한다”를 만드는 것도 잘못입니다.

### 진행

바꿀 문장을 먼저 diff로 써보세요. 그다음 이 표현이 들어간 개념·비교·질문을 찾아 검토합니다. 연결된 결정도 검토 후보로 올리되, 결정의 이유가 실제로 바뀌는지 따로 판단합니다.

```diff
--- wiki/comparisons/retrieval-vs-adaptation.md
+++ wiki/comparisons/retrieval-vs-adaptation.md
@@ 초기 비교 메모
- 외부 파일을 쓰는 시스템은 학습하지 않는다.
- 기본 모델 가중치가 고정돼 있으면 아무 파라미터도 학습하지 않는다.
+ 위키 파일 수정은 이 예제에서 모델 매개변수 학습과 별개의 작업이다.
+ 검색을 사용하는 시스템에도 학습 절차가 있을 수 있다.
+ LoRA는 기본 가중치를 고정해도 추가한 저랭크 행렬을 학습한다.
+ 근거: RAG §2.4 Training, LoRA Abstract.
+ 변경 이유: 파일 사용 여부와 학습 대상을 서로 다른 축으로 나눴다.
```

### 기대 결과와 해설

두 개의 과도한 일반화가 제거되고, 확인한 범위 안의 문장으로 바뀝니다. RAG 논문이 훈련을 포함한다는 사실을 모든 검색 제품에 훈련이 필요하다는 주장으로 늘리지 않습니다. LoRA의 학습 가능한 행렬을 확인한 다음에는 ‘기본 가중치 고정’과 ‘어떤 매개변수도 학습하지 않음’을 구분할 수 있어야 합니다.

관련 질문에 같은 일반화가 없었다면 문장을 억지로 바꿀 필요는 없습니다. 다만 새 근거를 확인했고 기존 답의 범위가 유지된다는 검토 기록은 남길 수 있습니다. **새 근거 반영은 매번 전체 결론 교체가 아닙니다.** 범위를 좁히거나 질문을 나누거나 현행 답을 유지하는 것도 검토 결과입니다.

## 5. 결정·index·log로 순환 닫기

### 진행

이번 스터디가 무엇을 하기로 했는지 한 개만 결정합니다. 아래 예시는 원논문에서 직접 나온 결론이 아니라 학습 목적에 맞춘 가상 선택입니다. 더 좋은 도구를 선정하는 문제와 기록 흐름을 경험하는 문제를 혼동하지 마세요.

```markdown
# 검토한 질문 답부터 파일로 남긴다

- 결정 ID: X-D1 — 가상 결정
- 상태: accepted
- 결정일·담당자: [예제 날짜], 가상 운영자 민지

## 배경

같은 질문을 반복하며 이전 답의 근거를 다시 찾고 있다.

## 선택과 이유

질문 하나와 관련 개념·비교 페이지부터 유지한다.
현행 답으로 쓰기 전에 핵심 문장의 근거와 범위를 대조한다.

## 대안과 결과

채팅만 남기는 선택도 가능하다. 현재는 검토 결과를 다시 읽는 연습을 택한다.
파일의 연결과 변경을 관리할 시간이 생긴다.

## 재검토 조건

반복해서 페이지를 찾지 못하거나, 검토가 밀리거나,
스터디의 질문 범위와 접근 권한이 달라지면 다시 본다.

## 연결

- [질문과 검토한 답](../questions/wiki-and-learning.md)
- 후속 결정이 생기면 이 결정의 대체 여부를 표시한다.
```

결정의 배경·선택·상태·결과를 남기는 방식은 [Nygard의 ADR 글](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)을 스터디 운영에 응용한 것입니다. 원래 글의 적용 대상과 이 실습의 응용을 구분합니다.

index에는 읽는 목적을 적어 연결하고, log에는 이번에 바꾼 이유를 적습니다. 두 파일이 서로 같은 목록이 되지 않도록 해보세요.

```markdown
# 스터디 위키 시작점

- 처음 읽기: [검색 문맥](./concepts/retrieval.md), [모델 적응](./concepts/parameter-update.md)
- 차이 알아보기: [검색과 적응 비교](./comparisons/retrieval-vs-adaptation.md)
- 질문에서 시작: [위키 수정은 학습인가](./questions/wiki-and-learning.md)
- 운영을 바꾸려 할 때: [답 저장 결정](./decisions/study-qa-policy.md)
```

```markdown
# 변경 기록

## [실습한 날짜]

- 두 논문 읽기 메모에서 개념·비교·질문 답을 만들었다.
- RAG Training을 추가로 읽고 '외부 파일 사용=학습 없음' 문장을 고쳤다.
- LoRA의 기본 가중치와 학습하는 행렬을 구분했다.
- 질문 답에 같은 일반화가 있는지 확인했다: [검토 결과]
- 답 저장 결정의 이유가 바뀌는지 확인했다: [검토 결과]
- 남은 질문: 우리 자료에서 검색이 놓치는 사례는 무엇인가?
```

### 기대 결과와 해설

index에서 질문까지 이동하고, 질문에서 개념·비교를 거쳐 원문으로 돌아갈 수 있어야 합니다. log에서는 왜 표현을 고쳤는지 찾을 수 있어야 합니다. 결정에서는 왜 이 기록 방식을 택했는지 읽을 수 있어야 합니다. 이 세 파일이 각자 다른 질문에 답하면 작은 순환이 완성됩니다.

## 6. 잘못된 예를 고쳐보는 최종 점검

각 문장을 ‘유지’, ‘범위 수정’, ‘미확인’, ‘결정으로 분리’ 중 무엇으로 다룰지 고르고 이유를 쓰세요. 정답 단어보다 근거와 조건을 설명할 수 있는지가 중요합니다.

| 검토할 문장 | 판정 예 | 해설 |
| --- | --- | --- |
| RAG 논문 모델은 검색 문서를 생성에 활용한다 | 원문 대조 후 유지 | 해당 구조 설명의 범위 안에서 말한다. |
| LoRA는 기본 가중치를 고정하므로 학습이 없다 | 범위·내용 수정 | 추가 행렬을 학습한다는 설명을 빠뜨렸다. |
| 위키를 만들면 모든 과제에서 모델 적응이 필요 없어진다 | 미지원 일반화 제거 | 서로 다른 역할에서 보편적 대체 결론이 나오지 않는다. |
| 우리 스터디는 질문 답부터 Markdown으로 남긴다 | 결정으로 분리 | 선택 이유와 결과·재검토 조건을 적는다. |
| 오늘 확인한 오래된 논문이므로 현재 도구의 동작도 확인됐다 | 적용 대상 수정 | 원논문 확인과 현행 도구 확인은 다르다. |
| 비교 페이지가 바뀌었으니 연결된 모든 결정도 자동 변경됐다 | 검토 과정 수정 | 영향 후보와 실제 결정 변경을 나눠야 한다. |

자신의 문서에서 원문이 지원하는 문장 하나, 해석 하나, 결정 하나를 직접 가리켜보세요. 그다음 누군가 질문 페이지의 한 문장을 의심한다고 가정하고, 어느 원문의 어디로 돌아갈지 설명해보세요. 이 경로를 설명할 수 없다면 링크를 더 다는 것보다 해당 문장의 근거와 범위를 먼저 정리합니다.

## 추가 도전 A. 링크가 있으면 충분한가

기본 실습을 끝낸 뒤 5~10분 더 공부하고 싶을 때 진행합니다. 추가 시간은 기본 20~30분에 포함하지 않습니다.

[ALCE 논문 §3.3 Citation Quality](https://arxiv.org/html/2305.14627v2#S3.SS3)를 읽습니다. 문장들이 인용된 자료로 지원되는지와 불필요한 인용이 붙었는지를 나누어 보는 관점에 주목하세요. 아래 두 문장을 대조합니다. 여기서는 사람의 읽기 연습을 하며 논문의 자동 평가를 실행하거나 현재 도구의 오류율을 측정하지 않습니다.

```markdown
## 검토 전 답

RAG는 검색 자료를 사용하므로 우리 스터디의 답을 항상 정확하게 만든다.
근거: https://arxiv.org/html/2005.11401v4
```

기전 설명과 우리 스터디의 보장 주장을 분리하고 아래처럼 바꿀 수 있습니다.

```diff
- RAG는 검색 자료를 사용하므로 우리 스터디의 답을 항상 정확하게 만든다.
+ RAG 논문은 검색 문서를 생성에 사용하는 모델을 설명한다.
+ 우리 스터디의 실제 답 품질은 이 실습에서 측정하지 않았다.
+ 질문을 검토할 때 각 핵심 문장이 근거에 의해 지원되는지 확인한다.
+ 마지막 문장은 ALCE의 평가 관점을 참고한 우리의 검토 절차 제안이다.
```

새 논문을 읽었을 때 이전 원문을 폐기할 필요는 없습니다. 기존의 구조 설명은 유지하고, ‘정확함을 보장한다’는 과도한 부분을 제거하며, 검토 질문을 더 구체화할 수 있습니다. 원문 두 개를 나란히 읽은 결과가 새 페이지 하나가 아니라 기존 문장의 더 정확한 범위가 될 수도 있습니다.

## 추가 도전 B. 결정이 바뀌었을 때 이력 남기기

가상 스터디의 후속 모임에서 같은 개념 페이지를 찾지 못한 사례가 반복됐다고 가정합니다. 다음과 같은 새 결정을 제안할 수 있습니다. 이 관찰과 결정은 실제 운영 결과가 아닌 추가 연습입니다.

```markdown
# 목차를 정비하고 파일 검색을 함께 시험한다

- 결정 ID: X-D2 — 가상 후속 결정
- 상태: proposed
- 배경: 필요한 개념을 찾지 못한 가상 사례가 모였다.
- 제안: index의 읽기 경로를 정리하고 파일 검색을 작은 질문 묶음으로 시험한다.
- 이유: 답 저장 방식을 버리기 전에 탐색 문제를 별도로 살펴본다.
- 결과: 검색 누락과 색인 갱신을 확인할 일이 생긴다.
- 이전 결정과 관계: X-D1의 모든 내용을 대체하지 않고 탐색 방식을 보완한다.
- 재검토: 시험 질문에서 필요한 근거를 찾았는지 검토한다.
```

이 경우 X-D1 전체를 무조건 `superseded`로 바꾸면 관계를 잘못 기록할 수 있습니다. 질문 답을 파일에 남기는 선택은 유지하면서 검색을 보완하기 때문입니다. 정말로 이전 선택을 폐기하는 경우에만 대체 관계를 분명히 적고, 유지되는 부분과 바뀐 부분을 설명합니다.

짧은 일정 예로도 연습할 수 있습니다. **가상 공지** 1판은 11월 5일 오후 8시, 2판은 같은 날짜를 오후 8시 30분으로 변경한다고 명시합니다. 이때 현행 안내 결정을 바꾼다면 이전 결정을 `superseded by 새 결정`으로 연결할 수 있습니다. 다른 모임의 시각까지 바꾸는 근거는 되지 않습니다. [스터디 가이드의 범위 설명](./study-guide.md#19-보조-사례로-범위를-한-번-더-확인하기)

## 실습을 마친 뒤
