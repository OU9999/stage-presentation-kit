# 다음 질문에 다시 쓰는 작은 파일 위키

읽은 것을 남기는 이유는 다음 질문에서 근거와 판단을 다시 쓸 수 있게 하기 위해서입니다. 이 예제는 **처음 답 → 근거 대조 → 파일 교정 → 새 운영 질문 → 보류와 결정 대체**를 실제 Markdown 파일로 따라갑니다.

이 패키지는 발표자가 작성한 학습용 구성 예제입니다. 초기 답에는 의도적으로 잘못된 일반화를 심었습니다. 실제 AI의 실패 수집이나 모델 성능 실험이 아닙니다. 스크립트는 사람이 승인한 고정 수정안을 적용하고 파일·링크·해시를 검사합니다. 문장의 진실성을 자동 판정하거나 LLM을 호출하지 않습니다. 로컬 source-notes는 공개 원문을 자기 말로 요약한 읽기 메모이며 원문 전문이 아닙니다.

## 실행

Node.js가 있는 컴퓨터에서 ZIP을 풀고 이 폴더로 이동하세요. 추가 패키지·로그인·API·네트워크 연결 없이 실행할 수 있습니다. 원문을 새로 대조하려면 각 메모의 공개 링크에 접속합니다.

```sh
node run-demo.cjs
node run-demo.cjs --check
```

첫 명령은 `after/`, `changes.diff`, `receipt.json`을 씁니다. 둘째 명령은 파일을 바꾸지 않고 승인안과의 일치·로컬 링크·source-notes와 before의 SHA-256 보존을 검사합니다. 의미 검토와 승인 내용은 `review/review.json`에 있습니다.

## 한 번 따라가기

1. `before/wiki/questions/wiki-and-learning.md`에서 Q1 “위키 파일을 고치면 모델도 그 내용을 학습하나요?”의 답을 읽습니다. 링크가 있어도 지원되지 않는 일반화가 있습니다.
2. `source-notes/rag-initial.md`와 `source-notes/rag.md`의 읽은 범위를 비교합니다. 같은 논문의 §2.3만 읽은 메모와 §2.4까지 확장해 읽은 메모를 함께 보존합니다. 논문 자체가 교체된 사례는 아닙니다.
3. `review/review.json`에서 C1의 범위를 어떻게 고치기로 했는지 읽습니다. RAG·LoRA는 이 오해를 교정하는 근거로만 사용합니다.
4. 실행 후 `changes.diff`와 `after/wiki/questions/wiki-and-learning.md`에서 달라진 답과 다음 질문을 확인합니다.
5. `after/wiki/questions/what-to-save.md`의 Q2 “우리 스터디는 어떤 답을 저장할까?”를 읽습니다. 교정된 C1·Q1과 기존 D1의 판단을 새 운영 답에 재사용한 구성 예제입니다.
6. `after/wiki/pending/retrieval-coverage.md`에서 근거 부족 답을 보류한 이유와 다음 행동을 확인합니다.
7. `after/wiki/decisions/save-all.md`의 D1은 `superseded`로 보존하고, 새 D2 `review-before-current.md`에 검토 후 현행으로 옮기는 선택과 부담을 적었습니다. 결정 형식은 Michael Nygard의 ADR 글을 참고했습니다.

기존 5쪽 갱신과 3쪽 생성으로 총 8쪽에 반영합니다. 이 파일 수는 이 예제의 규모이며 학습 효과나 정확도 수치가 아닙니다. 결과는 현행 8쪽·로컬 링크 25개, 보존 대상은 원자료 읽기 메모 5개와 초기 스냅숏 5쪽입니다.

## 내 자료에 적용

`starter.txt`에 자료 하나를 맡기는 짧은 요청과 작업 규칙이 있습니다. 원문 세 개와 질문 하나에서 시작하고, 실제로 읽은 파일·근거·보류한 부분을 확인해 보세요. 모든 자료에 위키를 도입할 필요는 없습니다. 다음 모임에서 답의 근거로 돌아가는 일이 쉬워지는지와 검토 부담을 함께 확인합니다.

발표 자료에 연결할 파일은 `llm-wiki-demo.zip`입니다. ZIP은 이 폴더의 원본·수정 후 파일·실행 도구·결과를 포함합니다. 링크를 위한 별도 웹앱이나 투표 집계 기능은 없습니다.
